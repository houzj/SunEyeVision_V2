# 方案测试 — 全链路验证闭环

> ⚠️ **项目当前无测试项目基础设施**。验证以代码合规审查 + 构建验证 + 手动验收为主。
> 验证时必须**逐项核对方案中声明的防御机制、验收标准、bug 模式修复**是否真实落地。

## 闭环定位

```
方案设计 ──→ 方案实施 ──→ 方案测试 ──┐
                          ↑          │ (问题反馈)
                          └──────────┘

关联技能：
  build-verify (MSBuild 配置 + 插件部署验证)
  cv-engine-builder (视觉算子封装验证)

Phase 0:   就绪检查 + 治本验证清单
Phase 0.1: 验证覆盖扫描 (Discovery)          ← 代码自发现 + git 历史比对
Phase 0.3: 自动验证清单生成 (Auto-Checklist)  ← 基于源码结构自动推导验证项
Phase 0.5: 防御机制清单核对
Phase 1:   构建验证 (Build)
Phase 2:   代码合规审查 (Code Review)        ← 替代单元测试（无测试项目）
Phase 3:   防御机制逐项验证
Phase 3.5: 手动验收引导 (Manual Verify)
Phase 4:   增量回归测试 (Incremental Regression) ← 依据覆盖表 + 变更类型定深度
Phase 5:   报告输出 (Report)
Phase 6:   验证结果记忆 (Persistence)          ← 持久化到 .codebuddy/memory/
Phase 6.5: 验证覆盖仪表盘 (Coverage Dashboard) ← 过期标记 + 衰减报告
```

## 就绪等级

| 等级 | 模式 | 说明 |
|:----:|------|------|
| **L1** | Report | 报告模式：分析改动影响范围，输出验证计划 |
| **L2** | Auto | 自动模式：执行验证 + 输出报告（默认） |
| **L3** | Full | 全量：L2 + 手动验收引导（手动跑图验证） |

## Phase 0: 初始化 + 治本验证清单

1. **读取方案报告** — 获取验收标准清单 + 防御机制清单 + bug 模式分析
2. **读取实施完成报告** — 获取修改清单 + 实施方声明的"治本验证表"
3. **确定验证范围**：
   - 方案报告中明确修改了哪些文件 → 重点审查
   - 方案报告中未修改但可能受影响的文件 → 回归验证
   - 注意 `dev/` 构建产物目录被 .gitignore 屏蔽，必须用 PowerShell 读取（rule-017）
4. **确认验证级别**：询问用户 L1/L2/L3

### 0.1 治本验证清单（强制）

逐项核对方案中"bug 模式分析"是否真的被实施方修复：

```markdown
**关键检查**：
- 实施方只修了"当前 bug 点"但没修"同类潜伏点" → ❌ 治本失败
```

## Phase 1: 构建验证 (Build)

> ⚠️ 注意：`dev/Debug/` 构建产物目录被 .gitignore 屏蔽（rule-017），验证插件部署必须用 PowerShell。

```powershell
# 编译单个工具 csproj（推荐起点）
dotnet build "tools/SunEyeVision.Tool.XXX/SunEyeVision.Tool.XXX.csproj" `
  --configuration Debug -v:minimal -nologo

# 编译解决方案（集成阶段）
dotnet build SunEyeVision.slnx --configuration Debug -v:minimal -nologo
```

### 工具插件部署验证（强制 — rule-016 §5.2）

编译成功后，必须验证工具输出目录是否干净：

```powershell
# 查看工具插件输出目录
$ToolName = "SunEyeVision.Tool.XXX"
$PluginPath = "d:\MyWork\SunEyeVision_V2-script\dev\Debug\plugins\$ToolName"
Get-ChildItem -Path $PluginPath -File | Select-Object Name

# 检查无 NuGet 污染（应只包含 <ToolName>.dll/.pdb + 显式复制的资源）
Get-ChildItem -Path $PluginPath -File | Where-Object {
  $_.Name -notmatch "^$ToolName\.(dll|pdb)$"
}

# 检查无语言子目录
Get-ChildItem -Path $PluginPath -Directory | Where-Object {
  $_.Name -in @("cs","de","es","fr","it","ja","ko","pl","pt-BR","ru","tr","zh-Hans","zh-Hant")
}

# 检查无 wpftmp / runtimes / .deps.json
Get-ChildItem -Path $PluginPath -Filter "*.deps.json" -File
Get-ChildItem -Path $PluginPath -Directory -Filter "*_wpftmp"
Get-ChildItem -Path $PluginPath -Directory -Filter "runtimes"
```

### 构建失败处理

```
构建失败 → 分析错误 → 分类：
  ├── MSBuild 配置错误 (MSB4xxx/MSB5xxx) → 通知 build-verify 或方案实施修复
  ├── 业务代码错误 (CS0xxx) → 通知方案实施修复
  └── 未知错误 → 输出错误详情，暂停验证
```

## Phase 2.5: 手动验收准备 (Manual Verify Prep)

> **视觉检测工具的特性决定了其验证必须以手动跑图为主**。Halcon 算子处理结果、区域合并效果、参数面板联动等很难用自动化测试覆盖。

### 准备步骤

1. **确定测试环境路径**：
   - 主程序：`dev/Debug/SunEyeVision.UI.exe`（.gitignore 屏蔽，确认存在用 PowerShell）
   - 测试图像路径：确认测试图在哪个目录
   - 工具插件输出：`dev/Debug/plugins/<ToolName>/`

2. **编写手动测试步骤**：

```markdown
### 手动测试引导：{改动的工具名称}

#### MT-01: 工具加载与参数配置
- 操作：启动主程序 → 添加 "{ToolName}" 工具 → 打开参数面板
- 预期：工具正常加载，参数面板显示正确的参数绑定
- 验证点：参数类型、取值范围、默认值是否符合预期

#### MT-02: 正常跑图验证
- 操作：加载一张标准测试图 → 配置正常参数 → 运行
- 预期：处理结果符合视觉检测逻辑
- 验证点：区域结果、图像结果、数据输出

#### MT-03: 异常输入处理（Fail-Forward 验证）
- 操作：加载无效图像（空白/全黑/格式错误）→ 运行
- 预期：系统报错提示而非崩溃
- 验证点：失败可见性（日志 + UI 提示）

#### MT-04: 参数边界验证
- 操作：设置参数的边界值（最小值/最大值）→ 运行
- 预期：不因边界参数导致异常
- 验证点：参数校验逻辑是否正确
```

### 不可自动验证的典型场景

- 视觉检测结果的正误（需要人工判断）
- Halcon 区域/图像处理的拓扑变更效果
- 参数面板 UI 联动（数据绑定是否正确）
- XAML 布局 / 样式视觉效果
- 插件部署目录的完整性（`dev/` 被 .gitignore 屏蔽）

## Phase 4: 增量回归测试 (Incremental Regression)

> **目的**：不再无差别全量回归。依据验证覆盖表（Phase 0.1）+ 代码变更类型，**只跑必要的验证**。

### 4.1 变更类型获取

从方案报告 + git diff 获取本次变更类型：

```powershell

```

### 4.2 增量决策树

依据覆盖表状态 + 变更类型，决定验证深度：

```mermaid
flowchart TD
    A[覆盖表状态] --> B{工具状态?}
    B -->|✅ 最新且代码未改| C[跳过跳过: 输出'已验证✅']
    B -->|🚩 从未验证| D[全量: 构建+契约+参数+规则+手动跑图]
    B -->|⚠️ 过期| E{变更类型?}
    E -->|Parameters 类| F[全量: 参数往返+契约+构建+手动跑图]
    E -->|Run 方法| G[偏量: 契约+构建+手动跑图]
    E -->|csproj| H[构建验证+插件部署验证]
    E -->|XAML/UI| I[仅构建+目视确认]
    B -->|🟡 衰减(>90天)| J[衰减验证: 构建+规则审查,无需手动跑图]
```

### 4.3 回归范围判定（保留原有依赖分析）

| 改动类型 | 回归范围 | 验证深度决策 |
|---------|--------|------------|
| 新增文件（无依赖） | 无回归 | 仅覆盖表状态判断 |
| 修改 Model/Parameters | 引用该 Model 的 Tool + ViewModel + View | 全量 |
| 修改 Service/CvEngine | 依赖该 Service 的 Tool + ViewModel | 全量 |
| 修改 ViewModel | 对应的 View + 关联的其他 ViewModel | 偏量 |
| 修改 XAML | 该页面 + 导航系统引用 | 仅构建 + 目视 |
| 修改 csproj / Directory.Build.targets | 所有使用该配置的工具 | 构建 + 部署验证 |
| **修改公共 API/接口 (Plugin.SDK)** | **所有工具全部重新构建验证** | **全量（覆盖表全部降级为⚠️）** |
| **修改 core/ 库 (CvEngine/ModuleBase)** | **所有使用该库的工具 + 主程序** | **全量** |

### 4.4 跳过声明

每次手动验证的跳过必须显式声明原因：


### 4.5 插件依赖链回归（SunEyeVision 特有）

```markdown
| 改动位置 | 回归范围 | 验证方式 |

| CvEngine | 使用 CvEngine 的工具 + 主程序 | 重新编译 + 手动跑图 |
```

- 若验证失败（整体结论为 ❌），**不写入**记忆文件

## 核心原则

1. **方案驱动** — 验收标准来自方案报告，不自行编造
2. **治本验证** — 方案中的 bug 模式分析必须真的修复（防打补丁冒充治本）
3. **防御机制验证** — 方案中的防御机制必须真实落地（防文档冒充实现）
4. **分层验证** — 构建 → 合规审查 → 验收 → 回归，逐层递进
5. **失败回退** — 发现严重问题必须回退，不隐瞒
6. **可重复** — 测试报告作为知识沉淀，下次回归可复用
7. **不修改代码** — 测试技能只验证，不修改
8. **覆盖扫描** — 每次测试启动时自动建立验证覆盖表，标记过期/未覆盖工具
9. **增量复用** — 验证结果持久化，哈希未变时自动跳过，不重复验证

## 禁止行为

- **禁止** 在验证过程中修改方案代码
- **禁止** 隐瞒验证失败
- **禁止** 跳过构建验证直接进入合规审查
- **禁止** 向用户承诺验证结果而不展示原始数据
- **禁止** 跳过治本验证清单（防打补丁冒充治本）
- **禁止** 跳过防御机制逐项验证（防文档冒充实现）
- **禁止** 用"实施方说做了"作为防御机制验证通过的标准，必须看到真实代码
- **禁止** 跳过 Phase 0.1 覆盖扫描直接进入 Phase 1 构建验证
- **禁止** 对已验证且哈希未变的工具重复跑参数/契约验证
- **禁止** 在验证失败时写入 verification-coverage.json（保持记忆文件仅记录通过）
- **禁止** 手动编造验证覆盖表（必须来自代码扫描 + git log 真实数据）
