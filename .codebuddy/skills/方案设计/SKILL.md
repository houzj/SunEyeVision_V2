# 方案设计 — 基于代码调研的方案设计流程

> 本技能遵循 rule-008 开发与代码纯净原则（YAGNI/KISS/零兼容/报错优先）
> 和 rule-004 方案设计要求（全局视角/复用优先）。
> 任何"先打补丁再说"、"只修当前 bug"、"不做逆向原厂取证"的输出均视为违规。

## 目的

本项目是**逆向同构**路线：目标是让本方与原厂（VisionMaster）对齐，语义来源是**原厂反编译源码 / 配置 XML / 实机取证**，不是业界最佳实践、不是外部参考项目、不是通用设计经验。实现路线已从"业界对标 + 自主设计"改为"逆向取证 + 同构迁移"。

确保每个方案设计都经过四个必要阶段：

1. **逆向原厂取证 (Reverse Evidence)** — 双链路：静态（反编译源码/配置 XML/XAML 资源，带文件:行号）+ 实机（agent-desktop 打开原厂含该节点方案，逐页签/弹窗快照+截图）。缺一不得判定对齐。
2. **信息调研 (Research)** — 出方案前全面搜索本方代码库，盘点可复用的已迁移控件与待补缺口，确保方案基于真实代码上下文
3. **源头标注 (Source Citation)** — 每个发现和决策必须标注来源位置（原厂证据文件:行号 或 本方文件:行号），禁止无依据推测
4. **bug 模式分析 (Bug Pattern Analysis)** — 治本而非治标，识别 bug 背后的模式

然后输出完整方案报告，移交 `方案实施` 技能执行。

## 工作流 — 逆向同构方案设计

### ━━━ Phase 0: 问题分析与方案验证（强制前置）━━━

> **在搜索任何代码之前，先想清楚该不该做、怎么做、为什么做。**

#### Step 1 — 拆解需求，定位根本问题

按顺序回答，答案必须基于当前项目实际，不能凭空推断：

1. **表面需求是什么？** — 用户的原话是什么
2. **根本问题是什么？** — 这个需求解决了什么本质痛点
3. **这个问题属于哪一类？**
   - 功能缺失（有这个功能但没做）
   - 实现方式有误（做了但做错了）
   - 架构冗余（两个地方做同一件事）
   - 边界情况（只在特定输入下出问题）

#### Step 2 — 架构分配检查

回答以下问题，答案必须来自实际代码搜索（标注来源），不能靠 LLM 记忆：

1. 现有系统的分层中，这个需求最自然的归属在哪一层？
2. 如果加到 A 层，B 层已有类似机制吗？（"会不会两个地方在做同一件事"）
3. 如果不做这个改动，现有机制是否能通过其他方式覆盖此需求？
4. 这个改动是否改变已有分层边界？（"是不是在打补丁"）

#### Step 3 — 方法对比

列出至少 3 种可能的实现方式，对比：

| 维度 | 方案 A（推荐） | 方案 B（备选） | 方案 C（备选） |
|------|--------------|--------------|--------------|
| 实现方式 | 一句话描述 | 一句话描述 | 一句话描述 |
| 与架构一致性 | 是否符合现有分层 | 是否符合现有分层 | 是否符合现有分层 |
| 复杂度 | 改动量预估 | 改动量预估 | 改动量预估 |
| 维护成本 | 长期维护难度 | 长期维护难度 | 长期维护难度 |
| 扩展性 | 是否容易扩展新场景 | 是否容易扩展新场景 | 是否容易扩展新场景 |
| 长期 ROI | 6 个月 / 1 年 / 3 年 | 同上 | 同上 |

**【否决门】Phase 0 通关检查**

```
以下任一条件不满足，退回原始需求重新澄清：

□ Step 1 明确了根本问题而非表面需求
□ Step 2 确认方案归属层与现有架构一致，无冗余
□ Step 3 至少对比了 3 种方案，推荐方案理由清晰
□ 以上答案均有代码来源标注，非 LLM 记忆
```

### ━━━ Phase 0.5: Bug 模式分析（强制 — agent-025 条款 1）━━━

> **违规判定**：只修当前 bug 不分析 bug 模式 → ❌ 违规
> 不允许"先把这次修了下次再说"，必须识别并消除背后的 bug 模式。

#### 步骤 1 — 当前 bug 的真因分类

| bug 类型 | 描述 | 治本做法 |
|---------|------|---------|
| **症状级 bug** | 表面表现（报错、卡顿） | 不止修症状，要追到底层 |
| **契约漏洞** | 双端协议无保护机制 | 加契约测试 + 端到端冒烟 |
| **状态泄漏** | AsyncLocal / 静态字段污染 | 加状态隔离 + 显式恢复 |
| **设计缺陷** | 架构层面就注定要出问题 | 必须重构而非打补丁 |
| **实现偏差** | 写了代码但没接上 | 接上 + 加 Fail-Forward |

#### 步骤 2 — 反问"这个 bug 还会以什么形式出现？"

```
问自己 3 个问题：
  1. 如果这个 bug 的产生条件再次发生，会再出错吗？
  2. 同类问题是否在别的地方也潜伏着？
     → search_content 搜相似 pattern
  3. 现有架构的哪个环节让这类 bug 必然出现？
     → 这个环节就是"治本点"
```

#### 步骤 3 — 治本点识别

输出：

```markdown
### Bug 模式分析

**当前 bug**: {描述}

**真因分类**: {契约漏洞/状态泄漏/设计缺陷/...}

**同类潜伏点**:
- [来源] path/file.cs:行号 — 同 pattern 在此处也存在
- [来源] path/file2.cs:行号 — 另一处类似

**治本点**: 修复 {治本点} 而非 {当前症状点}

**证据缺失警告**: 如果找不到同类潜伏点，写"本次为孤例，但仍按治本标准修复，防止未来复制"
```

### ━━━ Phase 0.7: 逆向原厂取证门禁（强制）━━━

> **违规判定**：方案没有原厂证据 → ❌ 违规
> 本项目是逆向同构，不是"业界最佳实践"选型。禁止用外部框架/参考项目/通用经验替代原厂证据。
> 每条 UI / 交互 / 状态 / 字段 / 端口 / 算法语义结论必须来自下面两条链路，且带可追溯引用。

#### 步骤 1 — 双链路取证（缺一不可）

| 链路 | 工具 | 定什么 | 证据形式 |
|---|---|---|---|
| A 静态证据 | REA MCP / 反编译源码 / 原厂配置 XML / XAML 资源 | 语义：字段名、类型、默认值、控件组合、页签分组、命令、资源键、生命周期、算法入口 | `文件:行号` / 配置键 |
| B 实机证据 | agent-desktop 驱动已安装原厂程序，打开含该节点的原厂方案 | 呈现与顺序：每个页签/弹窗真实可见控件、分组标题、按钮、顺序、状态、底栏命令 | `窗口快照编号` + 截图 PNG |

- 静态证据源：`docs/07-工具逆向/decompiled/`、`docs/evidence/original-release-units/<工具>/`、原厂模块目录的 `*.xml`。
- 实机证据：先复用用户已备好的原厂方案；逐页签/逐弹窗抓 `snapshot --window-id` + `screenshot`，存 `docs/evidence/<工具>-ui-<日期>/`。
- 只有链路 A（"代码里字段齐全、能打开"）**不得**判定 UI 对齐；历史返工根因即此。

#### 步骤 2 — 阻碍与成本分离（同构可行性判定）

先把"做不到"和"工作量大"分开，避免用"成本高"冒充"不可同构"：

| 判定 | 含义 | 处理 |
|---|---|---|
| 同构可行 | 本方通过迁移/重构/补代码可实现 | 计入成本，进入修改清单 |
| 硬阻碍 | 本方无论如何都实现不了（如私有加密且无算法、硬件狗且要求原格式兼容） | 登记 `unconfirmed`，说明范围取舍；算法库差异、数值精度不阻塞（用户口径） |
| 接缝 | 必须改写的宿主适配（执行调度、借帧、资源释放、服务注入） | 明确为接缝而非阻碍 |

#### 步骤 3 — 决策依据沉淀

把双链路证据沉淀为方案报告的"依据"章节：
- 每个设计决策至少 1 条原厂证据（`文件:行号` 或 `快照编号`）支撑。
- 明确"哪些是同构迁移、哪些是必要接缝、哪些未确认"，不把接缝或未确认写成同构。

**反面案例（违规）**：
- "参考业界某框架的最佳实践" → 不是逆向同构，违规
- "根据经验应该这样设计" / "看起来差不多" → 无原厂证据
- 只列静态代码"字段都有"就宣称 UI 对齐 → 缺实机链路

**正面案例**：
- "原厂窗口 900×534，依据 `FeaturepatMatchConfigPanalData.cs:250-251`；实机快照 `vm-contourmatch-ui-20261121/template-config.png` 确认右侧 8 行参数与底栏匹配中心。"
- "建模核心 `PatCreateCSharp` 不可见，但 `CreatePatE` 是虚方法接缝（`HPFeaturepatMatchDialogUI.cs:1664-1667`），注入本方 Halcon 引擎即可，属成本非阻碍。"

**三阶段顺序原则（新建工具与复核已有工具共用，写进方案报告的实施顺序）**：
**工程结构对齐 → UI 对齐 → 算法对齐**，顺序不可颠倒。
- 参数之所以存在是因为算法中有对应实现，但 UI/算法都必须落在稳定的结构基座上——先定 Runtime/Editor 分层、schema 字段/端口骨架、csproj/slnx。
- 工程结构未稳就动 UI/算法 → 边做边补结构、改一处推翻另一处 → 相互掣肘、效率极低（历史返工根因）。
- 每阶段完成才进下一阶段；方案报告按此分节列修改清单与验收标准。

### ━━━ Phase 1: 信息调研 (Research) ━━━

在出任何方案之前，必须全面搜索代码库。

#### 调研范围 (SunEyeVision 适配)

| 调研维度 | 搜索方法 | 目的 |
|---------|---------|------|
| 涉及文件定位 | search_file / search_content | 确定修改波及的文件 |
| 类/接口定义 | search_content | 找到类定义、接口签名、基类 |
| 调用链 | search_content 搜索调用方 | 确认修改的影响范围 |
| XAML 绑定 | search_content | 了解 UI 绑定和资源引用 |
| Halcon 算子调用 | search_content "HOperatorSet\|region.FillUp\|region.Connection" | 检查 rule-014 合规性 |
| csproj / MSBuild 配置 | search_file "*.csproj" / read_file | 检查 OutDir / Reference / IsToolPlugin |
| Toolkit 注册机制 | search_content "ToolRegistry\|IToolPlugin" | 了解工具注册/参数提取 |
| 参数系统 | search_content "ToolParameters\|GenericToolParameters\|ParametersTypeName" | 分析参数序列化/绑定 |
| 插件部署目录 | PowerShell Get-ChildItem dev/Debug/plugins/ | 验证构建产物（rule-017） |
| Rule 规则 | search_content "rule-\|\.mdc" | 确认 Rule 文件中的约束 |
| 现有 Skill | search_file / search_content | 复用现有技能模式 |
| **同类 bug 模式** | search_content pattern 搜索 | Phase 0.5 步骤 2 要求 |
| **逆向原厂证据（静态）** | REA MCP / 反编译源码 / 配置 XML / XAML | Phase 0.7 链路 A：字段/控件/命令/算法入口，带 `文件:行号` |
| **逆向原厂证据（实机）** | agent-desktop 打开原厂方案逐页签快照+截图 | Phase 0.7 链路 B：真实呈现与顺序，带快照编号+PNG |

#### 调研记录格式

```markdown
## 调研记录

### 文件分布
| 文件 | 行号 | 角色 |
|------|------|------|
| AgentWpf/ViewModels/XxxViewModel.cs | 10-50 | 定义/调用点 |
| AgentWpf/Services/XxxService.cs | 80-120 | 实现/调用方 |

### 类/接口定义
- [来源] AgentWpf/ViewModels/XxxViewModel.cs:25 — XxxViewModel 定义，继承 ObservableObject
- [来源] AgentWpf/Services/XxxService.cs:42 — XxxService 类定义

### 调用链
- [来源] AgentWpf/ViewModels/XxxViewModel.cs:88 — 调用 XxxService.DoSomething()
- [来源] AgentWpf/MainWindow.xaml:40 — XAML 绑定来源

### XAML 资源引用
- [来源] AgentWpf/Themes/Styles.xaml:15 — 按钮样式样式定义
- [来源] AgentWpf/Themes/Colors.xaml:20 — 主题色定义

### 现有模式参考
- [来源] AgentWpf/ViewModels/ExistingViewModel.cs:55 — 类似功能实现模式

### 同类 bug 模式（Phase 0.5 输出）
- [来源] path/file.cs:行号 — 同 pattern 在此处也存在
- [来源] path/file2.cs:行号 — 另一处类似

### 逆向原厂证据（Phase 0.7 输出）
- [来源-静态] docs/07-工具逆向/decompiled/.../style.xaml:494-916 — 控件组合/参数行/底栏
- [来源-静态] C:\Program Files\VisionMaster4.4.0\...\<模块>\AlgorithmTab.xml:62-367 — 页签/字段/默认值
- [来源-实机] docs/evidence/<工具>-ui-<日期>/xxx.png（snapshot_id=...）— 真实页签/按钮/顺序
```

> 调研要全面，不要只搜一个文件就停。必须找到：原厂静态证据、原厂实机证据、定义、实现、调用方、UI 绑定、同类 pattern。禁止用外部框架/参考项目/通用经验替代原厂证据。

### ━━━ Phase 2: 源头标注 (Source Citation) ━━━

方案报告中每个关键结论必须有可追溯的来源标注。

#### 标注规则

1. **每个发现点** 必须标注 [来源] 文件路径:行号
2. **禁止** 无依据的推断 — 如果找不到代码证据，标注为 [推测] 并说明原因
3. **引用格式**：
   - `[来源-原厂静态] docs/07-工具逆向/decompiled/.../File.cs:行号` — 原厂反编译/配置证据
   - `[来源-原厂实机] docs/evidence/<工具>-ui-<日期>/xxx.png（snapshot_id=...）` — 原厂实机截图
   - `[来源-本方] path/File.cs:行号` — 本方代码证据
   - `[推测]` — 没有代码证据，基于...的推断（须说明为何无法取证、影响哪个决定）
4. **标注位置**：方案报告中每个章节末尾，或内联在发现点后

#### 标注示例

```markdown
## 问题分析
- ChatHistory 上下文丢失
  - [来源] AgentEmployeeViewModel.cs:276 — 使用 InvokePromptAsync 单次调用
  - [来源] AgentChatViewModel.cs:1038-1045 — 正确使用 ChatHistory 的示例
  - [推测] 因两个 ViewModel 的开发路径不同导致模式不一致
```

## 方案报告输出

调研和标注完成后，必须输出结构化的方案报告，输出格式请参考 `templates/solution-report.md`。

方案报告必须包含（agent-025 硬性章节）：

| 章节 | 必需 | 说明 | 用于 |
|------|:----:|------|------|
| **改前/改后/依据** | ✅ | 用户视角 + 说人话（rule-019）+ 原厂证据引用 | 全员评审 |
| **问题分析** | ✅ | 调研结论 + 来源标注 | 设计依据 |
| **Bug 模式分析** | ✅ | Phase 0.5 输出，真因 + 同类潜伏 | 治本依据 |
| **逆向原厂取证与阻碍判定** | ✅ | Phase 0.7 输出：双链路证据 + 同构可行/硬阻碍/接缝三分类 | 设计依据 |
| **方案对比** | ✅ | ≥3 候选 + 长期 ROI + 推荐理由 | 决策 |
| **修改清单** | ✅ | 文件路径、变更类型、核心变更、前置依赖 | 方案实施 |
| **清理清单** | ✅ | 文件路径、清理内容（注释残留/死代码/无用 using/XML doc）、原因 | 方案实施 Phase 2 Step E |
| **防御机制** | ✅ | 至少 2 项：契约测试 / 端到端冒烟 / Fail-Forward / 失败兜底 | 方案测试 |
| **验收标准** | ✅ | 可验证的硬性标准，每个修改点对应一条 | 方案测试 |
| **测试方法** | ✅ | 自动/手动/code review 标记，关联测试用例 | 方案测试 |
| **风险评估** | ✅ | 实施风险、回退策略 | 实施决策 |

### 验收标准格式要求

每条验收标准必须包含：
1. **验收项** — 一句话描述
2. **验收方法** — unit test / manual / code review
3. **关联测试** — 对应测试用例编号（如有）
4. **对应防御机制** — 这条验收覆盖哪个防御机制

示例：

```markdown
| # | 验收项 | 验收方法 | 关联测试 | 对应防御机制 | 备注 |
|---|--------|---------|---------|------------|------|
| 1 | Employee 模型含 Username/PasswordHash | code review | - | 契约测试 | |
| 2 | AuthService.Login() 返回 Employee | unit test | UT-AS-01~03 | 单元测试 | |
| 3 | Viewer 不可见系统设置页 | unit test | UT-PM-04 | 端到端冒烟 | 回归 |
| 4 | 添加员工后自动创建登录账号 | manual | - | 端到端冒烟 | 界面操作 |
```

## 自检清单（输出前必跑）

```
□ 0. 用户功能性视角（改前/改后/依据）写在最前，且用大白话表达（rule-019，说人话，不堆术语）
□ 1. 方案对比 ≥3 候选 + 长期 ROI
□ 2. Bug 模式分析（真因 + 同类潜伏 + 治本点）
□ 3. 逆向原厂双链路取证齐备（静态文件:行号 + 实机快照编号），阻碍/成本/接缝已分离
□ 4. 防御机制 ≥2 项（契约测试 / 端到端冒烟 / Fail-Forward / 失败兜底）
□ 5. 验收标准覆盖"启动 → 用户看到结果"完整路径
□ 6. 没有"先打补丁"话术
□ 7. 所有结论有代码来源标注
□ 8. 推荐方案有明确理由（依据 X、Y、Z 条款）
□ 9. 清理清单已列出：每个修改文件对应的注释残留/死代码/XML doc 清理项
□ 10. 无"新增时未对应清理"的残留黑洞（新增 3 行代码却留下 10 行旧注释 = 净污染）
```

任一项未通过 → 重新修改方案，不要输出。

## 闭环节点：移交方案实施

方案报告通过用户确认后，**必须调用 `use_skill` 工具触发方案实施**，不能只口头说"移交"。

### 操作步骤

```
1. 调用 use_skill("方案实施")
2. 将以下内容作为上下文传给方案实施：
   ├── 方案报告全文（含修改清单、验收标准、防御机制）
   ├── 用户确认记录（"方案已确认，可以实施"）
   └── 本次已完成的调研记录（避免方案实施重复调研）
3. 方案实施负责代码修改 + 构建验证
4. 方案实施完成后自动 use_skill("方案测试") → 全链路验证
```

### 关键指令（硬性约束）

- ✅ **必须**用 `use_skill("方案实施")` 工具调用，不得只输出文字
- ✅ 必须等待用户确认方案后再移交实施（不跳过确认）
- ❌ **禁止**在方案设计阶段自行修改代码
- ❌ **禁止** 不确认方案就直接移交实施
