自有狗授权、文件保护与信任政策

为什么要动：当前缺独立产品狗许可服务；用户明确使用自己的加密狗。

① 当前方案实际怎样

自有加密狗与功能授权能力对照 · X03 src扫描未发现产品级加密狗服务；设计时LicenseManager与包MIT声明不算产品授权。

方案文件加密、密钥恢复与插件信任能力对照 · X04 SolutionRepository通过File.ReadAllText/JsonSerializer读取，并序列化JSON写临时文件；PluginLoader记录加载状态，不是签名验证器。

完整逐项证据见下方展开。

② VM什么机制可参考

只参考授权应覆盖运行/脚本/通信/后台入口；VM狗协议、密钥和授权实现均不采用。

③ 具体采用 / 改成什么

当前：无独立产品级许可链。建议：厂商适配 → LicenseService/能力快照（拟议） → 所有服务入口准入 → 拔狗/到期安全收尾。

为什么选这条路线

自主发行与用户要求决定新增自有体系；这不是从VM复制，也不是扩展设计时LicenseManager。

为什么没有选另外两条

采用VM狗不符合产品约束；只在启动窗口验一次无法约束后台副作用。

实施前还缺什么

先定型号/SDK、签发/功能席位/期限和离线宽限；文件保密/插件签名另定，不自动绑狗即全部安全。

代价 / 影响

驱动部署、签发恢复、换狗迁移与在途安全政策是成本；客户端不持签发私钥。

无/错/过期狗、驱动缺失、拔狗、到期/休眠、重插、换狗/备份迁移；拒新副作用、在途安全收尾、私钥不入客户端。
