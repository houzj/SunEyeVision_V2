## 2. 模板创建流程（当前实现）

### 2.1 ExecuteContourExtraction() 完整调用链

```
灰度化 (BGR2GRAY/BGRA2GRAY/ExtractChannel)
  -> ComputeShapeGradient(Scharr Gx+Gy, Magnitude归一化[0,255])
  -> BuildRoiMask(InspectionRegions -> 多边形填充掩码)
  -> AutoComputeContrast(Triangle Threshold 自适应)
  -> ApplyNms(沿梯度方向8象限, NMS细线化, Contrast过滤)
  -> CollectEdgePoints(遍历NMS像素->EdgePoint列表, 链长过滤)
  -> ★ AutoComputePyramidLevels(edgePoints.Count)  — 基于边缘点数自动计算金字塔范围
  -> 金字塔预计算 (for level=2 to pyramidStart)
      |- PyrDown 降采样
      |- Scharr 梯度计算
      '- **L1 坐标投影**到本层图像 + 重读方向/幅值 + 去重 + 稀疏化（非独立提取）
  -> SourceImageBytes(PNG编码, 保存参考图)
  -> ReferencePoint(边缘点质心)
```

**⚠️ 当前缺陷：** 金字塔 L2+ 并非真正独立提取边缘点。实际代码 `PreComputePyramidEdgePoints()` 做的是：
1. PyrDown 降采样图像
2. 将 L1 的 EdgePoint 坐标 `(x*scaleX, y*scaleY)` 投影到降采样后的图像坐标
3. 在该坐标处从当前层梯度重读方向和幅值
4. 去重（同像素保留最大幅值） + 稀疏化

这导致：
- L2+ 的 edge points **继承 L1 的位置**，而非该层图像自身的显著边缘
- 下采样后消失/模糊的细边仍然被投影到模板中，产生噪声
- 粗层无法利用下采样带来"只保留显著边缘"的天然优势

<hr>

**关键变更**：金字塔自动层数计算从 ROI 短边驱动改为 **边缘点总数驱动**（`AutoComputePyramidLevels(edgePointCount)`），保证最粗层至少保留 ~150 个点（`minEdgePointsAtCoarsest=150`）。

## 2.3 🔧 改造：金字塔每层真·独立边缘提取

### 2.3.1 改造目标

当前投影式方法（L1→L2+ 坐标映射 + 重读方向）导致粗层携带了本应在下采样中消失的细边。改造目标：
- 每层 **独立** 执行完整的边缘提取管线
- 所有层级使用统一的 Contrast 阈值，不做层级间缩放
- 归一化沿用当前方案：各层坐标统一减该层的 scaled 参考点，当前无问题，独立提取仍然沿用

### 2.3.2 核心算法流

```
PreComputePyramidEdgePoints (新):
  Level 1:
    EdgePoints（已有，直接复用）
    归一化到参考点 (refX, refY)

  Level 2 ~ pyramidStart:
    PyrDown 降采样 (2x, 与当前行为一致)
    → ComputeShapeGradient(Scharr Gx+Gy, Mag归一化)
    → ★ 统一 Contrast（所有层级使用同一 baseContrast，不做缩放）
    → ApplyNms(baseContrast)
    → CollectEdgePoints(链长过滤)
    → 归一化到参考点 (refX * scaleX, refY * scaleY)
    → 自适应稀疏化 (容量 = max(100, W+H) ~ 2000)
```


### 2.3.3 与投影式关键差异

| 方面 | 当前（投影式） | 改造后（独立提取） |
|------|--------------|------------------|
| L2+ 点来源 | L1 坐标投影 + 重读方向 | 在该层图像上独立 NMS + CollectEdgePoints |
| 点数与 L1 关系 | 与 L1 相同量级 → 稀疏化 | 独立决定（通常小于 L1，符合预期） |
| 细边残留 | 下采样消失的细边仍被投影携带 | 细边自然消失，只保留显著边缘 |
| 方向值 | 从该层梯度重读（但位置受 L1 约束） | 完全独立、位置+方向都是该层的真实值 |
| 稳定性 | N/A | 独立提取保证粗层只保留自身显著的边缘（下采样已自然滤除细边） |
| 匹配效果 | 粗层响应图可能带噪声 | 粗层响应图对应真正的强边缘 → 更鲁棒的粗搜 |

### 2.3.4 修改范围

| 文件 | 修改内容 |
|------|---------|
| `ShapeMatchTemplateEditorDialog.xaml.cs` | 重写 `PreComputePyramidEdgePoints()` 方法，L2+ 改用独立提取全路径 |
| 无新建 CvOp 方法 | 复用已有 `ComputeShapeGradient`, `ApplyNms`, `CollectEdgePoints` |

## 3. 匹配运行流程（当前实现）

### 3.0 当前匹配机制详解

当前匹配端已经实现了 Halcon 式「响应图 + LUT 累加」核心算法，但存在两个可优化的设计点：

**响应图数据结构（当前）：**
```csharp
private struct ResponsePyramidLevel
{
    public ushort[][] ResponseMaps;  // [8 方向][像素数] 每个像素存 8 个方向的相似度
    public int Width, Height;
    public double ScaleX, ScaleY;
}
```

**响应图构建（当前）：**
```
每像素: Scharr Gx/Gy → 量化方向 qdir → 查 DIRECTION_LUT[0..7, qdir]
→ 将 8 个相似度值写入 maps[0..7][idx]
→ 无效方向（幅值 < minContrast）不写入（默认 0）
```

**模板匹配累加（当前）：**
```
FullSearchOnResponseMaps:
  对每个 (角度, 缩放, 像素偏移):
    sum = Σ responseMaps[旋转后模板点方向][模板偏移位置]
    score = sum / (模板点数 * 255)
    Early Termination: maxPossible < minScore 则跳过
```

这个设计等价于 Halcon 的 LUT + 累加方案，但空间换时间——每像素存 8 个 ushort。

```csharp
public static void FindShape(
    Mat grayImage,
    Dictionary<int, List<EdgePoint>> pyramidEdgePoints,
    double minScore,
    int numMatches,           // 最大返回匹配数
    double maxOverlap,        // NMS 重叠率 0~1
    double greediness,        // 贪婪度 0~1
    double angleStart, double angleEnd, double angleStep,
    double scaleMin, double scaleMax, double scaleStep,
    int pyramidStart, int pyramidEnd, int timeoutMs,
    MinContrastMode minContrastMode, float minContrast,
    out List<ShapeMatchResult> matchResults,
    out MatchPerformanceStats perfStats)
```

### 3.2 完整匹配流水线

```
BuildResponsePyramid(Scharr, MinContrast过滤, 8方向量化)
  |
Level L 循环 (pyramidStart -> pyramidEnd):
  +- FullSearchOnResponseMaps (首层: 全图扫描)
  |   +- stepSize=8, coarseAngleStep=angleStep*3
  |   +- Early Termination (Greediness混合: safeDiscard || aggressiveDiscard)
  |   '- score >= minScore -> candidates.Add()
  +- Fallback (首层无候选: stepSize=4, minScore/2)
  +- Cascade 终止 (Fallback仍无候选 -> break)
  +- RefineSearchOnResponseMaps (后续层: 候选+/-6px窗口)
  |   +- Early Termination (Greediness混合)
  |   '- score >= minScore -> candidates.Add()
  '- ApplyMaxOverlapNms (基于IoU贪心去重, 替代旧动态上限)
  |
Level 0:
  +- SubPixelAngleRefine (0.1度 抛物线插值)
  '- SubPixelPositionRefine (3x3 二次曲面拟合)
```

### 3.5 🔧 改造：匹配段响应图优化

### 3.5.1 改造项 1 — 8→16 方向量化

**动机：** 当前 DIRECTION_BINS=8（45° 一个 bin），导致：
- 方向差 ≤22.5° 在同一 bin → 无法区分相近方向
- Halcon 使用 16 或 32 个 bin，更精细的方向量化提升匹配可靠性

**改动：**

| 项 | 当前 (8 bin) | 改造 (16 bin) |
|----|------------|--------------|
| DIRECTION_BINS | 8 | 16 |
| Bin 角度 | 45° | 22.5° |
| DIRECTION_LUT | `byte[8,8]` | `byte[16,16]` |
| QUANTIZED_DIR_LUT | Same | 适配 |
| NMS 扇区 | 8 扇区 | 保持 8 扇区（用于 NMS 插值，不变） |
| **响应图内存** | 8×2 bytes/像素 = 16 B/pixel | 16×2 bytes/像素 = **32 B/pixel** |

> ⚠️ 响应图内存翻倍，需配合改造项 2 做内存优化才能引入。**建议先完成改造项 2，再做方向量化升级。**

### 3.5.2 改造项 2 — 响应图内存优化

**动机：** 当前每像素存 8 × ushort（16 bytes），4 层金字塔的响应图内存占用：

| 图像尺寸 | 8 方向/像素 | 响应图层级 | 总内存 |
|---------|------------|-----------|--------|
| 1024×1024 | 16 MB | 4 层 (1024→512→256→128) | ~21 MB |
| 2048×2048 | 64 MB | 5 层 | ~85 MB |
| 4096×4096 | 256 MB | 6 层 | ~341 MB |

**方案：从"预计算相似度"改为"存储量化方向 + 运行时 LUT"**

```
改造前 (当前):
  maps[8][N] = 每个像素存 8 个方向的相似度 (ushort)
  匹配累加: val = responseMaps[rotatedMap[ti]][idx]   // 直接取值

改造后 (优化):
  directionMap[N] = 每个像素存量化方向 (byte, 0-15)
  匹配累加: val = DIRECTION_LUT[rotatedMap[ti], directionMap[idx]]  // 查 LUT

关键: 用 byte 替代 ushort, 而且 1 个方向值替代 8 个
```

**内存对比：**

| 方案 | 每像素 | 1024×1024 单层 | 4 层金字塔总内存 |
|------|-------|---------------|----------------|
| 当前 (8×ushort) | 16 B | 16 MB | ~21 MB |
| 优化后 (1×byte) | 1 B | 1 MB | ~1.3 MB |
| 优化后+16方向 (1×byte) | 1 B | 1 MB | ~1.3 MB（不变！） |

> 优化后内存降至 1/16，同时为 16 方向升级铺平道路。

**影响分析：**
- 匹配累加时增加一次 DIRECTION_LUT 查表开销
- BUT OpenCV 响应图构建时省掉了 `for (int dt = 0; dt < DIRECTION_BINS; dt++)` 循环
- **总体更快**：构建加速 > 累加快查表开销
- `FullSearchOnResponseMaps` 和 `RefineSearchOnResponseMaps` 中的查表代码需修改

### 3.5.3 改造项 3 — 模板点自适应选择

**动机：** 当前所有 EdgePoint 都参与匹配累加。对于边缘点密集的模板（数千点），每个候选位置都要累加全部点，浪费计算。

**方案：** 参考 Halcon 和 [shape_based_matching](https://gitee.com/doiob/shape_based_matching) 的做法，基于梯度幅值选择 Top-N 点用于匹配：

```csharp
// 对每层模板点按 Magnitude 降序排列
var selectedPoints = pyramidEdgePoints[level]
    .OrderByDescending(p => p.Magnitude)
    .Take(maxTemplatePoints)  // 默认 500~1000
    .ToList();
```

| 模板密度 | 原始点数 | 选择后 | 匹配加速 | 精度影响 |
|---------|---------|--------|---------|---------|
| 稀疏 (<300) | ~200 | 不截断 | ~1x | 无 |
| 中密度 | ~500 | ~500 | ~1x | 无 |
| 密集 | ~2000 | ~500-800 | ~2.5-4x | 可忽略（高幅值点占主导） |
| 非常密集 | ~5000+ | ~800-1000 | ~5x+ | 边缘像素化区域略降 |

> 截断在 `FindShape` 方法入口处做，不影响模板存储。

### 3.5.4 改造项影响总结

| 改造项 | 内存影响 | 速度影响 | 匹配精度 | 依赖关系 |
|--------|---------|---------|---------|---------|
| 8→16 方向 | -16x（搭配项2后）| 无显著变化 | 方向分辨率翻倍 | 依赖项2 |
| 内存优化（方向byte） | -16x | 构建加速, 累加略慢 | 无损 | 独立 |
| 模板点选择 | 无 | 2~5x 加速（密集模板） | 可忽略 | 独立 |

> 以下仅列**真正 pending** 的改造项。P0 候选过滤增强（Greediness/MaxOverlap/NumMatches）、运行时参数增删均已实现，不再列出。

### 4.1 P1 — 删除重采样（Resample）

**决策依据：**

> 重采样作为"降低模板点密度"的手段与金字塔层级控制功能重叠。用户通过调整 `PyramidStart`/`PyramidEnd` 即可控制不同密度层级的搜索范围，无需额外的点抽稀开关。重采样参数 `ResampleParam` 对 L1(全分辨率)和 L5(1/32 分辨率)的效果差异巨大，无法用单一参数合理控制。因此直接删除，改为金字塔层级调节。

#### 4.1.1 删除范围

| 文件 | 具体删除内容 |
|------|-------------|

## 🔧 改造：金字塔层级自动计算优化

### 改造目标

将旧版基于**密度翻倍链**（逻辑反了）的计算方法，替换为基于**最粗层最小边缘点数 + 最小尺寸**的双约束方法。

### 问题分析

旧算法：
```
density = edgePoints / (W×H)
threshold = baseDensity × 2
while density > threshold: target++; threshold *= 2
```

**问题**：PyrDown 后图像面积缩 4 倍，边缘点只掉约 2 倍，所以各层密度实际是 **×2 递增**的（越粗的层密度越大）。用密度推导层数本身就是反直觉的。

```
    密度的真实分布（反直觉）
  ┌─────────────────────────────────────┐
  │  L1: 密度 D₁                        │
  │  L2: 密度 2×D₁  (面积1/4, 点~1/2)  │
  │  L3: 密度 4×D₁                      │
  │  L4: 密度 8×D₁  ← 密度更大          │
  │  ...                                │
  │  L10: 密度 512×D₁ ← 密度最大        │
  └─────────────────────────────────────┘
```

**结论**：密度不是决定层数的正确物理量，应该用**绝对边缘点数**。

### 核心算法

两个硬约束取较小值：

```
start = min(maxByImage, maxByEdges)
```

#### 约束①：图像尺寸约束（maxByImage）

最粗层最短边 ≥ 16px，同时**硬上限 L6（最短边≥32px）**：

```
minDim / 2^(k-1) ≥ 16
→ k ≤ log₂(minDim / 16) + 1
最终 k ≤ min(log₂(minDim/16)+1, maxLevel=6)
```

```csharp
int minDim = Math.Min(width, height);
int maxByImage = (int)Math.Floor(Math.Log(minDim / 16.0, 2)) + 1;
```

#### 约束②：边缘点数约束（maxByEdges）

PyrDown 后边缘点约减半，最粗层保留 ≥ 150 个点：

```
L1点数 / 2^(k-1) ≥ 150
→ k ≤ log₂(L1点数 / 150) + 1
```

```csharp
int maxByEdges = (int)Math.Floor(Math.Log(edgePointCount / 150.0, 2)) + 1;
```

#### 搜索范围

结束层固定保留最后 3 层搜索，确保最细的精细层参与匹配：

```
end = start ≥ 4 ? start - 3 : 1
搜索层次: end ~ start（从精到粗）
```

**图解（以 start=6 为例）：**
```
   L1    L2    L3    L4    L5    L6
   ──    ──    ══    ══    ══    ══   ← 搜索
   ↑end                      ↑start
   (最细)                 (最粗, 搜索起点)
```
