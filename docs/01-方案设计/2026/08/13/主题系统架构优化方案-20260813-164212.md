## 🔄 改前 → 改后 → 依据（写在最前面）

### 改前（用户视角）
你切到深色主题，主框架变深了，但**工具调试窗口、对话框、属性面板、SDK 控件（ROI 编辑器等）还是一团亮色**，好像"主题没全覆盖"。而且有些地方修好了过几天又冒出来，因为问题不在单个控件，而在主题系统的**加载机制 + key 契约**上。

### 改后（用户视角）
切主题后，**SDK 控件、工具调试窗口内容区、对话框都整体跟随切换**，不再有"顽固亮色块"。主题 key 出现拼写不一致时，**程序启动直接报错提示**，而不是静默用错颜色（你无需排半天队才知道哪里错了）。工具调试窗口的深色标题栏（那是刻意设计）保持不变。

### 依据（业界参考）
调研了 WPF 官方机制 + MahApps.Metro、HandyControl、MaterialDesignInXamlToolkit 三套主流主题库（详见"业界对标"章）。业界共识：
1. 颜色/画刷/样式三层分离，样式文件不写死色值
2. DynamicResource 动态引用是主题切换前提
3. 主题字典是唯一色源，但**允许"无宿主兜底"**（MaterialDesign 的 BundledTheme 注入机制）
4. 不在窗口/控件级重复合入主题资源

**修正 v1 的核心依据**：v1 把 DefaultTheme 误判为"纯遮蔽元凶要删除"。深入调研发现，DefaultTheme 承担**工具调试窗口等脱离 UI 宿主场景的 SDK 兜底职责**，删除会破坏这些场景。真正的治本是**把 DefaultTheme 从 Generic 中拆出**（消除遮蔽根源）+ **修复 key 契约**。

### 契约错位证据（关键发现）
- [来源] `src/Plugin.SDK/UI/Themes/SdkThemeKeys.cs:36` — `DividerBrush = "ThemeDividerBrushBrush"`（拼写多了 Brush）
- [来源] `src/UI/Themes/Base/ThemeKeys.cs:56-57` — UI 层定义 `DividerBrush = "ThemeDividerBrush"` 和 `DividerBrushBrush = "ThemeDividerBrushBrush"` 两个独立 key
- [来源] `src/UI/Themes/Light/LightTheme.xaml:30` — 主题字典定义 `ThemeDividerBrush`（Color 层）
- [来源] `src/UI/Themes/Light/LightTheme.xaml:132` — 主题字典定义 `ThemeDividerBrushBrush`（Brush 层）

**结论**：SDK 的 `SdkThemeKeys.DividerBrush` 指向 `ThemeDividerBrushBrush`，与 UI 的语义 key `DividerBrush` 错位。靠注释约定，随时可能不同步——这正是需要契约校验的原因。

### 无依据推断
- [推测] DefaultDebugWindow 的 `StaticResource BackgroundBrush` 在宿主进程 Application.Resources（App→AppResources→Generic→DefaultTheme）中解析。因为 DefaultDebugWindow 自身不加载资源字典。

## 问题分析（Phase 0）

### 需求拆解
- **表面需求**：修复"主题切换后 SDK 控件/工具调试窗口不跟随"
- **根本问题**：主题系统半成品迁移——语义 token 体系（对）与旧体系（固定色+局部合入+key 契约断裂）并存
- **问题分类**：
  - 设计缺陷：DefaultTheme 被 Generic 合并，导致 Roi 控件级合入 Generic 时把固定色拉到控件级最高优先级 → 遮蔽
  - 契约漏洞：SdkThemeKeys 与 ThemeKeys 靠注释约定，实际已出现 DividerBrush 拼写错位
  - 实现偏差：SubroutineDebugControl 合入不存在的资源路径

### 架构分配检查
- 最自然归属层：UI 层主题加载链（App.xaml + ThemeManager）
- 已有类似机制：有（ThemeKeys 语义 token + ThemeManager 切换）— 保留
- 不改是否可覆盖：否（遮蔽 + 契约断裂是系统性的）
- 是否改变分层边界：否（仍由 ThemeManager 统一管理 Application 级主题字典）

### 方法对比（≥ 3 候选）

| 维度 | 方案 A'：拆分+契约（推荐） | 方案 A（v1 错误） | 方案 B：修修补补 |
|------|--------------------------|------------------|----------------|
| 实现方式 | DefaultTheme 从 Generic 拆出；AppResources 显式合入；key 启动校验 | 删 DefaultTheme + 无主题报错 | 只修当前遮蔽点 |
| 工具调试窗口兜底 | ✅ 保留 | ❌ 破坏（无兜底） | ✅ 保留 |
| 架构一致性 | ✅ 对齐业界（单一色源 + 无宿主兜底） | ⚠️ 过度简化 | ❌ 遮蔽复发 |
| 复杂度 | 中 | 中 | 低 |
| 长期 ROI | 6月:高/1年:高/3年:高 | 破坏场景，不适用 | 低 |
| 风险 | 中（需验证工具窗口） | 高（破坏工具窗口） | 低 |

**推荐方案 A'**，核心思路（治本）：
1. **拆出 DefaultTheme**：从 Generic 中移除对 DefaultTheme 的合并，AppResources（Application 级）显式合入 → 主题字典末尾覆盖 → SDK 随主题；无宿主时兜底正常
2. **Roi 控件合入保留 Generic**（只需样式），因 Generic 不再带 DefaultTheme 固定值，不再遮蔽
3. **修复契约**：ThemeManager 启动期校验 SdkThemeKeys 与 ThemeKeys 字符串一致性，不一致抛异常；修正已错位的 DividerBrush
4. **修复 SubroutineDebugControl 错误资源路径**
5. **清理残留**：ThemePalette 死代码 + AppResources 固定色块迁移语义 token + 窗口级重复合入

## Bug 模式分析（Phase 0.5）

**当前 bug**：SDK 控件/工具调试窗口在深色主题下仍显示亮色。

**真因分类**：设计缺陷（兜底色板被 Generic 合并导致控件级遮蔽）+ 契约漏洞（key 字符串无编译期保护，已实际错位）

**同类潜伏点**：
- [来源] `RoiEditorControl.xaml:10`、`RoiEditorManagerControl.xaml:8`、`ShapeToolBar.xaml:8` — 三个 Roi 控件都控件级合入 Generic（含 DefaultTheme 固定值）→ 全部遮蔽
- [来源] `SubroutineDebugControl.xaml:13` — 合入不存在的资源路径
- [来源] `SdkThemeKeys.cs:36` — DividerBrush 拼写错位（契约无保护）

**治本点**：修复"DefaultTheme 经 Generic 被局部合入导致的遮蔽" + "key 契约无编译期保护"，而非逐个修遮蔽点。

**证据缺失警告**：本次为系统性模式（3 个 Roi 控件 + key 契约断裂），非孤例，按治本标准修复。

| 框架/产品 | 关键特征 | 文档引用 | 借鉴/不借鉴 |
|-----------|---------|---------|------------|

| MahApps.Metro | Colors→Brushes→Styles 三层分离；ThemeManager 运行时替换 | deepwiki MahApps 5-styling-and-theming | 借鉴：三层分离 |

| MaterialDesignInXAML | BundledTheme 启动注入 + PaletteHelper 运行时替换；主题字典唯一色源 | MDIX Themes wiki | 借鉴：单一色源；**不借鉴**"无兜底"（本场景有脱离宿主场景） |

**关键借鉴修正**：业界共识"主题字典唯一色源"针对的是**应用内**。对插件化 SDK（本场景），成熟做法是"应用内单一色源 + 组件级无宿主兜底"（类似 MDIX BundledTheme 的启动注入 + 组件自备默认）。故 DefaultTheme 兜底**保留但仅存于 Application 级**。

## 解决方案（方案 A'）

### 方案概述
保留语义 token 体系 + DefaultTheme 兜底职责，修正三件事：拆出 DefaultTheme 消除遮蔽、修复 key 契约、清理残留。

### 技术方案
1. **拆出 DefaultTheme**（治本核心）：
   - `Generic.xaml`：移除 `<ResourceDictionary Source="DefaultTheme.xaml"/>` 合并（第 11-13 行）
   - `AppResources.xaml`：在 MergedDictionaries 中**显式添加** `<ResourceDictionary Source="pack://application:,,,/SunEyeVision.Plugin.SDK;component/UI/Themes/DefaultTheme.xaml"/>`（放在 Generic 之前或之后均可，被主题字典末尾覆盖）
   - 效果：Roi 控件级合入 Generic 只拿样式（DynamicResource 向上查），不再带 DefaultTheme 固定值 → 不遮蔽；Application 级主题字典末尾覆盖 DefaultTheme → SDK 随主题
2. **契约保护**：
   - `ThemeManager` 新增启动期校验：遍历 SdkThemeKeys 常量集合，确认每个字符串在 UI 主题字典（Light/Dark）中都能解析；不一致抛异常（rule-015 报错优先）
   - 修正 `SdkThemeKeys.DividerBrush`：`"ThemeDividerBrushBrush"` → `"ThemeDividerBrush"`（对齐 UI 语义）
3. **修复资源路径**：
   - `SubroutineDebugControl.xaml:13`：`Views/Resources/AppResources.xaml` → `Shell/Resources/AppResources.xaml`
4. **清理窗口级重复合入**：
   - `AboutWindow.xaml`、`HelpWindow.xaml`：删除 `../Resources/AppResources.xaml` 合入（Application 级已加载，窗口级重复会把固定色拉高优先级遮蔽主题）
5. **清理残留**：
   - 删除 `ThemePalette.cs`（零调用方死代码）
   - `AppResources.xaml` 固定色块（PrimaryBrush 等）分批迁移到语义 token
6. **分批迁移硬编码色值**（30+ 文件，可后置分批）

### 实施步骤（按依赖排序）
1. 拆出 DefaultTheme（Generic + AppResources）→ 构建验证
2. 契约保护（ThemeManager 校验 + SdkThemeKeys.DividerBrush 修正）→ 构建验证
3. 修复 SubroutineDebugControl 资源路径 → 构建验证
4. 删除 About/Help 窗口级重复合入 → 构建验证
5. 删除 ThemePalette 死代码 → 构建验证
6. AppResources 固定色块迁移 + 硬编码分批（后置，独立提交）

### 测试范围与分层

| 测试类型 | 范围 | 自动化 |

## 风险评估

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| 拆出 DefaultTheme 后某场景缺兜底 | 极端场景控件样式异常 | 保留 AppResources 显式合入 DefaultTheme + 全量构建 |
| key 校验误报 | 启动抛异常 | 校验逻辑遍历真实常量，先修 DividerBrush 再启用 |
| Roi 控件合入 Generic 依赖 | 样式丢失 | Generic 拆出 DefaultTheme 不影响其内样式（DynamicResource 向上查） |
| 工具调试窗口资源 | SubroutineDebugControl 路径修正后可能引入新依赖 | 验证其能解析 AppResources |
