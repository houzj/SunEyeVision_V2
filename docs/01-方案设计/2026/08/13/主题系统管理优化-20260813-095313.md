# 主题系统管理与优化方案

> 目标：从零搭建多主题系统，支持亮/暗两套主题，解决"主题无法覆盖所有 UI"的问题。
> 决策方向（已确认）：**增量迁移 + 自研轻量主题系统 + 只做亮/暗两套**。
> 架构增补（2026-08-13 已确认）：**主题/样式所有权下沉到 `Plugin.SDK` 资源层**——主题的"内容"（契约 ThemeKeys + 亮/暗两套值 + 通用控件样式）下沉 SDK 成为唯一维护点；UI 层只负责加载/切换，并保留宿主专属样式（受主题管理）；工具层纯引用 SDK 零维护。
> ⚠️ 下沉边界（2026-08-13 澄清）：**"下沉" ≠ "所有样式都进 SDK"**。主题"内容"归 SDK；宿主专属业务外观（画布节点/缩略图等）留 UI 层但**用 SDK 语义 key 上色、受主题管理**；通用控件样式归 SDK 唯一维护。详见"四、主题下沉 SDK"。

## 🔄 改前 → 改后 → 依据

### 改前（用户视角）
程序只有一套亮色皮肤，颜色全是写死在 XAML 和代码里的 `#XXXXXX`。想换色只能改源码重编译，而且因为 `StaticResource` 和代码造色的存在，就算做切换也只能换掉一小部分界面，"主题覆盖不全"。

### 改后（用户视角）
顶栏多一个"亮/暗"切换按钮（月亮/太阳图标），点一下整个程序——窗口底、面板、输入框、表格、日志、画布、节点、对话框——全部跟着变暗或变亮；关掉重开记住上次主题。将来想加第三套主题（如高对比度），只要新增一个字典文件，业务代码零改动。

### 依据（业界参考）
WPF UI、MaterialDesignInXaml、MahApps 三家主题系统都是同一套路——**语义色板 + 运行时换字典 + DynamicResource 动态引用**。自研轻量版即用最少代码落地该套路，不引第三方库（符合项目零依赖风格）。`CanvasStyleResources.xaml` 中"Color 定义 → Brush 用 DynamicResource 包一层"已是雏形，方案即推广为全局标准。

## 现状调研记录

### 当前工程没有主题系统
- `App.xaml` 把 5 个资源字典静态写死合并（AppResources / NodeStyle / ConnectionStyle / CanvasStyle / CommonStyle），无切换逻辑，无 `ThemeManager` / `ThemeService`。
- 颜色几乎全是硬编码十六进制：整个 UI 有 **32 个 XAML 文件、数百处 `#XXXXXX`** 写死（AppResources 48 处、LogPanelControl 44 处、ImagePreviewControl 45 处、GlobalVariableManagerDialog 42 处……）。
- C# 代码大量直接 `new SolidColorBrush` 造色：**39 个文件**，集中在 Converters（CommonConverters 13 处、CachedNodeConverters 12 处）、CanvasConfig 14 处、渲染服务（CanvasRenderer、NodeUIPool）。
- `NodeStyleConfig.cs` 注释明确写着"等待主题系统完善"——欠账早已知道。

### 覆盖不全的三断层（根因）
| 断层 | 现状 | 后果 |
|------|------|------|
| 1. `StaticResource` 编译期解析 | AppResources 大量 `{StaticResource PrimaryBrush}` | 换主题字典后引用不刷新，停留旧值 |
| 2. 代码层直接造色 | Converters / CanvasRenderer / CanvasConfig 里 `new SolidColorBrush(...)` | 完全脱离资源系统，主题换不到 |
| 3. 颜色无语义化抽象 | 到处都是 `#F5F5F5` 裸色值 | 系统不知道色值代表什么语义，无法统一换 |

### 可复用范本
`CanvasStyleResources.xaml` 局部正确模式：`Color` 定义一次 → `Brush` 用 `{DynamicResource}` 包一层 → 样式引用 Brush。缺的是"同一 Key 不同主题给不同色值"这层。

### 无依据推断
- [推测] 顶栏当前无设置入口，切换按钮需新增；具体位置以实施时 ShellTopBarControl.xaml 实际结构为准。

## 解决方案

### 方案概述
自研轻量主题系统：**语义色板（Design Token）+ 主题字典运行时交换 + ThemePalette 门面**，按批次把硬编码迁移到语义 Key，最终支持亮/暗两套主题且覆盖全 UI。

### 一、语义色板：主题的"合同"
所有 UI 颜色按语义归组（Key 描述用途，不描述具体色值）。亮/暗两套主题给同一组 Key 填不同色值：

| 组 | 语义 Key（示例） | 亮色示例 | 暗色示例 |
|----|-----------------|---------|---------|
| 窗口/面板底 | `WindowBackgroundBrush` / `PanelBackgroundBrush` | `#FFFFFF` / `#F5F5F5` | `#1E1E1E` / `#252526` |
| 控件底 | `ControlBackgroundBrush` / `ControlHoverBrush` / `InputBackgroundBrush` / `ReadOnlyBackgroundBrush` / `HeaderBackgroundBrush` / `AlternatingRowBrush` | 白 / 浅灰系 | 深灰系（VS 风格） |
| 文字 | `TextPrimaryBrush` / `TextSecondaryBrush` / `TextDisabledBrush` / `TextOnAccentBrush` | `#333` / `#666` / `#999` / 白 | 浅灰系 |
| 边框/分隔 | `BorderBrush` / `BorderLightBrush` / `SeparatorBrush` | `#CCC` / `#E0E0E0` | `#3F3F46` 系 |
| 品牌/状态 | `AccentBrush` / `AccentHoverBrush` / `AccentLightBrush` / `SuccessBrush` / `WarningBrush` / `ErrorBrush` | `#0066CC` 系 | 两主题共用，暗色微调 |
| 画布专属 | `CanvasBackgroundBrush` / `CheckerLightBrush` / `CheckerDarkBrush` / `GridMajorLineBrush` / `GridMinorLineBrush` / `SelectionBoxStrokeBrush` | 沿用现值 | 深色棋盘格 |

**关键约定**：亮色主题色值 = 现有界面原值（肉眼零变化，风险最小）；暗色为新设计。品牌色两主题共用，暗色下只微调。

### 二、架构与核心机制
```
src/UI/Themes/
├── Base/                       # 与主题无关：字体、尺寸、现有样式（样式只引用 Key，不含色值）
├── Light/LightTheme.xaml       # 语义 Key → 亮色值
├── Dark/DarkTheme.xaml         # 语义 Key → 暗色值
└── ThemeManager.cs             # 服务：切换 + 持久化 + ThemeChanged 事件
```

三个必须讲清的机制：
1. **XAML 层**：颜色全走 `{DynamicResource 语义Key}`。主题字典置顶后 WPF 内部自动把新值推给所有引用方（"切一下全变"的原理）。现有 `StaticResource` 在迁移批次里逐个改掉。
2. **代码层（最大的坑）**：Converters / CanvasRenderer / NodeUIPool 是 `new SolidColorBrush` 直接造色，换字典管不到（覆盖不全的第三断层）。方案：加 `ThemePalette` 门面统一 `GetBrush(key)` 现取现用（不缓存），Converters 改用它；缓存了笔刷的地方（CanvasRenderer/NodeUIPool）订阅 `ThemeManager.ThemeChanged`，切主题时清缓存重建。
3. **持久化**：主题选择写进现有 `SaveUserSettings()` 通道，启动时读出应用。

### 四、主题下沉 SDK（批次 2 前置，增补章节）

**为什么下沉**：SDK 控件（ROI 编辑器/图像控件/调试窗口）和工具插件做的界面，当前切主题纹丝不动——因为工具程序集只引用 `Plugin.SDK`、够不着 UI 层的语义 key，且 SDK 与 AppResources 存在同名短名 key（如 `PrimaryBrush`）跨程序集冲突覆盖（rule-015 违规）。下沉后 SDK 控件与工具控件天然引用 SDK，零成本吃到主题。

**下沉后架构**：契约（ThemeKeys）+ 值（Light/Dark 两套字典）在 `Plugin.SDK`；`ThemeManager` 留 UI 层只负责加载/切换（URI 指向 SDK 字典）。SDK 保留一套短名默认值作为"无宿主主题时的出厂样式"（控件库标准做法，非违规兜底）。

**三层最终归属模型（2026-08-13 澄清确认）**——下沉后每层各司其职：

| 层 | 在主题/样式里的角色 | 具体负责 |
|----|--------------------|---------|
| **SDK 层** | 唯一的**内容仓库** | 主题契约（ThemeKeys）+ 亮/暗两套值字典 + 通用控件样式。所有主题"内容"的唯一存放与维护点 |
| **UI 层** | **开关 + 宿主专属样式** | ① ThemeManager：加载/切换 SDK 字典（换肤开关）；② 宿主专属业务外观（画布节点/缩略图等），**外观定义留 UI，但颜色用 SDK 语义 key 上色、受主题管理** |
| **工具层** | 纯**使用者** | 只引用 SDK，界面直接用 SDK 的语义 key 与通用样式，切主题自动跟随，**自身不定义主题/通用样式** |

> 关键澄清：**专属样式留 UI 层 ≠ 不跟主题走**。画布节点、缩略图等专属样式，其"外观定义"（形状/尺寸/圆角）留在 UI 层，但"颜色"统一用 `{DynamicResource {x:Static base:ThemeKeys.XxxBrush}}` 取 SDK 的值——**颜色值真正存在 SDK，切换时随主题联动**。因此下沉后不存在"第三方插件/专属界面不受主题管理"的死角。

**三阶段下沉步骤**：

1. **下沉地基**：`ThemeKeys.cs` 迁到 `Plugin.SDK/UI/Themes/`（命名空间 `SunEyeVision.UI.Themes.Base` → `SunEyeVision.Plugin.SDK.UI.Themes`）；`LightTheme.xaml`/`DarkTheme.xaml` 迁到 SDK；`ThemeManager` 的 URI 改指向 SDK 组件；所有已迁移 xaml 的 `xmlns:base` 改指向 SDK 命名空间。
2. **解决短名冲突**：收敛 `AppResources.xaml:30-50` 与 SDK `Colors.xaml` 同名 key 覆盖；SDK `Colors.xaml` 短名保留为默认值；顺带理顺当前无合并点的孤儿资源（`Fonts.xaml`/`Layout.xaml`/`Styles.xaml`）。

**样式下沉（重点，与主题值下沉并列）**：主题下沉只解决"颜色值"跟随主题，**样式下沉**解决"通用控件长什么样、谁维护"。当前 UI 层 `AppResources.xaml`（66-373 行）自建了一整套与 SDK `Styles.xaml` 重复的通用控件样式，工具插件只引用 SDK、吃不到这套样式——这是"工具插件界面样式失控"的另一半根因。补充计划：

- **该下沉去重的通用控件样式**（从 UI 层收敛到 SDK `Styles.xaml` 唯一维护）：`PrimaryButton`/`SecondaryButton`（按钮）、`StyledTextBox`（文本框）、`StyledComboBox`（下拉框）、`StyledTreeView`（树）、`StyledExpander`（折叠面板）、隐式 `CheckBox`、隐式 `ProgressBar`。SDK `Styles.xaml` 已有对应样式（`PrimaryButtonStyle`/`StandardTextBoxStyle`/`StandardComboBoxStyle` 等），需统一命名与值，删除 UI 层重复定义。
- **留 UI 层的宿主特有样式**（不通用、属宿主业务）：`NodeBorder`/`ProcessingNode`/`PreprocessNode`/`DetectionNode`（画布节点，归批次4）、`ThumbnailCard`/`ThumbnailCardSelected`（图像缩略图）、`ImageTypeComboBoxStyle`/`ImageControlButtonStyle`/`ImageDisplayTabItemStyle`/`ReadOnlyTextBoxStyle`/`SideHeaderStyle`（面板专属）。这些若塞进 SDK 会绑架 SDK 复用性。
- **执行原则**：SDK `Styles.xaml` 接进合并链（当前是孤儿资源），作为通用控件样式的唯一维护点；UI 层改为引用 SDK 样式，宿主特有样式留在 UI 层独立字典。
3. **验证**：构建 slnx EXITCODE=0；两套字典 Key 对称脚本校验；冒烟切亮/暗看 SDK 控件 + 工具窗口跟随。

**关键依据**：MahApps.Metro / ModernWpf 控件库标准——控件库自带主题资源，宿主只负责加载切换；WPF ThemeInfo（`SunEyeVision.Plugin.SDK.csproj:58` 已用）。

## 风险评估
| 风险 | 影响 | 缓解 |
|------|------|------|
| 覆盖面广（32 XAML + 39 C#） | 迁移工作量大 | 增量分批，每批可验证回滚 |
| StaticResource 改 DynamicResource 遗漏 | 部分界面不刷新 | 批次验收逐一目视 |
| 代码层造色遗漏 | 代码画的内容不跟随 | 全仓搜 new SolidColorBrush 兜底 |
| 暗色下可读性/对比度不足 | 观感差 | VS Code 风格成熟配色参考 |
