## 一、问题全景（日志实证）

| 阶段 | 耗时 | 根因 |
|------|------|------|
| 窗口显示 | 1133ms | 构造函数 + Show()（可接受） |
| MefHostServices 首次初始化 | 3976ms | Roslyn 补全引擎首启（Roslyn 4.12 版本固有成本） |
| MetadataReferenceProvider 引用初始化 | 4321ms | **全量 287 个 + 逐文件 `IsManagedAssembly` 读 PE 头** |
| RebuildWorkspace 总计 | 6123ms | 前两者串行 + 工作区构建 |
| 用户感知 | 窗口弹出后 6-8 秒编辑器不可用 | 引用构建重活 + 工作区同步等待 |

**三个根因**：
1. **引用集合过度扫描**：`MetadataReferenceProvider` 扫全量 TPA（~230）+ ALC（~50）= 287 个，其中大量是脚本用不到的（WPF 内部、语言包等）
2. **破坏惰性**：每个引用都走 `IsManagedAssembly`（`AssemblyName.GetAssemblyName` 真实读 PE 头），287 次文件 IO，这是 4.3s 主凶；RoslynPad 直接惰性 `CreateFromFile`
3. **同步等待**：`RebuildWorkspace` 同步完成 MEF + 引用 + 工作区构建，用户窗口弹出后只能干等

## 二、设计层分析（BCL 来源 + 三层分离 + 严重问题）

> 本节对照 RoslynPad 老版引用架构（`RoslynPad-avalonedit/src/RoslynPad.sln`）逐层审计现有设计。

### 2.1 RoslynPad 老版的引用架构（三层分离）

| 层 | 来源 | 实现位置 |
|----|------|---------|
| BCL | 显式声明 ~20（11 类型导入 + mscorlib + Facades 完整 BCL） | `RoslynHostReferences.cs:24-66` |
| 宿主 | `additionalAssemblies` 参数，应用自行传入 | `RoslynHost.cs:77-80` |
| 增量 | `#r` 指令源码动态解析（文件/GAC/NuGet） | `RoslynWorkspace.cs:121-175` |

引用在 `RoslynHost` 构造时一次性构建、进程级共享；`MetadataReference.CreateFromFile` 惰性创建，无逐文件校验。

### 2.2 BCL 来源论证：运行时 TPA 是唯一正确选择

**问题**：RoslynPad 用 .NET Framework **Reference Assemblies**（编译期引用程序集），我们能不能照搬？

**结论：不能。** 关键差异：
- RoslynPad 是独立 IDE（子进程执行，只编译不加载运行时类型），用 reference assembly 只需元数据
- 我们是**同进程加载脚本**——脚本继承 `Script` 基类，脚本程序集加载进 `ScriptSandbox` 的 ALC 后，类型身份必须和宿主一致（`ScriptSandbox.cs:16-20` 注释约束）。用 reference assembly 编译会导致类型身份不一致、运行时崩溃

**因此"运行时程序集（TPA）为源"方向正确，错的是全量扫描方式**，不是来源本身。

### 2.3 设计层严重问题（对照 RoslynPad）

| # | 严重问题 | 现状 | RoslynPad 正确做法 |
|---|---------|------|-------------------|
| 1 | **无分层**：BCL/宿主/无关程序集混在一层全量扫 | 287 个无差别注入 | 三层分离，每层来源与数量可控 |
| 2 | **破坏惰性**：`IsManagedAssembly` 逐文件 PE 头校验 | 287 次文件 IO = 4.3s 主凶 | `CreateFromFile` 直接惰性创建，无效文件让编译报错（rule-015） |
| 3 | **TPA 随部署漂移**：引用集合 = 宿主进程加载了什么，非脚本需要什么 | 部署环境不同 → 引用集合不同 → 不可控不可测 | 显式声明程序集路径，确定可控 |
| 4 | 补全无 XML 文档（次要） | `CreateFromFile` 未传 documentation | `DocumentationProviderService` 加载 XML 注释（`RoslynHost.cs:106-109`） |

### 2.4 增量层现状实证

**ScriptRefs 目录当前为空（0 个 dll）**，已用双路径验证：
- `list_dir dev/Debug/plugins/SunEyeVision.Tool.Script/ScriptRefs/` → 空目录
- `search_file` ScriptRefs 内全量搜索 → 0 个文件

因此当前脚本实际类型全靠 BCL + 宿主两层覆盖，增量层不贡献耗时（`SharedMetadataReferenceProvider.cs:34-41` 已有"目录不存在/空"短路）。

## 三、定位澄清

本工具是**单文档脚本工具**（视觉软件的一个脚本节点调试器），非 RoslynPad 那种多文档独立 IDE。

方向演进结论：
- **否决的是"8.3s 全量背给启动"**（L0：MEF 4s + 引用构建 4.3s = 8.3s）。其中引用 4.3s 是自我惩罚（全量扫描 + PE 校验），不该背给启动
- **引用白名单化后（<0.5s 懒加载），MEF 版本成本单独放启动后台预热是合理的**（对齐新版 RoslynPad 的 `Task.Run` 启动初始化）——换来首次打开工具也补全立即可用

聚焦：
- ✅ L1 引用三层分离（必选）：4.3s → <0.5s，打开时懒加载
- ✅ L2 MEF 启动后台预热（必选）：Roslyn 4.12 版本成本 1.9~3.4s 放应用启动阶段 `Task.Run` 后台跑，**不阻塞启动**；首次打开脚本工具补全立即可用
- ✅ L3 兜底渐进（防极速场景）：用户在 MEF 预热完成前打开 → 状态栏"补全引擎就绪中…"短暂显示，就绪后自动上线

## 四、专业级优化方案（L1 三层分离 + L2 启动预热 + L3 兜底）

### L1：引用三层分离（核心，治本 4.3s，打开时懒加载）

**改动点 1**：`MetadataReferenceProvider` 从"全量 TPA + ALC 扫描"改为"BCL 白名单 + 宿主类型锚定"两层。

**Layer 1 — BCL 白名单**（按程序集名精确匹配 TPA，来源 = .NET 9 运行时程序集名）：

**A 必备（3）**：`System.Private.CoreLib`、`System.Runtime`、`netstandard`

**B 通用 C# 编程（~20）**：
`System.Collections`、`System.Collections.Concurrent`、`System.Collections.Immutable`、`System.Linq`、`System.Linq.Expressions`、`System.IO`、`System.IO.FileSystem`、`System.IO.Compression`、`System.Text.Encoding`、`System.Text.RegularExpressions`、`System.Text.Json`、`System.Threading`、`System.Threading.Tasks`、`System.Threading.Thread`、`System.Reflection`、`System.Runtime.Loader`、`System.Diagnostics`、`System.Diagnostics.Process`、`System.Globalization`、`System.ComponentModel`、`System.ObjectModel`、`System.Numerics`、`System.Runtime.InteropServices`

**C 视觉业务对接（~6）**：
`System.Net.Http`、`System.Net.Primitives`、`System.Xml.ReaderWriter`、`System.Xml.XDocument`、`System.Drawing.Common`、`System.Data.Common`

**Layer 2 — 宿主 API**（类型锚定，不依赖扫描）：
`typeof(Script).Assembly` → `SunEyeVision.Plugin.SDK.dll`
`typeof(HOperatorSet).Assembly` → `halcondotnetxl.dll`
`typeof(Mat).Assembly` → `OpenCvSharp.dll`

**Layer 3 — 用户增量**（原样保留，不预加载）：
`SharedMetadataReferenceProvider.GetScriptRefs`（ScriptRefs 目录扫描 + 按目录缓存），当前为空目录零耗时

实现要点：
- 白名单内程序集**直接 `MetadataReference.CreateFromFile`（惰性，不做 PE 校验）**
- **删除** `IsManagedAssembly`/`TryAddRef` 的逐文件 PE 头校验（4.3s 主凶）
- **删除** `AddLoadedContextAssemblies`/`EnumerateRelevantContexts`（宿主改类型锚定）
- 保留进程级缓存 `_cachedReferences` + `InvalidateCache` 骨架
- 白名单内 TPA 缺失 → `PluginLogger.Warning`（rule-015 可见，不静默）
- 补全 XML 文档（次要）：`CreateFromFile` 传 `XmlDocumentationProvider`（对齐 RoslynPad `RoslynHost.cs:106-109`）

### L2：MEF 启动后台预热（治本 MEF 版本成本，对齐新版 RoslynPad）

**背景**：Roslyn 4.12 的 MEF 首次初始化 1.9~3.4s（三天日志实测），是版本固有成本，无法像 RoslynPad 老版（Roslyn 2.3.1）那样前台同步无感。新版 RoslynPad 的选择是**应用启动阶段 `Task.Run` 后台初始化**（`MainViewModel.cs:224-229`）。

**改动点 2**：把 MEF 预热从"工具打开时"提前到"应用启动时"。

- `ScriptTool` 静态构造函数（应用启动 `LoadPlugins` 实例化它时自动触发）调用 `ScriptDebugControl.WarmupForStartup()`，内部 `Task.Run` 后台执行 `GetSharedMefHost()`（fire-and-forget，**不阻塞应用启动**）
- MEF 是进程级静态缓存（`_sharedMefHost`），预热结果直接复用，`RebuildWorkspace` 打开时 0ms
- 保留 `WarmupRoslynAsync`/`WarmupWorkspaceAsync` 骨架，挪入 `WarmupForStartup` 统一调度

**关键防竞态**：`RebuildWorkspace` 若在 MEF 未就绪时被调用（用户在启动瞬间极速打开工具），**绝不能去等 `GetSharedMefHost` 的锁**（否则 2-3s 延迟被拉回 UI 线程卡死）。改为检查 `_completionReady`，未就绪则先显示代码，等 MEF 就绪回调再触发重建。

### L3：兜底渐进（防极速打开场景）

**改动点 3**：MEF 就绪前打开工具时的兜底反馈。

- `RebuildWorkspace` 开头：MEF 未就绪 → 先显示代码（词法着色可用），注册"就绪后自动重建"，不碰 MEF 锁
- 状态栏三态：`"补全引擎就绪中…"` → `RebuildWorkspace 完成后` → `"补全就绪"`
- MEF 就绪回调置 `_completionReady = true`，触发重建 + 恢复诊断
- 补全未就绪时运行脚本不阻塞（`ScriptCompiler.Compile` 独立路径，仅引用共享）

## 十一、编辑器体验优化（高亮 / 流畅性 / 补全弹窗）

> 本节为 2026-08-19 补充。用户反馈：当前高亮很丑；编辑流畅性"老版最流畅、我们稍微卡、新版 RoslynPad 最卡"；补全弹窗内容需优化。三者均有 RoslynPad 老版可照抄的成熟实现。

### 11.1 高亮丑：现代配色 + 删手工类型名表

**现状问题**：
- 调色板是 VS2015 老配色（`CSharpLight.xshd:3-14`）：Keyword `#0000FF` **bold**、Comment `#008000` 纯绿、String `#A31515` 深红——老气，现代编辑器用柔和色
- xshd 内 **190-321 行手工硬编码 100+ BCL 类型名**（`DateTime`/`List`/`Dictionary`/`HttpClient` 全手写 `<Word>`）——漏一个类型不高亮、多一个抢占规则，且与语义着色功能重叠（rule-008 死代码风险）

**治本**：
1. 调色板换现代 C# 配色（对齐 VS2022 / VS Code）：Keyword `#569CD6`、String `#CE9178`、Comment `#6A9955`、类型青、方法黄、字段浅蓝，全部**去 bold**
2. **删除 xshd 手工类型名表**，类型/方法/字段着色全部交语义着色（Layer 2a `ClassifyToken`）全覆盖——与 RoslynPad 用 `ClassificationHighlightColors`（`ClassificationHighlightColors.cs:16-18`）+ `GetClassifiedSpansAsync` 的语义分类思路一致，不硬编码关键字

### 11.2 编辑流畅性：语义着色行级缓存 + 增量重算

**现状问题**（为什么"我们稍微卡"）：
- 每次编辑 100ms 节流后 → `RunSemanticAsync`（`ScriptDebugControl.xaml.cs:1310-1354`）**全文档遍历 `root.DescendantTokens()`** 重新生成所有 spans
- `SemanticColorizer.ColorizeLine`（1469-1492）渲染每行都**线性扫全部 spans**（`foreach` + 区间判断）

**对照 RoslynPad 老版**（`RoslynSemanticHighlighter.cs:42-77`）：
- **512 行缓存**（`CacheSize = 512`）+ worker 线程 + 队列
- **文档版本比对**（`BelongsToSameDocumentAs`，122 行）——只重算**变化的行**，未失效行直接复用缓存
- `HighlightLine` 只处理需要高亮的行

**治本**：语义着色加**行级缓存 + 增量重算**——编辑只影响改动段落，未变行从缓存取；`ColorizeLine` 按行号查缓存，不做全量遍历。实现可参考 RoslynPad 老版 `RoslynSemanticHighlighter` 的 `CachedLine`/版本比对模式。

### 11.3 补全弹窗内容差：补齐图标 / 描述 / 预选 / 排序

**现状问题**（`ScriptDebugControl.xaml.cs:1396-1422`）：

```csharp
public System.Windows.Media.ImageSource? Image => null;        // ❌ 无类型图标
public object Content => item.DisplayText;                      // 纯文本
public object? Description => item.InlineDescription;           // ❌ 只有一行内联描述
public double Priority => 0;                                    // ❌ 无预选/排序
```

**对照 RoslynPad 老版**（`RoslynCompletionData.cs:34-44, 114-131`）：

```csharp
Image = _glyph.ToImageSource();                                 // ✅ 类/方法/属性/字段 类型图标
Description = await GetDescriptionAsync(...)                    // ✅ 完整 XML 文档富文本
    .TaggedParts.ToTextBlock();
IsSelected => _item.Rules.MatchPriority == MatchPriority.Preselect;  // ✅ 预选中高亮
SortText => _item.SortText;                                     // ✅ 智能排序
Complete => GetChangeAsync(...)                                 // ✅ 正确替换范围 + snippet 支持
```

**治本**：照抄 RoslynPad 老版 `RoslynCompletionData` 模式：
1. `Image` 用 `CompletionItem.GetGlyph()` 映射类型图标（类/方法/属性/字段/枚举/常量不同图标）
2. `Description` 改走 `GetDescriptionAsync`（完整 XML 文档，含参数说明）
3. `IsSelected`/`SortText` 接上 Roslyn 的预选与排序
4. `Complete` 换 `GetChangeAsync`（正确处理替换范围，老版 `RoslynCompletionData.cs` 已用 `completionSegment.EndOffset > textChange.Span.End` 修正快照 Span 偏移，可照搬）

### 11.4 对齐结论

| 问题 | 治本 | 对照 RoslynPad 老版 |
|------|------|-------------------|
| 高亮丑 | 现代配色 + 删 xshd 类型名表 | `ClassificationHighlightColors` + 语义分类 |
| 编辑卡 | 语义着色行级缓存 + 增量重算 | `RoslynSemanticHighlighter` 512 行缓存 |
| 补全差 | 图标/描述/预选/排序 | `RoslynCompletionData` |

### 11.5 主题系统适配（编辑器高亮随主题切换）

> 本节为 2026-08-19 补充。方案 11.1 提出的 `#569CD6` 等配色若硬编码，会破坏项目现有主题系统（亮色在暗色主题下刺眼）。必须对齐项目成熟的主题 Token 机制。

**现状问题**：编辑器内高亮全部硬编码亮色，不随主题切换。
- xshd 语法高亮（`CSharpLight.xshd`）：关键词 `#0000FF` 等硬编码
- 语义着色 `SemanticBrushes`（`ScriptDebugControl.xaml.cs:1432-1435`）：静态 frozen Brush，硬编码类型青/方法紫/字段金
- 补全弹窗图标：无主题图标

而编辑器外壳已用主题（`ScriptDebugControl.xaml:12-13` 用 `ThemePanelBackgroundBrush`）。切暗色时背景变深灰（`#1E1E1E`），代码仍是亮色——关键字 `#0000FF` 在深灰上刺眼，这是"高亮丑"在暗色下更明显的原因。

**关键约束**：脚本工具插件**不能引用 `SunEyeVision.UI`**（`ThemeKeys` 所在层），只能引用 `Plugin.SDK`（`SunEyeVision.Tool.Script.csproj:34-43`）。

**项目已有成熟解法**：`SdkThemeKeys`（`src/Plugin.SDK/UI/Themes/SdkThemeKeys.cs:10`）注释明示设计动机：
> SDK 不能引用 UI 程序集（循环依赖），故在 SDK 层自建等值常量。字符串与 UI 层 ThemeKeys 完全一致，使 SDK 控件在 UI 宿主内可通过 DynamicResource 命中 UI 主题字典。

`CustomDebugWindow.cs:88` 已演示正确用法：`SetResourceReference(BackgroundProperty, SdkThemeKeys.PanelBackgroundBrush)` 动态绑定语义键，主题切换自动刷新。

**当前主题系统缺"代码编辑器语法"语义键**：`SdkThemeKeys`/`ThemeKeys` 有窗口/控件/文字/表格/状态键，但无 Keyword/Comment/String/Type/Method/Field 键。

**治本**（复用现有主题机制，rule-004 不重复造轮子）：
1. **`ThemeKeys`（UI 层）+ `LightTheme.xaml`/`DarkTheme.xaml`** 各新增代码语义键：
   - `EditorCodeKeyword` / `EditorCodeComment` / `EditorCodeString` / `EditorCodeType` / `EditorCodeMethod` / `EditorCodeField` / `EditorCodeText`
   - 亮色值：VS Code 亮色 `#569CD6`/`#6A9955`/`#CE9178` 等
   - 暗色值：VS Code 暗色（同色系，暗色下高可读）
2. **`SdkThemeKeys`（SDK 层）** 新增等值常量，脚本工具插件可引用
3. **`SemanticBrushes` 改动态取色**：从静态 frozen Brush 改为运行时从 `Application.Current.Resources` 取 `EditorCode*Brush`，或改用 `SetResourceReference` 动态绑定（对齐 `CustomDebugWindow.cs:88`），并监听 `ThemeManager.ThemeChanged` 刷新
4. **xshd 语法高亮改主题键**：`CSharpLight.xshd` 颜色引用主题语义键（DynamicResource）
5. **补全弹窗图标**：类型图标 `GetGlyph` 语义映射，图标前景随主题

**契约一致性（rule-015）**：新增键必须同时进 `ThemeKeys` + `SdkThemeKeys` + Light/Dark 双字典，满足 `ThemeManager.ValidateSdkThemeKeys` 契约校验（`ThemeManager.cs:169-185`，缺键抛异常，不静默回退）。

### 11.6 编辑器体验优化对齐结论（含主题）

| 问题 | 治本 | 主题适配 |
|------|------|---------|
| 高亮丑 | 现代配色 + 删 xshd 类型名表 | 改走 `SdkThemeKeys` 代码语义键，双主题 |

参考：`D:\MyWork\参考项目\RoslynPad-avalonedit\src\RoslynPad.sln`（老版，WPF+AvalonEdit 同栈）

**RoslynPad 快的本质（本次对齐）**：
- 老版窗口先显示再初始化（`MainWindow.xaml.cs:46-51`），因 Roslyn 2.3.1 快能前台同步无感
- **新版应用启动阶段 `Task.Run` 后台初始化 RoslynHost**（`MainViewModel.cs:224-229`），打开文档立即可用——**这是本方案 L2 的直接依据**
- 引用显式声明（`RoslynHostReferences.cs:24-66`）
- `CreateFromFile` 惰性（`RoslynHostReferences.cs:122-124`）

**RoslynPad 与我们的差异（合理性判断）**：
- 老版引用含完整 BCL Facades（~60-80 个）+ mscorlib，本质是"完整 BCL + 惰性创建"——引用数量不是快慢主因，**破坏惰性的 PE 校验才是 4.3s 主凶**
- 新版 RoslynPad 用 VS-MEF 替代 System.Composition MEF，引用彻底交给 #r/NuGet 动态解析——**多文档 REPL 场景**，单文档工具不需要 #r，已有 `AssemblyReferenceDialog` 管理 ScriptRefs 目录（工具级共享）
- 本工具是视觉工具，脚本必须访问宿主 API（halcon/CvEngine），同进程 ALC 是唯一正确解；RoslynPad 是 REPL 独立场景，子进程合理。此部分不改
