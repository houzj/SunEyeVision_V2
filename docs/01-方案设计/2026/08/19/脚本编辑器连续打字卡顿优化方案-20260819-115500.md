# 脚本编辑器连续打字卡顿根治方案（删 TextLoader · 恢复增量通道 · 补全去节流）

> 2026-08-19。编辑器体验优化专项方案之一（最终整合版，修订历史见文末）。
> 背景：用户反馈脚本编辑器"连续打字/删除/换行都卡顿"，而 RoslynPad 老版同样连续打字却丝滑。
> 初版曾误判为"每次按键全量重建 Roslyn 文本"，实施中引入 `AvalonEditTextLoader` 反而导致严重回归（语义全黑、补全失效、打字滞后）。
> 本版经完整调研 Roslyn 增量机制与参考项目源码，定位**真因 = TextLoader 每次返回新版本号强制全量重解析**，给出删 TextLoader、恢复 `SourceTextContainer` 增量通道的治本设计。

## 🔄 改前 → 改后 → 依据

### 改前（用户视角）
在脚本编辑器里连续打字，**光标明显跟不上手**；敲几个字母后 `HOperatorSet`、`UserScript` 等标识符**全部变黑**（语义着色失效）；补全列表要么不弹、要么弹出的是旧内容；打字过程中滚动也卡。

### 改后（用户视角）
打字**跟手**，语义着色实时正确，补全即时弹出且内容新鲜。恢复到老版 RoslynPad 同等流畅度。连续打字、删除、换行全程不卡。

### 依据（业界参考，可追溯）
- **RoslynPad 老版**（`RoslynPad-avalonedit/src/RoslynPad.Editor.Shared/AvalonEditTextContainer.cs:18-56`）：`AvalonEditTextContainer : SourceTextContainer`，编辑时用 `_currentText.WithChanges(new TextChange(span, insertedText))` **增量**更新，触发 `TextChanged` 事件；配合 `RoslynWorkspace.OpenDocument(documentId, textContainer)`（`RoslynWorkspace.cs:58-63`）走 **Roslyn 原生 SourceTextContainer 增量通道**
- **RoslynPad 老版**（`CodeTextEditor.cs:265-269`）：补全 `OnTextEntered` 直接异步查询，**零节流**
- **RoslynPad 新版**（Morgania 内核，`RoslynPad/src/RoslynPad/Roslyn/RoslynHost.cs:250`）：同样 `workspace.OpenDocument(documentId, args.SourceTextContainer)`，证明此机制是 Roslyn 长期支持的官方通道
- **Roslyn 官方**：增量 = `SourceText.WithChanges(TextChange)` + `WithDocumentText` + `TryApplyChanges`，新 Solution 复用未变语法树/编译/语义模型；`TextLoader` 返回新版本会强制全量重解析，是**错误适配**
- **VS Code LSP**：文件编辑走增量 `contentChanges` 通知（与 Roslyn 增量思想一致）

## 问题分析（Phase 0）

### 需求拆解
- **表面需求**：连续打字不卡、语义着色正常、补全即时。
- **根本问题**：Roslyn 文档文本同步通道用错——`TextLoader` 的契约是"整个文档从外部源加载 + 版本号"，我们每次返回新版本号，等于**每次查询都宣称整个文件变了**，Roslyn 被迫全量重解析。这不是增量解析效率变差的问题，是我们把 Roslyn 用错了姿势。
- **问题分类**：**实现方式有误**（机制误用，非功能缺失、非 Roslyn 本身问题）。

### 架构分配检查
- 最自然归属层：`ScriptDebugControl`（编辑器 View 层）— [来源] `ScriptDebugControl.xaml.cs:50`
- 已有类似机制：有——`AvalonEditTextContainer : SourceTextContainer` 本身就是正确的增量容器（`AvalonEditTextContainer.cs:47`），**只是被错包进了 loader** [来源] `:909-914`
- 不改是否可覆盖：否。TextLoader 通道本质上无法表达局部变化
- 是否改变分层边界：否。容器/workspace/补全/语义调用方全不变，只改绑定方式

### 方法对比（≥3 候选）

| 维度 | 方案 A：删 TextLoader + OpenDocument 注册容器（推荐） | 方案 B：保留 loader 但缓存文本不换版本 | 方案 C：回退 WithText 全量更新 |
|------|--------------|--------------|--------------|
| 实现方式 | `ScriptWorkspace.CanOpenDocuments=true` + `OpenDocument(id, container)`，对齐 RoslynPad | loader 返回固定版本，靠容器 TextChanged 手动 WithDocumentText | 每次打字 `WithDocumentText(全量)` + TryApplyChanges |
| 架构一致性 | ✅ 原生 SourceTextContainer 通道（VS/RoslynPad 同款） | ❌ 仍是 TextLoader 假语义 | ❌ 每次按键全量 solution 变化 |
| 复杂度 | 小（1 类 + 2 处绑定） | 中（双通道冗余、手动同步） | 中（打字一次全量重建一次） |
| 维护成本 | 低（业界标准模式） | 高（loader+容器两套状态难对齐） | 高（卡顿根源还在） |
| 长期 ROI | 6月/1年/3年均最高 | 低 | 低 |
| 卡顿消除 | ✅ 彻底 | ⚠️ 缓解 | ⚠️ 不彻底 |

## Bug 模式分析（Phase 0.5）

**当前 bug**: 连续打字全量重解析 → 卡顿 + 语义全黑 + 补全失效。

**真因分类**: **契约漏洞** — 对 Roslyn 文本同步双通道（`SourceTextContainer` 增量 vs `TextLoader` 全量）契约的误用，且无任何测试守护绑定契约。

**同类潜伏点**:
- [来源] `ScriptDebugControl.xaml.cs:892-893` — 注释声称"绑定 AvalonEditTextLoader 增量同步"，与实现南辕北辙
- [来源] `ScriptDebugControl.xaml.cs:1149,1180-1181,1420` — 三处注释声称"已绑定 AvalonEditTextContainer 增量"，误导后续维护者

**治本点**: 修复**文本同步通道选择**（用 SourceTextContainer 增量通道替代 TextLoader 全量通道），而非调小节流值、加缓存这类症状级手段。

**证据缺失警告**: 本 Bug 为 TextLoader 错误适配的孤例，但按治本标准修复，并新增契约测试防止未来复制此模式。

## 解决方案

### 方案概述
把用户文档的文本同步从"TextLoader 全量通道"改为"SourceTextContainer 增量通道"（`ScriptWorkspace.OpenDocument` 注册容器），补全去掉 50ms 节流改为纯取消竞态。容器、按行缓存、诊断/语义节流保留。

### 技术方案

**改动点 1：新增 `ScriptWorkspace : AdhocWorkspace`**
- override `CanOpenDocuments => true`（对齐老版 `RoslynWorkspace.cs:45`）：AdhocWorkspace 默认 `CanOpenDocuments=false`，直接 `OpenDocument` 会抛异常

**改动点 2：`RebuildWorkspace` 改绑定**
- 用户文档 `DocumentInfo.Create` 不带 loader → `AddDocument` → `_workspace.OpenDocument(userDoc.Id, _userTextContainer)`
- 容器存字段防 GC，重建前 Dispose 旧容器

**改动点 3：补全去 50ms 节流**
- 删 `Task.Delay(50, token)`，保留 `_throttleCts` 取消旧查询
- `FetchFreshCompletions` 增 `CancellationToken` 参数，查询完成若已取消则丢弃结果

**改动点 4：保留项**
- `_semanticSpansByLine` 按行缓存保留
- 诊断 500ms、语义 100ms 节流保留（现状架构下全量遍历需要；演进为按行懒查询后再去——YAGNI，本次不做）
