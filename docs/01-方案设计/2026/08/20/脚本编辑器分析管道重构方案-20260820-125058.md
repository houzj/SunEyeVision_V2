## 一、为什么写了本方案

阶段一/二（行号修复、波浪线、ToolTip、日志清理）已实施。但用户实测反馈仍有多项体验问题，且与本方案讨论中**反复出现同一类根因**：

| 用户反馈 | 直接表现 |
|---------|---------|
| 删除字母后补全和滚动卡顿 | 越删越卡，删到语法错误最卡 |
| 打字时卡顿 | 补全弹窗响应慢 |
| 打开调试窗口有明显颜色变化过程 | 打开瞬间默认色 → 约 300ms 变语义色 |
| 节流机制应对齐老版 | 老版无节流，我们 100ms/500ms 延迟 |

**用户核心质疑（原话）**："为什么优化了这么多轮还没根治，一会冒出一个全量一会冒出一个全量，到底还要优化几轮。"

## 二、根因诊断：同一个管道的四个症状

### 现有架构：全量管道

```
每次编辑 → 全量算一遍 → 存缓存 → 渲染按行查缓存
```

这个管道存在，**每次编辑天然就是一次全量计算**。四轮优化都是在"已有的全量管道上打洞"：
- 诊断全量 → 加 500ms 节流
- 语义全量 → 加 100ms 节流
- 着色 → 加按行缓存字典
- 删日志埋点

每轮把卡顿从 A 挪到 B，**管道本身没变**。

### 老版 RoslynPad：按需管道（根本无全量）

### Bug 模式

**当前 bug**：打字/删除/滚动卡顿 + 打开变色 + 节流滞后。
**真因分类**：**设计缺陷**（架构层面注定）。
**同类潜伏点**：语义遍历、诊断全量、WithDocumentText、RebuildWorkspace 四处同根。
**治本点**：修复"全量管道 + 每次重建"架构，而非单点。四件事是同一管道的四个症状。

## 六点五、设计决策：多工具 Workspace 隔离（关键修正）

### 现状（代码验证）

- `_workspace` 是**实例字段**（`ScriptDebugControl.xaml.cs:55`）——每个工具实例各持一个 `ScriptWorkspace`，**不同工具窗口互不共享、互不干扰** ✓
- `_preWarmedWorkspace` 是**静态字段**（`:92`），应用启动预热一次，**单发消费**：第一个打开的工具取走并置 null（`:825-829`），第二个工具只能 `new ScriptWorkspace(host)` 重建（`:833`）

### 关键结论：不能简单"进程级共享一个 Workspace"

共享同一 Workspace 是危险的：多个工具实例往同一 Workspace 的 Solution 里 `AddProject`/`ChangeDocument` 会**互相覆盖**（A 工具的文档把 B 工具的顶掉）→ 引入多工具互扰新 bug。RoslynPad 能"常驻一个 Workspace"，是因为它是**单文档编辑器**（同一时刻只有一个文档）；而我们的 Script 工具可**多节点同时打开多个调试窗**，不能共享。

### 正确设计：实例级复用（保持隔离）

| 场景 | 处理 |
|------|------|
| 工具实例首次打开 | 建 Workspace（拿预热骨架 `_preWarmedWorkspace` 或 new） |
| 同一实例重复 SetParameters / 重复打开 | **不 Dispose 重建**，`ChangeDocument` 只更新文档文本，复用实例 workspace |
| 不同工具实例 | 各持各的 Workspace，零干扰（保持现状隔离） |

即"常驻"是**实例级常驻**，不是**进程级共享**——既避免每次 267ms 重建，又避免多工具互扰。

### 参考依据

RoslynPad-avalonedit 的 `RoslynHost`/Workspace 是单文档语义；对多实例场景，业界通用做法是"每实例一 Workspace + 复用不重建"（避免共享可变状态）。
