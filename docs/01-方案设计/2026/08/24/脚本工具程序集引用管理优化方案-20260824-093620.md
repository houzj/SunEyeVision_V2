# 脚本工具程序集引用管理优化方案

## 🔄 改前 → 改后 → 依据

### 改前（用户视角）

| 问题 | 表现 |
|------|------|
| 编译慢 | 每次 Emit 绑定 35 个宿主程序集（含几百 MB 的 halcondotnetxl、OpenCvSharp），首次 Emit **1748ms**（实测日志 `Emit=1748ms, 宿主=35`） |
| 引用不可控 | halcondotnetxl / OpenCvSharp 被无条件注入编译基线，不管脚本用不用都得付代价 |
| 引用粒度全局化 | 所有脚本节点共享同一个 ScriptRefs 目录，无法做到"节点 A 用 halcon、节点 B 只用 OpenCvSharp" |
| 架构概念复杂 | 引用分三层（BCL/宿主/用户），各自无条件注入，无统一真相源 |

### 改后（用户视角）

1. **每节点程序集列表 = 唯一真相源**：每个脚本工具节点自己维护一张 `AssemblyReferences` 列表（序列化到节点配置，随方案保存/加载），编译只引用列表里的程序集
2. **一张勾选列表 UI**：打开"引用程序集"，看到一张清单（系统必需锁定 + halcon/OpenCvSharp + 用户 DLL），**勾选的才被引用**
3. **编译基线最小化**：默认只引系统必需项（BCL + Script 基类），halcon/OpenCvSharp 从基线移除，Emit 大幅提速
4. **三层取消**：不再有"BCL层/宿主层/用户层"概念，退化为一个"名称→路径"解析函数
5. **勾选 halcon 即用**：候选库预置 halcondotnetxl（类型锚定拿路径），勾选即引用，不用手动找 DLL

### 依据（业界 + 实测）

- **VM 程序集管理界面**（用户提供截图）：一张列表管理引用，按需引用，门面隔离大程序集
- **实测数据**：Emit 1748ms 主因 = halcondotnetxl 等大程序集元数据绑定（35 个宿主引用）
- **MAGE3D**：脚本默认最小引用，视觉 API 按需
- 用户定调：不做独立进程（图像跨进程代价）；列表是唯一真相源；无磁盘缓存 / 无启动预热

## 一、问题分析

### 需求拆解

- **表面需求**：脚本编译慢、不同脚本要用不同程序集
- **根本问题**：编译基线无条件注入大程序集（halcon/OpenCvSharp）+ 引用管理无统一真相源（三层各自注入）
- **问题分类**：架构冗余（基线含非必需引用 + 三层概念）+ 功能缺失（无每节点引用管理）

### 架构分配检查（已核实）

| 检查项 | 结论 | 来源 |
|--------|------|------|
| 引用注入层 | `AddHostApiAnchored` 无条件含 `typeof(HOperatorSet)`/`typeof(Mat)` | [来源] `ScriptEngine/MetadataReferenceProvider.cs:179-193` |
| 引用管理 UI | `AssemblyReferenceDialog` 已存在（全局 ScriptRefs 目录） | [来源] `Views/AssemblyReferenceDialog.xaml.cs:21-43` |
| 编译引用组装 | `ScriptCompiler` = HostReferences(35) + ScriptRefs | [来源] `ScriptEngine/ScriptCompiler.cs:131-145` |
| 引用目录配置 | `ScriptParameters.AssemblyReferenceDir = "ScriptRefs"` 固定 | [来源] `Models/ScriptParameters.cs:50` |
| 编译缓存键 | `代码SHA256 + 宿主指纹`，不含引用列表 | [来源] `ScriptEngine/ScriptCompiler.cs:95` |
| ALC 隔离 | `ScriptSandbox` 已有自定义 ALC | [来源] `ScriptEngine/ScriptSandbox.cs:36` |

### 方法对比

| 维度 | 方案 A（推荐）：列表唯一真相源 | 方案 B：只移除 halcon 基线 | 方案 C：三层候选池 |
|------|------------------------------|--------------------------|------------------|
| 实现方式 | 每节点 AssemblyReferences 列表 + ResolveAssemblyPath 解析 | 只改 AddHostApiAnchored 移除 2 锚定 | 三层保留为候选池，UI 从池选 |
| 架构一致性 | 单一真相源，最简洁 | 符合但粒度仍全局 | 真相源仍是三层，复杂 |
| 复杂度 | 中 | 低 | 中高 |
| 维护成本 | 低（一个列表管一切） | 低（不解决多节点） | 中（两套概念并存） |
| 长期 ROI | 6月✓/1年✓/3年✓ | 6月✓/1年✗ | 6月✓/1年△ |
| 结论 | **推荐** | 过渡 | 否决（已收敛） |

## 二、Bug 模式分析

**当前 bug**：脚本编译 1748ms + 引用粒度全局化。

**真因分类**：设计缺陷（基线含非必需大程序集 + 三层概念无唯一真相源）。

**同类潜伏点**：
- [来源] `MetadataReferenceProvider.cs:179-193` — 把可选能力（halcon/OpenCvSharp）当必要依赖（同 pattern）
- [来源] `ScriptCompiler.cs:95` — 编译缓存键不含引用列表（引用列表化后会导致错误缓存命中）

**治本点**：① 每节点 AssemblyReferences 为唯一真相源；② 缓存键含引用列表指纹。

## 四、解决方案（修改清单）

### 第一部分：每节点引用列表（唯一真相源，核心）

| # | 文件 | 变更 | 核心变更 |
|---|------|------|---------|
| 1 | `Models/ScriptParameters.cs` | 修改 | 新增 `[JsonPropertyName("assemblyRefs")] public ObservableCollection<string> AssemblyReferences`（每节点启用的程序集列表，序列化保存）；新节点预置系统必需项（mscorlib/Script 基类等，UI 锁定）；删除/弃用 `AssemblyReferenceDir` 固定字符串 |
| 2 | `ScriptEngine/ScriptCompiler.cs` | 修改 | 编译引用 = 遍历 `AssemblyReferences` 逐个 `ResolveAssemblyPath(name)` → CreateFromFile；**缓存键改为 `代码SHA256 + 宿主指纹 + 引用列表SHA256`**（引用变化自动失效） |

### 第二部分：路径解析（三层退化，核心）

| # | 文件 | 变更 | 核心变更 |
|---|------|------|---------|
| 3 | `ScriptEngine/MetadataReferenceProvider.cs` | 修改 | 新增 `ResolveAssemblyPath(string name)`：BCL 走 TPA 白名单匹配 / 宿主 API 走类型锚定（Script/HOperatorSet/Mat）/ 用户 DLL 走 ScriptRefs 目录；找不到 → 抛异常（rule-015 不静默）。保留 `GetHostReferences()`（BCL+Script 必需项，缓存一次）作为新节点默认列表来源 |

### 第三部分：程序集管理 UI（核心）

| # | 文件 | 变更 | 核心变更 |
|---|------|------|---------|
| 4 | `Views/AssemblyReferenceDialog.xaml(.cs)` | 修改 | 从"全局目录管理"改为"当前节点勾选列表"：一张列表（系统必需锁定 + halcon/OpenCvSharp 候选 + ScriptRefs DLL），勾选写入节点 `AssemblyReferences` |
| 5 | `ScriptDebugControl.xaml.cs` | 修改 | `AssemblyRefButton_Click`（:515）改调新对话框，保存后失效缓存 + 重建 workspace |

### 第四部分：迁移与运行时保障

| # | 文件 | 变更 | 核心变更 |
|---|------|------|---------|
| 6 | `ScriptDebugControl.xaml.cs` | 修改 | 打开脚本节点时，检测代码引用 `HOperatorSet`/`using HalconDotNet` 但 `AssemblyReferences` 缺 halcondotnetxl → 黄字提示"补加引用" |
| 7 | `ScriptEngine/ScriptSandbox.cs` | 确认 | 运行时 ALC 不变：宿主 DLL（halcon/OpenCvSharp）由默认 ALC fallback 解析，用户 DLL 预加载沙箱（已有机制，无需改） |

### 第五部分：Demo 示例改为纯通用 SDK API（对齐 VM 门面哲学）

| # | 文件 | 变更 | 核心变更 |
|---|------|------|---------|
| 8 | `Resources/DemoCode.txt` | 修改 | **彻底移除 `HalImage` 和 `HOperatorSet`**，Demo 只处理 `IVisionImage` 通用接口（Width/Height/Channels/IsEmpty/Clone/GetPixelData）+ `GetGlobal/SetGlobal`；不使用 `HalImage.CreateGrayFromColor`（它暴露具体引擎类型）；同步更新文件头 `using`（移除 `using HalconDotNet`）和注释说明 |
| 9 | `Models/ScriptParameters.cs` | 修改 | 更新 `DemoCode` 的 XML doc 注释（移除"覆盖 5 个场景含 halcon 算子"描述，改为"覆盖图像信息/图像拷贝/像素数据/全局变量读写"）；Demo 默认引用（系统必需项）即可编译，无需额外勾选 halcon |

> 说明：Demo 只处理 `IVisionImage` 通用接口，**不涉及 `HalImage` 具体类型**——这样脚本编译和运行都零 halcon 依赖（`HalImage` 内部持 HImage 虽能由宿主解析，但 Demo 保持纯净不暴露引擎类型）。需 halcon 底层算子的场景走"程序集管理勾选 halcondotnetxl"（正规入口）。对标 VM 脚本默认只引 `Script.Methods` 门面、不裸用 halcon。依据 [来源] 用户提供 VM 最简脚本模板 + [来源] `IVisionImage.cs:9-28`（通用接口）

## 七、风险评估

| 风险 | 影响 | 缓解 |
|------|------|------|
| 移除 halcon 基线导致现有脚本编译失败 | 中 | 候选库预置 + 打开时检测提示补引用（迁移保障） |
| 每节点引用列表序列化破坏旧方案兼容 | 中 | 新节点默认预置系统必需项，旧节点迁移时列表含 ScriptRefs 现有 DLL |
| 缓存键含引用指纹后首次编译变多 | 低 | 只在引用列表变化时重编译（低频），正常执行仍命中缓存 |
