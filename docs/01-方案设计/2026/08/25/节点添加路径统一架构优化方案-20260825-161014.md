# 节点添加路径统一架构优化方案

> 类型: 架构优化方案
> 日期: 2026-08-25
> 状态: 待实施

## 一、改前 / 改后 / 依据（用户视角）

**改前**：往画布拖放一个新脚本节点，**有些时候**它第一次运行要 40-60ms（现场编译+建沙箱），有些时候只要 2ms——**行为随"添加路径"而变，不可预测**。原因是节点添加存在两条路径，一条做全量业务处理（日志/命令/绑定/预编译），另一条裸操作集合绕过一切。

**改后**：无论节点从哪来（拖放/工具栏/代码），**都经过唯一的添加管道**，所有业务处理（日志、命令、自动绑定、预编译）**必定执行**。新脚本节点首次执行稳定 ~4ms，行为可预测。

**依据**：这是**设计缺陷**（架构层面注定行为分裂），不是 bug——两条路径的存在让"添加节点"的语义不确定。业界节点编辑器（React Flow/Nodify）均以**受控变更**为唯一入口。

---

## 二、问题分析（调研结论 + 来源标注）

### 2.1 两条添加路径（代码事实）

| 路径 | 位置 | 行为 |
|------|------|------|
| **A. `AddNodeToWorkflow`** | `MainWindowViewModel.cs:2153` | ✅ 日志 + `AddNodeCommand`（命令/撤销）+ `TryAutoBindImageSource` + 预编译 |
| **B. 裸 `WorkflowNodes.Add`** | `DragDropHandler.cs:354` | ❌ 直接操作集合，绕过一切 |

`DragDropHandler.cs:346-355` 的分支逻辑：
```csharp
var viewModel = GetCachedViewModel();
if (viewModel != null)
    viewModel.AddNodeToWorkflow(newNode);   // 路径 A
else
    workflowTab.WorkflowNodes.Add(newNode);  // 路径 B ← 回退
```

### 2.2 路径 B 何时触发（真实场景）

`GetCachedViewModel()`（`DragDropHandler.cs:73-89`）是**静态缓存**，带 30 秒过期；缓存过期且 `Application.Current?.MainWindow` 获取失败时返回 null → 走路径 B。

**证据**：日志 `SunEyeVision_160322.txt` 中，节点添加时**无 `➕ 添加节点:` 日志**（`AddNodeToWorkflow` line 2165 的日志），但节点确实添加成功——证明走了路径 B。而 `DragDropHandler.cs:349` 若走路径 A 必打该日志。→ 用户实际触发路径 B。

### 2.3 为什么这是设计缺陷

| 维度 | 问题 |
|------|------|
| **单一入口破坏** | `AddNodeToWorkflow` 注释宣称"添加节点"，但非唯一入口 |
| **副作用丢失** | 路径 B 丢日志/命令/绑定/预编译 |
| **行为不可预测** | 首次执行耗时随路径变（40-60ms vs 4ms）|
| **隐藏故障** | 回退路径掩盖 `GetCachedViewModel` 获取失败的根因 |

## 三、Bug 模式分析

**当前 bug**: 新添加脚本节点首次执行 40-60ms（路径 B 未预编译）

**真因分类**: **设计缺陷**（添加路径分裂，架构注定行为不一致）

**同类潜伏点**:
- [来源] `DragDropHandler.cs:354` — 裸 `WorkflowNodes.Add` 绕过业务（本次根因）
- [来源] `MainWindowViewModel.cs:2177` — `AddNodeToWorkflow` 用 `AddNodeCommand` 但**预编译是 add 之后手动调用的**（业务副作用散落在调用方，而非管道内）
- [推测] 未来新增"复制节点/从模板添加"等路径时，同样可能绕过统一管道

**治本点**: 建立**单一受控添加管道**——所有节点添加必须经命令执行，且**业务副作用（日志/绑定/预编译）作为管道的固有部分**，不依赖调用方自觉。

## 四、业界对标（3+ 框架）

| 框架 | 关键特征 | 文档引用 | 借鉴/不借鉴 |
|------|---------|---------|-----------|
| **React Flow** | `onNodesChange` 是**唯一变更入口**，所有节点增删改通过 `applyNodeChanges` 统一处理；添加用 `addNodes` 受控 API | reactflow.dev 官方文档 | **借鉴**：单一受控变更入口，副作用在 reducer 层统一处理 |
| **Nodify（WPF 节点编辑器）** | `ItemsControl` 绑定 `Nodes` 集合，节点操作通过 Command/事件在 ViewModel 统一处理 | devpress.csdn.net Nodify 指南 | **借鉴**：ViewModel 是唯一操作入口，View 不直接改集合 |
| **WPF Command 模式（MVVM）** | `ICommand` 封装操作，撤销/重做由 CommandManager 统一管理 | learn.microsoft.com WPF Command | **借鉴**：项目已有 `AddNodeCommand`，应作为唯一执行通道 |
| **VisionMaster（海康）** | 节点添加/连线全部走内部命令栈，支持 Ctrl+Z 撤销 | 海康 VisionMaster 文档 | **借鉴**：命令栈统一管理所有编辑操作 |

**决策依据**：
1. 项目**已有 `CommandManager` + `AddNodeCommand`**（`WorkflowTabViewModel.CommandManager`）——命令模式基础设施完备，**复用而非另起炉灶**
2. React Flow 证明"单一受控入口"是节点编辑器的主流做法
3. 业务副作用（预编译）属于"节点加入后的固有处理"，应收敛到管道内，而非散落在 UI 调用方

## 五、方案对比（3 候选）

| 维度 | 方案 A（推荐）统一受控管道 | 方案 B：预编译挂集合事件 | 方案 C：删除回退分支 |
|------|--------------------------|------------------------|--------------------|
| 实现方式 | `DragDropHandler` 删除回退分支，强制 `AddNodeToWorkflow`；`AddNodeToWorkflow` 内把预编译移入命令管道 | `WorkflowCanvasControl` 监听 `CollectionChanged`，新增节点时统一预编译 | 仅删除 `DragDropHandler.cs:354` 的 else 分支 |
| 与架构一致性 | ✅ 复用现有 CommandManager + AddNodeCommand | ⚠️ UI 层直接做业务预编译，越层 | ✅ 最小改动 |
| 复杂度 | 中：改 2 个文件 | 中：改 1 个文件，但职责错位 | 低 |
| 维护成本 | 低：单一管道，未来新路径自动继承 | 高：预编译逻辑在 UI 层，工具层改动需同步 | 中：只堵当前漏洞 |
| 扩展性 | ✅ 强：复制/模板添加自动走管道 | ⚠️ 依赖集合事件时序 | ⚠️ 仅拖放生效 |
| 长期 ROI | 1 年 ✅ 3 年 ✅ | 6 月 ✅ 1 年 ⚠️ | 6 月 ✅ 1 年 ❌ |
| **否决项** | — | **UI 层做业务预编译（职责错位）** | **只堵当前入口，新入口仍会漏** |

**推荐方案 A**：建立单一受控管道。
1. `DragDropHandler` 强制走 `AddNodeToWorkflow`（`GetCachedViewModel` 返回 null 时**报错而非回退**，暴露根因）
2. `AddNodeToWorkflow` 内预编译作为**管道固有部分**（已是，保留）
3. 修复 `GetCachedViewModel` 的脆弱性（注入而非静态缓存）

## 六、修改清单

### 1. `DragDropHandler.cs` — 删除回退分支，强制统一管道

```csharp
// line 346-355 改为：
var viewModel = GetCachedViewModel()
    ?? throw new InvalidOperationException("ViewModel 未就绪，无法添加节点（应修复 GetCachedViewModel 而非回退裸操作集合）");
viewModel.AddNodeToWorkflow(newNode);
```

### 2. `DragDropHandler.cs` — 修复 `GetCachedViewModel` 脆弱性（line 73-89）

静态缓存改属性注入（类已有 `TabViewModel` 注入模式，`DragDropHandler.cs:51-55`）：
```csharp
// 移除静态缓存，改用构造函数/属性注入的 ViewModel
// （_tabViewModel 已存在，但类型是 WorkflowTabControlViewModel，需补 MainWindowViewModel 引用或经 TabViewModel 间接获取）
```
或者：保留静态缓存但**失败时抛异常而非返回 null**——让缓存问题显性化。

### 3. `MainWindowViewModel.cs` — 预编译收口确认

`PrecompileNodeIfNeeded`（line 2195）已在 `AddNodeToWorkflow` 内调用——**保留**，作为管道固有部分。无需改。

### 4. 防御：新增第三条路径时不会漏

`AddNodeToWorkflow` 是唯一管道——未来复制节点/模板添加必须调用它。可在 `WorkflowTabViewModel` 增加 `AddNode` 包装方法，强制所有调用方走命令。

## 八、防御机制（2 项）

| # | 防御机制 | 内容 |
|---|---------|------|
| 1 | **唯一管道强制** | `DragDropHandler` 无回退分支，`AddNodeToWorkflow` 失败即抛异常——新添加入口无法绕过 |
