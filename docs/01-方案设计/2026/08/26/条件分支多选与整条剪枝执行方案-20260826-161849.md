# 条件分支多选 + 整条剪枝执行 方案

> 类型：01-方案设计 | 日期：2026-08-26 | 状态：待实施 | 模块：T-CONDITION

## 一、问题（现状缺陷）

1. **未命中不剪枝**：条件分支未命中时，`NextNodeId=null` 被引擎当作"无信号"，后续节点全部照常执行（应该剪掉）。现象：不符合条件的分支只有第一个下游节点不执行，后续节点仍执行。
2. **单选限制**：多个规则命中时只走第一个（`ConditionTool.Run` 遇命中即 return），无法多分支并行。
3. **跳转模型错误**：现有 `forcedNextNodeId` 只对"下一组"过滤一次，会跳过目标的上游中间层（数据断链）、且后续组"复活"非目标分支。

## 二、核心机制：剪枝集合（Pruning）

**一句话**：拓扑分组照旧（谁先谁后不变），条件分支只负责"给不该跑的节点贴跳过标签"，执行时跳过贴标签的节点。

**唯一规则（图算法不动点）**：
> **一个节点被剪 ⟺ 它的所有前驱都被剪。**

条件分支评估完（一组内）后：
- **未命中** → 它的**全部直接下游**加入剪枝集合
- **命中 N 条** → 它的直接下游中**不属于任一命中分支**的节点加入剪枝集合

然后按"前驱全剪才剪"**迭代传播**（直到不再新增）。执行时：组内节点 `- 剪枝集合` = 实际执行；剪枝集合内的节点标记 `Skipped`。

**为什么能覆盖所有结构**：这是图论标准的"剪枝不动点"算法，对**任意 DAG**（汇合/不汇合/多层嵌套/多条件分支/并行线）都成立，不依赖具体拓扑形态。

## 三、场景执行逻辑（具体推演）

### 场景 1：同源多分支（不汇合）
```
[采集A] → [条件分支] → [分支A] → [结果1]
  │       → [分支B] → [结果2]
  └→ [阈值B] → [Blob] → [结果3]
```
| 情况 | 执行 |
|---|---|
| 命中分支A | 分支A→结果1 执行；分支B→结果2 剪；阈值B→Blob→结果3 照常（前驱=采集A，不剪）|
| 未命中 | 分支A、分支B 及各自下游剪；阈值B 线照常 |

### 场景 2：多源多分支（不汇合）
```
[采集A] → [条件分支] → [分支A] → [结果1]
[采集B] → [阈值B] → [Blob] → [结果2]
```
| 情况 | 执行 |
|---|---|
| 命中 | 条件分支下游按命中走；采集B 整条线照常（前驱与条件分支无关）|
| 未命中 | 只剪条件分支下游；采集B 线照常 |

### 场景 3：同源多分支 + 汇合点（有汇合）
```
[采集A] → [条件分支] → [分支A](剪) ──┐
  └→ [阈值B] → [Blob](不剪) ──────┴→ [汇合] → [结果]
```
| 情况 | 执行 |
|---|---|
| 分支A命中、阈值B线正常 | 分支A、Blob 都执行 → 汇合执行（前驱有 Blob 未剪）|
| 分支A未命中、阈值B线正常 | 分支A剪、Blob 执行 → 汇合执行（只要一条分支通）|
| 两线都剪（都过条件分支且都未命中）| 汇合剪（所有前驱都被剪）|

### 场景 4：多层嵌套条件分支
```
[采集A] → [条件分支1] → [分支A] → [条件分支2] → [分支A1] → [结果]
                      → [分支B] ─────────────────→ [结果2]
```
- 条件分支1 评估 → 决定剪分支B（或全剪）
- 若分支A执行 → 条件分支2 正常评估 → 再剪自己的非命中分支
- 外层剪了 → 内层整棵子树跟着剪（前驱全剪传播）；外层命中 → 内层独立评估

### 场景 5：多命中并行（核心新增）
```
[条件分支] 规则1命中→节点A；规则2命中→节点C；规则3未命中→节点B
```
- 节点A、节点C 的执行分支保留；节点B 分支剪
- 多个目标节点按其拓扑位置各自执行（同一组并行 / 不同组按序）
- 引擎不再"只取一个目标"，而是保留所有命中目标

## 四、代码改动清单

| 文件 | 改动 |
|---|---|
| `IControlFlowResult.cs` (SDK) | `NextNodeId`(单值) → `IReadOnlyList<string> NextNodeIds`；新增 `bool HasControlSignal` |
| `ConditionResults.cs` (工具) | `NextNodeIds` 多值集合；`HasControlSignal => true` |
| `ConditionTool.Run` (工具) | 不再遇命中即 return；遍历全部规则，收集所有命中的目标节点到 `NextNodeIds` |
| `WorkflowExecutionEngine.cs` (引擎) | 删除 `forcedNextNodeId` 跳转；新增剪枝集合 + "前驱全剪才剪"传播；每组执行前过滤剪枝节点并标记 Skipped |
| `WorkflowExecutionManager.cs` (UI) | 状态映射 `NextNodeIds.Count > 0 ? "OK" : "NG"` |

## 五、验收标准

1. 未命中：条件分支下游全 Skipped，独立流程线照常执行
2. 单命中：只走目标分支（原单选行为不回归）
3. 多命中：所有命中分支都执行，未命中分支剪
4. 汇合点：任一分支通即执行；全剪才剪
5. 多层嵌套：逐层独立评估剪枝，外层剪带动内层剪
6. 同源/多源多分支：只剪条件分支自己下游，其他线不受影响
7. 普通工作流（无条件分支）：完全不受影响（HasControlSignal=false）

## 六、关键设计决策记录

- 条件分支语义 = 路由选择（OR）：选中分支执行，未选中分支剪，全灭才终止该分支流程
- 汇合点 = 任意一条前驱分支通即执行（不是"所有前驱都执行"）
- 剪枝传播 = "前驱全剪才剪"（图不动点），自动覆盖汇合/不汇合/多层/多分支
- 分组仍用拓扑 BFS 分层（谁先谁后不变），条件分支不干预分组，只贴跳过标签
- 被跳过分支的数据缺失（后续节点需容错），是"剪枝"的必然结果
