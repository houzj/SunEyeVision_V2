# 方案报告：工具栏与交互状态机通用化重构（修正版 v2）

> 本方案遵循 rule-004（全局视角/复用优先/零兼容）与 rule-008（开发与代码纯净原则：YAGNI/KISS/报错优先）。
> 历史代码均已提交 git（用户确认可放手重构），回退无忧。
>
> **版本说明**：
> - v1（20260828-111543）：原方案 B——抽取 `InteractionHostBase` 统一交互状态机基类。
> - **v2（本版）**：实施中发现 v1 方案 B 存在"抽象泄漏"（见 §2.2），放弃统一交互状态机；
>   改为**通用工具栏薄壳 + 几何工具集复用 + 交互状态机各自保留**。

## 0. 用户功能性视角（必读）

### 改前：你看到的问题
- **形状工具栏**（区域编辑器用）与**测量工具栏**（边缘检测用）是两套几乎逐字重复的代码：控件 2 个、模型 2 个、XAML 2 份、宿主初始化代码 2 套。
- 工具栏只是"选择 UI"——**选中后由宿主交互状态机响应**，工具栏本身无业务逻辑。
- 想给未来任何新工具加"类型选择"，都得**复制-改名**一整套餐（模型 + 控件 + 宿主样板）。
- 修改一个交互行为（如选中高亮样式），要同时改多处。

### 改后：你将看到什么
- SDK 层只有一套 **`ToolBarControl` 通用工具栏薄壳**（类型无关）+ **`ToolItem` 通用模型**。
- 工具栏是**薄壳**：只做"展示 + 选中 + 通知"，**不承载任何交互能力**，可给任何宿主复用。
- 现有 `RoiEditorControl` / `MeasureEditorControl` 的交互状态机**各自保留**（历史良好，不动）。
- 现有 `ShapeToolItem` / `MeasureToolItem` 继承 `ToolItem`，`ShapeToolBar` / `MeasureToolBar` 降级为 `ToolBarControl` 薄封装（事件签名不变）。
- 共享的几何算法（命中测试/距离/角度）抽成 `GeometryToolkit`，两编辑器复用消除重复。
- 新工具加工具栏 = 提供 `ToolItem` 数据 + 在事件里写自己的交互逻辑，**零控件样板**。

### 关键认知（对话共识）
> **"工具栏 = 薄壳"**：只做展示 + 选中 + 通知，选中后由谁响应、怎么响应，工具栏一概不管。
> 因此它可以被区域编辑器、边缘检测、以及未来所有工具复用——每个宿主只提供自己的
> `ToolItem` 数据 + 在事件里写自己的交互逻辑。

### 依据（业界成熟做法）
| 决策 | 依据 | 引用 |
|------|------|------|
| 工具栏 = 命令容器 + ItemsSource 数据驱动 | WPF 官方 `ToolBar` 控件 | [Microsoft Learn - ToolBar](https://learn.microsoft.com/zh-cn/dotnet/desktop/wpf/controls/toolbar) |
| 同一基础系统构建、可独立定制工具栏 | Avalonia UI 工具栏 | [Avalonia Docs - Toolbar](https://docs.avaloniaui.net/controls/input/text-input/richtexteditor/toolbar) |
| 通用控件库、数据驱动模板、主题内建 | WPF UI (lepoco) | [github.com/lepoco/wpfui](https://github.com/lepoco/wpfui) |
| 工具条"形状行"与工具实现解耦 | 海康 VisionMaster | [VisionMaster 找圆工具-博客园](https://www.cnblogs.com/stevenchen2016/p/18259338) |

## 1. 问题分析（含来源标注）

### 1.1 重复点（代码核实）

| 层 | 重复内容 | 位置 A | 位置 B | 差异 |
|----|---------|--------|--------|------|
| **模型层** | `ShapeToolItem` vs `MeasureToolItem` 100% 同构（Name/ToolTip/IconGeometry/ShortcutKey/IsVisible/IsEnabled/IsSelected） | `[来源] Roi/Models/ShapeToolItem.cs:10-80` | `[来源] Measure/Models/MeasureToolItem.cs:27-100` | 仅业务枚举 |
| **控件层** | `ShapeToolBar` vs `MeasureToolBar` 逻辑逐行一致 | `[来源] Roi/Views/ShapeToolBar.xaml.cs:16-105` | `[来源] Measure/Views/MeasureToolBar.xaml.cs:16-103` | 无 |
| **XAML 模板** | ItemsControl 模板逐字一致 | `[来源] ShapeToolBar.xaml:1-63` | `[来源] MeasureToolBar.xaml:1-63` | 仅 Path 尺寸 18 vs 20 |
| **几何算法** | 手柄命中/点到线段/角度范围/点在四边形 | `[来源] Measure:386-408` | Roi 对应逻辑 | 算法同构 |

### 1.2 交互状态机：异构（不可统一抽取）

| 维度 | RoiEditorControl | MeasureEditorControl | 差异 |
|------|-----------------|---------------------|:---:|
| 事件路由 | `ProcessMouseMove(position)`，Manager 路由，内部逆变换坐标系 | `ImageMouseEventArgs.ImagePosition` 直接可用 | 🔴 数据结构不同 |
| 绘制模型 | 多边形逐点流式（双击完成）+ 橡皮筋；普通形状按下-拖动-松开 | 全部按下-拖动-松开三段式 | 🔴 交互范式不同 |
| 手柄编辑 | `dx/dy` 增量 + `_handleDragStartPoint` 基准 + region 数据模型 | `current` 绝对坐标直接写回 + `_model` 参数化 | 🔴 数据语义不同 |
| 状态 | 区域集合 + 坐标系矩阵 + 订阅模式 + 旋转 | 引导几何参数模型 + 卡尺带 | 🟠 差异大 |

**结论**：两个编辑器的交互骨架"看似同构，实则异构"，强行统一会抽象泄漏（§2.2）。

## 2. 方案演进（v1 → v2）

### 2.1 v1 方案 B：统一交互状态机（已放弃）
抽取 `InteractionHostBase` 统一基类，Roi/Measure 降级为策略子类。

### 2.2 v1 放弃原因：抽象泄漏（实施中发现）
按 P2 深入调研后确认：
1. 事件机制不同（Manager 路由 vs ImageMouseEventArgs）`[来源] Roi:804` vs `[来源] Measure:274`
2. 绘制范式不同（多边形流式 vs 三段式）`[来源] Roi:882-915` vs `[来源] Measure:627`
3. 手柄编辑数据语义不同（增量 vs 绝对坐标）`[来源] Roi:1372-1465` vs `[来源] Measure:567-618`

硬抽基类会：基类塞满 `if (editorType==...)` 抽象泄漏、子类实现大量空虚方法、耦合更难维护。**违背 YAGNI/KISS，属"打补丁"而非"治本"。**

### 2.3 v2 方案：通用工具栏薄壳 + 几何工具集复用

**复用单元分层**：

| 层 | 归属 | 复用方式 |
|----|------|---------|
| 选择 UI（工具栏） | 通用 `ToolBarControl` 薄壳 | ✅ 完全共享 |
| 几何算法 | 通用 `GeometryToolkit` 静态工具 | ✅ 完全共享 |
| 手柄渲染 | 已有 `HandleRenderer` | ✅ 已共享 |
| 交互状态机 | Roi / Measure **各自保留** | ❌ 不抽取 |

**"每个几何的交互自己管自己"**：交互状态机是各自编辑器的私有能力，不被抽成基类；但几何计算/命中测试这些纯算法抽成共享工具，让"自己管自己"不再复制代码。

## 3. Bug 模式分析

### 当前问题
两个编辑器"复制-改名"式重复开发工具栏与几何算法。

### 真因分类
**设计缺陷**（工具栏与几何算法属通用能力，却被复制成两份）。

### 同类潜伏点
| # | 位置 | 描述 | 优先级 |
|---|------|------|:---:|
| 1 | `ShapeToolItem` + `MeasureToolItem` | 双份同构模型 | P0 |
| 2 | `ShapeToolBar` + `MeasureToolBar` | 双份同构控件 | P0 |
| 3 | 几何算法（命中/距离/角度） | 双份同构算法 | P1 |
| 4 | 未来新工具工具栏 | 复制扩散风险 | P1 |

### 治本点
- 工具栏 → 通用薄壳（已做 P1）
- 几何算法 → `GeometryToolkit` 共享
- 交互状态机 → 各自保留（不强行统一）

## 4. 方案对比（3 候选）

| 维度 | 方案 A：通用控件+兼容层 | 方案 B：统一交互状态机（v1，已弃） | **方案 C：薄壳+工具集（v2，推荐）** |
|------|------------------------|-------------------------------|--------------------------------|
| 解决"工具栏不可复用" | ⚠️ 仅控件，交互仍各自 | ✅ | ✅ 薄壳 |
| 交互状态机复用 | ❌ 未解决 | ⚠️ 过度设计/抽象泄漏 | ❌ 不强行统一（正确） |
| 消除几何算法重复 | ❌ | ⚠️ 未明确 | ✅ `GeometryToolkit` |
| 新工具加工具栏成本 | 中 | 高 | 低 |
| 改动量 | 中 | 大（含失败风险） | 中 |
| 风险 | 低 | **高（抽象泄漏）** | 低 |
| 符合 YAGNI/KISS | ✅ | ❌ | ✅ |

### 推荐：方案 C（v2）
- **理由**：
  1. 治本：工具栏通用薄壳 + 几何算法共享，交互状态机各自保留（其本身差异大，强行统一是过度设计）。
  2. 工具栏薄壳类型无关（`SelectedValue` object? 承载业务枚举），任何宿主复用零改动。
  3. P1 已实施（ToolItem + ToolBarControl），方案 C 不推翻，直接延续。

- `ToolBarControlContractTests`：Toggle（点已选→取消/点未选→选中）、`SelectedValue` 双向同步、`IsVisible=false` 不参与。
- `GeometryToolkitContractTests`：手柄命中保底 24px、点到线段距离、角度范围（跨 0）、点在四边形。
- **验收**：unit test 全绿。

### 防御机制 #2：端到端冒烟（手动）
- 区域编辑器：6 形状选择/取消/绘制。
- 边缘检测：3 卡尺选择/取消/绘制引导几何。
- **验收**：两个宿主行为与重构前一致。

### 防御机制 #3：Fail-Forward
- `SelectedValue` 为 null（未选中）时宿主走"取消选中/选择模式"分支 `[来源] RoiEditorControl.xaml.cs:2731-2734`；未绑定 ImageControl 时安全跳过。

## 10. 风险评估

- **影响范围**：`RoiEditorControl`（区域编辑器）、`MeasureEditorControl`（边缘检测）两个宿主 + 工具栏相关。
- **回退策略**：历史已提交 git，每阶段独立提交，可随时回退。
- **兼容性**：P3 保留薄封装（事件签名 `ShapeType?`/`MeasureGeometryType?` 不变），宿主改动最小。
- **范围收敛**：交互状态机不抽取（差异大），避免过度设计。
