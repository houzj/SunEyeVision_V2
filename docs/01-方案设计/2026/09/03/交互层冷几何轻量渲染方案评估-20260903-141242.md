# 交互层冷几何轻量渲染方案评估

> 背景：讨论"结果层用几何图元、交互层用 Shape 对象"的架构差异后，确认交互层 Shape 树在元素量增大时同样存在性能风险（WPF UIElement 数量临界）。本文评估"交互层只读几何迁往轻量渲染（DrawingVisual/DrawingContext）、保留手柄热区"的影响范围与风险。

- 方案类型：显示层架构演进评估（01-方案设计）
- 日期：2026-09-03
- 状态：评估结论，待决策是否进入 Phase 1 详细设计

---

## 1. 背景与动机（用户视角大白话）

**改前**：交互层所有图形（测量带、方向三角、ROI 箭头）都是 WPF `Shape` 控件对象。几十个卡尺/ROI 叠加时，Canvas 上几百~上千个 UIElement，缩放/拖动会掉帧。

**为什么结果层不卡**：结果层用 DrawingContext 把几何合批一次画完（无对象树），量级无上限。结果层与交互层的差异不是"谁写错了"，而是"可交互需 UIElement"+"量大需批渲染"的取舍。

**本评估的目标**：是否值得、以及如何把交互层的"只读几何"（不参与拖拽的带、三角、箭头）也迁到轻量渲染，只保留手柄作为 UIElement 热区。

## 2. 核心认知（澄清误区）

1. **交互 ≠ 必须是 Shape/UIElement**。交互三要素（命中/反馈/状态）都不硬依赖 UIElement：
   - 命中 → 数学命中（点线距/点在多边形），本项目手柄命中本就是数学计算（`MeasureEditorControl.QueryCursor` → `ToReference` → 手算距离）
   - 反馈 → 重绘（DrawingContext 可重画）
   - 状态 → 操作数据模型 + 触发重绘
2. **WPF 性能临界**（业界经验）：<200 UIElement 无感；~500~1000 开始掉帧；>2000 明显卡顿。
3. **WPF 三种渲染层次**：
   | 方案 | 性能 | 命中 | 适用 |
   |---|---|---|---|
   | Shape 对象树 | 差（数千对象卡） | WPF 自带 | 少量可交互元素 |
   | DrawingVisual + `VisualTreeHelper.HitTest` | 好 | WPF 像素级命中，免费 | 大画布 + 精确点击 |
   | DrawingContext 批量 + 自建数学命中 | 最好 | 自写 | 海量只读 + 少量可点 |
4. **业界最终形态 = 冷热分层**：热区（手柄/选中框，十几个）用 UIElement；冷几何（带/三角/箭头/轮廓）用视觉层渲染。

## 3. 目标改动定义（建议分层）

| 层 | 内容 | 处置 |
|---|---|---|
| 热区（保留 UIElement） | ROI 缩放手柄、旋转手柄、Measure 编辑手柄 | 不动（`HandleRenderer`） |
| 冷几何（迁 DC） | 卡尺引导线/测量带/极性三角、ROI 方向箭头/连接线、屏蔽区轮廓 | 迁移候选 |

## 5. 关键机制约束（主要风险源）

**`Canvas.Children` 只接受 `UIElement`，DrawingVisual 不能直接挂**。需新增"视觉宿主"类（`FrameworkElement` 重写 `VisualChildrenCount/GetVisualChild` 承载 DrawingVisual）。这是新基建，也是最大复杂度点。`ResultRenderLayer`（FrameworkElement.OnRender + DrawingContext）已建立可参照的 DC 模式。

## 6. 风险矩阵

| # | 风险 | 等级 | 影响 | 缓解 |
|---|---|---|---|---|
| 1 | 新宿主引入布局/坐标/失帧回归 | 🔴 高 | 所有冷几何显示错位 | 宿主放同一 ImageContainer Grid 复用 ImageScaleTransform，坐标系零改动；先做 Measure 单层试点 |
| 2 | 命中测试语义变化 | 🟡 中 | 选中/拖拽失效 | 现有命中全是数学命中；事件仍在 MainCanvas 路由，不受影响 |
| 3 | ZIndex 分层破坏 | 🟡 中 | 手柄被几何盖住 | 宿主整体一个 ZIndex；手柄 `Canvas.SetZIndex` 置顶规则保留 |
| 4 | 屏蔽区增量优化丢失 | 🟡 中 | 频繁拖动时 ROI 全量重绘 | 此层最后迁；或实测 ROI 数量（<300 可不迁） |
| 5 | 虚线/透明/标签形态差异 | 🟢 低 | 视觉差异 | Pen.DashStyle / FormattedText 在 DC 均支持（ResultRenderLayer 已示范） |
| 6 | 全链路 UI 回归面大 | 🔴 高 | 卡尺/ROI 编辑全流程 | 分批迁移 + 每批独立手动验收清单 |
| 7 | 清理机制重写 | 🟢 低 | 残留元素 | 现有 Tag/List 清理改为"移除宿主+重画"，反而更简单 |
| 8 | 性能收益不明显时白改 | 🟡 中 | 当前交互层元素多在数百量级 | 先量化（单屏 ROI×卡尺元素数）再决定是否全迁 |

## 7. 建议的实施路径与回归范围

```
Phase 1（低风险试点）: MeasureBandOverlay 迁 DC
  → 回归：直线/圆/弧卡尺的绘制、拖拽、缩放幂律显示、极性三角
Phase 2: RotatedRectangleHelper（ROI 方向箭头）迁 DC
  → 回归：旋转矩形绘制/旋转/方向箭头显示
Phase 3（可选，高风险）: WpfShapeRenderer 屏蔽区迁 DC
  → 仅当 ROI 实际数量导致卡顿再做；回归面最大
```

- 自动验证：契约测试基本不受影响（纯 UI 层）；构建 slnx 0 错误
- 手动回归：每 Phase 一份验收清单
- 回退：每 Phase 单文件/单渲染器 revert，互不牵连

## 8. 与既有方案的关系

- `docs/01-方案设计/2026/09/03/双渲染层幂律缩放治理方案-20260903-132423.md`：已治理"公式唯一源"。本评估是下一个自然治理点——渲染机制可不同，但缩放语义与渲染性能应统一。
- 若 Phase 1 落地，`MeasureBandOverlay` 冷几何迁移后，其极性三角仍由交互层代码在创建时反除 zoom（屏幕恒定），与结果层装饰图元语义后续统一。

## 9. 结论

- 影响面收敛：核心是 4 个写入方 + 1 个新宿主基建；命中/事件/坐标系三块不需要动（最大降险因素）。
- 值得先做 **Phase 1**（MeasureBandOverlay 全量重建模式 + 无命中依赖 = 风险最低、收益直接），用真实卡尺编辑验证宿主机制后再决定 Phase 2/3。
- 若当前交互层实测元素量 <300，Phase 3 可永久缓置。
