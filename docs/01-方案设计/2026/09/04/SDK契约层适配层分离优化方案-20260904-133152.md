# SDK 契约层/适配层分离优化方案

> 日期：2026-09-04
> 类型：方案设计（架构重构/分层治理）
> 状态：待实施确认

## 0. 用户功能性视角（改前/改后）

**改前（架构的内在矛盾）**：`SunEyeVision.Plugin.SDK.csproj:21` 自称"零依赖的纯契约层"，但实际引用了 `halcondotnetxl.dll` + `OpenCvSharp4`，SDK 内 `VisionAdapters/`（HalImage/CvImage/HalRegion/CvRegion）、`ToolRegionHelper`、`SdkTypeVocabulary` 都直接依赖引擎类型。结果：**契约层名不副实、SDK 体积臃肿、引擎依赖不可选**——一个只想做纯数据序列化/绑定的宿主也被迫背上 OpenCV+Halcon 两套运行时。

**改后**：
- SDK 收敛为**真·纯契约层**：接口 + 纯数据模型 + 序列化 + 绑定 + UI 控件（零引擎依赖，可独立发布/测试）；
- Halcon 适配、OpenCV 适配迁到各自独立适配项目（`SunEyeVision.HalAdapter`、`SunEyeVision.CvEngine` 已在 src 下，正好复用）；
- 工具插件按需引用对应适配层，依赖方向 = `工具 → 适配层 → SDK 契约`，单向清晰。

## 1. 问题分析（现状分层画像）

### 1.1 SDK 内"契约 vs 适配"实际分布

| 子层 | 文件 | 引擎依赖 | 角色 |
|---|---|---|---|
| `Execution/Results`（AffineMatrix/ToolResults）| 20+ 文件 | **无** | 真契约：序列化/绑定/流通 |
| `Execution/Parameters`（参数/绑定）| 15+ 文件 | **无** | 真契约 |
| `Models/Geometry`（Circle2d/Arc2d/HalconArcAdapter）| 30 文件 | 适配器无调用但有转换语义 | 混合：纯数据 + Halcon 角度适配器 |
| `VisionAdapters/`（IVisionImage + HalImage/CvImage）| 16 文件 | **Halcon + OpenCV** | 接口与双实现混放 |
| `Execution/Helpers/ToolRegionHelper` | 1 文件 | **Halcon 算子**（AffineTransRegion 等）| 运行时算法辅助 |
| `Models/SdkTypeVocabulary` | 1 文件 | **OpenCvSharp（Mat 映射）** | 契约但渗入引擎类型 |
| `UI/`（117 文件）| 控件库 | **无**（已核实） | 纯 WPF 控件 |

### 1.2 依赖方向事实

- SDK 被 **23 个 csproj** 引用：12 个工具 + `Workflow/UI/Core/Infrastructure/CvEngine/CommonControl` + 2 测试；
- **11 个工具 csproj 直接引 `halcondotnetxl`**（非仅经 SDK）；
- 工具取 Halcon 图像走 **SDK 扩展** `HalconHelpers.GetHalconImage(this ToolParameters)`（`HalconHelpers.cs:11`），内部 `ResolvedInputImage`（IVisionImage 接口）→ `Unwrap()` 取 HImage | `ToolParameters.cs:108`；
- `src/SunEyeVision.CvEngine/`：已有独立 OpenCV 算子层，引用 SDK | `CvEngine.csproj:21`；
- `src/SunEyeVision.HalAdapter/`：**空壳**（仅 bin/obj，无源码）——本应承载 Halcon 适配，被放弃；
- `SdkTypeVocabulary.cs:34` 用 `typeof(Mat)` 映射 "Image" | 契约渗入引擎。

### 1.3 矛盾点

1. SDK 自称纯契约却引两套引擎（csproj Description vs Reference/Package）；
2. `HalImage` 等适配实现与 `IVisionImage` 接口同居 VisionAdapters（接口与实现未分离）；
3. tools 层已经直接引 halcondotnetxl（11 个工具），说明 tools 本就承担 Halcon 边界——适配层放 SDK 并非必需；
4. 空壳 HalAdapter 表明团队曾想做分层，中途放弃，历史包袱未清。

## 2. Bug 模式分析

**当前 bug**：契约层携带引擎依赖（架构腐化）。
**真因分类**：设计缺陷（分层边界未执行到 csproj 级）。
**同类潜伏点**：
- `SdkTypeVocabulary` 用 `typeof(Mat)`（`SdkTypeVocabulary.cs:34`）——契约层出现 OpenCV 类型；
- `HalconArcAdapter` 在 `Models/Geometry`（纯几何模型里混 Halcon 角度语义）| `HalconArcAdapter.cs:23`；
- `ToolRegionHelper` 在 `Execution/Helpers`（SDK 执行辅助调 Halcon 算子）| `ToolRegionHelper.cs:305`。
**治本点**：按"接口（契约）↔ 实现（适配）↔ 工具（消费）"三层重构，csproj 依赖单向化。

## 3. 业界对标

| 框架 | 做法 | 借鉴 |
|---|---|---|
| .NET 生态（EF Core/HttpClient 抽象）| 契约（接口/抽象）独立程序集，实现（SqlServer/Json）分插件包 | 契约零依赖、实现按需加载 |
| Roslyn/VS 插件体系 | SDK（抽象 API）与具体语言服务分离，适配在独立程序集 | 单一依赖方向 |
| VisionPro/Halcon .NET | 图像类型（CogImage8Grey/HImage）由厂商引擎提供，框架不复制引擎抽象 | 图像载体由引擎适配层提供，框架经接口消费 |

## 4. 方案对比

| 维度 | A：契约/适配彻底分离（推荐） | B：仅把 HalImage/ToolRegionHelper 迁出 | C：维持现状 |
|---|---|---|---|
| SDK | 纯契约（接口+模型+绑定+UI 控件）| 仍留 CvImage/OpenCV | 契约/适配混居 |
| 适配 | HalAdapter + CvEngine 两个独立项目 | 只迁 Halcon 侧 | - |
| 工具改动 | 每个 csproj 加 HalAdapter 引用 | 同左（较少）| 无 |
| 改动范围 | 大（csproj + 命名空间 + 注册）| 中 | 无 |
| 长期收益 | 高（可独立发布 SDK 包）| 中 | 低 |
| **决策** | **推荐**（治本）| 备选（分步）| 否决 |

## 5. 修改清单（分阶段）

### 阶段 1：契约收敛（SDK 瘦身到真·纯契约）
| 文件 | 变更 |
|---|---|
| `src/Plugin.SDK/SunEyeVision.Plugin.SDK.csproj` | 移除 halcondotnetxl Reference + OpenCvSharp PackageReference；仅保留接口所需 |
| `src/Plugin.SDK/Models/SdkTypeVocabulary.cs` | `typeof(Mat)→Image` 映射改为注册式（适配层向词汇表登记 `Mat` 类型），SDK 不含 `using OpenCvSharp` |
| `src/Plugin.SDK/VisionAdapters/IVisionImage.cs` 等接口 | 保留在 SDK（纯契约：定义 IVisionImage/IVisionRegion/IMonitorable）|

### 阶段 2：适配迁出（新/复用独立项目）
| 文件 | 变更 |
|---|---|
| `src/SunEyeVision.HalAdapter/`（空壳复活）| 迁入 `HalImage/HalRegion/HalconHelpers/DisplayCollectorHalconExtensions/ToolRegionHelper`（Halcon 侧全部）；csproj 引 SDK |
| `src/SunEyeVision.CvEngine/`（已存在）| 迁入 `CvImage/CvRegion/CvContour/CvToolHelpers`（OpenCV 侧）|
| 各处 `using SunEyeVision.Plugin.SDK.VisionAdapters` | 按类型分拆到对应适配项目命名空间 |

### 阶段 3：工具/主程序依赖调整
| 文件 | 变更 |
|---|---|
| 12 个工具 csproj | 已直接引 halcondotnetxl 的，改引 HalAdapter（或保留直接引，按工具是否纯 Halcon 判定）|
| `src/Workflow`、`src/UI`、`src/Core` | 补充对 HalAdapter/CvEngine 的项目引用（凡使用 HalImage/CvImage 处）|

### 阶段 4：注册/词汇表接缝
| 文件 | 变更 |
|---|---|
| 适配层启动代码 | 向 SdkTypeVocabulary 登记 `Mat→Image`、`HImage→Image` 类型映射（替代 SDK 内硬编码）|

## 6. 清理清单
- `src/Plugin.SDK/VisionAdapters/HalImage.cs` 等迁出后删除源文件；
- SDK csproj 移除引擎引用后同步删 `libs/halcon` 相关 HintPath；
- `SunEyeVision.HalAdapter` 空壳目录历史残留 bin/obj 清理。

## 7. 防御机制
- **契约层零引擎测试**：新增测试项目仅引用 SDK（不带 halcon/opencv dll），验证 AffineMatrix JSON 往返、SdkTypeVocabulary 字符串映射可独立运行；
- **词汇表注册契约测试**：适配层登记 `Mat→Image` 后，词汇表往返断言通过（D1 迁移测试）；
- **构建门禁**：SDK csproj 不含引擎引用 = 编译期强制契约纯净。

## 9. 风险评估
| 风险 | 等级 | 缓解 |
|---|---|---|
| 23 个 csproj 引用面，命名空间改动量大 | 高 | 分 4 阶段、每阶段构建验证；namespace 用 `global using` 平滑 |
| SdkTypeVocabulary 的 Mat 映射改动影响绑定树 | 中 | 注册式登记 + 契约测试锁定 |
| 工具 `GetHalconImage()` 扩展方法迁移导致大量调用点 | 高 | 保留扩展方法签名、仅移项目（调用点不改代码，只改 using/引用）|

## 10. 影响总览

**改动面**：csproj ~23 个、迁文件 ~20 个、命名空间/using 若干。
**核心算法逻辑不动**：`GetHalconImage`/`ToolRegionHelper` 等签名保留，仅换归属项目。

**后续联动**：
- 位置修正矩阵构造走 Halcon 原生链（`vector_angle_to_rigid`）应落在新 HalAdapter 或 tools 工厂（不污染 SDK 契约）；
- 修复 `BestPositionCorrection` 平移基准 `match − M·ref` 的问题与本次分层独立，可并行推进。

## 11. 移交

方案确认后移交「方案实施」技能分阶段执行：阶段 1（SDK 瘦身）→ 阶段 2（适配迁出）→ 阶段 3（依赖调整）→ 阶段 4（词汇注册），每阶段构建验证。
