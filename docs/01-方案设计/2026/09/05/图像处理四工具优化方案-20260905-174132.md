## 1. 改前 → 改后（用户功能性视角）

- **改前**：四工具各自在 Run 里手写同一段"取图→灰度→（开启区域限制时）取检测区/屏蔽区 + 位置修正 + BuildHalconROI + ReduceDomain→分步计时"前置管线，重复约 60 行 ×4；新增图像类工具时仍要再抄一遍。
- **改后**：这段前置管线收敛到 `SunEyeVision.HalAdapter` 的公共 helper（与 `ToolRegionHelper.BuildHalconROI` 同一层、同一风格）；四工具 Run 只保留"核心算子 + 结果计算"，前置调 helper。新增图像工具只写核心算子与结果模型。

> 行为零变化（重构不改变算子、参数、结果、UI）。

## 3. Bug 模式分析

**当前问题**：四工具 Run 前置模板重复。

**真因分类**：架构冗余（同一"取图→ROI/掩码→位置修正→ReduceDomain→计时"逻辑在 4 个文件重复）。

**同类潜伏点**：
- [来源] `tools/SunEyeVision.BlobAnalysis/BlobAnalysisTool.cs:121-176` — 同段管线（本方案不做，因 Blob 被定为标准，但 helper 设计对它是兼容的，未来可选接入）
- [来源] `tools/SunEyeVision.Tool.LineDetect|CircleDetect` Run 取图 + 位置修正段 — 领域更特殊（Metrology），不纳入本次

**治本点**：在 HalAdapter 提供 `HalconImageOpPipeline.Prepare`（取图→灰度→ROI/掩码+位置修正→ReduceDomain→计时一次性完成），四工具接入，消除模板复制。

## 5. 方案对比

| 维度 | A：抽 HalAdapter 公共 helper（推荐） | B：仅抽一个工具验证后其余复制 | C：抽 SDK 内 helper |
|---|---|---|---|
| 实现方式 | `HalconImageOpPipeline.Prepare(...)` 一次性收敛四工具前置管线 | 先改造 1 个再人工复制 | helper 放 Plugin.SDK |
| 与架构一致 | ✅ helper 与 BuildHalconROI 同层（HalAdapter） | ✅ | ❌ SDK 不引 Halcon（分层 V2 已明确） |
| 复杂度 | 中（helper ~70 行 + 4 工具接入） | 中低（逐工具） | 冲突（SDK 无 Halcon 引用） |
| 维护成本 | 长期低 | 长期重复 | — |
| 长期 ROI | 6 个月~3 年：高 | 短期高、长期低 | — |

**推荐 A**：HalAdapter 是四工具共用的适配层（均引 HalAdapter），helper 与 `ToolRegionHelper` 同源。

## 8. 防御机制

1. **契约测试**：helper 在各开关/ROI/Mask/位置修正/灰度场景下返回与现状一致（对比改动前单测快照）。
2. **端到端冒烟**：四工具 demo 图执行 → 结果图像与耗时正常、无 HRegion 泄漏（多次 Run 内存稳定）。
3. **Fail-Forward**：无输入图 helper 直接抛 `InvalidOperationException`（rule-015），Run catch 记 SetError。
