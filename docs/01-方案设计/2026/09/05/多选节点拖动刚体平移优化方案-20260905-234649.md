# 多选节点拖动"刚体平移"优化方案

> 日期：2026-09-05 23:46
> 状态：方案已确认（用户拍板方向），待实施
> 相关模块：src/UI/Features/WorkflowUI/Canvas、src/UI/Services/Connection

## 0. 改前 / 改后（用户视角·大白话）

**改前**：一次拖动多个节点，程序每秒几十次地做三件重复功：① 全画布翻一遍找"谁被选中"；② 把被选中节点**所有相连的线**（包括组内互相连的线）全部重算贝塞尔；③ 每条线重算还要对全部节点做一遍避障判断。节点越多、连线越密越卡。

**改后**：拖动 = **整组当作一张卡片平移**。
- 实时只做：挪 N 个节点的位置（成本与节点数成正比，但不再"翻全仓"）；
- 组内互相连的线**不用重算**——整组平移，它们形状没变，跟着整体平移即可（一次平移所有组内线，成本固定）；
- 只有**伸出去连到组外的"边界线"**需要实时重算——而这类线通常很少；
- 松手：边界线最后对齐一次，清空临时状态。

**效果**：拖动的性能消耗从"≈ 选中数 × 相关连线 × 全节点避障"降为"≈ 节点数 + 边界线数"。**拖几十个与拖几个的差别只在线性小头**，不再放大。

## 1. 问题分析（调研 + 来源）

### 1.1 现状三处浪费

### 1.2 关键架构事实（决定方案可行性）

- 节点位置 = 数据 + UI 绑定双通道：`Position` setter 写 `PositionX/Y` 并通知 [来源] `WorkflowNode.cs:200-212`；XAML `Canvas.Left = {Binding Position.X}` [来源] `WorkflowCanvasControl.xaml:206-207`。**连线路径完全依赖 `node.Position` 逻辑坐标** [来源] `ConnectionPathCache.cs:271-285`。
- 连线 UI 刷新：`connection.InvalidatePath()` → `PathUpdateCounter` PropertyChanged [来源] `Workflow/Workflow.cs:932-936` → `Path.Data` MultiBinding 重求值取缓存 [来源] `WorkflowCanvasControl.xaml:94-99, 138-143`。
- 已有未接线的刚体工具：`BatchMoveNodesCommand` 支持拖拽期抑制通知 [来源] `BatchMoveNodesCommand.cs:62-100`，但画布 MouseUp 注释明确"不再执行（防二次移动）" [来源] `WorkflowCanvasControl.xaml.cs:1689-1693`。

- 已有效果：连线有 5px 位置节流 [来源] `WorkflowCanvasControl.xaml.cs:155, 1940-1984` + 16ms DispatcherTimer 批量 [来源] `ConnectionBatchUpdateManager.cs:29`。

## 2. Bug 模式分析

**当前 bug（症状）**：多选拖动性能随节点/连线数线性放大。

**真因分类**：**设计缺陷**（把"刚性平移"当"逐件重算"处理）。

**同类潜伏点**：
- [来源] `WorkflowCanvasControl.xaml.cs:1659-1663`（MouseUp 又全量扫一次选中）
- [来源] `SelectionHandler.cs:152` / `NodeInteractionHandler.cs:354`（各 Handler 各自 `ClearAllSelections` 全遍历——选中维护入口分散，是"常驻选中集合"难以引入的结构原因）
- [来源] `ConnectionPathCache.cs:136-148` `MarkNodeDirty` 也是 O(连接数) 线性遍历

**治本点**：引入"**拖动组（drag group）快照 + 组内/跨组连接分类**"的概念，把一次拖动建模为一次刚体平移，而非"对每个零件单独处理"。

## 3. 业界对标

| 框架/平台 | 关键特征 | 引用 | 借鉴点 |
|---|---|---|---|
| WPF（Microsoft） | 高频视觉变换应用 `RenderTransform`（渲染阶段，不触发布局），而非每帧改布局坐标 | [WPF 中 RenderTransform 与 LayoutTransform 区别 - jishuzhan.net](https://jishuzhan.net/article/1823993899669000193)；[csdn #121650696](https://blog.csdn.net/technologyleader/article/details/121650696) | 高频拖动若需再提速，节点视觉移动走渲染变换层（本项目连线依赖 Position 逻辑坐标，故阶段 1 仍写 Position，阶段 2 再上 RenderTransform 快层） |
| mxGraph / diagrams.net | 正交边路由（orthogonal edge routing）由 `mxEdgeStyle` 按"源/目标顶点"驱动；顶点移动只对**受影响的边**做 routing 重算 | [mxEdgeStyle - jgraph.github.io](https://jgraph.github.io/mxgraph/docs/js-api/files/view/mxEdgeStyle-js.html) | "只算受影响边" = 本项目"只算跨组边界线"的同构做法 |
| Figma / Sketch（设计器） | 多选 = 场景图子树整体移动（父变换一次生效），子对象坐标不逐个更新 | 思想参照（业界节点编辑器共同认知） | 整组一次变换 = "组内线共享一个平移变换"的指导思想 |

## 4. 方案对比

| 维度 | A. 组快照 + 跨组线裁剪 + 组内线共享平移（推荐） | B. 纯渲染快层（RenderTransform 整组视觉移动，松手落账） | C. 维持现状只调节流参数 |
|---|---|---|---|
| 实现方式 | Down 锁组快照；实时 O(组节点) 写 Position；组内线几何共享一个 `TranslateTransform`（O(1)/帧）；跨组线走现有节流批量 | 拖动中节点容器/线全部挂 RenderTransform，Position 松手一次写 | 调大节流阈值/降帧 |
| 消除浪费 | 全扫①、组内重算②③、tick 线性查找 | ①②③ 全消 | 仅缓解 |
| 连线正确性 | 写 Position 保证锚点逻辑一致，安全 | 连线锚点依赖 Position → 需同步处理线，易断线 | — |
| 复杂度 | 中（画布状态 + Cache 一个 API） | 高（容器引用、虚拟化、坐标嵌套、端口命中） | 低 |
| 风险 | 低-中 | 高（多入口渲染、缩放嵌套、虚拟化不可见节点） | — |
| 长期 ROI | 高 | 高（但建议留作阶段 2，先测数据） | 低（治标） |

**否决**：C 只压频率不改模型（已被用户否掉）。B 正确但改动面大、依赖渲染细节多，且**当前无实测卡顿数据支撑**——先落 A（收益大、风险小），若实测百节点仍卡再评估 B。

**`Node_MouseLeftButtonDown`（L1604 附近）**：`RecordSelectedNodesPositions` 之后

- 预热+绑定：对 `_dragInner` 经 Cache 绑定共享 `_dragGroupTranslate = new TranslateTransform()`（见 5.2），确保缓存非脏

**`Node_MouseMove`（L1784-1877 改造）**

// ① 不再全量扫描：遍历 _dragGroup 快照

// ② 组内线：仅更新共享平移（O(1)，不 InvalidatePath 不重算）

- 清理全部临时状态（`_dragGroup`/`_dragBoundary`/`_dragInner`/translate/节流记录）

### 5.2 `ConnectionPathCache.cs`（新增 1 个方法，支撑组内线零重算平移）

```csharp
/// <summary>把一组组内连接当前缓存几何绑定到共享平移变换（拖动中只改 translate.X/Y）。
/// 仅对缓存干净（非 dirty）的连接生效；dirty 的先重算一次再绑定，保证基准正确。</summary>
public void AttachGroupTranslate(IEnumerable<WorkflowConnection> inner, TranslateTransform shared)
{
    lock (_lockObj)
    {
        foreach (var c in inner)
        {
            if (!_pathCache.TryGetValue(c.Id, out var cached))
                continue;                        // 未缓存 → 拖动中不会移动（保持原样，落账 ForceUpdate 补）
            if (_dirtyFlags.TryGetValue(c.Id, out var dirty) && dirty)
            { var p = CalculatePath(c); UpdateCache(c.Id, p); cached = _pathCache[c.Id]; }
            cached.Geometry.Transform = shared;  // Geometry 是 Freezable，Transform 变更会触发 Path 重绘
        }
    }
}
```

> 依据：缓存几何为 `PathGeometry`（未冻结）[来源] `ConnectionPathCache.cs:369-379, 417-423`；`Geometry.Transform` 变更触发 Freezable Changed → `Path.Data` 已引用该几何的 Path 自动重绘（无需 `InvalidatePath` 重算）。
> 刚体数学保证：组内线两端同步平移 → 正交路径形状不变（相对几何与外部环境均不变）→ 平移即精确解，等价于重算结果。

### 5.3 维持项（不做）

`ConnectionBatchUpdateManager`、`SelectionHandler`、`WorkflowNode`、XAML 均不改；`NodeDragHandler` 保持现状（未接线，不动）。

## 7. 防御机制

1. **几何平移基准防御**：`AttachGroupTranslate` 对 dirty/未缓存连接先重算或跳过，杜绝"平移叠加在过期几何上"造成的错位。
2. **端到端冒烟（手动验收全路径）**：拖 → 实时 → 松手 → 保存重开，五类场景覆盖（见验收表）。
3. **边界兜底**：`_dragGroup` 为空 / 全部节点选中（组=全画布，边界线=0）/ 无连线 / 仅组内线 / 仅跨组线，均不产生异常（遍历前判空、集合允许空）。
4. **回退**：改动收敛在拖拽状态机 + Cache 单方法内；异常时 Catch 复位 `_isDragging=false` 与临时字段（沿用现有 try 结构）。

## 8. 验收标准

| # | 验收项 | 方法 | 关联测试 | 对应防御 |
|---|---|---|---|---|
| 1 | 单节点拖动行为与现状一致（边界限制、5px 节流、连线跟随） | manual | 场景 A | 冒烟 |
| 2 | 多选 N 节点拖动：组整体平移、组内线随动不断裂、跨组线平滑跟随 | manual | 场景 B | 冒烟 |
| 3 | 全部节点选中拖动（边界线=0）：实时只 O(N) 位置 + 无连线重算，不卡 | manual | 场景 C | 冒烟 |
| 4 | 松手后保存→重开：所有节点位置与组内线形状正确（无 translate 残留/错位） | manual | 场景 D | 基准防御/冒烟 |

## 9. 测试方法

- **自动**：对 `ConnectionPathCache.AttachGroupTranslate` 的三种缓存状态做单元测试（需 Cache 构造不依赖 UI：其构造函数仅需节点集合+路径计算器 [来源] `ConnectionPathCache.cs:51-60`，可测）
- **手动冒烟**：宿主内按验收表五场景逐条执行，重点观测：拖 N=50/100 节点 + 密集连线的帧率；组内线拖动中是否平滑（16ms 内无断线感）
- **code review**：确认无新增全量扫描、无 `_dragInner` 误入 `ScheduleUpdateForNodes`、临时字段全部复位

## 10. 风险评估

| 风险 | 等级 | 缓解 |
|---|---|---|
| `Geometry.Transform` 共享引用被后续重算覆盖/残留 | 低 | 缓存替换时新几何无 Transform；重算以新 Position 为准，视觉一致 |
| 组内线在拖动中若被其它逻辑 Invalidate（如连接增删） | 低 | 重算覆盖 → 平移基准失效但结果正确（新几何无 Transform）；下次 Attach 重绑 |
| 阶段 1 保留逐帧写 Position：M 极大（数百节点）时位置层仍是 O(M) | 中 | 本方案目标量级（几十~上百）已达标；如实测仍卡，启用阶段 2（RenderTransform 快层 + 落账） |
| 改动跨画布状态机 + 缓存，回归面 | 中 | 验收 1/2 先跑通再扩展；可随时按 5.1 单点回退 |

## 11. 推荐理由

推荐 **方案 A**：依据 — ① 消除的三处浪费有代码实证（§1.1）；② 与现有"批量延迟 + 节流"架构复用而不推翻 [来源] `ConnectionBatchUpdateManager.cs`；③ 组内线共享平移利用了 WPF Freezable/Geometry.Transform 机制与 mxGraph"只算受影响边"同构（§3）；④ 风险低、改动集中在拖拽状态机 + Cache 一个方法；⑤ 保留 Position 作为单一真相源，避免引入渲染层多源不一致（rule-004 分层一致性）。
