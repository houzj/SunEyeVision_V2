## 一、改前 / 改后 / 依据（说人话）

### 改前（现状）

1. **"并行"名不符实**：执行引擎里名为 `ExecuteNodesInParallel` 的方法实际上**逐个顺序执行**；所谓的"异步入口"只是把整个执行丢到线程池跑，并非真正异步调度。
2. **提速只能靠单节点优化**：并行组只能用于拓扑分层，组内节点始终串行。
3. **全局变量有两套容器**（`Variables` 与 `GlobalVariables`），职责边界不清，谁在什么时机写、并行下是否安全，没有约定。

### 改后（目标）

1. **执行入口真异步**：调度基于 Task 的异步管线（而非 `Task.Run` 包裹整个同步流程）
2. **组内真并行（可选、可配）**：对**确认无相互依赖**的节点并行执行；并行度默认 1（行为与现状完全一致），需要提速时再调高
3. **全局变量语义收敛**：明确"全局变量 = 执行期只读输入"，节点中间值统一走节点结果容器（按节点 ID 天然隔离）；若确需运行期写，走显式 API + 线程安全容器 + 变更通知

### 依据（可追溯）

| 结论 | 依据 |
|---|---|
| DAG 编排中"无依赖子集并行 + 依赖序串行"是标准做法 | Apache Airflow 并行调度 — https://airflow.apache.org/docs/apache-airflow/stable/core-concepts/dags.html |
| 并发容器替代普通 Dictionary 是并行化前置 | .NET `System.Collections.Concurrent` 官方文档 — https://learn.microsoft.com/dotnet/api/system.collections.concurrent |
| 数据流变量按"生产者-消费者"隔离，共享可变状态需显式保护 | LabVIEW 数据流编程模型 — https://docs-be.ni.com/bundle/labview/page/dataflow-programming.html |
| 任务失败与并行度解耦（并行不改变失败语义） | Nextflow `errorStrategy` — https://nextflow-io.github.io/patterns/ignore-failing-process/ |

## 三、Bug 模式分析

- **真因分类**
  - 伪并行 = **实现偏差**（方法命名与实现不符，掩盖了"组内串行"的事实）
  - 并发风险 = **设计缺陷**（SSOT 容器早于并行需求设计，非线程安全；一旦并行即集中暴露）
  - 全局变量 = **架构冗余**（两套容器语义重叠，职责边界未定义）
- **同类潜伏点**
  - 任何以"节点级共享容器"为写入目标的位置都会在并行后失效：`_executionResults` / `NodeStates` / `Logs` / 引擎共享字段
  - "名实不符"的命名会持续误导后续优化（`ExecuteNodesInParallel`）
- **治本点**
  1. **先解除并发障碍**（容器 + 共享状态），再谈提速
  2. **并行度显式可配，默认 1**（默认行为不变，可渐进开启）
  3. **全局变量语义收敛为执行期只读**，写入走独立通道

## 五、方案对比

### 5.1 执行模型

| 维度 | **A. 真异步管线 + 并行度可配（推荐）** | B. 维持现状（伪异步、组内串行） | C. 全量并行（不设并行度） |
|---|---|---|---|
| 实现 | `async` 化执行管线；组内无依赖子集用 `Parallel.ForEachAsync`/`Task.WhenAll`；并行度配置默认 1 | 仅重命名/注释纠偏 | 全部组内节点并发 |
| 架构一致性 | ✅ 复用现有拓扑分层与依赖排序 | ✅ 零风险 | ❌ 与参数绑定解析顺序冲突 |
| 复杂度 | 中（容器改造 + 调度改造） | 低 | 高（需大量同步原语） |
| 维护成本 | 中 | 低 | 高 |
| 扩展性 | 高（后续可做帧级流水） | 无 | 中 |
| 长期 ROI | 高（吞吐 + 架构正确性） | 低 | 负（并发缺陷集中爆发） |

**推荐 A**：先解除并发障碍、默认并行度 1（行为不变），再按需开启。

### 5.2 全局变量

| 维度 | **A. 收敛为"执行期只读输入"（推荐）** | B. 保持两套容器 | C. 全局变量运行期可写 |

| 架构一致性 | ✅ 与"节点结果按 nodeId 隔离"一致 | ⚠️ 职责模糊 | ⚠️ 需新增语义 |
| 复杂度 | 低 | 零 | 高 |
| 并行安全性 | ✅ 天然安全 | ⚠️ 需逐处排查 | 需严格同步 |
| 长期 ROI | 高 | 低 | 中（视需求） |

**推荐 A**；若确有运行期写全局变量的业务需求，再单独立案 C。

## 八、防御机制

1. **契约测试**：并行度 = 1 时，节点执行顺序与结果与现状**逐条一致**（回归保护）
2. **并发压力冒烟**：并行度 > 1 时，多分支流程重复执行 N 次无死锁/无结果错乱
3. **Fail-Forward**：并行子集内任一节点失败，不阻断其他子集（依赖前述"执行中断隔离"先行落地）
4. **配置护栏**：并行度非法值（≤0）直接报错，不静默回退

## 十一、风险评估与回退

| 风险 | 缓解 | 回退 |
|---|---|---|
| 并行引入数据竞争（HObject 生命周期、工具静态状态） | 并行度默认 1；逐工具核查静态状态；压力冒烟 | 并行度置 1 |
