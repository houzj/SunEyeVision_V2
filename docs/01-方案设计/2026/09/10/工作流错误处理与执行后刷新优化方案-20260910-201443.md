## 一、改前 / 改后 / 依据（说人话）

### 改前（现状）

| 场景 | 现象 |
|---|---|
| 某节点参数报错 | 整条流程**立刻停止**，后面的节点一个都不跑；打开调试窗口发现上游没执行、没有输入图、无法配置 |
| 选中节点 | 图像区**黑屏**，即使上游明明有图像输出 |

### 改后（目标）

| 场景 | 现象 |
|---|---|
| 某节点参数报错 | 报错只影响**它自己和它下游**（下游标"跳过"），其他分支/后续节点照常跑完；跑过的节点都有结果 → 调试可用 |
| 选中节点 | 从下拉（本节点 + 上游图像输出）中按顺序找**真有图**的源显示（优先你选的那个，**下拉同步跟随**）；下拉没有本节点项时自然用上游图；整链都没图才黑屏 |

### 三条已确认规则

1. **有图像输出的节点 → 只要输入图没问题，显示就没问题**
2. **输入图像有问题 → 显示空**（如实反映，不掩饰、不造假图）
3. **节点没有图像输出 → 下拉不会有本节点项** → 回退显示上游图，天然成立

### 依据（可追溯）

| 结论 | 依据 |
|---|---|
| 上游失败 → 下游跳过，无关任务继续 | Nextflow `errorStrategy = 'ignore'` — https://nextflow-io.github.io/patterns/ignore-failing-process/ |
| 上游失败不必然阻断下游（触发规则化） | Apache Airflow `trigger_rule`（`all_success`/`all_done`/`none_failed`）— https://www.astronomer.io/docs/learn/airflow-trigger-rules/ |
| 错误随数据流传播：下游不再执行，无关分支继续 | LabVIEW error cluster — https://docs-be.ni.com/bundle/labview/page/using-error-clusters.html |
| 失败后继续执行不相关作业 | Snakemake `--keep-going` — https://snakemake.readthedocs.io/en/stable/executing/cli.html |

## 三、Bug 模式分析

- **真因分类**
  - 问题二 = **设计缺陷**（把"节点失败"等同于"流程失败"，缺少"失败传播"与"失败隔离"的区分）
  - 问题一 = **实现偏差 + 架构冗余**（取图逻辑双份实现，且都缺少"可用性判定"）
- **同类潜伏点**
  - 组内 `break`（`:362`）与组间 `return`（`:193`）是同一模式的两处，**必须同改**
  - "无结果就清空"共 4 处：`MainWindowViewModel.cs:3317/3330` + `NodeResultManager.cs:143/149` → 双份实现是复发温床
  - `NodeResultManager.cs:198-229` 空壳方法 与 `WorkflowContext.cs:494-523` `CreateSubContext`（**全库无调用点**）= 同类"写了没接上"
- **治本点**
  1. 在**引擎**建立失败隔离语义（失败节点 → 自身 Failed；下游 → Skipped；无依赖分支 → 继续），不在 UI 层兜
  2. 在 **ViewModel** 建立**唯一**的"解析生效显示源"入口，`NodeResultManager` 调用它（消除双份）
  3. 删除死代码，而不是保留

## 五、方案对比

### 问题二（错误传播）

| 维度 | **A. 失败隔离 + 下游跳过（推荐）** | B. 全部继续（不判前驱） | C. 可配 trigger_rule |
|---|---|---|---|
| 实现方式 | 失败节点 Failed；下游 Skipped；无依赖分支继续 | 只删 `return`/`break` | 每节点可配 all_success/all_done |
| 架构一致性 | ✅ 复用现有 `NodeStatus.Skipped` + 剪枝语义 | ⚠️ 下游带空输入跑出级联假错误 | ❌ 模型/UI/序列化都要动 |
| 复杂度 | 引擎 2 处 + 1 个判定函数 | 极小 | 大 |
| 维护成本 | 低 | 中（错误日志噪音） | 高 |
| 长期 ROI | 高（错误语义清晰、可产品化） | 低 | 低（YAGNI） |

**推荐 A**，依据：Nextflow `ignore` 语义 + LabVIEW error 传播；B 违背 rule-015（应明确报错而非产出假错误）；C 违背 YAGNI。

### 问题一（显示源）

| 维度 | **A. 按序取第一个可用源 + 下拉跟随（推荐）** | B. 保留选中项不变 + 角标 | C. 回退链/取帧 |
|---|---|---|---|
| 与现有机制一致 | ✅ 下拉本就是"有图像输出的源"清单 | ⚠️ 下拉与实际显示不一致 | ❌ 新增机制，掩饰真实缺失 |
| 复杂度 | ViewModel 1 个入口方法 | 1 个方法 + UI 角标 | 高（执行链 + SSOT） |
| 用户可理解 | ✅ 下拉即真相 | ❌ 需角标解释 | ❌ 语义混乱 |
| 长期 ROI | 高 | 中 | 负 |

**推荐 A**（用户已确认：不要角标；下拉为真相）。

## 八、防御机制

1. **契约测试**：构造 `A(失败) → B(依赖 A) → C(独立)`，断言 B 状态 = `Skipped`、C 状态 = `Completed`、`result.NodeResults` 同时含 A 与 C、执行未提前结束
2. **端到端冒烟**：图像链正常 + 中间一个节点参数非法 → 断言后续独立节点有结果、选中无输出节点显示上游图、调试窗口能拿到上游输入
3. **Fail-Forward 呈现**：`TryResolveDisplaySource` 全失败时 `DisplayImage = null` + 日志（不静默、不造假图）
4. **兜底稳健**：`GetNodeStatus` 对未记录节点返回 `Pending`（不抛异常）

## 十二、明确不做（含论证）

1. **不做"取帧 / 执行上游"**：图的问题应当明确报错或如实显示空，用取帧掩饰会把"上游未执行"变成隐形状态（用户已否决）
2. **不做"主图回退链 / 保留上一帧"**：数据源列表本就含上游图，只需"按可用性择源"，无需虚构回退层级（用户已否决）
3. **不加角标提示**：下拉选中项即为显示源的表示，保持一致即可（用户已否决角标）
4. **不引入"依赖图"**：入度分层（Kahn）已是拓扑排序；绑定源被限定为连接上游，依赖已被拓扑覆盖
5. **不做节点级并行**：本轮范围外，单独立案（见《工作流真异步与全局变量方案》）
