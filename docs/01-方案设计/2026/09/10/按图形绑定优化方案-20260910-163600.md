# 「按图形」绑定优化方案

> 版本：v3（新增阶段 **P0.5「绑定显示名 SSOT 重构」**）
> 原则：从设计端解决根因，再解决具体问题；不背技术债，不将就。

## 1. 改前 vs 改后（用户视角）

| | 改前（今天） | 改后 |
|---|---|---|
| 打开点-圆「按图形」 | 看到"整体/点/直线/圆/矩形…"全是检测框，**没有真正的点** | 直接出现上游算出的**圆心、交点、点1、卡尺检测点** |
| 选了某个形状 | 显示"已绑定"，**实际没生效**，点一直是 (0,0) | 能用的才出现；真转不动的红字报错 |
| 上游圆心传给下游 | 只有"圆心X""圆心Y"两个数字，得绑两次 | 圆心作为**完整点**出现，一次绑定 |
| 绑 20 个卡尺点 | **悄悄失败** | 来多少算多少，出 20 个测量结果 |
| ROI 编辑器选图形 | 一筐异构图形全列出，自己猜 | **ComboBox 先选类型**（圆/矩形/点…），只给该类型 |
| **同一个源在两种界面显示** | `圆查找1.Center.X`（英文、无 `[]`）**vs** `Blob分析1.中心X[]`（中文、带 `[]`）—— 同一件事两种说法 | **完全一致**：`圆查找1.圆心.X[]` / `圆查找1.中心X[]`，中文 + 数组语义带 `[]` |
| 重开工程后显示名 | 依赖**解析显示字符串**还原（`Split('.')`），格式一变就错位 | 显示名是**只读投影**，由绑定路径重新推导 |

## 2. 依据（可追溯）

- **Halcon tuple 语义**：结果以数组传递，单值 = 长度 1 数组；两数组运算按"等长逐元素 / 长度 1 广播 / 其余报错"规则（本地 `doc_en_US/html`）
- **Halcon iconic-control 分离**：图形（区域/XLD）与数值分属两条流，跨流走显式提取算子（`area_center` 等），图形不能直接当坐标用
- **分层原则**：UI 交互类型不得进入数据契约层（本项目 P0 要重建的约束）
- **本项目决策**（`docs/01-方案设计/2026/07/输出变量契约统一重构方案-20260716.md`）：数组语义、单值 = 长度 1 数组
- **单一真相源（SSOT）原则**：同一份信息只允许有一个生产者；呈现层只做**只读投影**，不得反向成为数据来源
- **VisionMaster**：检测区与结果数据分离，批量测量逐项判定

## 3. 根因（已查证）

### 3.1 表层根因（三层）

1. **上游没"点"**：几何点（圆心/交点/最近点/点1/点2）都是 WPF `Point`，不入词表，被拆成 X、Y 两个 double。全项目单点 `Point2d` 输出 **0 个**
2. **下游口子错位**：点参数要坐标，却被当"几何图形目标"放行了图形容器，把"整体/圆/直线/矩形"全塞进候选
3. **中间缺工序**：从图形容器只能拿到"图形对象"或单个数字，**拿不到整个几何值**（`Circle2d[]`/`Point2d[]`）

### 3.2 设计端根因之一、之二（数据契约层）

> 上述三层都是**症状**。真正的根因在数据契约层的设计错误。

**事实 1：`Point2D` 的设计目的是正确的，不是技术债**

```9:14:src/Plugin.SDK/Execution/Parameters/Point2D.cs
    /// 点结构（可观察，UI 交互/绘制用）。
    /// 注：与 SDK 纯值点 Point2d（readonly struct，算法/契约用）并存，
    /// 本类用于可交互场景（多边形顶点、几何扁平编辑桥、命中坐标）。
    public class Point2D : INotifyPropertyChanged, IMonitorable
```

`Point2D`（class + 属性通知）服务 **UI 交互层**，`Point2d`（readonly struct）服务 **契约/算法层**——这是有意的分层，设计正确。

**事实 2：真正的设计错误——UI/WPF 类型被用作数据契约的几何载体**

`RoiShape.Geometry`（会序列化进工程文件）却使用 UI/WPF 类型承载图形：

| ShapeType | Geometry 实际类型 | 性质 |
|---|---|---|
| Point | `Point2D`（UI 交互类型） | ❌ UI 类型进数据层 |
| Rectangle | `System.Windows.Rect`（WPF 类型） | ❌ WPF 类型进数据层 |
| Line / Circle / RotatedRect / Polygon / Annulus / Arc | `Line2d` / `Circle2d` / `RotatedRect2d` / `Polygon2d` / `Annulus2d` / `Arc2d` | ✅ 契约类型 |

**事实 3：错误被序列化白名单固化**

```28:29:src/Plugin.SDK/Execution/Parameters/GeometryJsonConverter.cs
        ["Point2D"]       = typeof(Point2D),
        ["Rect"]          = typeof(System.Windows.Rect),
```

即早期用现成 UI/WPF 类型顶替契约几何类型，后来契约类型（`Point2d`/`RotatedRect2d`）有了却未迁移，反而把 UI 类型注册进白名单，使其成为"既成事实"。

**事实 4：错误已扩散 34 处，跨 4 层**

| 层 | 文件 | 情况 |
|---|---|---|
| SDK 核心 | `RoiShape.cs` | 26 处（GetCenter/SetCenter/ToString/Clone/扁平属性/默认几何工厂） |
| UI 编辑器 | `RoiEditorControl.xaml.cs`、`EditHistory.cs` | ~12 处 |
| 算法适配器 | `HalAdapter/RegionConverter.cs`、`ToolRegionHelper.cs` | `Rect → GenRectangle1` 分支 |
| 算法适配器 | `CvAdapter/CvRegionBridge.cs` | `Rect` 分支 |
| 其他 | `PositionCorrectionResolver`、`RoiGeometryTransformer`、`SubroutineTool`、`ScriptVariableTab` | 若干 |

WPF `Rect` 已泄漏到 Halcon / OpenCV 适配器——数据层用 WPF 类型，算法适配器被迫认识 WPF 类型，分层被破坏。

**结论**：契约域（词表 `Point` = `Point2d[]`）与数据域（Geometry = `Point2D`）永远对不上，绑定层被迫做类型转换。**根在设计端，不在绑定层。因此必须先做 P0 设计端修复。**

### 3.3 设计端根因之三：绑定显示名没有单一真相源（SSOT）

**触发事实（用户实测）**：同一个"几何输出字段"的绑定，在两个界面显示不同——

| 界面 | 控件 | 显示 | 走的分支 |
|---|---|---|---|
| 点-圆调试窗「X 坐标」 | `ConfigSetting` | `圆查找1.Center.X`（**英文、无 `[]`**） | `GetDisplayLeafName` 分支② |
| ROI 订阅面板「几何参数」 | `ParamBinding` | `Blob分析1.中心X[]`（**中文、带 `[]`**） | 分支① |

**事实 1：显示文本有 6 个生产者**（同一份信息多处生产）

| # | 生产者 | 位置 |
|---|---|---|
| 1 | `AvailableDataSource.DropdownDisplayText` | `AvailableDataSource.cs:163-172` |
| 2 | `AvailableDataSource.GetDisplayText()` | `AvailableDataSource.cs:233-239` |
| 3 | `ImageSourceReference.DropdownDisplayText`（**连 `[]` 规则都不同**） | `ImageSourceReference.cs:88` |
| 4 | `ParamBinding.GetDisplayLeafName` / `GenerateBindingDisplayText` | `ParamBinding.cs:844-918` |
| 5 | ViewModel/模型缓存的 `*BindingDisplayText`（位置修正、文本样式、子程序、脚本、循环等 **20+ 处**） | `RoiParameters.cs:254`、`TextStyle.cs:78/96`、`Subroutine*Config.cs`、`Script*Config.cs` 等 |
| 6 | 持久化字段 `ParamSetting.SourceNodeName/SourceDisplayName` | `ParamSetting.cs:85/94/224-253` |

**事实 2：显示名被当成"控件状态"，而不是"数据源的只读投影"**

`ParamBinding.BindingDisplayText` 是**可写 `TwoWay` 依赖属性**，`ConfigSetting` 再**转发 + 缓存**：

```951:957:src/Plugin.SDK/UI/Controls/ConfigSetting.cs
                _paramBinding.BindingSourceSelected += (s, e) =>
                {
                    // 【顺序关键】先设置显示文本，再设置绑定源。
                    // 因为设置 BindingSource 会触发 OnBindingSourceChanged → SyncBindingConfigToParamValue
                    // → BindingConfigChanged，保存到 TextStyle 时需要 BindingDisplayText 已经就位。
                    BindingDisplayText = _paramBinding.BindingDisplayText;
                    BindingSource = _paramBinding.BindingSource;
```

**一旦显示名可被三方写入、可缓存、可持久化，它就不再是推导结果，而是"第二份数据"**——两份数据必然漂移。XAML 里 `Mode=TwoWay` 共 **20+ 处**（12 个工具调试窗 + 子程序 8 处 + 脚本等）。

**事实 3：显示文本同时被当成"数据格式"（隐蔽且致命）**

持久化不是从模型取字段，而是**把显示文本按 `.` 拆开反解**：

| 位置 | 代码行为 |
|---|---|
| `ConfigSetting.cs:1176-1181`、`1297-1302` | `BindingDisplayText.Split('.')` → `SourceNodeName` / `SourceDisplayName` |
| `TextStyle.cs:104-157`、`175-198` | 同上（`PositionX/YBindingDisplayText`） |
| `SubroutineTool.cs:282-284` | `input.BindingDisplayText?.Split('.')` |

**这意味着：显示格式 = 持久化格式。** 一旦显示名改成中文（或含更多 `.`），持久化立刻错位、老工程显示错乱。**这是"显示名 SSOT 重构"必须先解决的前置耦合。**

**事实 4：显示规则按"路径字符串形态"分支，而不是按语义分支**

```902:918:src/Plugin.SDK/UI/Controls/ParamBinding.cs
        private static string GetDisplayLeafName(TreeNodeData node)
        {
            var ds = node.DataSource;
            if (ds == null)
                return node.Text;
            if (ds.BindingSuffix != null)
            {
                // P2：RoI 类型分组（[Type=Circle]）显示名统一为"短名[]"（圆[]），与普通数组"宽度[]"同风格。
                if (ds.BindingSuffix.StartsWith("[Type=", StringComparison.OrdinalIgnoreCase))
                    return $"{node.Text}[]";
                return $"{ds.PropertyName}{TranslateBindingSuffix(ds.BindingSuffix)}";
            }
            if (ds.PropertyType?.IsArray == true)
                return $"{ds.DisplayName}[]";
            return node.Text;
        }
```

判断的是 `BindingSuffix` 的**字符串前缀**（实现细节），不是语义。后果：
- 分支① → 强制 `[]`、用中文 `node.Text`
- 分支② → 不加 `[]`、用**英文 `PropertyName`**，而 `node.Text` / `ds.DisplayName`（中文"圆心X"）就在手上却被忽略

**结论**：显示名应当由**数据源模型声明**（中文叶子名 + 数组语义标记），全项目**只有一个格式化入口**，控件只**渲染**。`BindingSuffix` 的职责只是**运行期解析路径**，不得参与显示。

## 4. 设计决策（已拍板）

| # | 决策 |
|---|---|
| 1 | **异构不处理**，需要多种图形就拆成多个节点，一个节点绑一种图形 |
| 2 | **移除"整体"**入口，一律按 `[类型]` 取同类图形 |
| 3 | **DataType 分层**：点-圆等明确要点的 → **固定 `Point2d`** 不加 ComboBox；**ROI 编辑器** → 加 ComboBox 动态选类型 |
| 4 | **点参数为数组口子**：`P1Point` → `ParamValue<Point2d[]>`，**来多少算多少，不报错** |
| 5 | **数组语义贯穿**：单值 = 长度 1 数组，全程对齐 Halcon tuple |
| 6 | **设计端优先**：先修 `RoiShape.Geometry` 类型契约（P0）、显示名 SSOT（P0.5），再做绑定层优化 |
| 7 | **分层原则重建**：`RoiShape.Geometry` 只允许 `Models.Geometry.*` 契约类型；UI 类型（`Point2D`、WPF `Rect`/`Point`）只许待在 UI 交互层 |
| 8 | **显示名 SSOT**：显示名由数据源模型声明（`LeafDisplayName` + `IsArraySemantics`），**唯一格式化入口**；控件只渲染，不生产、不缓存、不回写 |
| 9 | **`[]` 按语义统一**：数组语义即带 `[]`，**不按控件分叉**（不做 `ShowArrayMarker` 开关）；**显示文本与持久化彻底解耦** |

## 6. 向量化计算规则（新增核心契约）

点/线/圆元素都可能是 N 个，两元素运算对齐 **Halcon tuple 广播规则**：

| 元素1 长度 | 元素2 长度 | 行为 |
|---|---|---|
| N | N | 逐对计算 → **N 个结果** |
| 1 | N | 广播 → **N 个结果** |
| N | 1 | 广播 → **N 个结果** |
| N | M（N≠M 且都≠1） | **报错**"长度不匹配（N vs M）" |

**判定规则**（推荐默认，待确认）：每个结果单独判定，**整体 OK = 全部合格**；`JudgmentDetails` 逐个列出明细。

**输出契约**：测量结果为数组（如 `DistanceToCenter` → `double[]`），下游按数组绑定（词目 Double，一致）。

## 7. 验收标准

### P0 专项（数据契约类型）

1. `RoiShape.Geometry` 承载点图形时类型为 `Point2d`；承载矩形时为 `RotatedRect2d`
2. 新建工程保存 → 重开，图形类型正确还原（`$geom` 为 `Point2d` / `RotatedRect2d`）
3. **老工程（含旧 `Point2D`/`Rect` 图形）能正常打开**，且读入后已转为新类型
4. Hal / Cv 适配器对矩形区域的处理结果不变（回归验证）
5. `Point2D` 在代码中仅出现于 UI 交互场景（多边形顶点编辑桥等），不再作为 `Geometry` 值

### P0.5 专项（显示名 SSOT）

6. **同一绑定源在两个界面显示完全一致**：点-圆「X 坐标」绑 `圆查找1` 的圆心字段 → 与 ROI 面板同源绑定显示同为中文 + 语义一致（`圆查找1.圆心.X[]`）
7. **不再出现英文路径**：绑定下拉/显示位不出现 `Center.X` 这类 CLR 路径
8. **`[]` 按语义统一**：数组语义带 `[]`，标量语义不带；两个控件（`ParamBinding` / `ConfigSetting`）规则一致
9. **持久化与显示解耦**：把显示名改成任意文本（如手输乱写）后重开工程，`SourceNodeName`/`SourceDisplayName` 仍正确还原
10. **显示名不可回写**：外部对 `BindingDisplayText` 赋值不影响 `BindingSource`；重开窗口显示名由路径重算而非缓存

### 绑定层

| **P0.5-D 摘 `Mode=TwoWay`**（20+ 处 XAML） | 先保留属性但**改为只读/忽略写入**（一步过渡），验证显示不漂移后再摘绑定 |
| **P0.5-F 持久化迁移** | 旧工程按 `SourceNodeName`/`SourceDisplayName` 读入（格式未变），仅**写入侧**改为取模型字段；显示文本不再参与持久化 |
| **VM `*BindingDisplayText` 被 20+ 处引用** | 分级处理：先改为"由源推导的只读计算属性"，再逐处删除；不做一次性大爆破 |
| 改 Results 影响老工程反序列化 | **只增不删**：新增 `Point2d[]` 输出，保留 X/Y double 与旧标量字段 |
| 点参数改数组口子，`P1Point` 类型变更 | 反序列化适配：标量旧值自动包成长度 1 数组 |
| 测量结果为数组影响下游绑定 | 词目仍是 Double，double 与 double[] 同词目，下游零改动 |
| "抠几何"覆盖 7 种图形可能遗漏 | 逐类型契约测试；未覆盖直接报错（rule-015） |
| 移除"整体"影响存量绑定 | 运行期保留 `[]` 路径解析，仅 UI 移除入口 |
| 向量化改动面大（计算/判定/显示） | 分阶段实施，先点类三工具，验证后推广 |

## 9. 实施步骤（每阶段独立可验）

| 阶段 | 内容 | 验证 |
|---|---|---|
| **P0 设计端修复（类型）** | Geometry 类型统一（Point→`Point2d`、Rect→`RotatedRect2d`）+ 序列化迁移 + 清理 34 处扩散 + `Point2D` 回归 UI 层 | 验收 1-5 |
| **P0.5 设计端修复（显示名）** | A 声明字段 → B 唯一入口 → C 删显示分支 → E 叶子名声明 → D 只读化 → F 持久化解耦 | 验收 6-10 |
| **P1 点-圆试点** | Results 输出点 + P1Point 改数组口子 + 工具适配 + 候选只出点 + 失败报错 | 验收 11、12、14 |
| **P2 点类推广** | 点-点 / 点-线 同 P1 处理 | 验收 11、12、14 |
| **P3 向量化** | N 点 → N 结果的批量计算 + 判定/显示适配（6 个测量工具统一） | 验收 13、16 |
| **P4 抠几何 + UI** | 抠几何（P0 后已简化，无类型转换）+ ROI ComboBox + 移除"整体" | 验收 15 |

> **P0 是地基中的地基**：做完 P0，契约域与数据域一致，P4 的抠几何从"switch 类型转换"退化为"取 Geometry 组成数组"。
> **P0.5 是显示层的地基**：做完它，"同一源两处显示不同"与"改显示名会破坏持久化"两个隐患同时消失。

### P0.5 内部顺序（不可颠倒）

```
A 声明字段  →  B 唯一入口  →  E 叶子名由构造方声明  →  C 删显示分支
                                            ↓
                            F 持久化与显示解耦（前置）→  D 显示名只读化
```

理由：F 必须早于 D——若先摘掉 `TwoWay`，而持久化仍依赖 `BindingDisplayText.Split('.')`，会出现"绑定丢失"的空窗。
