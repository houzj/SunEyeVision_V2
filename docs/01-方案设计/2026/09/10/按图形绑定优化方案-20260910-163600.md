# 「按图形」绑定优化方案

> 版本：v4（新增阶段 **P0.6「能力层根治」**：能力声明 / 框架契约单源 / 结构与值分离 / 拆基类）
> 原则：从设计端解决根因，再解决具体问题；不背技术债，不将就。

## 1. 改前 vs 改后（用户视角）

| | 改前（今天） | 改后 |
|---|---|---|
| 打开点-圆「按图形」 | 看到"整体/点/直线/圆/矩形…"全是检测框，**没有真正的点** | 直接出现上游算出的**圆心、交点、点1、卡尺检测点** |
| 选了某个形状 | 显示"已绑定"，**实际没生效**，点一直是 (0,0) | 能用的才出现；真转不动的红字报错 |
| 上游圆心传给下游 | 只有"圆心X""圆心Y"两个数字，得绑两次 | 圆心作为**完整点**出现，一次绑定 |
| 绑 20 个卡尺点 | **悄悄失败** | 来多少算多少，出 20 个测量结果 |
| ROI 编辑器选图形 | 一筐异构图形全列出，自己猜 | **ComboBox 先选类型**（圆/矩形/点…），只给该类型 |
| **同一个源在两种界面显示** | `圆查找1.Center.X`（英文、无 `[]`）**vs** `Blob分析1.中心X[]`（中文、带 `[]`）—— 同一件事两种说法 | **完全一致**：`圆查找1.圆心.X[]` / `圆查找1.中心X[]`，中文 + 数组语义带 `[]` |
| 重开工程后显示名 | 依赖**解析显示字符串**还原（`Split('.')`），格式一变就错位 | 显示名是**只读投影**，由绑定路径重新推导 |
| **测量工具的结果树** | 明明没用 ROI，却出现「检测区图形/屏蔽区图形」；且组名 `输入` 与 `输入区域` **两个"输入"并存** | 测量工具**不再出现**区域条目；顶层组名统一 `输入` / `拟合结果` / `结果`（+`执行信息`） |
| 结果业务命名 | `元素1` / `元素2`（内部槽位词），用户看不懂 | 语义名 `点1` / `圆2` / `直线1`（编号保留）；绑定框显示 `点-圆测量1.圆2圆心[]` |

## 2. 依据（可追溯）

- **Halcon tuple 语义**：结果以数组传递，单值 = 长度 1 数组；两数组运算按"等长逐元素 / 长度 1 广播 / 其余报错"规则（本地 `doc_en_US/html`）
- **Halcon iconic-control 分离**：图形（区域/XLD）与数值分属两条流，跨流走显式提取算子（`area_center` 等），图形不能直接当坐标用
- **分层原则**：UI 交互类型不得进入数据契约层
- **单一真相源（SSOT）原则**：同一份信息只允许一个生产者；呈现层只做**只读投影**
- **声明式优先（本项目 rule-016）**：能力/结构/字段一律**声明**，不从类型身份或运行值**推断**
- **本项目决策**（`docs/01-方案设计/2026/07/输出变量契约统一重构方案-20260716.md`）：数组语义、单值 = 长度 1 数组
- **VisionMaster**：检测区与结果数据分离，批量测量逐项判定

## 3. 根因（已查证）

### 3.1 表层根因（三层）

1. **上游没"点"**：几何点（圆心/交点/最近点/点1/点2）都是 WPF `Point`，不入词表，被拆成 X、Y 两个 double。全项目单点 `Point2d` 输出 **0 个**
2. **下游口子错位**：点参数要坐标，却被当"几何图形目标"放行了图形容器，把"整体/圆/直线/矩形"全塞进候选
3. **中间缺工序**：从图形容器只能拿到"图形对象"或单个数字，**拿不到整个几何值**（`Circle2d[]`/`Point2d[]`）

### 3.2 设计端根因之一、之二（数据契约层）

> 上述三层都是**症状**。真正的根因在设计端。

**事实 1：`Point2D` 的设计目的是正确的，不是技术债**

```9:14:src/Plugin.SDK/Execution/Parameters/Point2D.cs
    /// 点结构（可观察，UI 交互/绘制用）。
    /// 注：与 SDK 纯值点 Point2d（readonly struct，算法/契约用）并存，
    /// 本类用于可交互场景（多边形顶点、几何扁平编辑桥、命中坐标）。
    public class Point2D : INotifyPropertyChanged, IMonitorable
```

`Point2D`（class + 属性通知）服务 **UI 交互层**，`Point2d`（readonly struct）服务 **契约/算法层**——这是有意的分层，设计正确。

**事实 2：真正的设计错误——UI/WPF 类型被用作数据契约的几何载体**

`RoiShape.Geometry`（会序列化进工程文件）却使用 UI/WPF 类型承载图形：

| ShapeType | Geometry 实际类型 | 性质 |
|---|---|---|
| Point | `Point2D`（UI 交互类型） | ❌ UI 类型进数据层（**待核实收口**） |
| Rectangle | `System.Windows.Rect`（WPF 类型） | ✅ 已统一为 `RotatedRect2d`（`ShapeType.Rectangle` 已删） |
| Line / Circle / RotatedRect / Polygon / Annulus / Arc | `Line2d` / `Circle2d` / `RotatedRect2d` / `Polygon2d` / `Annulus2d` / `Arc2d` | ✅ 契约类型 |

**事实 3：错误曾被序列化白名单固化**

早期把 UI 类型（`Point2D` / WPF `Rect`）注册进 `GeometryJsonConverter` 白名单，使其成为"既成事实"；`Rect` 分支已在 P0-2 迁移（`ShapeTypeJsonConverter` 读入时迁移为 `RotatedRectangle`）。

**事实 4：错误曾扩散 34 处，跨 4 层**（`RoiShape.cs` 26 处 / UI 编辑器 ~12 处 / Hal·Cv 适配器 / 其他）

WPF `Rect` 曾泄漏到 Halcon / OpenCV 适配器——数据层用 WPF 类型，算法适配器被迫认识 WPF 类型，分层被破坏。

### 3.3 设计端根因之三：绑定显示名没有单一真相源（SSOT）

**触发事实（用户实测）**：同一个"几何输出字段"的绑定，在两个界面显示不同——

| 界面 | 控件 | 显示 | 走的分支 |
|---|---|---|---|
| 点-圆调试窗「X 坐标」 | `ConfigSetting` | `圆查找1.Center.X`（**英文、无 `[]`**） | `GetDisplayLeafName` 分支② |
| ROI 订阅面板「几何参数」 | `ParamBinding` | `Blob分析1.中心X[]`（**中文、带 `[]`**） | 分支① |

**事实 1：显示文本有 6 个生产者**（同一份信息多处生产）

| # | 生产者 | 位置 |
|---|---|---|
| 1 | `AvailableDataSource.DropdownDisplayText` | `AvailableDataSource.cs:163-172` |
| 2 | `AvailableDataSource.GetDisplayText()` | `AvailableDataSource.cs:233-239` |
| 3 | `ImageSourceReference.DropdownDisplayText`（**连 `[]` 规则都不同**） | `ImageSourceReference.cs:88` |
| 4 | `ParamBinding.GetDisplayLeafName` / `GenerateBindingDisplayText` | `ParamBinding.cs:844-918` |
| 5 | ViewModel/模型缓存的 `*BindingDisplayText`（位置修正、文本样式、子程序、脚本、循环等 **20+ 处**） | `RoiParameters.cs:254`、`TextStyle.cs:78/96`、`Subroutine*Config.cs`、`Script*Config.cs` 等 |
| 6 | 持久化字段 `ParamSetting.SourceNodeName/SourceDisplayName` | `ParamSetting.cs:85/94/224-253` |

**事实 2：显示名被当成"控件状态"，而不是"数据源的只读投影"**

`ParamBinding.BindingDisplayText` 是**可写 `TwoWay` 依赖属性**，`ConfigSetting` 再**转发 + 缓存**（`ConfigSetting.cs:951-957`）。**一旦显示名可被三方写入、可缓存、可持久化，它就不再是推导结果，而是"第二份数据"**——两份数据必然漂移。XAML 里 `Mode=TwoWay` 共 **20+ 处**。

**事实 3：显示文本同时被当成"数据格式"（隐蔽且致命）**

| 位置 | 代码行为 |
|---|---|
| `ConfigSetting.cs:1176-1181`、`1297-1302` | `BindingDisplayText.Split('.')` → `SourceNodeName` / `SourceDisplayName` |
| `TextStyle.cs:104-157`、`175-198` | 同上 |
| `SubroutineTool.cs:282-284` | `input.BindingDisplayText?.Split('.')` |

**显示格式 = 持久化格式**：显示名一改（中文/多 `.`），持久化立刻错位。**必须先解耦。**

**事实 4：显示规则按"路径字符串形态"分支，而不是按语义分支**

`GetDisplayLeafName`（`ParamBinding.cs:902-918`）判断的是 `BindingSuffix` 的**字符串前缀**，后果：分支① 强制 `[]` 用中文；分支② 不加 `[]` 且用**英文 `PropertyName`**（`node.Text`/`ds.DisplayName` 就在手上却被忽略）。

### 3.4 设计端根因之四：能力层——「继承即能力」+ 结构与值混淆

**触发事实（用户实测）**：测量工具（点-圆等）**根本不使用 ROI 检测区/屏蔽区**（只借用了"引导几何/卡尺"能力），结果树与绑定下拉里却出现「检测区图形 / 屏蔽区图形」。

**事实 1：`RoiParameters` 混装 4 种正交能力**

| 能力 | 成员 | 谁需要 | **未使用时的后果** |
|---|---|---|---|
| 图像源 | `ImageSourceRef` / `ImageSource` | 图像类工具（14/14） | 无害 |
| 位置修正 | `IsPositionCorrectionEnabled` / `PositionCorrectionSource` | 算法工具（多数） | 无害 |
| **引导几何+卡尺** | `HasMeasureGuide`（virtual 默认 false）/ `GuideStyle` / `CaliberStyle` / `BuildMeasureGuideItems` | 圆查找、直线查找、6 个测量 | ✅ **无害**（默认关，不产出） |
| **区域输入** | `InspectionRois` / `MaskRois` / 区域样式 | Blob、阈值、形态学… | ❌ **有害**（设计期恒注册 → 无用条目） |

**能力是集合（2⁴ 种组合），继承是树**——用树表达集合，必然"为了要 A 被迫带上 B"。测量工具要"引导"，被迫带上"区域"。

**事实 2：用「类的身份」推断「能力使用」**

```491:495:src/Plugin.Infrastructure/Managers/Tool/ToolRegistry.cs
                if (plugin.ParamsType != null && typeof(RoiParameters).IsAssignableFrom(plugin.ParamsType))
                {
                    RegisterRoiContractMetadata(toolId, nameof(ToolResults.InspectionGeometries), "检测区图形");
                    RegisterRoiContractMetadata(toolId, nameof(ToolResults.MaskGeometries), "屏蔽区图形");
                }
```

**14 个工具全部继承 `RoiParameters`** → 判定**恒真** → 门槛形同虚设。

**事实 3：结构与值混淆（最隐蔽）**

| 阶段 | 判定标准 | 后果 |
|---|---|---|
| 运行期 `ToolResults.AddRoiContractVariable`（`:586-587`） | **值**（空值/空数组 → 跳过） | 条目随值波动、**结构抖动** |
| 设计期 `ToolRegistry.RegisterRoiContractMetadata` | **类型身份**（继承即注册） | 恒注册 → **不用的工具也有** |

历史痕迹（`ToolRegistry.cs:490` 注释）："修复 `b593533c` 把'空区跳过'放入契约层导致注册派生丢失 RoI 结构、未运行节点输入区域整体消失的回归"——补丁**方向对**（结构应稳定），但**依据错**（拿类型身份当依据）。

**事实 4：框架契约"双份真相"**

「检测区/屏蔽区」的属性名 / 显示名 / 组名 / 类型在**两个文件各写一遍**（运行期 `ToolResults` 一份、设计期 `ToolRegistry` 一份）——改一次组名要同时改两处，极易漏（本次改名即同时踩到）。

**结论**：根治 = **能力声明（唯一判定源）+ 框架契约单源 + 结构与值分离**；配套拆基类只是"承载层整理"。

## 4. 设计决策（已拍板）

| # | 决策 |
|---|---|
| 1 | **异构不处理**，需要多种图形就拆成多个节点，一个节点绑一种图形 |
| 2 | **移除"整体"**入口，一律按 `[类型]` 取同类图形（**待定：区域订阅是否保留**） |
| 3 | **DataType 分层**：点-圆等明确要点的 → **固定 `Point2d`** 不加 ComboBox；**ROI 编辑器** → 加 ComboBox 动态选类型 |
| 4 | **点参数为数组口子**：`P1Point` → `ParamValue<Point2d[]>`，**来多少算多少，不报错** |
| 5 | **数组语义贯穿**：单值 = 长度 1 数组，全程对齐 Halcon tuple |
| 6 | **设计端优先**：先修数据契约（P0）、显示名 SSOT（P0.5）、能力层（P0.6），再做绑定层优化 |
| 7 | **分层原则重建**：`RoiShape.Geometry` 只允许 `Models.Geometry.*` 契约类型；UI 类型（`Point2D`、WPF `Rect`/`Point`）只许待在 UI 交互层 |
| 8 | **显示名 SSOT**：显示名由数据源模型声明（`LeafDisplayName` + `IsArraySemantics`），**唯一格式化入口**；控件只渲染，不生产、不缓存、不回写 |
| 9 | **`[]` 按语义统一**：数组语义即带 `[]`，**不按控件分叉**；**显示文本与持久化彻底解耦** |
| 10 | **能力声明**：工具**显式声明**能力（`ToolCapabilities`）；**禁止**用"继承某基类"推断能力使用 |
| 11 | **框架契约单源**：框架级输出的 属性名/显示名/组名/类型**只声明一处**，设计期与运行期同源生成 |
| 12 | **结构与值分离**：**结构**由能力声明决定（两阶段一致）；**值**由运行结果决定（空值渲染占位 `--`，**不从结构里删条目**） |
| 13 | **术语对齐（不造新词）**：能力位 `ImageSource` / `RoiInput` / `MeasureGuide` / `PositionCorrection`；承载层**只新增 `MeasureGuideParameters`**，`RoiParameters` 类名与 `[JsonDerivedType(..., "RoiParameters")]` 判别符**保持不变** |
| 14 | **结果显示名用用户域词汇**：弃内部槽位词"元素N"，用语义名 + 编号；顶层组名统一三层语义 |
| 15 | **呈现诉求与值语义分离**：收敛输入（形状筛选）**不得**复用值类型 `DataType` —— 复用会把值类型误声明（区域源恒为 `RoiShape[]`），造出新的"能选不能用" |
| 16 | **形状是声明数据，不是 UI 状态**：形状真相源在模型（`Roi`），UI 只作编辑视图。两子模式**共用形状状态**、但**持久化方式不同**：参数拼装写 `ComposeShapeType`；区域订阅由绑定路径 `[Type=X]` 表达（回显靠 `ParseShapeTypeFromBinding`）——故区域订阅下忽略 `ShapeTypeChanged` 是**有意**设计，非特例残留 |
| 17 | **框架契约唯一产出点**（本版新增，事故驱动）：框架级契约条目（检测区/屏蔽区等）**只由** `ToolResults.GetOutputVariables()` 产出，设计期必须消费同一产出，**禁止旁路注册**。典型事故：病根（契约层"空值跳过"）治好后，为它打的补丁（设计期显式注册）未撤 ⇒ 结构产出两遍，「选择绑定源 → 输入」出现**两套**「检测区图形/屏蔽区图形」 |
| 18 | **显示配置分层**（本版新增，**用户决定**）：**编辑器 UI 不提升到 SDK 层** —— 各工具独立实现。理由：工具样本尚少、模型未定型，过早抽象会把**尚未确定的结构**固化成"事实标准"（Rule of Three：≥3 处逐字重复才值得抽象）。**提升触发条件**（满足任一即重新评估）：① 工具数 ≥ 12 且均有显示编辑器；② ≥3 个工具的编辑器 XAML 逐字重合；③ 出现"同一改动须在 ≥3 个工具重复"的横切需求。**硬边界（不可越）**：样式**数据模型**（`GraphicsStyle`/`TextStyle`/`DisplayItemBase`）与**渲染管线**（`ResultRenderLayer`）**必须**留在 SDK —— 渲染层直接消费 `LineWidth`/`OkColor`/`NgColor`/`LineDashStyle`/`IsFilled`/`CrossSize`（`ResultRenderLayer.cs:359,360,441,496,589`），工具层若自建样式类则**编译不过**。故"独立实现" = **各自的 XAML 与交互**，**禁止新建工具本地样式模型**（需新样式字段时，加进共享 `GraphicsStyle`/`TextStyle` 并同补渲染） |

> **决策 18 附注**：`DispItemColorControl`（`src/Plugin.SDK/UI/Controls/DispItemColorControl.cs`，106 行 + `Generic.xaml` 模板，现被 10 个工具引用）**维持现状不下移** —— "不再提升"≠"把已有的下移"；下移是纯 churn 且立刻产生 10 份副本，收益为负。**新增**编辑器一律走工具层。

## 6. 向量化计算规则（核心契约）

点/线/圆元素都可能是 N 个，两元素运算对齐 **Halcon tuple 广播规则**：

| 元素1 长度 | 元素2 长度 | 行为 |
|---|---|---|
| N | N | 逐对计算 → **N 个结果** |
| 1 | N | 广播 → **N 个结果** |
| N | 1 | 广播 → **N 个结果** |
| N | M（N≠M 且都≠1） | **报错**"长度不匹配（N vs M）" |

**判定规则**：每个结果单独判定，**整体 OK = 全部合格**；`JudgmentDetails` 逐个列出明细。

**输出契约**：测量结果为数组（如 `DistanceToCenter` → `double[]`），下游按数组绑定（词目 Double，一致）。

## 11. ROI 形状收敛专项（架构视角）— 本版新增

> **触发**：实测「ROI 管理器 → 订阅区域 → 区域源」下拉把「整体 + 全部 7 类形状」全倒出来，需要"一个 ComboBox 选择筛选类型"；并拍板**取消「整体」**——其原为"上游一个节点绘制了多种图形 → 一把全绑"的**异构**场景服务，现订阅方工具只能绑**固定形状**，该语义已废。

### 11.1 架构问题（不是"加个 ComboBox"）

| # | 问题 | 证据 |
|---|---|---|
| **P1** | 「形状」无单一真相源：`ComposeShapeType`（持久化）/ `DeclaredShapeType`（`[JsonIgnore]` 派生 + 三层兜底）/ `LocalGeometry.ShapeType`（绘制）/ VM `CurrentShapeType`（UI 缓存）/ 绑定路径 `[Type=X]`（隐式） | `RoiInput.cs:109-134`、`ParameterPanelViewModel.cs:130-141` |
| **P2** | **`ParamBinding.DataType` 一个入参身兼三职**：① 候选源过滤 ② 数组子树形态（形状收敛）③ 绑定值类型 | `ParamBindingBase.cs:275`、`:192-196` |
| **P3** | 「整体」是异构时代遗留语义，与决策 1 及"工具只绑固定形状"冲突 → 提供不可用入口 | 唯一产出点 `ArrayTreeFormatter.cs:167-172` |
| **P4** | 形状清单**两份手写副本**且互相不一致（VM 4 类含重复项 vs 实际 7 类） | `ParameterPanelViewModel.cs:118-125`、`:244-246` |

**P2 是枢纽**：形状筛选是**呈现诉求**，而 `DataType` 承载**值语义**；复用会让区域源值类型被误声明为 `Circle2d[]`，反而造出新的"能选不能用"。

### 11.2 目标模型（单向数据流闭环）

```
Roi.ComposeShapeType（唯一持久化真相源；语义升格 = 订阅形状，两子模式共用）
    ↓ LoadFromRoi 回显
VM.CurrentShapeType（唯一 UI 状态）
    ├─ 几何参数模式 → UpdateParameterDefinitions()（参数行按形状）
    └─ 区域订阅模式 → ParamBinding.ShapeTypeFilter → BuildRoiTypedChildren（候选收敛为 1 片叶）
    ↓ 用户改选
RoiEditorViewModel.OnShapeTypeChanged → 回写 Roi.ComposeShapeType
```

**架构收益**：`OnShapeTypeChanged` 注释里"整对象订阅模式忽略"（`RoiEditorViewModel.cs:704-711`）正是旧缺陷的直接证据——当时区域订阅不需要形状。两子模式共用形状后特例消失，数据流成为闭环。

| ❌ 否决：`DataType` 设成选中形状的 CLR 类型 | 值类型误声明 → 新"能选不能用" |

| ❌ 否决：整体改为"灰显" | 决策 2 是"移除"；灰显留着语义歧义 |
| 多边形是否列入筛选 | **列入**（区域订阅绑的是图形本身，不需要字段）；若几何参数模式列到无参数定义的形状，**显式提示不支持拼装**，不出空行 |

### 11.5 兼容策略（取消整体的影响面）

树只决定"选择器里**能不能选**"，**不影响已有路径解析**（`OutputVariableResolver` 不依赖树）→ 老工程若曾绑"整体"，**值仍在不丢**，仅选择器不再提供该入口——正是"取消"的预期行为。

### 11.6 风险与回退

| 风险 | 回退 |
|---|---|
| 取消整体影响所有 ROI 下钻入口 | 影响面天然收窄：数值目标（`ArrayTreeFormatter.cs:134-162`）与几何值目标**本来就没有整体**。回退 = 恢复一句 `children.Add` |
| `ComposeShapeType` 语义扩展影响参数拼装 | JSON 键与判别符不变，`LoadFromRoi` 兼容分支保留 |
| 几何参数模式缺 3 类形状参数定义 | 本次不混入：两清单分别是"全形状"与"可拼装形状"，属**显式差异**；补全单独一步 |
