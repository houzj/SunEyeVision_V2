## 一、一句话

**现在的工具是"没带行李的客人"，全靠主程序临时给东西；要改成"自带行李的客人"——在自己机器上能开发、能调界面、能调试，做完拷进 `plugins` 就能跑。**

---

## 二、需求定义（验收总纲）

| # | 需求 | 可验证判据 |
|---|---|---|
| R1 | 每个工具**具备完整依赖与引用** | 工具目录自包含业务依赖；无宿主源码也能构建 |
| R2 | **设计时 + 运行时都独立** | 设计器开箱可渲染；F5 可跑通 |
| R3 | 开发完**拷进 `plugins/`** 即可运行 | drop-in 后可发现、可配置、可执行 |
| R4 | 支持**多人协作** | 契约版本校验 + 坏插件可见 + 开发包可分发 |
| R5 | 同一份工具工程**同时支持"有/无主程序源码"两种开发场景** | 工程目录拷出仓外仍可构建、F5、交付 |

## 三、现在到底哪里不对（人话版）

| # | 现象 | 根子在哪（来源） |

## 六、目标架构

### 6.1 唯一的取舍：依赖分三类

| 类别 | 举例 | 策略 | 理由 |
|---|---|---|---|
| **契约** | `SunEyeVision.Plugin.SDK` | **大家共用一份**（放在主程序，插件只用它那份） | 各带各的会出现**两套同名类型**：程序不报错、功能悄悄失灵（`ScriptSandbox.cs:15-21` 已写明该坑） |
| **大件平台** | Halcon 25 个原生 dll、OpenCV、桌面框架、宿主自身程序集 | **主程序里一份，共用**（工具目录不放） | 否则每个工具目录数 GB，14 个工具上百 G；开发包无法分发 |
| **工具自己的库** | 工具自身第三方 NuGet、私有 dll、以及工具会直接引用的框架程序集 | **工具自带**（含依赖清单 `.deps.json`） | 这才叫"独立"；顺带隔离版本冲突 |

> 一句话：**大件共用、小件自带、契约只留一份。**

### 6.2 运行时加载

```
主程序启动
  └─ 扫描 plugins/ 下每个工具文件夹
       └─ 为每个工具建一个"隔间"（独立 AssemblyLoadContext + 依赖解析器）
            ├─ 契约 / 大件平台找不到 → 回主程序拿（共用）
            ├─ 其余 → 在工具文件夹内解析（自带）
            └─ 核对"证件"（SDK 契约版本）→ 不合格：明确报错 + 只跳过这一个
```

### 6.3 开发时（本地闭环）

- 工具工程把**启动程序设为主程序**：F5 → 起真实宿主 → 里面跑的就是刚编的工具。
- 设计时依赖随工程复制 ⇒ **设计器可渲染、智能提示恢复**（不再需要任何补丁）。

### 6.4 多人协作治理

| 机制 | 做法 |
|---|---|
| **契约版本** | SDK 暴露契约版本常量；宿主启动校验（对标 VS Code `engines.vscode`） |
| **不匹配行为** | 明确报错并跳过该插件，列出"插件需要 X / 宿主提供 Y"；**不静默回落宿主同名 dll**（rule-008 报错优先） |
| **隔离** | 单插件失败不影响其它插件（替换 `PluginManager.cs:155-162` 的静默 `catch{}`） |
| **开发包** | `主程序文件夹（含大件依赖） + SDK 包 + 工具模板 + 开发说明 + 私有 feed 配置` |

### 6.5 双场景开发（R5）

| | **场景 A：有主程序源码** | **场景 B：无主程序源码** | 统一机制 |
|---|---|---|---|
| SDK 来源 | 仓库内 SDK 源码工程 | 开发包里的 **SDK 包** | 同一份 csproj + 条件引用（**禁止分叉成两套工程**） |
| 构建规则 | 同一份规则 | **同一份规则（随 SDK 包分发）** | 规则下沉为可分发的 MSBuild 包 |
| 主程序目录 | 本仓构建产出 `dev/Debug` | 开发包里的 `host/` | 单一 `HostRoot` 属性 |
| 开发流程 | 改代码 → 设计器看界面 → F5 起主程序 | 完全一样 | 模板预置启动配置 |
| 交付 | 构建输出到 `plugins/<Tool>/` | 工具文件夹发回 → 拷进 `plugins/` | 同一自包含产物 |

**架构不变量（硬标准）**：
> 工具工程**只认两个外部输入**：① SDK（源码工程 **或** SDK 包）② 主程序目录 `HostRoot`。
> **禁止**依赖仓库专有设施（`$(WorktreeBasePath)`、仓库级构建文件的隐式行为、测试 hack）。
> 验收方法：把工具工程目录**整体拷到仓外空目录**，只给"主程序文件夹 + SDK 包"，必须能**构建、F5、交付**。

## 七、方案对比（≥3 候选 + 长期 ROI）

| 维度 | A：现状 + 设计时补丁 | **B：契约共享 + 大件共用 + 小件自带（推荐）** | C：完全自包含（含大件） |
|---|---|---|---|
| 实现方式 | 保留剔除逻辑，另加设计时复制 | 依赖三类 + 每插件隔间 + 契约校验 | 所有 dll/原生都进工具目录 |
| 与架构一致性 | 否（补丁叠加，违反 rule-008） | **是**（与 .NET 官方插件模型一致） | 部分（可行但笨重） |
| 复杂度 | 低 | 中（构建反转 + 加载器 + 开发包） | 低 |
| 维护成本 | **高**（每加依赖改构建规则） | **低**（依赖归工具自己） | 中（体积治理） |
| 扩展性 | 弱 | **强**（新工具零改宿主） | 强 |
| 6 个月 ROI | 负 | **正** | 中 |
| 1 年 ROI | 负 | **高** | 中（下载/磁盘成本） |
| 3 年 ROI | 严重负 | **高** | 低（14×GB 不可持续） |

**推荐 B**：唯一同时满足 R1~R5；有 .NET 官方文档/样例支撑；**每插件隔间恰好解决**了 `Directory.Build.targets:89` 担心的"版本冲突"（各带自己版本，而非共享一份）。

## 八、要做的 5 件事（人话版）

1. **加"隔间"加载 + 证件核对**（先做，风险最低）：每个工具在自己的隔间里加载；启动核对 SDK 版本；**不合格只跳过它并说明原因**。
2. **让工具自带行李**（改构建规则）：把"剔除依赖"那几步反过来——工具的库**保留**、依赖清单**保留**；只继续拦真正的大件（Halcon 原生、OpenCV）。
   👉 **做完这一步，设计器黄框应消失**（无需任何补丁）。
3. **把构建规则从"仓库私有"变成"可分发"**：现在规则写在仓库公共构建文件里 → 别人无效。改为**随 SDK 包分发**，两场景行为一致。
4. **把"启动程序指向主程序"固化到模板**：新工具自带该配置；老工具逐个补。
5. **打开发包 + 搬 14 个工具**：开发包 = `主程序 + SDK 包 + 模板 + 说明`；同时把 14 个工具改成"只认两个外部输入"的形态。

# 十七、双场景工具开发详细方案（补充）

> 本章把 R5 展开成**可直接照做**的开发流程。核心原则：**同一份工具工程，两种环境都能构建/调试/交付**；
> 差异只体现在两个外部输入的**来源**（SDK 从哪来、主程序目录在哪），其余全部相同。

## 17.0 两个外部输入（先记住这个）

| 输入 | 场景 A（有主程序源码） | 场景 B（无主程序源码） |
|---|---|---|
| **SDK** | 仓库内工程 `src/Plugin.SDK/SunEyeVision.Plugin.SDK.csproj` | 开发包里的 `nupkg/SunEyeVision.Plugin.SDK.*.nupkg` |
| **HostRoot**（主程序运行目录） | 本仓构建产出 `dev/Debug/` | 开发包里的 `host/` |

> 工具工程**只认这两个**。任何"我记得仓库里有个路径/有个公共 props 会帮我处理"的想法都必须放弃（那是场景 B 会崩的根因）。

## 17.1 场景 A：有主程序源码（本仓内开发）

### A-1 环境准备
1. .NET SDK（`net9.0`）+ `net9.0-windows` 桌面工作负载。
2. 本仓首次构建（产出宿主与大件依赖）：
   ```
   dotnet build SunEyeVision.slnx -c Debug
   ```
   产出：`dev/Debug/`（宿主 + Halcon 25 个原生 + OpenCV 等，见 `Directory.Build.targets:224-236`）。
3. 工具工程位置：`tools/SunEyeVision.Tool.<Name>/`。

### A-2 工程形态（工具 csproj 关键内容）
```xml
<PropertyGroup>
  <TargetFramework>net9.0-windows</TargetFramework>
  <UseWPF>true</UseWPF>
  <IsToolPlugin>true</IsToolPlugin>
  <!-- F5 直接起本仓宿主（HostRoot 由规则给出 = $(WorktreeBasePath)dev\Debug\） -->
  <StartAction>Program</StartAction>
  <StartProgram>$(HostRoot)SunEyeVision.UI.exe</StartProgram>
  <StartWorkingDirectory>$(HostRoot)</StartWorkingDirectory>
</PropertyGroup>
<ItemGroup>
  <!-- 场景 A：SDK 走源码工程（能改 SDK、能一步到位联调） -->
  <ProjectReference Include="..\..\src\Plugin.SDK\SunEyeVision.Plugin.SDK.csproj"
                    Condition="Exists('$(WorktreeBasePath)src\Plugin.SDK\SunEyeVision.Plugin.SDK.csproj')" />
</ItemGroup>
```

### A-3 依赖策略（三类落地）
| 类别 | 在 A 场景怎么处理 |
|---|---|
| 契约（SDK） | 源码工程引用；**改了 SDK 契约必须 bump 契约版本**（影响所有外部开发者） |
| 大件平台 | 由统一规则剔除、宿主根提供（工具目录不放） |
| 既有业务依赖 | **默认复制本地**（去掉 `Private=false`）→ 设计器可用、可独立运行 |
| 新增第三方库 | 直接加 `PackageReference`，**自动复制**进工具输出目录（无需改宿主任何东西） |

### A-4 开发与调试
| 步骤 | 做法 | 现象 |
|---|---|---|
| 写界面 | 打开 `Views/<Name>ToolDebugControl.xaml` | **设计器可渲染**、智能提示正常 |
| 加参数 | 在 `<Name>Parameters.cs` 加属性（`ParamValue<T>` 口子） | 宿主自动出参数行 |
| 写算法 | 实现 `Run(...)`，结果显示走 `DisplayCollector`/结果类 | — |
| 调试 | **F5**（不是"启动主程序再手点"） | 起真实宿主，里面就是刚编的工具 |
| 验证 | 工具箱 → 拖到画布 → 配参 → 执行 → 结果树/显示 | — |

### A-5 测试与交付
- 测试工程：`tests/SunEyeVision.Tool.<Name>.Tests/`，**直接引用工具工程**（删除共享加载器 hack）。
  ```
  dotnet test tests\SunEyeVision.Tool.<Name>.Tests
  ```
- 交付产物：构建即产出到 `dev/Debug/plugins/SunEyeVision.Tool.<Name>/`（自包含）。
- 提交：走本仓 git（提交规范见「代码提交」技能）。

### A-6 A 场景常见问题（含本轮实测）
| 现象 | 原因 | 处置 |
|---|---|---|
| 设计器黄框 + ⓘ"由于程序集缺失" | 工具输出目录缺依赖（被剔除逻辑清空） | P2 反转剔除规则后**结构性消失**；临时验证可确认输出目录里是否有 SDK |
| `dev/Debug` 根出现同名工具 dll | 历史残留旧拷贝 | 删除（加载器会报错提示，见 `tests/_shared/ToolPluginTestLoader.cs:92-98` 同款判定） |
| 工具里用了新库但运行报"找不到文件" | 依赖没进工具目录 | 检查是否被大件清单误拦（应只在清单内的才拦） |

### B-6 契约版本纪律（多人协作核心）
| 情形 | 行为 |
|---|---|
| 工具用错版本 SDK 编译 | 宿主启动**明确报错**：`插件需要契约 X / 宿主提供 Y`，并**只跳过该插件**，其它插件照常 |
| 工具需要"宿主没有的能力" | **不能改宿主**；走**能力需求通道**：提需求 → 主程序方扩展 SDK → bump 契约版本 → 发新 DevKit |
| 升级 SDK | 按 DevKit 的《契约版本与兼容矩阵》执行；不匹配的旧工具会被明确拒绝（**不静默**） |

| 允许 | 不允许 |

| 用宿主提供的大件依赖 | 把大件 dll 复制进工具目录（体积与版本会失控） |
| 用模板自带测试工程 | 引用 SDK 的 internal 类型（`InternalsVisibleTo` 不对第三方开放） |

### B-8 B 场景常见问题
| 现象 | 原因 | 处置 |
|---|---|---|
| 设计器黄框 | SDK 包没装/没还原 | 检查 `nuget.config` 与还原是否成功（应有 SDK dll 在工具输出目录） |
| F5 起不来 | `HostRoot` 没设/路径错 | 检查环境变量或 `local.props`，确认 `host\SunEyeVision.UI.exe` 存在 |
| 工具在宿主里看不到 | 证件核对没过 / 没拷到 `plugins\` | 看宿主启动日志的加载结果（明确报错，不静默） |
| 工具目录里出现 halcon 大件 dll | 大件清单规则未生效 | 确认 SDK 包的 `build/` 规则已被导入（还原日志可见） |

## 17.4 双场景必须共同满足的"架构不变量"（可自动验收）

1. 工具工程**只引用两个外部输入**：SDK（源码工程或包）+ `HostRoot`。
2. **不得引用**：`$(WorktreeBasePath)` 之外的仓库路径约定、仓库级 `Directory.Build.*` 的隐式行为、`tests/_shared/*`。
3. **不得**在工具工程里硬编码宿主绝对路径（必须走 `HostRoot`）。
4. 工具的一切依赖（除大件外）**必须落在工具输出目录**内（可复制、可交付）。
5. **验收动作**：把工具工程目录整体拷到**仓外空目录** → 配好 SDK 包与 `HostRoot` → `dotnet build` 成功 + F5 起宿主可用 ⇒ 通过。

## 18.2 设计器「黄框 / 控件空白」的**实测根因是两条**（原方案 §三 只记了一条）

| # | 根因 | 可追溯证据 | 治本 |
|---|---|---|---|
| 1 | 只覆盖 `OutDir` ⇒ SDK 早期算出的 `TargetPath` 仍指向 `dev\Debug\<Tool>.dll`，与产物实际位置**分叉**；VS 设计器按 `TargetPath` 找项目输出程序集 ⇒ 报「**由于程序集缺失，元素[ToolDebugControlBase]无法显示**」 | `dotnet msbuild -p:DesignTimeBuild=true -getProperty:TargetPath` → `dev\Debug\…dll`，而 `OutDir` 已是 `plugins\…\`；同款坑已在 `Directory.Build.props:30-32` 记录过 | `Directory.Build.targets:51-53` 同步 `OutputPath/TargetDir/TargetPath` |
| 2 | SDK **缺 `[assembly: ThemeInfo]`** ⇒ WPF 不去查 `themes/generic.xaml` ⇒ SDK 自定义控件（`ToggleSwitch`/`LabeledControl`/`RangeInputControl`…）在设计器里渲染为**空白**。宿主内正常，是因为宿主在 Application 级显式合并了 SDK 样式库 | 探针实测：同位置纯 `TextBlock` 可见、SDK 控件空白；SDK 原有 `<ThemeInfo Include="Themes\Generic.xaml" />` 是**无效项**（既不生成特性也不起作用） | `src/Plugin.SDK/AssemblyInfo.cs` 显式声明 `[ThemeInfo(None, SourceAssembly)]` |

> ★ 二者现象**极其相似**（都表现为"控件看不到"），但成因一个在**构建路径**、一个在**程序集自描述**。
> 结论：**"设计器可用" = 路径正确（1） + 程序集自描述主题（2）**，缺任一条都会复现，诊断时须分别验证。

## 18.3 显示配置的归属口径（决策 18 · 用户决定）

| 内容 | 归属 | 理由 |
|---|---|---|
| 显示项**清单 / 标签 / 绑定源**（点1、点距连线…） | **工具层** | 业务差异 |
| **结果判断**区（判定项 + 取值映射） | **工具层** | 项名与取值语义逐工具不同（"距离"在点-线/线-线/线-圆里是三件事） |
| 显示编辑器 **XAML 与交互** | **工具层**（本决定） | 工具样本尚少、模型未定型；过早抽象会把**尚未确定的结构**固化成"事实标准"（Rule of Three） |
| 样式**数据模型** `GraphicsStyle`/`TextStyle`/`DisplayItemBase` | **SDK（硬边界）** | 渲染层直接消费其字段（`ResultRenderLayer.cs:359,360,441,496,589`）⇒ 工具层自建样式类**编译不过** |
| **渲染管线** `ResultRenderLayer` | **SDK（硬边界）** | 同上 |
| 现有 `DispItemColorControl` | **SDK · 维持不动** | "不再提升" ≠ "把已有的下移"；下移是纯 churn 且立即产生 10 份副本 |

- **唯一规矩**：新增样式字段（透明度/线宽/字号…）**必须加进共享 `GraphicsStyle`/`TextStyle` 并同步补渲染**，禁止工具本地样式模型。
- **提升触发条件**（满足任一即重新评估）：① 工具数 ≥ 12 且均有显示编辑器；② ≥3 个工具的编辑器 XAML **逐字重合**；③ 出现"同一改动须在 ≥3 个工具重复"的横切需求（如主题化收敛）。

## 18.5 事故档案：`Script` 判别符不可识别（2026-09-14 · 本批回归）

**现象**：加载解决方案失败 —— `Read unrecognized type discriminator id 'Script'. Path: $.Parameters`（同一文件在**上一版本**可正常打开）。

**定性：实现偏差 + 设计缺口**（**不是**简单 bug）

| 层面 | 结论 | 依据 |
|---|---|---|
| 实现偏差 | 方案 §6.1 已写明"大件平台 = Halcon / OpenCV / **桌面框架** / 宿主自身程序集 → 主程序一份，共用"；实现 `PluginAssemblyPolicy` 时**漏了"桌面框架"这一类** | §6.1、§6.2 原文 |
| 设计缺口 ① | 边界清单**存在两处**（构建期剔除清单 vs 加载期回落清单），加一处漏一处**不报错** | `Directory.Build.targets` vs `PluginAssemblyPolicy` |
| 设计缺口 ② | **无一致性守卫** ⇒ 分叉无感 | 原 4 条守卫**恰好**没覆盖"框架程序集"这一类 |
| 设计缺口 ③ | **正确性靠偶然**：18 个工具里 17 个正常，只因它们目录里**恰好**没有跨边界库副本 | 实测：仅 Script 目录 `dll数=28`，其余为 1 |

**因果链（可追溯）**
1. Step 1 反转（业务依赖保留）⇒ Script 工具目录自带 `System.Text.Json.dll`；
2. 隔间解析顺序为"**优先插件目录**"⇒ 载入目录那一份；
3. 工具参数类 `ScriptParameters` 上 `[JsonDerivedType]` 特性的**类型**即来自那一份 ⇒ 宿主用自己的 `JsonDerivedTypeAttribute` 扫描时**看不见**；
4. ⇒ 判别符 `Script` 未注册 ⇒ 反序列化报错。

**关键证据**（`PluginLoadingSmokeTests` 输出）
```
[取证]   特性 System.Text.Json.Serialization.JsonDerivedTypeAttribute @ System.Text.Json 10.0.0.0   ← 插件目录那份
[取证]   宿主 JsonDerivedTypeAttribute 来自 System.Text.Json 10.0.0.0                                  ← 宿主那份
判别符 'Script' 解析失败: JsonException - Read unrecognized type discriminator id 'Script'
```
⇒ **同名、同版本、不同隔间 = 两个不同类型**。这是 .NET 类型身份（含加载上下文）的必然结果，不是加载失败。

**治本（3 条，已落地）**

| # | 做法 | 效果 |
|---|---|---|
| 1 | 加载判定改为「**共享优先**」顺序：契约/`SunEyeVision.*` → 框架/BCL → **宿主已加载** → **宿主运行目录可解析** → 才在隔间内解析 | 覆盖**类别**而非枚举条目，同族隐患一并消除 |
| 2 | **删除加载期的"大件平台清单"**，改由上述**事实判定**覆盖 | 清单唯一真相源只剩**构建期一份**（职责＝体积治理）⇒ **两侧无分叉可能**（消除缺口 ①/②） |
| 3 | **可诊断**：逐插件输出「隔间内解析依赖 N 个」 | 把"自带了某库却没被使用"这类盲区变成可见（本次事故的第一现场盲区） |

**防御（已落地）**
- 守卫测试 `PluginLoadPolicyContractTests`：框架程序集（`System.Text.Json` 等）**必须**判为宿主所有；契约/框架模块同理。
- 端到端冒烟 `PluginLoadingSmokeTests`（设 `SUNEYE_PLUGIN_SMOKE=1` 运行）：断言 ① **发现插件数 == 注册工具数**（不再出现"某个插件默默没加载"）；② **`Script` 判别符可解析**（本次事故的直接回归守卫）。

**验证结果**：构建 **0 错误** ｜ 冒烟：**发现 18 == 注册 18**、**判别符 `Script` 解析成功** ｜ 全量测试仅剩既有无关失败（`ShapeMatch` 1 + `Script` 7，与加载无关）。
