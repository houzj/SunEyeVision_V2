## 0. 一页摘要

### 0.1 病根

一个"参数"对象同时承载 **4 种身份** —— 值、值的来源、展示文案、结构元数据；且"值从哪来"被做成了**属性类型的一部分**（`ParamValue<T>`），而不是旁路状态。

```
"同一生命周期内共享一个对象；只有生命周期不同才分家。"
"同住一个类不是罪；同住却无法判定谁是谁才是罪。"
```

### 0.2 五阶段路线

| 阶段 | 目标 | 性质 | 破坏性 |
|---|---|---|---|
| **A 视觉与文案** | 6 项 UI 缺陷 | 治标 | 无 |
| **B 判据与交互** | 「目标参数」列什么、怎么勾 | 治标 | 无 |
| **D 参数契约层（SDK）** | **接口 + 清单 + 硬校验**，判据唯一化 | 治本（轻） | **无**（D1/D2） |
| **N 插件分层与命名** | 补 `Algorithm` / `ViewModel` 层，命名规范 + 守卫 | 治本（轻） | 无~低 |
| **C 参数模型解耦** | 拆 `ParamValue<T>`、按生命周期分层、完成 `ToolExecutionRequest` 迁移 | **治本（重）** | **有** |

> **前四段（A/B/D/N）全部可立即做，零到低破坏**；只有 C 需独立排期。

## 2. 基类审计（4 个基类 + 2 个约束）

| 基类 | 承载了什么 | 审计结论 |
|---|---|---|
| `ToolParameters` | ① 序列化元数据 `Version` ② **运行时注入态** `Context`/`NodeResults`/`ResolvedInputImage`（`[JsonIgnore]`）③ 分类查询方法（排除法）④ 行为 `Validate`/`CopyFrom` | ❌ **四类混装**；②与 `ToolExecutionRequest` **重复** |
| `MeasureGuideParameters` | 图像源（输入）+ 位置修正（输入 + 运行开关）+ 测量引导样式 + `BuildMeasureGuideItems()`（**渲染逻辑**） | ❌ 参数基类含 UI 样式与渲染职责 |
| `RoiParameters` | 区域输入集合 + 显示样式（`GraphicsStyle` + `System.Windows.Media.Color`）+ `GetRoisByType()`（运行时过滤） | ❌ 同上；类注释自认"**能力是集合，继承是树**" |
| `ToolResults` | 执行元信息 + `GetPropertyMap()`（声明式清单）+ `GetOutputVariables()`（SSOT）+ **`GetBindableOutputProperties()`（排除法）** + `AddResultItem` 动态结果 | ⚠ **两套判据并存**；且有一处纯冗余 |

### 2.1 七条具体发现

| # | 发现 | 证据 / 含义 |
|---|---|---|
| **F1** | **继承被当作"能力"用，项目自己承认了** | `MeasureGuideParameters.cs:17` 明写"**能力是集合，继承是树**"；而 P0.6-4 的解法是**再加一层继承**（`MeasureGuideParameters` → `RoiParameters`）⇒ **用继承缓解继承问题** |
| **F2** | **「输入与运行耦合」是已承认的问题，且解药已存在** | `ToolExecutionRequest.cs:15-17`：*"此对象将持久化的 `Parameters` 与本次运行的数据分开表达。**当前为兼容既有工具**，`ToolExecutor` 会在调用工具前将运行时字段映射到参数对象；**新入口和后续工具契约只应依赖此对象携带运行数据**。"* ⇒ **问题已知、解药已有、迁移未完成** |
| **F3** | 因此**运行时态有两条路径并存** | `parameters.Context/NodeResults/ResolvedInputImage` vs `ToolExecutionRequest.{NodeResults, ResolvedInputImage, NodeName, NodeId, CancellationToken}` |
| **F4** | **参数基类里有 UI 样式与渲染逻辑** | `RoiParameters.InspectionRoiStyle`/`MaskRoiStyle`（`GraphicsStyle`，`[JsonIgnore]`）+ `MeasureGuideParameters.BuildMeasureGuideItems()`（构建显示项） |
| **F5** | **`ToolResults` 内部两套判据并存 + 一处纯冗余** | 清单式 `GetPropertyMap()`（新，P0.6-5）vs 排除式 `GetBindableOutputProperties()`（旧，`:517-521`）；后者与 `GetOutputParameterProperties()`（`:508-512`）**过滤条件完全相同** ⇒ 冗余 |
| **F6** | `where TParams : ToolParameters, new()` 的 **`new()` 约束** | 要求无参构造 ⇒ 若将来输入/运行按能力组合注入，会被此约束卡住 |
| **F7** | **`PropertyMapEntry` 是成熟的声明式条目** | `ToolResults.cs:31-33`，record(`PropertyName, DisplayName, GroupName, IsGroupPlaceholder, DisplayInResultPanel`)，P0.6-5 已把"UI 硬编码中文分组名"改成声明式 ⇒ **参数侧清单形状照抄即可，不用另发明** |

### 2.2 审计结论（战略判断）

| 项 | 判定 |
|---|---|
| 输出侧清单范式 | ✅ **成熟**（record 形状 + 声明式 + 硬校验）→ **照抄** |
| 继承表达能力 | ❌ 不合理（项目自认）→ 改**组合 + 接口**（阶段 C） |
| 参数与运行时态 | ❌ 违反 SDK **自己写下的设计意图** → **完成 `ToolExecutionRequest` 迁移** |
| 参数基类含 UI 样式/渲染 | ❌ 职责不清 → 移出（阶段 C） |
| 两套判据并存 | ⚠ 要收口（阶段 D） |
| `new()` 约束 | ⚠ 阶段 C 评估放宽 |

> **最重要的一条**：**SDK 已经写下了正确方向**（F2 的注释 + F7 的声明式条目），只是**迁移没做完**。
> ⇒ 本方案**不是"重新设计基类"，而是"完成 SDK 已声明的迁移"** —— 风险与争议因此显著降低。

## 3. 区分三类参数的正确形态：接口 + 清单 + 硬校验

### 3.1 现状做法为什么不行

| 问题 | 说明 |
|---|---|
| 排除法 | `GetAllParameterProperties()` = 所有 public 属性减 `Version`；再减 `[IgnoreBind]` ⇒ **默认"一切都是输入参数"**，漏标即漏 |
| 运行参数无 SDK 判据 | 判据散在 UI 层（`TargetParameterViewModel.IsBindableParamForTargetBinding`） |
| 类型猜不出语义 | `string` 可能是运行参数（`FilePath`）、派生展示（`PositionCorrectionBindingDisplayText`）、结构（`SubroutineId`） |

### 3.2 机制选型：三难困境（必须显式取舍）

"属性级角色"要同时满足 A/B/C 是**不可能的**：

| 想要的 | ① 类型承载 `RuntimeParam<T> X` | ② 特性标注 `[RuntimeParam] double X` | ③ **接口 + 清单** |
|---|---|---|---|
| **A** 属性为原生类型 | ❌ | ✅ | ✅ |
| **B** 编译期强制（不可能漏） | ✅ | ❌ | ⚠ 类级强制，清单可漏写 |
| **C** 单一来源 | ✅ | ✅ | ❌ 清单与属性两处 |

| 选择 | 得到 | 放弃 | 谁在用 |
|---|---|---|---|
| 类型承载 | B + C | A | 现状（`ParamValue<T>`） |
| 特性标注 | A + C | B | 已否决 |
| **接口 + 清单** | **A + B** | C（用**硬校验**补） | **输出侧（`GetPropertyMap`）** ✅ |

**决策：采纳 ③ 接口 + 清单 + 硬校验**，理由：
1. 与输出侧**同一套范式**（不引入第三套）
2. **A 达成** —— 属性类型不动，`ParamValue<T>` 拆解推迟到阶段 C，**两件事解耦**
3. **B 达成** —— 类不实现接口编不过
4. **C 的缺口用两条硬校验补** —— 照抄输出侧"声明了但属性不存在 → `throw`"

### 3.3 契约定义（照抄 `IOutputContractProvider` / `PropertyMapEntry`）

```csharp
// 类级契约（消费者只依赖接口）
public interface IInputSlotContract     { IReadOnlyList<InputSlotDescriptor> GetInputSlots(); }
public interface IRuntimeParameterContract { IReadOnlyList<RuntimeParameterDescriptor> GetRuntimeParameters(); }
// 输出：沿用 IOutputContractProvider / GetPropertyMap()，不动

// 清单条目（形状对齐 PropertyMapEntry）
public sealed record InputSlotDescriptor(
    string PropertyName, string DisplayName, SlotKind Kind, bool Required = true);
public sealed record RuntimeParameterDescriptor(
    string PropertyName, string DisplayName, string? GroupName = null);

public enum SlotKind { Image, Roi, Geometry, Collection }
```

> ⚠ **命名避让**：`IRuntimeParameterProvider` **已被占用**（含义是"运行时注入键值池"：`CurrentImagePath`/`CurrentImage`/`ExecutionId`），新契约命名须用 `…Contract`。

### 3.4 基类与工具层写法（对称于 `GetPropertyMap`）


### 3.5 两条硬校验（补掉"两处维护"缺口）

| # | 校验 | 失败处理 |
|---|---|---|
| **V1** | 清单里声明的属性必须**存在** | **`throw`**（契约漏洞，照抄 `ToolResults.cs:600-601`） |
| **V2** | 类里 public 属性必须**都在清单里**（或明确不算参数） | 守卫测试失败并列出遗漏项 |

| 收益 | 说明 |

## 4. 工具层适配指南

### 4.1 减量表：大部分属性在 SDK 基类声明一次即可

| 声明位置 | 覆盖范围 | 属性 |
|---|---|---|
| `ToolParameters` | **18 个工具全部** | `Context`、`NodeResults`、`ResolvedInputImage` |
| `MeasureGuideParameters` | **14 个工具** | `ImageSource`、`ImageSourceRef`、`PositionCorrection*` |
| `RoiParameters` | **8 个工具** | `InspectionRois`、`MaskRois` |
| **各工具自己的参数类** | 逐工具 | 约 **105 个**运行参数属性（按 `ParamValue<` 次数 ÷ 2 估算） |

### 4.2 每个工具要做的 4 件事

| # | 动作 |
|---|---|
| 1 | 实现 `IRuntimeParameterContract` 并写运行参数清单 |
| 2 | 工具自有输入集合加入 `GetInputSlots()` 清单（继承来的已声明） |
| 3 | 结构字段**不写进清单**（即自动排除） |
| 4 | 中文名写进清单（替代 `[DisplayName]`） |

### 4.3 机械判定规则

```
属性是 ParamValue<T> 且 T ∈ {数值, 字符串, 枚举}  → 运行参数清单
属性是 RoiCollection / AvailableDataSource /
        ImageSourceReference / *Input 集合       → 输入槽位清单（继承来的已声明）
属性是 Template集合 / *Override集合 / *Config /
        *DisplayText / Id / Name / Code / Dir    → 不写清单（自动排除）
以上都不是                                       → 守卫测试报错（V2）
```

### 4.4 两个正交关注点，别混

| 关注点 | 用哪个 |
|---|---|
| 是否持久化 | `[JsonIgnore]`（**保留不动**） |
| 语义角色 | **清单**（新） |
| 中文显示名 | **清单的 `DisplayName`**（统一） |
| 是否可绑 | **由清单推出** ⇒ `[IgnoreBind]` 废弃 |

### 4.5 三道验证关

| 关 | 方法 | 通过标准 |
|---|---|---|
| 守卫测试 | 遍历 18 个工具：V1/V2 校验；运行参数必须有中文名；可绑集合在"空配置 / 有配置"下**一致** | 全通过 |
| 快照 diff | 适配前导出各工具可绑参数清单，适配后再导 | **只应减少**（结构字段消失），**不得丢失运行参数** |
| 回归 | 按 UI 方案 §14 验收表逐项比对 | 全通过 |

## 5. 工具插件分层与命名规范

### 5.1 目标分层（用户提出并经审计确认）

| 角色 | 现状 | 动作 |
|---|---|---|
| **输入槽位** | ❌ 无独立类（继承带进 `Parameters`） | 靠**清单**可见；`partial` 文件分区（可选） |
| **运行参数** | ⚠ 混在 `XxxParameters`（名实不符） | 靠**清单**可见 |
| **输出** | ✅ `XxxResults : ToolResults` | 保持 |
| **算法** | ❌ 混在 `XxxTool`（且依赖 WPF） | **抽 `XxxAlgorithm`** |
| **View** | ✅ `Views/XxxDebugControl` | 保持（剥离 VM 职责） |
| **ViewModel** | ❌ 基本缺失 | **补 `ViewModels/`** |

### 5.2 目录与命名规范

```
tools/SunEyeVision.Tool.Xxx/
├── XxxPlugin.cs              插件入口：只放 [Tool] 元数据 + 装配（不写算法）
├── XxxAlgorithm.cs           算法（可选：复杂才独立；不依赖 WPF/View/ViewModel）
├── XxxParameters.cs          运行参数
├── XxxParameters.Inputs.cs   输入槽位（partial，可选，零破坏"看得出"）
├── XxxResults.cs             执行产物 + 输出契约（保持现名）
├── ViewModels/XxxViewModel.cs
└── Views/XxxDebugControl.xaml(.cs)    纯 View
```

### 5.3 判定规则（可直接写成守卫测试）

| 后缀 | 职责 | **禁止依赖** |
|---|---|---|
| `Plugin` | 元数据 + 装配 | 算法细节、WPF |
| `Algorithm` | 纯计算：**输入值 + 运行参数 → 输出** | **WPF / View / ViewModel / 插件入口** |
| `Parameters` | 执行前配置 | WPF / View |
| `Results` | 执行产物 + 输出契约 | WPF / View |
| `ViewModel` | UI 数据 + 命令 | View（不得反向依赖） |
| `Control`/`Window`/`Dialog` | 纯 View | 算法 |

### 5.4 为什么不改名 `XxxResults`（决策记录）

| # | 理由 |
|---|---|
| 1 | 基类就叫 `ToolResults`，改了与基类不一致 |
| 2 | 它装的不只是输出值，还有执行元信息（`IsSuccess`/`ErrorMessage`/`ExecutionTimeMs`）⇒ `Outs` 丢语义 |
| 3 | `OutputVariable` 已存在（SDK）⇒ `Outs`/`Outputs` 会概念重叠 |
| 4 | 缩写不符项目命名习惯（项目用 `ToolResults`/`OutputVariable`） |
| 5 | **对称性**：`XxxParameters`（执行前配置）↔ `XxxResults`（执行后产物）是**对称的一对容器**，两侧都靠清单区分细节；改名破坏对称 |

### 5.5 更正（前轮口径）

上轮称"重命名有迁移成本（`JsonDerivedType` 判别符绑定）"——**实测不成立**：

```14:15:tools/SunEyeVision.Tool.ShapeMatch/ShapeMatchParameters.cs
[JsonDerivedType(typeof(ShapeMatchParameters), "ShapeMatch")]
public class ShapeMatchParameters : RoiParameters
```

判别符 `"ShapeMatch"` 是**独立字符串**，与类名无关 ⇒ **改类名只要不动字符串，老工程照读**。重命名是**重构**（IDE 批量），不是破坏性变更。

### 5.6 为什么不把"输入/运行"拆成两个类型（决策记录）

| # | 理由 |
|---|---|
| 1 | **同属"执行前配置"这一个生命周期**；分家的判据是生命周期，不是职责 |
| 2 | 算法层同用一个对象（`parameters.InspectionRois` 与 `parameters.MinMatchScore.Value`）⇒ 拆家要改 18 个入口 + 214 处引用 |
| 3 | **来源机制会分裂成两套**（`RoiCollection` 注释明写"支持常量模式和绑定模式"；运行参数也有绑定）⇒ 正好是要消灭的重复 |
| 4 | 序列化分两处 ⇒ 迁移风险 |
| 5 | 输入/运行互相引用（`IsPositionCorrectionEnabled` 作用于输入源；ROI 按模式过滤）⇒ 拆家要跨对象同步 |
| 6 | **重演 P0.6-4 的教训**（F1） |

> **结论**：角色可见性靠**清单 + partial 文件分区**解决；**不拆类型**。
> 真要拆，按**生命周期**（配置态 / 运行态 / 展示态）拆，属阶段 C。

## 7. 阶段 C：参数模型解耦（治本，破坏性）

### 7.1 病根二：`ParamValue<T>` 三职责同体

`ParamValue<T>` 自述装 4 件事（`ParamValue.cs:12-21`）：值 / 来源配置 / 展示文案 / 模式切换备份。

**同一个值存三份**（`ParamValue.cs:148-161`：`_value` 与 `_bindingConfig.ConstantValue` 同写，另有 `BindingConstantValue`）；
**绑定态覆盖用户常量**（`ParameterResolver.cs:217`）⇒ 必须靠 `BindingConstantValue` 抢救。

**注释写出了正确答案，代码没照做**：

```14:21:src/Plugin.SDK/Execution/Parameters/ParamSetting.cs
/// 核心概念：
/// 1. 绑定类型（BindingType）：回答"值从哪里来"
/// 2. 数据类型（DataType）：回答"值是什么类型"
```

**`ParamSetting` 6 种职责 + 一处自相矛盾**：`TargetType` 声明 `[JsonIgnore]` 称"无需序列化"（`:103`），`ToDictionary` **却序列化**（`:250-251`），`FromDictionary` **又读回**（`:324-331`）。

### 7.2 目标形态

```
节点
├─ 【输入槽位】InputSlots          ← 唯一职责：从外面进来的数据（含配置/运行/展示三态分明）
├─ 【运行参数】RuntimeParameters    ← 唯一职责：运行时可变的标量（**原生类型**）
├─ 【输出契约】OutputContract       ← 现状已解耦 ✅
└─ 【结构元数据】NodeMeta          ← 不算"参数"，从参数类搬出
旁路：参数来源表（按参数名）+ 本次运行取值（执行上下文快照，不覆盖参数属性）
```

### 9.4 依赖顺序

```
D1 新增契约(框架) ─→ D2 基类清单(框架) ─→ D3 硬校验+守卫(框架)
                                             │
                              ▼（工具等待框架就绪）
                     D4 工具补清单（约 105 条）
                                             │
                              ▼
                     D5 收口：删排除法 + 废弃 [IgnoreBind] + F5 判据合一

N1 命名规范+守卫 ─→ N2 抽 Algorithm/ViewModel(工具) ─→ N3 前缀统一 ─→ N4 改名

C1 ADR(决策) ─→ C2 ParamSetting 瘦身+改名 ─→ C3 拆 ParamValue + 迁移器（框架先行）
                                                          │
                                                          ▼（框架迁移器就绪后）
                                                    工具跟随改造
```

**硬依赖**：
1. **D4 必须等 D1~D3** —— 工具实现接口前，框架须先有接口与校验；
2. **工具跟随 C3 必须等迁移器就绪** —— 否则老方案打不开；
3. **C3 必须与 M5 的运行快照合并为同一工作包**。
