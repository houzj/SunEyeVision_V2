# 全局变量与运行快照端到端验证方案

## 1. 验证目标

验证节点参数从设计配置到运行快照的完整链路：

```text
全局变量管理器
  -> 节点 ParamSettings
  -> AlgorithmNode.ParameterBindingSet
  -> ToolExecutionRequest
  -> RuntimeParameterSnapshot
  -> 参数运行副本
  -> 工具执行
```

重点确认：

1. 普通 CLR 参数（`int`、`double`、`bool`、枚举）可以绑定全局变量并参与实际算法执行。
2. 运行时使用的是本次执行快照，设计期参数值不会被运行值覆盖。
3. 连续运行时每一批都重新解析快照，不会读取上一批的旧值。
4. 绑定解析失败时节点明确失败，后续依赖节点不会误用旧值。
5. 旧的 `ParamValue<T>` 工具仍能正常执行，迁移没有破坏历史方案。

## 2. CodeBuddy 执行边界

CodeBuddy 只负责：

- 按本方案创建测试方案和操作记录；
- 启动 Release 程序进行人工验证；
- 查看运行快照、节点结果和日志；
- 汇总截图、日志时间点和通过/失败结论。

CodeBuddy 不修改以下代码：

- `src/Plugin.SDK/`；
- `src/Workflow/AlgorithmNode.cs`、`WorkflowExecutionEngine.cs`；
- `src/UI/Services/Workflow/`；
- 全局变量绑定核心逻辑。

发现失败时先记录复现步骤、方案文件、输入值、日志和截图，交回 Codex 修复。

## 3. 测试准备

### 3.1 构建版本

- 使用当前工作区最新 Release 构建。
- 不使用旧安装包验证。
- 记录程序版本、构建时间和 Git 提交号。

### 3.2 测试工作流

创建一个最小工作流，包含：

```text
图像源1 -> 图像二值化1 -> Blob分析1 -> 结果显示
```

其中：

- 图像二值化1 的 `Threshold` 绑定全局变量 `GV_Threshold`；
- Blob分析1 的 `MinArea` 或等价纯 CLR 数值参数绑定全局变量 `GV_MinArea`；
- 至少保留一个未绑定参数，用于确认设计值未被影响；
- 保存方案后关闭并重新打开，确认绑定定义仍存在。

### 3.3 建议测试数据

准备一张能稳定产生 Blob 的灰度图，并记录预期结果：

| 变量 | 首次值 | 第二次值 | 预期影响 |
|---|---:|---:|---|
| `GV_Threshold` | 80 | 180 | 二值区域明显变化 |
| `GV_MinArea` | 20 | 5000 | Blob 数量或匹配状态变化 |

## 4. 测试用例

### E2E-01：绑定定义保存

操作：

1. 在全局变量管理器创建 `GV_Threshold`，类型为 `int`，初值 80。
2. 在目标参数管理或模块结果绑定入口，将图像二值化1 的 `Threshold` 绑定到该变量。
3. 保存方案，关闭并重新打开。

通过标准：

- 节点 `ParamSettings` 中存在 `Threshold` 绑定；
- 输入来源显示为全局变量；
- 目标参数页面显示绑定关系；
- 没有生成第二个输入控件或重复绑定记录。

### E2E-02：单次运行使用运行快照

操作：

1. 将 `GV_Threshold` 设置为 80。
2. 执行一次工作流。
3. 打开状态栏“执行快照”。

通过标准：

- 工作流成功执行；
- 二值化节点实际使用 80；
- 快照显示本次运行的节点状态和耗时；
- 设计界面中的参数仍显示绑定状态，不被改成常量 80。

### E2E-03：修改变量后再次运行

操作：

1. 将 `GV_Threshold` 改为 180。
2. 不重新绑定，直接再次单次运行。
3. 对比两次结果图和运行快照。

通过标准：

- 第二次运行使用 180；
- 结果图或 Blob 结果发生符合阈值变化的变化；
- 第二次快照显示新的运行批次；
- 第一次快照内容不被覆盖。

### E2E-04：连续运行批次隔离

操作：

1. 开启自动切图或连续运行。
2. 第一批使用 `GV_Threshold=80`。
3. 在批次切换前或下一批开始前修改为 180（按当前产品允许的变量修改入口操作）。
4. 连续执行至少 3 批。

通过标准：

- 每批使用自己的执行开始快照；
- 同一批执行期间不会因 UI 修改而中途改变；
- 下一批读取新值；
- 不出现上一批结果串入下一批的情况。

### E2E-05：设计参数隔离

操作：

1. 记录二值化1 的设计参数默认值和绑定状态。
2. 用全局变量执行一次，变量值设置为与设计默认值不同的值。
3. 执行结束后关闭调试窗口，再重新打开工具参数界面。

通过标准：

- 设计参数仍是“已绑定”状态；
- 不显示运行值被永久写回设计值；
- 解除绑定后才恢复/编辑本地常量值。

### E2E-06：解析失败处理

操作：

1. 将绑定源改为不存在的全局变量，或删除源变量。
2. 执行工作流。

通过标准：

- 当前节点状态为失败/NG，不显示成功；
- 日志包含参数名和绑定解析失败原因；
- 下游依赖节点被跳过或按现有失败策略处理；
- 不使用上一批次的旧运行值。

### E2E-07：旧工具回归

操作：

1. 使用仍保留 `ParamValue<T>` 的旧工具配置一个历史绑定。
2. 执行一次工作流。

通过标准：

- 旧工具仍能解析绑定并执行；
- 结果与迁移前基线一致；
- 不影响纯 CLR 工具的快照执行。

### E2E-08：不同入口一致性

分别从以下入口执行同一工作流：

- 主界面工具栏单次运行；
- 工作流 Tab 单次运行；
- 工具调试窗口单次运行；
- 连续运行入口。

通过标准：

- 绑定值来源一致；
- 节点结果一致；
- 快照均属于当前工作流和当前批次；
- 不出现某个入口读取设计值、另一个入口读取全局变量值的差异。

## 5. 必须采集的证据

每个失败或关键通过用例至少保留：

1. 全局变量当前值截图；
2. 目标参数/输入来源截图；
3. 执行快照截图；
4. 模块结果截图；
5. 对应时间段日志；
6. 工作流方案文件副本或方案名称；
7. 测试入口和运行批次号。

## 7. 验收结论

只有 E2E-01 至 E2E-08 全部通过，才能进入下一阶段：

1. 将更多工具迁移到纯 CLR 参数；
2. 缩小 `ParameterResolver.ApplyBindings` 的使用范围；
3. 删除全局变量管理器对 `ParamValue<T>` 的写入；
4. 最终移除旧反射绑定路径。
