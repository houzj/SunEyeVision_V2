## 3. 版本方案：四段版本号 + 单一真源 + 智能体自动推导

### 3.1 决策：产品版本采用**四段**（与 Windows 习惯一致）

**为什么否决原方案的三段 SemVer**（实测驱动）：

| 依据 | 说明 |
|---|---|
| **安装包版本资源要求四段** | Inno Setup 的 `VersionInfoVersion` 只接受 `a.b.c.d` 纯数字 ⇒ 三段+渠道后缀（`1.0.0-alpha.1`）**写不进去**；实测成品内测安装包右键属性**版本为空** |
| **全处一致** | 四段可同时喂给 exe `FileVersion`、安装包版本资源、注册表 `DisplayVersion`、界面"关于" ⇒ 用户在哪看到的都是同一个号 |
| **"一个版本号 = 一份产物"** | 第 4 段承载交付序号，重新出包必须递增 ⇒ 机制上消除"同版本号两份包、哈希不同"（已实际踩过） |
| **渠道不污染版本号** | 渠道改由安装向导显示名、产物名、发布清单承载 |

| 段 | 名称 | 谁决定 | 触发条件 |
|---|---|---|---|
| 1 | Major | 智能体标注 + 脚本计算 | 不兼容变更（老方案打不开、插件契约破坏） |
| 2 | Minor | 同上 | 向后兼容的新功能 |
| 3 | Patch | 同上 | 向后兼容的修复 |
| 4 | **Build（交付序号）** | **脚本自动** | 每次对外交付递增 |

### 3.2 五层版本语义（分层不变，示例改四段）

| 层 | 字段 | 目标值示例 | 用途 |
|---|---|---|---|
| **产品版本** | `InformationalVersion` | `1.0.0.1+1eb5aadc` | 界面/日志/清单/产物名 |
| 文件版本 | `FileVersion` | `1.0.0.1` | Windows 文件属性（**与产品版本一致**） |
| 程序集版本 | `AssemblyVersion` | `1.0.0.0` | 加载/绑定（**不随交付序号变动**，利于绑定稳定性） |
| 安装包版本 | `.iss AppVersion` + `VersionInfoVersion` | `1.0.0.1` | 注册表 `DisplayVersion`、安装包属性、产物名 |
| **方案文件格式版本** | `Solution.SchemaVersion`（**新增**） | `2`（整数，单调递增） | **迁移器**；与产品版本**解耦** |

> `SchemaVersion` 的必要性来自 2026-09-18 实测 BLOCKER：Codex 将 ImageThreshold/ImageFilter/BlobAnalysis/Morphology 参数改为纯 CLR 后，旧方案文件（`"Method": { "Value": 32, "BindingConfig": … }` 包装形态）**直接加载失败**（`JsonException @ $.Parameters.Method`），用户被迫删除历史方案。

### 3.3 单一真源（已按"甲"实施）

| 方案 | 落点 | 优点 | 代价 |
|---|---|---|---|
| **甲（推荐，零禁区）** | 仓库根 `version.json` | 零禁区改动；脚本/CI/清单/文档共用；提升版本只改一处 | 直接 `dotnet build` 时程序集版本仍为 SDK 默认（**仅走打包脚本才正确**） |
| **乙（治本，需授权）** | `Directory.Build.props` 加 `<Version>` | 任何构建都带正确版本（.NET 正统） | **rule-021 禁区**，需明确授权；须避免与甲形成双真源 |

`version.json` 建议结构：

```json
{
  "version": "1.0.0",
  "channel": "alpha",
  "revision": 1,
  "releaseDate": "2026-09-18",
  "schemaVersion": 2
}
```

⇒ 脚本组装产品版本：`1.0.0-alpha.1`（`stable` 时不带后缀）。

### 3.4 版本号规范

| 项 | 规则 |
|---|---|
| 格式 | **四段**：`MAJOR.MINOR.PATCH.BUILD`（如 `1.0.0.1`） |
| 第 4 段 | **交付序号**：每次对外交付递增；**同一版本号不得对应两份产物** |
| 渠道 | `alpha`（内测）/ `beta`（公测）/ `rc`（候选）/ `stable`（正式）；**不进版本号** |
| 渠道承载 | 安装向导/程序组显示名 `（内测版）/（公测版）/（候选版）`、产物名 `-alpha-`、清单 `channel` |
| 程序集 | `AssemblyVersion` 固定 `MAJOR.MINOR.PATCH.0`（**不随交付序号变动**） |
| 文件版本 | `FileVersion = 产品版本`（四段，与用户可见号一致） |
| 追溯 | `InformationalVersion = <产品版本>+<commit>`（工作区脏时清单记 `dirtyFileCount`） |
| 安装包 | `AppVersion = VersionInfoVersion = 产品版本`；产物名 `SunEyeVision-Setup-<产品版本>-<channel>-x64.exe` |
| **升级语义** | Inno **不做自动版本比较**；升级判定依赖固定 `AppId`。内测版与正式版并存须用**独立 AppId + 独立安装目录**（脚本 `-Coexist`） |

### 3.5 版本自动推导（智能体驱动，免人工填号）

**原理**：提交信息已是规范的 Conventional Commits，本身就编码了"改动性质" ⇒ 版本号可由提交历史**确定性推导**，不需要任何人判断或手填。

| 提交信息 | 判定 | 版本变化 |
|---|---|---|
| `feat!:` / `fix!:` / 正文含 `BREAKING CHANGE` | 不兼容变更 | **MAJOR +1**（后三位归 0） |
| `feat:` | 新功能 | **MINOR +1**（第三位归 0） |
| `fix:` / `perf:` | 修复 / 性能 | **PATCH +1** |
| `docs:` / `chore:` / `refactor:` / `test:` / `build:` | 非功能变更 | 不动（进 CHANGELOG 分类） |
| 只有"不动"类 | 无可推导项 | **BUILD +1**（仅递增交付序号） |

**推导实现**

```
Pack-Release.ps1 -AutoVersion            # 建议为默认；不传版本参数即自动推导
  1) 读 version.json：当前版本 + 基线提交 releasedCommit
  2) git log <releasedCommit>..HEAD --pretty=%s  → 全部提交标题
  3) 按上表归并（取最高级别）→ 得 MAJOR/MINOR/PATCH.BUILD
  4) 写回 version.json（并更新 releasedCommit = 当前 HEAD）
  5) 自动向 CHANGELOG.md 追加该版本条目（按 type 分组）
  6) 继续：构建 → 打包 → 校验 → 清单（可选 -Tag）
```

**首次基线**：以本次发版为起点写入 `releasedCommit`，历史提交不参与推导（规避历史不规范提交造成的误判）。

**自校验（防漂移）**：打包脚本产出的版本必须等于推导结果；若人工传了 `-Version` 且与推导结果不一致 ⇒ **拒绝打包**（防手填错号）。

**示例（用真实提交历史）**：当前版本 `1.0.0.0`，基线后的提交中含 `feat(workflow): …` ⇒ 推导为 **`1.1.0.0`**；
而本轮人工填的是 `1.0.0-alpha.1` ⇒ **人工方式确实会漏判**，这正是要交给机器算的理由。

### 3.6 分工：谁负责什么（直白）

| 环节 | 责任方 | 说明 |
|---|---|---|
| **标注"是不是不兼容改动"** | **智能体** | 写提交信息时即判断，不兼容打 `!:`。**机器无法从 diff 看出**（如"方案文件格式变更"），必须由改动者标注 |
| **算下一个版本号** | **脚本** | §3.4 的机械计算，不依赖任何人的"感觉" |
| **写变更日志** | **脚本** | 按 `type` 分组自动生成条目 |
| **校验版本与产物一致** | **脚本** | 推导结果 vs 产物版本串不一致 ⇒ 拒绝打包 |
| **决定"现在发不发"** | 人（一句"发内测版"） | 交付时机是业务决定；**不涉及版本号管理** |
| 改版本号 | **无人** | 由脚本写回真源 |

> **结论：从此不存在"人工填/判断版本号"这个动作** —— 版本号是提交历史的必然结果。

## 10. 验收标准

| 组 | 条目 |
|---|---|
| **自动推导** | 不传版本参数即可出包；推导结果与提交历史一致（含 `feat:`→Minor、`fix:`→Patch、`!:→`Major）；人工传入值不一致时**拒绝打包** |
| 真源 | `version.json` 是唯一版本来源；源码**无**版本号字面量（扫描 + 守卫测试通过）；含 `build` 与 `releasedCommit` |
| 版本一致 | **四段全处一致**：exe `FileVersion`、安装包版本资源、注册表 `DisplayVersion`、界面"关于"、产物名 |
| **安装包版本** | 右键属性显示版本（当前为空 ⇒ 待补 `VersionInfoVersion`） |
| 追溯 | 产物 `ProductVersion` 的 commit == 打包时 HEAD；清单含版本/渠道/commit/SHA256 |
| 内测版 | 可产出 `dist\SunEyeVision-Setup-<版本>-alpha-x64.exe`；安装向导显示"（内测版）"；`-Coexist` 时不覆盖正式版 |
| 图标 | 软件图标含 16~256 多尺寸；`.solution` 图标与软件图标同源一致；注册表路径**有效**；双击 `.solution` 可打开 |
| 自愈 | 程序换目录后重新运行 ⇒ 关联路径自动更新（无需手工改注册表） |
| 治理 | rule-022 入表；「版本发布」skill 可一条指令走完发版 |
