## 0. 一句话

**交付版本统一（一个安装包一个版本号）；契约版本显式声明并以 `2.0` 为当前基线；工具和 SDK 默认跟随产品版本。**

---

## 1. 先把三个词说清楚

| 词 | 大白话 | 谁持有 | 变不变 |
|---|---|---|---|
| **交付版本** | "这批货是第几版"（`2.0.0.1`） | `version.json`（唯一真源） | ✔ 每次打包第 4 位 +1 |
| **契约编号** | "接口标准是第几版"（`2.0`） | `ToolContractVersionAttribute` + `ToolContract` | ✘ 除非接口不兼容才变 |
| **绑定身份** | "程序集的身份证号"（`2.0.0.0`） | 构建配置（`Directory.Build.props`） | 2.x 内恒定 |

三者**互不推导**。它们唯一的接触点是"宿主按契约编号决定放行/拒绝插件"。

---

## 2. 一个 dll 里有三个字段，各放各的

| 字段 | 放什么 | 谁看它 |
|---|---|---|
| `FileVersion` | **交付版本** `2.0.0.1` | 人：资源管理器"详细信息"、关于窗口、售后定位 |
| `InformationalVersion` | **交付版本 + 提交 SHA** `2.0.0.1+4bfe67c5` | 人：排查"这是哪一次构建" |
| `AssemblyVersion` | **绑定身份** `2.0.0.0`（2.x 恒定） | 机器：CLR 程序集绑定 |

⇒ **"统一"指的是前两个字段统一成产品版本；第三个字段恒定不动。** 不是把三个合成一个。

## 4. 为什么 `AssemblyVersion` 不能跟交付版本统一（今日事故实录）

**历史判定机关**：旧实现读取插件编译时引用的 SDK 程序集版本。当前实现改为读取插件程序集显式声明的 `ToolContractVersionAttribute(2,0)`，契约语义与 `AssemblyVersion` 分离。

**事故时间线**（日志可查）：

| 时间 | 构建 | 结果 |
|---|---|---|
| 10:25 / 10:29 / 10:51 | 改动前 | `插件加载完成：成功 18 个，未加载 0 个` |
| **11:56** | 版本注入后（Debug） | `成功 0 个，未加载 18 个` ⚠ |
| **13:00** | 版本注入后（Release） | `成功 0 个，未加载 18 个` ⚠ |
| 13:07 | 修正后 | 拒载错误 0 条，插件恢复 ✅ |

**原因**：把产品版本注入到 `AssemblyVersion`，使 `SunEyeVision.Plugin.SDK.dll` 的主版本由 `1` 变成 `2` ⇒ 18 个工具全部被判"契约不兼容"。

**推论**：只要兼容判定还读这个字段，它就必须恒定 —— 否则**主程序每次大版本升级都要求 18 个工具全部重编**，"工具可独立迭代"直接失效。

> 当前已把契约语义迁移到显式元数据；`AssemblyVersion=2.0.0.0` 只承担 2.x 程序集绑定身份。

### 4.1 标准软件工程里怎么管理（依据）

**① 官方分工**（.NET 设计本意，非本项目自创）：

| 字段 | 官方定位 | 谁消费 |
|---|---|---|
| `AssemblyVersion` | **绑定身份**：加载器据此解析引用；改变它 = 对引用方不兼容 | 编译器 / 运行时加载器 |
| `AssemblyFileVersion` | **文件版本**：供 Windows 文件系统显示 | 资源管理器"详细信息" |
| `AssemblyInformationalVersion` | **产品/包版本**：供人与包管理器识别（可带 `+SHA`） | NuGet、安装包、售后 |

> 官方依据：.NET《Versioning and .NET libraries》（learn.microsoft.com/dotnet/standard/library-guidance/versioning）、Microsoft KB 556041《Use AssemblyVersion and AssemblyFileVersion attributes》。

**② 行业实例（本机实测，可自行复核）** —— .NET 运行时自己的 `System.Private.CoreLib.dll`：

| 运行时版本 | `FileVersion` | `ProductVersion` | `AssemblyVersion` |
|---|---|---|---|
| 10.0.12 | `10.0.1226.42308` | `10.0.12-servicing.26422.108+95017c7…` | **`10.0.0.0`** |
| 9.0.14 | `9.0.1426.11910` | `9.0.14+19c0782…` | **`9.0.0.0`** |
| 8.0.31 | `8.0.3126.42015` | `8.0.31+1219a42…` | **`8.0.0.0`** |

复核命令（PowerShell）：

```powershell
$dll = Join-Path $env:ProgramFiles 'dotnet\shared\Microsoft.NETCore.App\9.0.14\System.Private.CoreLib.dll'
(Get-Item $dll).VersionInfo | Format-List FileVersion, ProductVersion
[System.Reflection.AssemblyName]::GetAssemblyName($dll).Version      # -> 9.0.0.0
```

⇒ **与本方案 §3 完全同构**：`AssemblyVersion` 恒为 `major.0.0.0`；发版进度放在 `FileVersion`/`ProductVersion`；`ProductVersion` 带 `+提交SHA`。即：本方案选的结构，就是 .NET 运行时自己采用的结构。

**③ 三种流派与选择**：

| 流派 | `AssemblyVersion` | 适用 | 代价 |
|---|---|---|---|
| **A 显式恒定**（本方案采用） | 固定 `2.0.0.0`（2.x） | 有外部引用方／插件体系／多批交付 | 程序集版本不反映发版进度（由 `FileVersion` 承担） |
| B 跟随产品 `major.minor` | `2.0.0.0` → `2.1.0.0` | 单体应用、无外部引用方 | 次版本升级可能需引用方重定向/重编 |
| C 跟随完整版本 | 每次构建都变 | ❌ 不推荐 | 引用方几乎必然失效 |

**④ ⚠ 最易踩的坑："不管它" ≠ "用框架默认"**

| 以为的"不管" | 实际发生的事 |
|---|---|
| ".NET SDK 会自动处理" | SDK 的**默认行为是 `AssemblyVersion = $(Version)`** ⇒ 自动跟随产品版本 ⇒ 每次发版都换绑定身份 ⇒ 18 个工具全挂（§4 事故） |

实测印证：`Version=2.0.0.1` ⇒ SDK 默认产出 `AssemblyVersion=2.0.0.0`（后两位按约定归 0）。
⇒ **对有引用方的产品，"不管"是最危险的选项**，必须**显式声明并锁死**。

**⑤ 因此本项目的"管理"落在四处**：

| 管理动作 | 落点 |
|---|---|
| 声明一次 | `Directory.Build.props` 显式 `<AssemblyVersion>1.0.0.0</AssemblyVersion>` |
| 变更时机 | 仅当契约不兼容（`ToolContract.Major` 升级）时才允许改 |
| 用测试锁住 | §7-4 守卫：断言 SDK 程序集主版本 == `ToolContract.Major`（本次事故正因无人锁住） |
| 文档化 | 本方案 §4 + `Directory.Build.props` 注释中的陷阱说明 |

**⑥ 本项目的契约语义已独立于 `AssemblyVersion`**：插件通过 `ToolContractVersionAttribute` 声明契约，宿主读取该元数据判定兼容；`AssemblyVersion` 只作为 2.x CLR 绑定身份。

## 5. 兼容规则（最终三条）

```
放行 ⇔ ① 工具声明的契约主版本 == 宿主契约主版本（2）      ← 已实现
        ② 工具声明的契约次版本 <= 宿主契约次版本（0）      ← 已实现
        ③ 工具只依赖契约层（SDK），不依赖产品程序集        ← 16/18 个工具现在违规
```

| 条 | 解决的问题 | 现状 |
|---|---|---|
| ① | 接口形状是否兼容 | ✅ 已实现 |
| ② | 防"新工具装到旧宿主"：判定通过但运行时找不到新接口而崩 | ✅ 已实现 |
| ③ | 防"契约通过了、实际跑不起来"：工具绑在随主程序版本变化的 `HalAdapter` 等产品程序集上 | ❌ 实测 **16/18** 个工具越界（仅 `Condition`、`Subroutine` 只依赖 SDK） |

## 6. 工具版本规则：当前统一跟随产品

```
工具 csproj 没写 <Version>  →  跟产品版本（2.0.0.1）
SDK 包和工具包             →  跟产品版本（2.0.0.1）
```

**为什么统一跟随**：18 个工具同批构建、进入同一个安装包，没有独立交付通道；统一后现场只需报告一个产品版本即可定位全部内容。

**为什么不设"共享默认值"文件**：共享默认值会让工具们隐式一起走，且掩盖"忘了声明"；本规则下"没写"本身就是一个有意义的语义（= 跟随产品）。

**现状**：18 个工具和 SDK 均跟随产品版本；只有未来真正对外独立发布 SDK 或插件时，才另行引入独立包版本。

**配套要求**：`Directory.Build.props` **不要写死** `FileVersion`，要让各项目自己的 `Version` 自然流入各自的 `FileVersion`（否则将来某工具写了 `<Version>1.2.0</Version>`，它的 `FileVersion` 仍是产品版本）。
