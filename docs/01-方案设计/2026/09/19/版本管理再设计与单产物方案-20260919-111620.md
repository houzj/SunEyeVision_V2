## 0. 改前 / 改后 / 依据（用户视角）

### 改前

| 现象 | 用户感受 |
|---|---|
| 同一个程序"报出 5 个不同版本"：真源 `1.0.1.0`、载荷 `1.0.0`、启动画面 `版本 2.0.0`、关于 `v1.0.0.0`、安装包 `1.0.0.1-alpha`/`1.0.1.0-alpha` | "到底哪个才是我的版本？" |
| 打了两次包，`dist` 里就多出两组产物 | "怎么会有两个安装包？我只要内测版" |
| 只是提交了一个"记录发布"的提交，下次打包版本号就变了 | "代码没改，版本号凭什么变？" |
| 不经打包脚本直接 `dotnet build -c Release`（今天 10:48 发生过） | 载荷版本**回落成 `1.0.0`** —— 版本丢了 |

### 改后

| 改进 | 用户感受 |
|---|---|
| **版本号由人声明**（写在唯一真源里），打包不再"发明"版本 | 版本可评审、可预期；**重复打包不会升号** |
| **构建即带版本**：任何构建方式（含裸 `dotnet build`）都注入真源版本 | 载荷不再回落 `1.0.0` |
| 程序自己能报版本（单一 API），启动画面/关于/配置对话框全部读它 | 界面显示的版本**是真的** |
| 打包产出**唯一一个**产物：同名产物已存在则拒绝，打包后清掉非当前版本的旧产物 | `dist` 永远只有一组 |
| 提交 SHA 只作为**构建元数据**附加（`1.0.1.0+<sha>`），不再影响版本号 | 版本号与"提交了几次"解耦 |

### 依据（一句话）

> 版本是**产品的属性**，应由产品自己声明（改前由打包脚本按提交信息的措辞临时推导）；每次"交付"的差异属于**构建元数据**，不属于版本号。依据 SemVer 2.0.0 规则 10（构建元数据不参与版本优先级）与规则 3（已发布版本内容不可修改）。

### 1.1 版本的决定权错位

| 发现 | 来源 |

| 推导区间 = `releasedCommit..HEAD` | [来源] `installer/Pack-Release.ps1:85` |

## 2. Bug 模式分析（Phase 0.5）

**当前 bug**：同一逻辑版本存在 5 个不同版本串；重复打包即升号；裸构建载荷版本回落 `1.0.0`。

**真因分类**：**设计缺陷**（架构层面注定要出问题）—— 版本的**决定权**被放在打包脚本的提交推导里，而**不是产品的真源**；同时"界面显示"没有唯一的读取入口。

**同类潜伏点**（同一 pattern：把版本/版本身份写死在别处）

| # | 位置 | 说明 | 来源 |
|---|---|---|---|
| 1 | `Directory.Build.props:45,47` | Release 输出路径名写死 `SunEyeVision_v1.0.0`（第三个"版本"） | [来源] `Directory.Build.props:45,47` |
| 2 | `Directory.Build.targets:41,168` | 同上，插件与调试根目录路径写死 | [来源] `Directory.Build.targets:41,168` |
| 3 | `run_rule_checker.bat:12,23` | 规则检查器路径写死同一目录名 | [来源] `run_rule_checker.bat:12,23` |
| 4 | `installer/SunEyeVision.iss:58` | `ReleaseDir` 默认值写死同一目录名（已有 `#ifndef` 保护） | [来源] `installer/SunEyeVision.iss:58` |
| 5 | 界面三处假版本 | 同 §1.3 | [来源] 同上 |
| 6 | 无 tag | 版本与提交无绑定标记 | [来源] §1.5 |

**治本点**：让"版本"只有**一个可手改来源**（`version.json`），并且
① **编译期**被注入程序集（任何构建方式都带版本）、
② **运行期**有唯一读取 API（程序自报版本）、
③ **打包期**只做"读取 + 一致性校验 + 唯一产物"。
⇒ 修复"决定权错位"这个治本点，而非"每次打包记得传 `-p:Version`"这个症状点。

**治本验证判据**：改后**裸 `dotnet build -c Release`（不带任何版本参数）产出的程序集，版本串必须等于真源**；且**重复打包同一真源版本号不发生变化**。

| 设计决策 | 支撑依据 |

## 4. 方案对比（≥3 候选 + 长期 ROI）

| 维度 | **方案 A（推荐）** 真源人工声明 + 构建期注入 + 打包只读/校验/唯一产物 | 方案 B 真源人工声明，但打包保留推导作"建议" | 方案 C 维持现状 git 推导，仅加 `dist` 清理 |
|---|---|---|---|
| 实现方式 | 版本由人写进真源；`Directory.Build.props` 读真源注入程序集；打包读真源 + 四方校验 + 唯一产物 | 同 A，但另留 `-AutoVersion` 输出"建议升号"（不自动写回） | 不动推导；只在打包后清理旧产物 |
| 与架构一致性 | ✅ 版本成为**编译期属性**，与"单一配置文件集中注入"的既有做法一致 | ✅ | ❌ 版本仍由打包时刻决定 |
| 复杂度 | 中（改 props + 新增 `AppVersionInfo` + 脚本收敛） | 中高（两套语义并存） | 低 |
| 维护成本 | **低**：行为可预测（打包不改版本、不改代码） | 中：仍需解释"建议是什么、谁采纳" | 高：每次发版都要解释"为什么升号/为什么两个包" |
| 扩展性 | 高（新增渠道/预发布/tag/交付序号规则清晰） | 中 | 低 |
| 长期 ROI | 6 月：消除困惑；1 年：版本可追溯/可离线打包；3 年：多产品线可复用同一真源约定 | 6 月可用；1 年后仍会被"到底谁定版本"反复质疑 | 每次发版都付解释成本，问题不消失 |

**推荐方案 A**，理由：
1. 直接消除用户提出的三个痛点（推导不合理 / 程序应自持版本 / 只出一个产物）；
2. 有 SemVer 规则 3·10 与 NBGV 官方做法支撑，不是自创；
3. 修掉 §1.2 的"裸构建回落 `1.0.0`"根因（版本不再依赖"谁记得传参数"）。

## 5. 目标设计

### 5.1 真源与四位归属（2026-09-19 用户确认）

**四位定义与"谁管哪一位"**（用户口径）：

| 位 | 名称 | 含义 | 谁来定 |
|:--:|---|---|---|
| 1 | **主版本号 Major** | 重大更新 / 架构重构 / 不兼容旧版本 | **人工审核**（智能体只能"建议"，不得擅改）· **当前 = 2** |
| 2 | **次版本号 Minor** | 新增功能、向下兼容 | **智能体**（按判据维护） |
| 3 | **修订号 Patch** | 只修 Bug、安全补丁、小优化 | **智能体** |
| 4 | **构建号 Build** | **打包次数**，区分"同一份代码第几次构建"，主要用于内部追踪 | **机器自动**（每次打包 +1） |

**真源只写前三段 + 一个机器维护的构建计数**：

```jsonc
// version.json —— 唯一真源；打包脚本只读前三段，永不改写第 1/2/3 位
{
  "version": "2.0.0",        // 三段：人工审核(第1位) + 智能体(第2/3位)；升 Minor/Patch 时低位归零
  "build": 1,                // 构建号：机器维护（每次打包 +1），智能体/人不得手改
  "channel": "alpha",        // alpha | beta | rc | stable，不进版本号
  "releaseDate": "2026-09-19",
  "schemaVersion": 2         // 方案文件格式版本，与产品版本解耦
}
```

- **删除** `releasedCommit`（推导机制的产物，一并移除）。
- **第 1 位立即由 1 对齐到 2**（用户确认：主版本 = 2）⇒ 起始交付版本 `2.0.0.1`。
- 第 4 位保留的理由：Inno `VersionInfoVersion` 只接受四段纯数字；渠道以安装显示名（`SunEyeVision（内测版）`）与产物名后缀表达。
- **第 4 位语义 = 甲（打包次数）**：打包时 `build + 1` ⇒ 四段版本 `2.0.0.<build>`，打包成功后写回真源 `build`（**这是脚本唯一允许写的字段**，第 1/2/3 位永不自动改）。

### 5.2 构建期注入（机械，唯一路径）

在 `Directory.Build.props` 读取真源并注入，**任何构建方式**都生效：

```xml
<_VerJson>$([System.IO.File]::ReadAllText('$(MSBuildThisFileDirectory)version.json'))</_VerJson>
<Version>$([System.Text.RegularExpressions.Regex]::Match($(_VerJson), '"version"\s*:\s*"([^"]+)"').Groups[1].Value)</Version>
<FileVersion>$(Version)</FileVersion>
<AssemblyVersion>$([System.Text.RegularExpressions.Regex]::Match($(Version), '^(\d+\.\d+\.\d+)\.\d+$').Groups[1].Value).0</AssemblyVersion>
```
- SDK 会自动把 `AssemblyInformationalVersion` 变成 `<Version>+<sha>`（现状已如此，如 `1.0.1.0+49a59e47…`）⇒ 提交可反查，且 SHA 属**构建元数据**、不进版本号。
- 渠道/发布日期经 `<AssemblyMetadata Include="Channel" Value="…"/>` 注入，供运行期读取（避免真源成为运行期依赖）。

### 5.3 程序内自报版本（消灭三处假版本）

新增 `AppVersionInfo`（`src/Core/Versioning/`）：

| 成员 | 来源 |
|---|---|
| `Product` | `AssemblyInformationalVersion` 的 `+` 之前部分（如 `1.1.0.0`） |
| `Commit` | `+` 之后部分（如 `95cd1095…`） |
| `Channel` / `ReleaseDate` | 注入的 `AssemblyMetadata` |
| `Display` | 如 `1.1.0.0（内测版）` |
| `Full` | `1.1.0.0+95cd1095…` |

`SplashScreen.xaml:85`、`AboutWindow.xaml:37,46`、`SolutionConfigurationDialog.xaml.cs:53` 全部改绑它。

### 5.4 打包作业（收缩为：读 → 校验 → 唯一产物）

| 步 | 动作 |
|---|---|
| 1 | **读**真源（不推导、不写回） |
| 2 | **四方校验**（任一不一致 ⇒ `Fail`，逐条打印不一致项）：① 真源 `version` == 载荷 `ProductVersion` 前缀；② 真源 `channel` == 产物名后缀 == 安装显示名；③ 真源 `version` 为四段纯数字（Inno 约束）；④ 工作区干净（`-AllowDirty` 可放行，并写入清单 `dirtyFileCount`） |
| 3 | 计算构建号：`build = 真源.build + 1` ⇒ 四段版本 `2.0.0.<build>` |
| 4 | 打包（ISCC 一次，产物名形如 `SunEyeVision-Setup-2.0.0.<build>-alpha-x64.exe`） |
| 5 | 打包成功后：**删除 `dist` 中所有非本次产物**（旧版本安装包与其清单）⇒ **`dist` 恒为「1 个安装包 + 1 个清单」** |
| 6 | 写回真源 `build`（仅此字段）；输出清单、CHANGELOG 条目、可选 tag `v2.0.0.<build>[-<渠道>]` |

### 5.5 守卫（契约测试）

`VersionConsistencyTests`：
1. 真源存在、四段纯数字、`channel` ∈ {alpha,beta,rc,stable}；
2. **程序集版本 == 真源版本**（防"注入失效"）；
3. 源码**禁止版本号字面量**（`v?\d+\.\d+\.\d+`，路径名白名单除外）；
4. 界面 XAML 不含 `版本 \d+\.\d+` 字面量（防假版本回潮）；
5. `Pack-Release.ps1` 不含提交类型推导关键字（防推导机制回潮）。

## 8. 防御机制

## 12. rule-022 修订要点
