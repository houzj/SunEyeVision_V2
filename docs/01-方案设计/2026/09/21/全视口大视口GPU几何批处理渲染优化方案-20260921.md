# 全视口/大视口 GPU 几何批处理渲染优化方案

日期：2026-09-21  
适用范围：Blob、轮廓、旋转矩形、质心、杆件及其他大批量结果图元  
关联基线：`docs/01-方案设计/2026/09/19/大批量结果渲染架构基线-20260919.md`

## 1. 结论

当前 `ResultTileHost + DrawingVisual + StreamGeometry` 方案已经改善了局部视口的缩放和平移，但不能解决全视口/大视口性能问题。

2026-09-21 单例日志 `logs/2026/09/21/SunEyeVision_081158.txt` 已确认：

```text
图像：5120×5120
Blob：3000
批量几何 Tile：322
首次全视口绘制：594.2 ms
首次刷新总耗时：599.4 ms
自动诊断：composite-geometry-heavy
```

局部放大后多数刷新为 0.2–12 ms。因此当前主因不是 Tile 数量或 WPF Visual 管理，而是全视口下仍然需要对大量复杂 `StreamGeometry` 执行实际几何绘制。

本方案不把“位图替代矢量图”作为主方向，而是将结果图元编译为连续的 GPU 几何批次，减少逐对象、逐 Tile 的绘制调用和重复计算。

## 2. 核心设计

```text
完整算法结果
    ↓
后台几何编译器
    ├── 连续 VertexBuffer
    ├── Index/RangeTable
    ├── Tile → Range 空间索引
    └── Style Batch
    ↓
一个 GPU 结果画布
    ├── OK 轮廓 Batch
    ├── NG 轮廓 Batch
    ├── 矩形 Batch
    ├── 点/十字 Batch
    └── 选中/编辑 Overlay
    ↓
仅更新 Transform、样式和可见范围
```

关键变化：

1. Tile 只负责空间索引、命中候选和局部范围管理，不再把每个 Tile 当作一个 WPF `DrawingVisual`。
2. 同类、同样式图元连续存储并批量提交，不再逐个 `StreamGeometry` 绘制。
3. 缩放和平移只更新变换矩阵，不能触发完整几何重建。
4. 结果选择、ROI、卡尺和高亮保留独立交互层，只绘制少量动态对象。

## 3. 数据结构

### 3.1 轮廓批次

```text
ContourBatch
    VertexBuffer      所有轮廓点连续存储
    RangeTable        BlobId → 起始偏移、点数、Bounds
    TileRanges        Tile → 顶点范围
    Style             OK/NG、颜色、线宽、绘制模式
```

3000 个 Blob 不再对应 3000 个 WPF 图形对象，而是按颜色、线宽和绘制模式拆成少量 Batch。

### 3.2 Tile 的新职责

```text
Tile
    ├── 记录相交图元范围
    ├── 提供命中测试候选
    ├── 提供局部更新范围
    └── 提供可见范围裁剪
```

Tile 不负责创建 WPF Visual，也不负责独立提交一套复杂几何。

## 4. 渲染后端

### 4.1 首选：Direct3D 11 顶点批处理

高批量结果层使用一个长期存在的 GPU 结果画布：

- 顶点数据上传一次；
- 按 Batch 设置颜色、线宽和绘制模式；
- 每帧只更新缩放/平移矩阵；
- 每个样式批次执行一次 Draw；
- 不为每个 Tile 创建 `D3DImage`。

轮廓线宽不依赖 WPF Stroke。需要粗线时，将中心线在顶点阶段扩展为三角形带，避免每次缩放重新生成 WPF 几何。

### 4.2 过渡：Direct2D Geometry Realization

如果第一阶段不能立即引入完整 Direct3D 11 管线，可使用 Direct2D Geometry Realization 缓存静态几何的 tessellation，降低重复几何处理成本。

该方案是过渡后端，不改变结果模型和 Tile 空间索引。

### 4.3 不推荐的方向

- 继续增加 WPF `DrawingVisual` 数量；
- 继续把每个 Tile 作为独立复杂几何提交；
- 每次缩放重新生成 `StreamGeometry`；
- 每个 Tile 使用一个 `D3DImage`；
- 仅通过调整 Tile 大小解决全视口问题。

## 5. 与 WPF 的边界

```text
WPF 层
    ├── 图像显示
    ├── 参数和图层开关
    ├── 交互事件
    ├── ROI/卡尺
    └── 少量选中高亮

GPU 结果层
    ├── 大量轮廓
    ├── 大量矩形和点
    ├── 批量颜色与线宽
    └── 平移缩放
```

WPF 结果层保留为小数据量和兼容后端：

```text
ResultRenderer
    ├── WpfGeometryRenderer
    └── GpuBatchRenderer
```

算法工具不依赖 WPF，也不直接创建 GPU 资源。GPU 资源由渲染编译层和渲染后端管理。

## 6. 图像切换和结果一致性

显示图像切换时，结果层必须使用独立的 `ImageIdentity` 和 `RenderGeneration`：

```text
切换图像
    ↓
生成新的 ImageIdentity
    ↓
取消旧几何编译和 GPU 上传任务
    ↓
清空旧 Batch/Ranges/Tile 映射
    ↓
加载与新图像匹配的结果
    ↓
重新编译并提交新 Batch
```

禁止复用不同图像的几何缓存，即使图像尺寸相同也不能仅按宽高判断相同。

异步任务回写前必须同时验证：

```text
ImageIdentity 相同
RenderGeneration 相同
结果节点 ID 相同
```

否则直接丢弃旧任务结果。

## 7. 实施阶段

### M1：轮廓 GPU Batch 原型

- 只处理 Blob 轮廓；
- OK/NG 分为两个 Batch；
- 保留现有 WPF 命中测试；
- 保留 WPF 高亮层；
- 不改变算法结果契约。

验收：3000 个 Blob 全视口绘制不再经过 322 个 `StreamGeometry`。

### M2：矩形、点和十字批处理

- 旋转矩形使用独立顶点格式；
- 质心和十字使用实例化或连续顶点；
- 样式按颜色和线宽分组。

### M3：交互和高亮分层

- 命中测试继续使用空间索引；
- 只对选中对象绘制动态高亮；
- 选择变化不重建全量 Batch。

### M4：Direct2D/Direct3D 后端稳定化

- 设备丢失恢复；
- 多显示器适配；
- GPU/软件回退；
- 图像切换和任务取消；
- 关闭窗口时安全释放资源。

## 9. 验收基线

使用当前单例：5120×5120 图像、3000 个 Blob、当前显示样式，至少验证：

1. 首次全视口显示；
2. 全视口连续平移；
3. 全视口连续缩放；
4. 放大后的局部平移；
5. 切换显示图像；
6. 切换 OK/NG/轮廓/矩形可见性；
7. 选中、命中和高亮；
8. 快速连续执行新结果时旧 Batch 不回写。

目标不是单纯降低某一次 `RenderMs`，而是保证：

```text
全视口普通交互不阻塞 UI 线程
缩放/平移只更新 Transform 或可见 Range
结果切换不会显示旧图像的几何
大结果任务可取消、可追踪、可自分析
```
