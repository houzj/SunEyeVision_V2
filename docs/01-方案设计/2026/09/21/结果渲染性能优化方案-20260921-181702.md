## 3. Bug 模式分析（治本依据）

**当前问题**：① 查找数量设了却被渲染层再砍一刀；② 显示开关去决定算法是否执行。

| 项 | 内容 |
|---|---|
| **真因分类** | ① **架构冗余（双真源）**：同一个语义（"显示多少个/是否显示"）在工具层与渲染层各有一份可变实现（`BlobCountLimit` vs `LOD_MAX_CONTOURS`；`OutputContours` vs `contours.Style.IsVisible`）；② **实现偏差**：把"呈现开关"当成"执行开关"（`OutputBlobImage/OutputBinaryImage/OutputContours`） |
| **同类潜伏点** | ① 渲染层三处数量闸同源（`:391-392`、`:643-647`、`:786-787`、`:902`）；② `OutputContours` 与 `contours` 样式可见性双真源（`BlobAnalysisTool.cs:432`）；③ Blob 与 Threshold/Morphology 的同能力语义分裂（前者有开关、后者无）；④ 原方案的"逐轮廓元数据"属于**为已取消的抽稀而生的派生数据**，若保留将变成僵尸字段 |
| **治本点** | ① **数量只认工具参数**：渲染层不得做任何数量决策（含抽稀、上限）；② **显示只认呈现层真源**：结果图像用 `GetDisplayImages()`，图形用 `Style.IsVisible`；③ **算法产出与呈现解耦**：工具一律算完、产出完整结果，显示端自行决定画不画 |

## 6. 数量语义裁定：「查找数量」与其它筛选的关系

### 6.1 执行链真实顺序（`BlobAnalysisTool.Run`）

| 顺序 | 环节 | 代码位置 | 作用对象 | 语义 |
|---|---|---|---|---|
| 1 | 检测区 / 屏蔽区 ROI | `:146-156` | 图像域 | 只在检测区内找、屏蔽区挖掉 |
| 2 | 阈值分割 + 形态学 | `:171-210` | 图像→区域 | 二值化 |
| 3 | **连通域 Connection** | `:214-221` | 区域 | `rawBlobCount` = 原始连通域数 |
| 4 | **面积筛选**（Halcon `SelectShape`） | `:227-239` | 区域 | 区域层面直接砍掉 |
| 5 | **圆度 / 矩形度筛选**（C# 逐 blob） | `:296-315` | 候选集合 | 逐 blob 判通过/丢弃 |
| 6 | **排序** | `:341-345` | 通过质量的 blob | 决定"谁排前面" |
| 7 | **查找数量截断（取前 N）** | `:347-348` | 已排序集合 | **筛选链最后一环** |
| 8 | 区域本体 / OK-NG 区域重建 | `:350-352`、`:381-383` | 截断后集合 | `SelectObj` 一次性抽取 |

| 11 | 显示构建（矩形 / 质心 / 文本） | `:421-477` | 截断后集合 | 画面只画最终集合 |

### 6.2 裁定

| 议题 | 裁定 | 说明 |
|---|---|---|
| 查找数量是"筛选"还是"上限" | **上限（取前 N）**，排在质量筛选与排序之后 | 不是"不合格就丢"，而是"合格的按顺序只要前 N 个" |
| 质心 / 轮廓是否在筛选后计算 | 轮廓：**是**（`:353` 遍历最终集合）；质心：值在 `:257-260` 批量预算，但只有最终集合的 blob 进入结果，呈现等价 | 与用户表述一致，无需改代码 |
| NG 是否占查找数量名额 | **占**（保持现状） | 判断在 `:321` 完成、截断在 `:347`，两者顺序不变；查找数量语义是"检出多少 blob"，NG 也是检出项 |
| 整体判断用哪个集合 | **最终集合**（`:576-582`） | 因此"改查找数量会影响 Blob数量/面积类判断"，需在参数说明与文档写明 |
| 不排序（`SortMode=None`）时取前 N | 按 Halcon 连通域原始编号顺序 | 已在注释中写明 |
| 「白色像素比例」口径 | 观察项，本次**不改**（`WhitePixelRatio` 用未筛选 `binaryRegion`，`:583-585`），与其它统计口径不同源于历史 | 超出 C1/C2 范围，避免范围蔓延（YAGNI） |

### 7.1 改动 1 的实现要点（不减少图元）

1. **视口裁剪（已有，保留）**：`SetViewport`（`:273-281`）+ `IsInViewport`（`:403`、`:798`）；无视口时全画（`:661`）——保证"没有视口信息时不会少画"。
2. **块级几何复用（已有，保留）**：后台构建冻结 `StreamGeometry`、按 512px 图像坐标 tile 归档、`HashSet` 去重（`:110-156`、`:181-184`、`:659-676`）。
3. **整组 / 分块两级（新增）**：
   - 分块级：视口内 tile 的冻结几何逐个 `DrawGeometry`（现状路径）。
   - 整组级：把该批次全部 tile 几何装入一个 `GeometryGroup`（**引用**已有冻结几何，零顶点复制），一次 `DrawGeometry`。
   - 判据：**可见覆盖率**（视口覆盖该批次 `Bounds` 的比例）≥ 0.6 → 整组；≤ 0.4 → 分块；0.4~0.6 → **滞回**保持上次选择（防同视口抖动）。
   - 硬护栏：单组顶点 > 50 万 → 强制分块（换画法，**不减少图元**）。
4. **诊断（新增）**：每次 `OnRender` 输出 `[RenderDiag] items/contours/crosses/texts/drawCalls/renderMs/mode(整组|分块)`；`renderMs` 超阈值（100ms）升 `LogLevel.Warning`。日志走 `VisionLogger.Instance`（同 `ImageControl.xaml.cs:233` 通道）。
5. **禁止项**：不得引入任何形式"超过 X 个就跳过/抽样"的分支。

## 12. 风险评估与回退

| 风险 | 程度 | 应对 / 回退 |
|---|---|---|
| 删掉数量闸后，查找数量调大（或关闭筛选）会导致帧率下降 | 中 | 这是 C1 的必然代价：数量由用户参数决定。用 `[RenderDiag]` WARNING 让用户看到"慢是因为画了 6 万个"，而不是静默少画 |
| `GeometryGroup` 子几何过多反而更慢 | 中 | 覆盖率判据 + 滞回 + 50 万顶点护栏；实测取数据后再定阈值；保留分块路径可切回 |
| 无条件产出二值图/轮廓增加耗时与内存（关显示不再省时） | 中 | C2 的必然代价；风险在文档与参数说明中写明；轮廓提取耗时已有阶段计时（`:353-365`）可量化 |
| 老方案文件含 `OutputXxx` 字段 | 低 | `System.Text.Json` 默认忽略未知成员，无需迁移代码（rule-008 零兼容） |
| 与在飞渲染改动（`-comm` M1/M2/M3）冲突 | 低 | 基线不同（`eb22d2b4` vs `72dddc7c`），本方案不含它们 |
| 需求回调到优化版 | 低 | tag `backup/render-opt-20260921` 随时切回 |
