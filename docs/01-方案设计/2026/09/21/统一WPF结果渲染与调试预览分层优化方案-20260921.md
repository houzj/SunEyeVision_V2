# 统一 WPF 结果渲染与调试预览分层优化方案

**日期**：2026-09-21  
**状态**：方案基线，待实施  
**适用范围**：Plugin.SDK 结果渲染层、Blob/测量等工具结果显示、主界面节点结果显示、调试窗口生命周期

## 1. 背景与问题

当前结果显示经历过多轮优化：早期是 `InvalidateVisual()` 触发 `OnRender()` 的直接 WPF 绘制，之后增加了批量轮廓、异步几何构建、场景缓存、Tile 和批次缓存。现阶段继续叠加渲染模式会提高维护成本，也容易把工作流结果和调试窗口预览混在同一结果层中。

需要解决的核心问题：

1. 工作流结果、调试预览、ROI/卡尺交互和数据分析高亮缺少清晰的显示职责边界。
2. 关闭调试窗口时，不能误清理工作流结果，也不能通过通用 `RefreshResultDisplay()` 产生不可编辑的残留图形。
3. Blob 等工具仍可能产生大量细粒度显示项，导致对象、订阅、遍历和 WPF 绘制提交成本升高。
4. `SetDisplayCollector()`、`SetRegionItems()` 等多个入口可能对同一批结果重复触发构建和刷新。
5. 不应继续按“小结果/大结果/超大结果”切换多套产品级渲染模式。

## 2. 设计结论

采用统一 WPF 渲染管线：

```text
语义结果
  → RenderSnapshot
  → 按图元类型构建 RenderBatch
  → 少量 DrawingVisual
  → DrawingContext.DrawGeometry / DrawText
```

统一使用 WPF，不按结果数量切换渲染模式。`StreamGeometry` 是可复用的几何缓存形式，`DrawingContext` 是 WPF 的绘制提交 API，两者属于同一条管线，不是两种互斥策略。

后台构建、取消、generation、空间索引等只作为内部实现优化，不暴露为“小结果路径/大结果路径/超大结果路径”。

## 3. 显示职责分层

`ImageControl` 内部逻辑上划分为四个显示层：

```text
WorkflowResultLayer      工作流执行结果
DebugPreviewLayer        调试窗口立即执行结果
InteractionLayer         ROI、卡尺和编辑手柄
HighlightLayer           数据分析选中高亮
```

这些层可以继续由同一个宿主控件承载，但必须拥有独立数据源和清理入口：

```csharp
SetWorkflowResult(RenderSnapshot snapshot);
SetDebugPreview(RenderSnapshot snapshot);
SetInteractionItems(...);
SetHighlightItems(...);

ClearWorkflowResult();
ClearDebugPreview();
ClearInteraction();
ClearHighlight();
```

禁止用一个无语义的 `ResultRenderLayer.Clear()` 同时清理所有显示来源。

## 4. 关闭调试窗口的目标逻辑

关闭调试窗口时执行：

```text
PersistParameterBindings()
  → ClearDebugPreview()
  → ClearInteraction()
  → ClearHighlight()
  → 保留 WorkflowContext 中的工作流结果
```

关闭调试窗口不应：

- 清除工作流结果缓存；
- 自动重跑算法；
- 通过通用 `RefreshResultDisplay()` 把调试结果重新画回主图像；
- 清理与调试预览无关的工作流结果。

如果产品需要关闭窗口后继续显示工作流结果，必须显式执行：

```text
ClearDebugPreview()
  → 从 WorkflowContext 获取当前节点结果
  → SetWorkflowResult(...)
```

## 5. 统一结果状态模型

不把 `Contour`、`Rectangle`、`Circle`、`Line` 等几何形状设计成对上层暴露的显示层级。对于图像处理工具，结果显示的主要语义是结果状态：

```text
RenderSnapshot
  ├── PassItems       OK
  ├── FailItems       NG
  ├── NeutralItems    无判定/普通辅助结果
  └── HighlightItems  当前选中高亮
```

其中 `PassItems`、`FailItems` 和 `NeutralItems` 内部可以包含任意几何数据：

```text
RenderItem
  ├── GeometryKind: Contour / Rectangle / Circle / Polygon / Arc / Line / Point
  ├── GeometryData
  ├── Style
  └── DisplayState: Pass / Fail / Neutral
```

几何类型只属于渲染编译器的内部实现，用于选择对应的 WPF 绘制命令；工具和宿主不需要按几何类型维护多套结果接口。

批次最终按状态、样式和绘制属性合并：

```text
PassItems   → OK 样式批次
FailItems   → NG 样式批次
NeutralItems→ 普通样式批次
```

必要时，编译器内部再按颜色、线宽、填充、线型等属性拆分 Geometry，但这不改变上层的 OK/NG 结果模型。

说明：不能只保留 OK 和 NG 两种状态，因为部分工具存在没有判定语义的辅助结果，例如输入区域、测量引导线、坐标轴和普通中间结果。因此保留 `Neutral`，并将高亮作为独立的交互状态。

不再采用“每个 Blob 一个矩形、一个十字、一个文本”的细粒度显示项模型。

## 6. WPF Visual 结构

结果层目标维持少量 `DrawingVisual`：

```text
ResultRenderLayer
  ├── ResultVisual       Pass / Fail / Neutral 结果
  ├── TextVisual         结果文字
  └── InteractionVisual  ROI / 卡尺 / 高亮
```

`ResultVisual` 内部可以同时处理轮廓、矩形、圆、线、点等几何类型，只按结果状态和样式形成绘制批次。目标是让大量 Blob 只产生少量 Visual。图形数据由批量 `StreamGeometry` 承载，提交时使用 `DrawingContext`：

```text
RenderBatch
  → StreamGeometry
  → Freeze()
  → DrawingContext.DrawGeometry()
```

## 7. RenderSnapshot 与一次性提交

结果渲染应从多个独立刷新入口收敛为一次提交：

```csharp
SetRenderFrame(
    RenderSnapshot result,
    RenderSnapshot? regions,
    RenderSnapshot? highlight);
```

或者使用更新事务：

```csharp
BeginRenderUpdate();
SetWorkflowResult(...);
SetRegionItems(...);
SetHighlightItems(...);
EndRenderUpdate();
```

`EndRenderUpdate()` 只触发一次批次构建和一次 WPF Visual 提交。

这样可以避免 `SetDisplayCollector()`、`SetRegionItems()` 连续调用导致同一结果重复编译、重复刷新和重复提交。

## 8. 刷新粒度

不按数据量切换渲染模式，只按变化类型刷新对应批次：

```text
结果数据变化       → 重建对应 GeometryBatch
颜色/线宽/线型变化  → 重建对应样式批次
缩放/平移           → 复用 Geometry，只重新提交绘制
高亮变化            → 只刷新 Highlight/InteractionVisual
文本开关变化        → 只刷新 TextVisual
```

缩放、平移不应重新执行算法，也不应重新生成工具结果。

## 9. 空间索引、后台构建与 GPU 的位置

这些能力均属于内部实现细节：

- 空间索引用于快速查询当前视口相交的几何；
- 后台线程用于构建可冻结的 `StreamGeometry`；
- generation 用于取消和丢弃过期回写；
- GPU 仅在统一 WPF 批量管线仍达不到性能指标时再评估。

它们不改变上层结果模型，也不形成多套产品级渲染分支。Tile 可以作为空间索引或数据分组使用，但不应强制每个 Tile 创建独立 WPF Visual。

## 10. 工作流与调试执行流程

### 10.1 工作流运行

```text
Blob 工具执行
  → BlobAnalysisResults
  → RenderSnapshot
  → WorkflowContext 保存结果
  → 当前节点选中时 SetWorkflowRenderFrame()
  → GeometryVisual / MarkerVisual / TextVisual 绘制
```

### 10.2 调试窗口立即执行

```text
调试控件执行
  → BlobAnalysisResults
  → 保存调试预览结果
  → SetDebugPreviewFrame()
  → 更新数据分析控件
```

### 10.3 调试窗口关闭

```text
提交参数绑定
  → 清理 DebugPreview
  → 清理 Interaction
  → 清理 Highlight
  → 保留 WorkflowResult
```

## 11. 实施阶段

### M1：显示语义分离

- 区分工作流结果和调试预览；
- 修改调试窗口关闭逻辑；
- 增加关闭窗口后工作流结果保持的回归测试；
- 明确所有显示层的清理责任。

### M2：Blob 图元批量化

- 轮廓改为 OK/NG 批次；
- 矩形改为 OK/NG 批次；
- 十字改为批次；
- 文本改为独立 `TextBatch`；
- 保持颜色、可见性和判定语义不变。

### M3：RenderSnapshot 与统一提交

- 新增 `RenderSnapshot`；
- 新增 `RenderBatch`；
- 合并 `SetDisplayCollector()` 与 `SetRegionItems()` 的刷新；
- 消除同一结果连续构建两次的问题。

### M4：少量 WPF Visual

- 建立 Geometry、Marker、Text、Interaction 四类 Visual；
- 缩放和平移复用几何数据；
- 样式变化只刷新对应图层；
- 清理旧 Tile Visual 管理中的重复提交路径。

### M5：内部性能优化

- 后台构建冻结 Geometry；
- 增加 generation 取消过期任务；
- 需要时增加空间索引；
- 记录构建耗时、提交耗时、Geometry 数量和 Visual 数量。

GPU 后端不纳入第一阶段，待 M1–M5 完成并有真实性能数据后再单独评估。

## 12. 验收标准

### 语义验收

1. 工作流运行后选中 Blob，结果可以正常显示。
2. 打开并关闭 Blob 调试窗口，不会误清理工作流结果缓存。
3. 调试窗口执行的临时预览在关闭后消失。
4. ROI、卡尺、结果高亮可以独立清理。
5. 重新选中节点可以从 `WorkflowContext` 恢复工作流结果。

### 渲染验收

1. Blob 轮廓、矩形、十字和文本的 OK/NG 颜色保持正确。
2. 显示开关、颜色、线宽变化不触发算法重跑。
3. 缩放和平移不重复构建工具结果。
4. 一次结果更新只发生一次统一提交。
5. 大量 Blob 不产生每个图元一个 WPF Visual 的结构。
6. 图像切换或快速刷新时，旧结果不会回写到新图像。

## 13. 明确不采用的方案

- 不按 500、5000 等数量阈值切换多套渲染模式；
- 不把小结果、大结果、超大结果设计成不同公共 API；
- 不优先引入 GPU 以掩盖显示职责和生命周期问题；
- 不让调试窗口直接拥有或清理工作流结果层；
- 不通过重复调用 `RefreshResultDisplay()` 解决关闭窗口后的显示状态。
