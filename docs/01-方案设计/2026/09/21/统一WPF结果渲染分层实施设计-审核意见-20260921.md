# 《统一 WPF 结果渲染分层实施设计》审核意见

**审核日期**：2026-09-21  
**审核对象**：`统一WPF结果渲染分层实施设计-20260921-113636.md`  
**审核结论**：方案方向通过，实施设计暂不通过，修改后再实施  
**审核人**：Codex

## 1. 总体结论

CodeBuddy 的实施设计整体方向与上位方案一致：

- 统一使用 WPF 渲染；
- 不按小结果/大结果切换多套公共渲染模式；
- 工作流结果与调试预览分层；
- 结果按 `Pass / Fail / Neutral` 组织，几何类型作为渲染内部数据；
- 通过一次性提交和少量 Visual 减少重复构建与 WPF 提交成本。

但是，当前施工图仍有关键接口和生命周期缺口。若直接实施，可能出现调试结果继续写入工作流结果层、关闭窗口无法准确清理调试预览、SDK 反向依赖 UI 宿主等问题。

因此当前不能直接开始代码实施。

## 2. 必须修改的阻断项

### 2.1 `DebugPreview` 没有进入正式提交接口

实施设计第 1 节定义：

```csharp
SetRenderFrame(RenderSnapshot workflowResult,
               RenderSnapshot? regions,
               RenderSnapshot? highlight = null);
```

但设计第 2 节又要求结果层维护：

```text
_workflowResult
_debugPreview
_regionItems
_highlightItems
```

当前公共接口没有 `debugPreview`，导致调试预览没有正式写入路径，最终仍可能被当成工作流结果处理。

必须改为以下两种方案之一。

方案 A：分层接口。

```csharp
SetWorkflowFrame(RenderSnapshot? workflowResult,
                 RenderSnapshot? regions);

SetDebugPreview(RenderSnapshot? debugPreview);
SetHighlight(RenderSnapshot? highlight);
```

方案 B：统一 Frame 对象。

```csharp
public sealed class RenderFrame
{
    public RenderSnapshot? WorkflowResult { get; init; }
    public RenderSnapshot? DebugPreview { get; init; }
    public RenderSnapshot? Regions { get; init; }
    public RenderSnapshot? Highlight { get; init; }
}

void SetRenderFrame(RenderFrame frame);
```

推荐方案 B，能够避免后续继续增加多个平行参数。

**原文位置**：实施设计第 1 节、第 2 节。

### 2.2 工作流结果和调试结果的写入入口必须分开

当前 `NodeResultManager.UpdateNodeResult(node, result)` 同时被以下两类事件使用：

- 工作流执行完成事件；
- 调试窗口立即执行完成事件。

如果只增加渲染层，不区分结果来源，调试结果仍会进入：

```text
WorkflowContext
→ WorkflowResultLayer
```

这会破坏“调试预览与工作流结果分离”的目标。

必须增加明确的来源入口，推荐：

```csharp
UpdateWorkflowResult(node, result);
UpdateDebugPreview(node, result);
```

也可以使用来源参数：

```csharp
UpdateNodeResult(node, result, ResultSource.Workflow);
UpdateNodeResult(node, result, ResultSource.DebugPreview);
```

推荐前一种方式，调用语义更清晰。

工作流结果应当：

```text
写入 WorkflowContext
→ 更新 WorkflowResultLayer
```

调试结果应当：

```text
更新 DebugPreviewLayer
→ 是否写入 WorkflowContext 需要单独定义
```

不能让调试执行通过普通工作流结果入口覆盖当前工作流结果。

### 2.3 SDK 基类不能直接清理 UI 宿主的调试预览层

实施设计第 2 节要求在以下组件中统一调用：

```text
ToolDebugControlBase
DefaultDebugWindow
CustomDebugWindow
```

```csharp
ClearDebugPreview();
ClearInteraction();
ClearHighlight();
```

但 `ToolDebugControlBase` 位于 Plugin.SDK，不能直接依赖宿主的 `ImageControl` 或 `MainWindowViewModel`。这会违反项目架构边界：工具插件和 SDK 不应依赖 UI 宿主程序集。

必须通过宿主注入接口或关闭通知解决。

推荐增加：

```csharp
public interface IDebugPreviewHost
{
    void ClearDebugPreview(string nodeId);
    void ClearInteraction(string nodeId);
    void ClearHighlight(string nodeId);
}
```

由 UI 在初始化调试控件时注入。SDK 只依赖接口，不依赖 UI 实现。

另一种可接受方案是：调试窗口只触发 `DebugWindowClosed(nodeId)`，由 `MainWindowViewModel` 负责清理宿主渲染层。

不建议让 `ToolDebugControlBase` 自己查找或持有 `ImageControl`。

### 2.4 `RenderBatchCompiler` 不能承担所有编译职责

实施设计第 4 节要求保留 `RenderBatchCompiler` 作为唯一编译入口，同时删除 `ScheduleBatchGeometryBuild` / `RebuildScene` 等逻辑。

当前代码中的编译职责至少分为两类：

```text
RenderSceneCompiler
  → 空间索引、视口查询、命中候选

RenderBatchCompiler
  → 绘制批次、顶点/轮廓合并、WPF Geometry 数据
```

这两个职责不能强行合并成一个编译器。

正确目标应当是：

```text
一次 RenderFrame 提交
├── 一次 RenderBatchCompiler：生成绘制批次
└── 一次 RenderSceneCompiler：生成空间/命中索引
```

需要消除的是重复提交和重复构建，而不是删除所有不同职责的编译器。

建议把原文“收敛为一条编译管线”修改为：

> 收敛为一个 RenderFrame 提交入口；内部允许存在绘制批次编译和空间索引编译两个职责明确的阶段。

## 3. 必须调整的设计项

### 3.1 不建议使用 `object Geometry`

实施设计第 1 节定义：

```csharp
object Geometry { get; }
```

这会造成类型不安全、运行时模式匹配、潜在反射依赖和后续维护困难。

建议使用强类型几何抽象：

```csharp
public interface IRenderGeometry
{
    RenderGeometryKind Kind { get; }
    Rect Bounds { get; }
}
```

具体几何类型可以包括：

```text
ContourRenderGeometry
RectangleRenderGeometry
CircleRenderGeometry
LineRenderGeometry
PointRenderGeometry
TextRenderGeometry
```

几何类型可以不暴露给工具宿主，但渲染内部必须保持强类型。

### 3.2 批次数量测试不能断言固定的“≤3”

实施设计第 3 节提出：

```text
同一 style ⇒ 只产生 ≤3 个批次
```

实际批次数还会受以下因素影响：

- Pass / Fail / Neutral；
- 颜色；
- 线宽；
- 填充；
- 虚线；
- 几何是否可以合并；
- 文本与几何是否需要分离。

测试应改为验证：

```text
同一状态
+ 同一兼容样式
+ 同一绘制语义
→ 只生成一个批次
```

同时验证 Pass、Fail、Neutral 的颜色和显示状态正确，而不是固定批次数。

### 3.3 `ResultTileHost` 的收敛边界需要明确

实施设计第 5 节要求 `ResultTileHost` 退化为查询宿主、不再创建 Tile Visual。这个方向可以接受，但当前 `ResultTileHost` 同时负责：

- `VisualCollection`；
- `DrawingVisual` 生命周期；
- 视口刷新；
- Tile 管理；
- RenderBackend 回调。

不能只删除 `CompositeVisibleTileThreshold` 分支就完成迁移。

必须明确以下方案之一：

```text
方案 A：ResultTileHost 保留 FrameworkElement，
        但只维护一个或少量 Visual，不再创建 Tile Visual。

方案 B：ResultRenderLayer 改为新的 WPF VisualHost，
        ResultTileHost 仅保留空间查询职责。
```

推荐方案 A，改动范围较小。

同时必须明确“Visual ≤ 3”的统计范围：

- 只统计 `ResultRenderLayer`；
- 是否包括高亮层；
- 是否包括 InteractionLayer；
- 是否包括 ImageControl 的其他 Visual。

否则自动化测试结论不稳定。

## 4. 建议调整后的实施顺序

建议把原来的施工顺序细化为：

```text
M1a：结果来源与生命周期分离
M1b：调试窗口关闭清理接口
M2：RenderFrame 一次性提交
M3：Blob 状态批量化
M4：少量 WPF Visual
M5：后台构建、generation 和空间索引收敛
```

其中 M1a 必须先于 M1b，因为没有区分：

```text
WorkflowResult
DebugPreview
```

关闭窗口时就没有可靠的清理对象。

## 5. 实施前需要 CodeBuddy 回填的内容

CodeBuddy 修改实施设计后，必须明确回答以下问题：

1. `RenderFrame` 是否包含 `DebugPreview`？
2. 工作流结果和调试结果的独立写入入口是什么？
3. SDK 与 UI 宿主之间通过什么接口清理调试预览？
4. `RenderSceneCompiler` 和 `RenderBatchCompiler` 的职责边界是什么？
5. 是否移除 `object Geometry`，改用强类型几何抽象？
6. `ResultTileHost` 是保留为少量 Visual 宿主，还是拆分为空间查询组件？
7. 批次测试是否改为“兼容状态/样式合并”断言？
8. “Visual ≤ 3”的统计范围是什么？

## 7. 用户最终拍板的三项决策

### 7.1 本次实施授权范围

本次统一 WPF 结果渲染任务明确授权 CodeBuddy 修改以下目录：

```text
src/Plugin.SDK/**
tools/SunEyeVision.BlobAnalysis/**
src/UI/Services/Workflow/**
src/UI/Shell/Windows/**
```

授权仅限本次结果渲染分层与批量化任务，不包含 `src/Workflow/**` 执行核心。实施期间 CodeBuddy 是唯一代码写入者，Codex 只读审核；不得并行修改上述目录。

### 7.2 调试结果是否写入 WorkflowContext

调试窗口立即执行结果**不写入生产工作流的 `WorkflowContext`**，避免污染：

- 工作流结果；
- 工作流数据源；
- 下游节点执行输入；
- 全局变量生产结果。

如果调试数据分析或调试链路需要缓存，使用独立的 `DebugExecutionContext` 或调试结果缓存。工作流执行结果继续使用生产 `WorkflowContext`。

### 7.3 关闭调试窗口后的恢复策略

关闭调试窗口后**自动恢复已缓存的工作流结果**，但不重新执行算法：

```text
提交参数绑定
→ 清除 DebugPreview / Interaction / Highlight
→ 从生产工作流结果缓存读取当前节点结果
→ 重新提交 WorkflowResult
```

这项决策取代原施工图第 10 节中“重新选中节点时恢复”的临时建议。重新选中节点仍应能够恢复结果，但不再是关闭窗口后恢复结果的必要条件。

### 7.4 区域渲染方案最终决策

本轮不实施 CodeBuddy 提出的三种区域栅格/矢量策略：

```text
甲：区域一律栅格
乙：按数量自动切换矢量/栅格
丙：由结果呈现配置逐项选择矢量/栅格
```

工作流结果区域继续纳入统一 WPF 矢量结果层，按 `Pass / Fail / Neutral` 结果状态组织，沿用统一的坐标、缩放、图像身份和命中语义。

原因是透明贴图会引入独立的图像身份、尺寸、缩放、generation 和过期回写管理；底层图像切换时还必须清除旧贴图并确认新贴图与当前图像匹配。同时，栅格区域天然不支持逐区域命中、选中和高亮，可能背离当前统一结果层与命中设计。

原始 `HRegion`、轮廓和结果数据继续保留，用于算法、结果树和下游绑定。透明栅格贴图只作为未来在有明确性能证据、且确认静态区域不需要逐个点选时的可选后端优化，不得作为本轮新的公共显示分类或分支路径。
