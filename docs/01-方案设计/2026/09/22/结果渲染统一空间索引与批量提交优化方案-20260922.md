# 结果渲染统一空间索引与批量提交优化方案

**日期**：2026-09-22  
**适用基线**：当前回退后的 `ResultRenderLayer` 实现（单体 WPF `OnRender`、批量轮廓异步缓存、512×512 Tile 索引）

## 1. 方案结论

结果渲染统一使用一条路径：

```text
结果提交
  → 建立轮廓记录和空间索引
  → 根据当前视口查询候选轮廓
  → 按轮廓 ID 去重
  → 按颜色、线宽、填充和 OK/NG 状态分组
  → 每组生成合并 Geometry
  → 使用少量 DrawGeometry 提交
```

全视口和局部视口不再使用两套渲染算法。两者只在候选数量和缓存复用策略上不同：全视口候选接近全部轮廓，局部视口候选较少；查询、去重、分组和提交流程保持一致。

Tile 只负责空间索引，不再作为独立绘制对象。最终目标不是“每个 Tile 一次绘制”，而是将可见轮廓合并为少量渲染批次。

## 2. 当前实现和问题

当前流程如下：

```text
轮廓结果
  → 每 1000 条轮廓创建一个 StreamGeometry
  → 按整个几何块 Bounds 放入多个 Tile
  → 查询视口覆盖的 Tile
  → HashSet 去重
  → 多次 DrawGeometry
```

主要问题：

1. **空间粒度过粗**：一个 1000 条轮廓的几何块只要跨过某个 Tile，整个几何块都会被取出和绘制。
2. **Tile 只是候选索引**：当前没有按轮廓实际范围裁剪，视口可能只覆盖大几何块的一小部分，但仍绘制整个几何块。
3. **提交次数仍然较多**：多个 Tile 最终仍然对应多个 `DrawGeometry` 调用，没有形成真正的渲染批次。
4. **结果刷新可能重复构建**：`SetDisplayCollector()` 和 `SetRegionItems()` 连续调用时，会启动两轮缓存构建，前一轮通常被后一轮取消。
5. **缓存未完成时存在回退成本**：批量缓存尚未完成时，会走逐轮廓回退路径，大结果下可能阻塞 UI 绘制。
6. **其他图形没有统一空间索引**：点、十字主要逐元素判断视口，线、矩形和圆等图形基本直接绘制。
7. **高亮层没有参与批量缓存构建**：批量高亮轮廓可能直接走回退路径。

## 3. 目标数据结构

轮廓不再以“1000 条轮廓一个大几何块”作为空间索引单位，而是建立不可变轮廓记录：

```text
ContourRecord
  - ContourId
  - Points
  - Bounds
  - IsClosed
  - IsPass
  - StyleKey
```

空间索引：

```text
TileKey → ContourId 集合
```

Tile 中只保存可能相交的轮廓 ID，不直接保存需要重复挂接的大块 `StreamGeometry`。视口查询后使用 `HashSet<ContourId>` 去重，保证一次渲染中同一轮廓只处理一次。

## 4. 统一渲染流程

### 4.1 结果提交

增加统一结果提交语义，逻辑上一次替换工具输出、区域输出和高亮输出：

```text
替换三层数据
  → 递增 RenderGeneration
  → 取消旧构建
  → 合并连续刷新请求
  → 启动一次新的缓存构建
```

当前 `SetDisplayCollector()`、`SetRegionItems()` 连续触发构建的方式应逐步收敛为一次提交，避免重复 CPU 消耗。

### 4.2 视口查询

当前视口覆盖多个 Tile 时，先查询 Tile 范围，再取得候选轮廓 ID：

```text
视口
  → minTileX/maxTileX、minTileY/maxTileY
  → 合并覆盖 Tile 的轮廓 ID
  → 去重
  → 得到真正的候选轮廓
```

全视口也走同一流程；当视口覆盖全部图像时，候选集合自然接近全部轮廓。

### 4.3 批量合并

候选轮廓按渲染状态分组：

```text
OK 轮廓
NG 轮廓
OK 填充区域
NG 填充区域
其他颜色/线宽组合
```

每组构建一个合并 `StreamGeometry`，绘制目标为少量 `DrawGeometry` 调用，而不是每个 Tile 或每个几何块单独提交。

## 5. 缓存策略

缓存必须与以下状态关联：

```text
RenderGeneration
图像身份
轮廓数据版本
样式版本
视口候选集合
```

规则：

- 图像切换、结果替换、轮廓数据变化时递增代次并取消旧任务。
- 后台只构建不可变数据和冻结 Geometry。
- UI 线程只接受代次匹配的构建结果。
- 缓存构建期间避免每个中间状态都触发完整重绘。
- 视口稳定后可缓存当前视口的合并 Geometry。
- 缩放只改变视口和线宽时，尽量复用轮廓路径，不重新执行算法。

## 6. 其他图形的处理

轮廓优先改造，其他图形按数量逐步接入同一模型：

- 点、十字：建立轻量 Bounds 索引，视口内合并绘制。
- 矩形、圆、线：数量较大时建立轻量空间索引。
- 文本：按实际文本 Bounds 做视口过滤，并保留排版缓存。
- 少量特殊图形：继续使用即时绘制路径。
- ROI 和测量交互：继续保持独立交互层，不并入生产结果批次。

## 7. 实施顺序

1. 合并 `SetDisplayCollector()` 与 `SetRegionItems()` 的刷新和缓存构建，消除重复构建。
2. 增加轮廓记录、Bounds、稳定 ID 和 RenderGeneration。
3. 将 Tile 从几何缓存容器改为空间候选索引。
4. 视口查询后按轮廓 ID 去重。
5. 按 OK/NG、颜色、线宽和填充状态合并 Geometry。
6. 使用少量 `DrawGeometry` 统一提交。
7. 将点、十字以及高数量矩形/圆接入轻量空间索引。
8. 完成日志和性能指标后，再评估 Direct2D 或 D3D11 后端。

## 8. 验收标准

- 全视口和局部视口使用同一套查询、去重、分组和提交逻辑。
- 同一轮廓在一次渲染中只绘制一次。
- 结果刷新只启动一次有效缓存构建。
- 稳定状态下不再走大批量逐轮廓回退路径。
- 可记录候选轮廓数、去重后轮廓数、最终批次数、缓存命中率和实际绘制耗时。
- 3000、10000 条轮廓在适配窗口、放大、缩小、平移和切换图像时无明显 UI 卡顿。
- OK/NG 颜色、填充、可见性、文本、区域和高亮语义保持不变。
- 调试预览不会污染生产工作流结果，清理调试预览后生产结果仍可恢复。

## 9. 最终原则

```text
Tile 负责找轮廓
Geometry Batch 负责合并轮廓
DrawingContext 只提交少量批次
全视口和局部视口共用同一套渲染逻辑
```

当前阶段不直接引入 GPU 后端，先解决空间索引粒度、重复构建和 `DrawGeometry` 调用数量问题，再根据真实运行数据决定是否进入 Direct2D/D3D11。
