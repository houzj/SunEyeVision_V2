## 2. 参考产品的功能边界

- **设备管理**配置 TCP 客户端／服务端、UDP、串口和 PLC 等通信设备。设备页提供原始接收／发送调试。基本协议的“接收结束符”用于处理粘包和分包；“数据上传”影响原始数据在软件中的显示、全局字符串触发等，但帮助明确说明它**不影响接收事件接收设备数据**。因此不能把“设备页能看到收到的数据”等同于“接收事件一定解析成功”，也不能以数据上传开关作为接收事件绑定条件。
- **接收事件**绑定明确的设备；凡需定位设备内具体数据目标的协议还需绑定该目标，而不是只判断“PLC 类”或统一叫“地址”。VM PLC 示例绑定寄存器地址，Modbus 示例把两寄存器读回的 `00 5C 41 44` 数据字节分段解析。文本-协议解析按分隔符和顺序配置输出类型；文本-协议比对增加单项比较和组装回复；字节匹配-协议比对按字节区间、顺序和类型解析；脚本是通信专用 Python 脚本。帮助说明按列表顺序解析，任一项失败则整体解析失败。
- **发送事件**定义数据的直接输出／组装输出／脚本处理格式，实际发送须由流程中的“发送数据”模块调用。**响应配置**则由方案加载、流程空闲／忙碌、相机连接／掉线等系统动作自动触发发送；两者不是同一功能。
- **全局触发**独立消费已解析接收事件或原始字符串，再决定是否执行流程／模块等命令。**心跳管理**按设备定时发送单个内容或两个内容交替发送。**通信示例**是文档示范，其中的 `ABC,2` 示例将 `ABC` 和整数 `2` 解析后绑定运行参数、触发流程。

## 4. 接收事件的共同处理链与长度规则

建议执行顺序：

```text
设备字节流／数据报
  → 按协议和结束符确定完整报文（分帧）
  → 按显式 DeviceId + 协议所需的目标身份（若有）匹配接收事件
  → 可选整报文长度校验
  → 文本按分隔符拆字段／字节载荷按字节区间解码／OPC UA 保留原生类型
  → 按列表顺序读取所需字段、类型验证、比较规则逐项校验
  → 整体成功后原子发布字段值和事件结果
  → 可选触发工作流、组装回复设备
```

**已从帮助确认的行为**：“字符长度比较”是在文本解析前检查**收到的数据总字符长度是否与配置值完全一致**，分隔符也占字符；不一致就不解析。它不是固定长度切片，也不是单个字段长度配置。`ABC,2` 在不计报文结束符时长度为 5，按逗号解析为 `ABC`、`2`，不能将逗号产出为字段。字节模式应使用单独的“字节长度”概念，不混用字符数。

**项目行为澄清（2026-09-30 用户验收）**：输出／解析列表的 item 数量不是“字符长度比较”的依据，也不要求等于报文按分隔符拆出的段数。列表规则从第一个字段起按顺序消费所需的段；多余段不产生隐式输出，缺少已配置字段才解析失败。例如只配置一个 `string` 项时，`4,3,4,5,6,7` 解析出字符串 `"4"`；若另行启用字符长度比较，则在分隔和字段解析前按整条文本的长度 11 校验。

**项目仍需明确的协议约定**：长度校验以“分帧后、去掉帧结束符的有效文本”为对象；原始接收历史同时保留原始字节，以便复核。若某协议需要把结束符计入长度，应由该协议配置显式声明，而非隐藏地随 UI 开关改变。文本长度单位建议明确为 Unicode 字符数；遇到多字节编码时，不要将字符数误当 UTF-8 字节数。

校验失败时保留原始报文、时间、设备和失败阶段／原因；当前轮的字段结果不得残留上一轮值，不发布部分成功的字段，不执行依赖解析成功的触发与回复。接收历史建议记录成功与失败，不仅记录最终的字段文本；十六进制显示是同一份原始字节的展示方式，不是再次解析。

历史差异：原 `CommunicationManagerViewModel.SplitReceiveValues` 在启用 `CharacterLengthCompare` 后用 `Substring` 按长度切片；2026-09-29 已移至 `CommunicationReceiveProcessor` 并改为整报文校验。2026-09-30 又移除了“列表项数必须等于分隔段数”的附加限制。

2026-09-30 目标绑定修订：VM Modbus 示例先绑定地址、轮询保持寄存器，再对寄存器**数据字节**做字节匹配；先前“Modbus 不适合字节匹配”的说法不成立。OPC UA 不能强制套入文本／字节解析：它应绑定数据点（变量节点），检查质量后按实际值类型选择规则。完整映射见目标绑定最终方案。

## 5. 字段比较、身份与组装的项目决策

- **原始报文与解析字段类型分开**：TCP 接收的原始字节及解码后的文本不因字段类型选择而被改写。按本项目当前验收口径，文本模式 UTF-8 解码、分隔后字段仍为 `string`，不强制转成数值；若 item 配为 `int/float`，即使文本为 `"4"`，也判解析失败、清空数据结果并显示 `NG`。二进制模式仍可按协议读取原生数值。VM 帮助的 `ABC,2` 示例曾把第二字段设为 `int`，这与本项目当前约束有差异；不要把项目约束误述为 VM 的通用实现。
- Vision Master 文本比对帮助列出“不比较、=、!=”，并要求数值类型配置范围；**本项目已确认的界面规则不同**：`int/float` 可选“不比较／范围”，`string` 可选“不比较／等于／不等于”。不要仅为模仿参考产品而改回旧下拉选项。
- 状态统一为 `OK/NG`：不比较在**字段成功解析**后为 `OK`；范围为含端点的 `[Minimum, Maximum]`，落入为 `OK`、否则 `NG`；字符串按明确的比较方式判断。无报文、长度不符、字段缺失或文本字段类型不匹配不能显示 `OK`，应显示“未接收”或具体解析错误；事件整体成功与单字段比较状态须分别定义。
- 解析字段创建时分配稳定 GUID。名称是可修改显示名称；组装与下游按 `SourceFieldId` 绑定，重命名刷新快照，删除后同名新增不恢复旧绑定。组装页只提供当前事件的解析字段，不默认追加全局变量。
- 组装回复是事件处理完成后的可选动作，必须明确触发条件（仅解析成功还是仅比较通过）；建议默认仅**整体通过**时回复，可按产品需求提供显式失败响应配置，不能让部分失败字段隐式进入回复。

## 6. 分阶段实施与验收重点

1. **先收敛接收链**：分帧、可选整报文长度校验、分隔／字节解析、已配置字段是否足够与类型校验、`OK/NG` 计算、原子发布、带原因的历史。优先使用用户实际运行的 Debug 配置验证；不能只凭构建通过宣称收发逻辑已验收。
2. **再接通消费链**：稳定字段绑定、有效接收事件发布、触发配置与工作流执行层快照；验证接收失败不触发。
3. **再实现主动发送**：发送事件格式定义和流程发送动作分离，类型匹配、分隔符／结束符／编码、发送失败可追踪。
4. **最后补自动发送**：响应配置和心跳共享底层发送服务，正确处理连接断开、取消和方案切换。
5. **示例与诊断**：提供 TCP `ABC,2`、失败长度、失败类型、数值范围 NG、组装回复、发送事件调用的端到端用例；文档示例不与业务设置混为一页。

以上为 2026-09-29 的参考与实施划分；最新落地状态见下节及协作记录。

## 7. 2026-10-08 发送事件实现

通讯管理器所有分隔符入口统一使用 CommunicationSeparators 数据目录及 CommunicationUiResources 显示样式，保持普通 ComboBox，不新增自定义控件。默认选项共享，各事件的选中值与已保存自定义值独立；接收仍默认逗号、发送仍默认分号，不迁移或改写原配置。表格单元格文字统一水平／垂直居中，编辑框保留铺满宽度；界面资源局部作用，不改全局主题。

分隔符选项采用显式 DataTemplate 绑定 DisplayName，不依赖全局主题模板对 DisplayMemberPath 的隐式支持；显示标签与选中 Value 始终分离，避免向用户显示选项对象或让真实换行值撑开下拉行。

- 列表“＋”打开“事件管理”窗口，处理方式仅提供文本，事件类型为直接输出／组装输出。创建后列表使用稳定事件 GUID，支持右键重命名和删除；没有事件时显示空状态。
- 直接输出：绑定设备及必要目标，配置可编辑分隔符（默认 `;`），参数列表按配置顺序输出。组装输出：输入配置维护设备、目标及参数，组装配置维护分隔符和输出列表；输出可引用当前事件输入参数或填写常量。表头“设备”修正为“类型”。
- 参数列表合并显示序号、名称、类型、可编辑测试值、只读数据结果、状态，不再重复列出测试参数。仅保留“发送测试”，点击后执行设备写入并展示实际发送内容与成功／失败；移除预览入口，结束符只用于原始文本设备。打开配置页、添加规则或修改测试值均不自动发送；测试值不替代流程调用方提供的当次参数快照。
- 输入／组装页签使用局部主题模板，文字、选中下划线及悬停色跟随主题资源，不修改全局主题。两种输出的分隔符改为明确标签的非编辑下拉：无、逗号、分号、空格、竖线、CR、LF、CRLF；显示标签与真实分隔值分离，稳定选项集合避免选中值因刷新丢失，已有自定义分隔符保留为独立选项。
- 与接收事件一致，新增、修改、删除发送配置实时同步到当前解决方案共享对象；不提供发送页独立“保存配置”，也不因发送配置改动触发 OPC UA 设备保存／撤销提示。保存解决方案时统一持久化到本地，未保存时关闭通讯窗口仍保留内存配置；设备管理的已有保存机制不在本轮修改范围。
- 参数及组装字段保存稳定 GUID；组装引用以 `SourceFieldId` 为准，名称变化刷新显示路径，删除后同名新增不恢复旧绑定。运行时结果、页签和发送历史不保存到方案；历史保留最近 200 条，打开和更新时自动滚动到底部。
- 原始 TCP／UDP／串口按 UTF-8 文本发送。Modbus 输出按绑定地址块的位数／字节序编码并使用 FC16 写入；同块类型须一致，只读、超容量或超过单次写入上限时整次失败，不截断发送。OPC UA 最终输出为一个原生标量，须与目标实际类型匹配且有写权限；S7／CIP 的发送事件暂未接通。
- `CommunicationSendEventFormatter` 独立组装参数快照；配置常量按声明类型校验，调用方传来的原生值必须类型匹配，不将字符串强制转换为数字。`CommunicationApplicationService.SendEventAsync` 接受发送事件 GUID 及以参数字段 GUID 为键的值快照，供宿主后续发送模块调用；该服务不访问 WPF 控件、不调度流程。工具插件接入时需通过 SDK 服务契约注入，不能直接引用 UI 宿主程序集。
- 已验证格式组装、稳定绑定、方案序列化、WPF 创建窗口与页签切换、TCP 回环发送、Modbus FC16 回环写入及 OPC UA 本地测试服务器写入。实际设备与 Visual Studio 设计时／布局人工验收以协作记录为准。
