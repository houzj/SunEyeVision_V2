# SunEyeVision 相机采集架构与设备管理最终方案

**日期：** 2026-09-18  
**状态：** 架构方案冻结前评审稿  
**适用范围：** 相机设备抽象、品牌/协议兼容、设备运行时、相机工具、工作流采集、插件接口和 UI 边界

## 1. 结论摘要

当前 `src/DeviceDriver/`、`CameraPoolManager`、Hikvision 相机实现、旧版 `SimulatedCameraDriver` 以及相机 UI 均视为占位实现，不能作为目标架构的参考依据。后续应以本方案重新冻结接口和边界，再逐步替换现有代码。

最终采用“架构上有设备运行时管理器、用户侧以相机工具为主、设备维护作为同一应用中的高级场景”的混合方案。当前项目没有用户管理系统，因此本方案不把普通用户和工程师视为已有权限角色；未来接入用户管理后，再将页面和操作映射到权限策略。

- 系统内部必须存在 `CameraRuntimeManager`，统一管理设备会话、并发访问、连接、重连、采集流和资源租约。
- 普通工作流开发者主要使用“相机采集工具”，不要求先进入独立设备管理器。
- 当前所有用户可以访问“设备与驱动”页面，但默认只展示常用操作；高级诊断、厂商参数和危险操作通过渐进式展开控制复杂度。
- 未来如果接入用户管理，可将“设备维护”“厂商参数”“设备删除”“运行中断开”等操作绑定到权限，而不改变底层接口。
- 物理设备、逻辑设备、采集配置和运行期快照必须分离建模。
- 兼容策略采用“标准协议优先、厂商 SDK 兜底、能力模型驱动 UI、扩展参数动态化”。
- 相机工具只持有逻辑相机引用和采集配置，不直接拥有物理设备，也不直接访问厂商 SDK。
- 相机采集应作为工作流中的正式输入工具/节点，由工作流运行时将帧送入图像处理链路。

该选择既避免了“每个工具重复连接设备”的失控，也避免了“所有用户必须先维护设备管理器”的复杂体验。

## 2. 产品形态取舍

### 2.1 仅有设备管理器

设备管理器统一发现、连接和配置相机，工作流只引用已配置设备。

优点：

- 设备生命周期集中管理；
- 多流程共享设备比较容易；
- 适合现场部署、设备诊断和权限管理；
- 可以统一处理驱动、重连、参数恢复和资源占用。

缺点：

- 设备配置和工作流采集配置容易分散；
- 用户必须理解设备、接口、驱动和逻辑名称的区别；
- 简单的单次采集需要跨多个界面；
- 流程复制和迁移时，设备外部依赖不够直观；
- 普通算法开发者会接触过多底层概念。

### 2.2 仅有相机工具

每个相机工具自行选择、连接和配置设备。

优点：

- 工作流上下文完整，配置直观；
- 适合快速试用和低代码体验；
- 单个流程迁移时配置更集中；
- 用户不必先维护一个全局设备列表。

缺点：

- 同一设备可能被多个工具重复打开；
- 每个工具都要重复实现超时、重连、参数和释放；
- 多流程运行时无法统一做资源仲裁；
- 预览、调试和正式运行容易互相抢占设备；
- 不同工具之间的设备行为会逐渐分叉。

### 2.3 最终选择：混合架构

不在产品上强制二选一，而是分离“内部能力”和“用户入口”：

```text
当前产品形态：
  工作流开发场景：相机采集工具
  设备维护场景：设备与驱动维护页
  内部架构：CameraRuntimeManager
  底层实现：标准协议适配器 / 厂商 SDK 适配器 / 模拟适配器

未来权限模型（可选）：
  用户 / 角色 / 权限策略
              ↓
  页面可见性与操作授权
              ↓
  同一套 CameraRuntimeManager 和适配器
```

主流视觉软件也采用类似分工。Cognex VisionPro 将设备配置与 Acquisition/FIFO 工具关联；NI Vision Builder 同时提供 MAX 设备配置和 Acquire Image 工作流步骤；HALCON 通过 Image Acquisition Assistant 配置采集，并用 Image Source 统一封装插件、接口、设备和数据流。

参考：

- [Cognex VisionPro：Acquiring Camera Images](https://docs.cognex.com/vpromx_1000/web/en/visionpro/Content/Topics/users-guide/quickbuild/acquire-images.htm?TocPath=VisionPro+Users+Guide%7CQuickBuild%7CUsing+the+Workspace%7C_____1)
- [NI Vision Builder：Vision Acquisition Software](https://www.ni.com/pdf/manuals/375131g.html)
- [HALCON：Image Acquisition Assistant](https://www.mvtec.com/fileadmin/Redaktion/mvtec.com/products/halcon/documentation/halcon/hdevelop_users_guide.pdf)
- [HALCON：Image Source Concept](https://www.mvtec.com/doc/halcon/2605/en/toc_imagesource.html)

## 3. 总体架构

```text
工作流中的 Camera Tool
          ↓
Plugin.SDK / Host Service Contract
          ↓
ICameraCaptureService
          ↓
CameraRuntimeManager
          ↓
CameraSession（单设备会话、锁、状态、流）
          ↓
ICameraAdapter
   ├─ GenTL / GenICam Adapter
   ├─ GigE Vision Adapter
   ├─ USB3 Vision Adapter
   ├─ Camera Link / Frame Grabber Adapter
   ├─ Vendor SDK Adapter
   └─ Simulated Adapter
```

分层职责：

- `Plugin.SDK`：只定义相机无关的执行契约、帧契约和服务访问契约。
- `DeviceDriver`：定义设备模型、适配器、协议实现和厂商 SDK 集成。
- `CameraRuntimeManager`：管理设备会话、资源、连接、重连、流和诊断。
- `Workflow`：负责相机采集节点、运行快照、图像队列和工作流取消。
- `UI`：负责设备维护界面、相机工具属性面板和状态展示，不访问厂商 SDK。
- 厂商适配器：只负责把具体 SDK/协议映射到统一设备能力，不参与工作流调度和 UI。

## 3.1 新契约的代码归属

新契约不能同时在 `Plugin.SDK`、`DeviceDriver` 和 `Workflow` 中各定义一份。采用“插件/工作流可见的稳定契约”和“驱动内部的硬件契约”两层归属：

```text
src/Plugin.SDK/Devices/Camera/
  ├─ CameraDeviceRef.cs              逻辑设备引用和稳定身份引用
  ├─ CameraDescriptor.cs             对插件和工作流公开的设备描述
  ├─ CameraFrame.cs                  插件/工作流使用的统一帧
  ├─ CameraCaptureRequest.cs         采集请求
  ├─ CameraParameterSnapshot.cs      运行期参数快照
  ├─ CameraCapabilities.cs           能力描述
  ├─ CameraState.cs                  稳定状态枚举
  ├─ CameraErrorCode.cs              稳定错误码
  ├─ ICameraCaptureService.cs        宿主提供给工具的采集服务
  └─ IExecutionServices.cs           受控的执行期服务访问入口

src/DeviceDriver/Cameras/Contracts/
  ├─ ICameraAdapter.cs               驱动/协议适配器接口
  ├─ ICameraDiscoveryProvider.cs     设备发现器接口
  ├─ ICameraParameterProvider.cs     原始参数 Schema 与读写
  ├─ CameraParameterSchema.cs        动态节点和厂商参数描述
  ├─ CameraSession.cs                单设备会话内部模型
  └─ CameraRuntimeManager.cs         设备运行时管理器

src/Workflow/Camera/
  ├─ CameraWorkflowBinding.cs        节点中的相机引用和参数覆盖
  └─ CameraRunSnapshot.cs            一次工作流运行的相机快照
```

原则：

- `Plugin.SDK` 中的类型不能引用厂商 SDK、WPF 或 `DeviceDriver`；
- `DeviceDriver` 可以实现 SDK 契约，但不能让 SDK 反向依赖驱动；
- `Workflow` 只消费 SDK 稳定契约和自身运行快照，不消费厂商类型；
- UI 只消费运行时服务和 Schema，不直接消费厂商适配器；
- 同名的 `CameraFrame`、参数快照和错误码不得在多个层重复定义。

### 3.1.1 M0 冻结范围

以下内容在 M0 一并冻结，而不是推迟到 M5：

- `CameraDeviceRef`、`CameraDescriptor`；
- `CameraFrame` 和帧所有权规则；
- `CameraCaptureRequest`；
- `CameraParameterSnapshot`；
- `CameraCapabilities`；
- `CameraState`；
- `CameraErrorCode`；
- `ICameraCaptureService`；
- 最小化的 `IExecutionServices`。

M5 不再定义这些接口，M5 只负责：

- 插件消费 SDK 相机契约；
- 宿主服务注入验证；
- 插件样例和兼容性验证；
- 第三方插件迁移说明。

`IExecutionServices` 只提供受控服务访问，不暴露 DI 容器、WPF 对象或 `CameraRuntimeManager`：

```csharp
public interface IExecutionServices
{
    T? Get<T>() where T : class;
}
```

如果 M0 期间确认所有工具都由宿主显式注入服务，可以保留该接口为空实现或延后启用，但其边界应先冻结，避免 M5 再修改执行上下文结构。

必须保持以下依赖边界：

- UI 不承担工作流调度。
- 工作流执行层不访问 WPF 控件。
- 插件不得依赖 UI 宿主程序集或具体厂商程序集。
- 工具不得自行创建厂商 SDK 句柄。
- 设备驱动不得反向引用工作流执行引擎。

## 4. 设备模型

### 4.1 物理设备

物理设备描述真实硬件及其可发现信息：

```csharp
public sealed record CameraDescriptor(
    string DeviceId,
    string Manufacturer,
    string Model,
    string SerialNumber,
    CameraTransport Transport,
    string? IpAddress,
    string? MacAddress,
    IReadOnlyDictionary<string, object?> Metadata);
```

设备身份不能只依赖 IP 地址。推荐身份优先级：

1. 厂商 + 序列号；
2. 厂商 + MAC 地址；
3. 协议层稳定设备标识；
4. 最后才使用 IP + 端口。

### 4.2 逻辑设备

逻辑设备是用户可理解的稳定别名，例如“上料位相机”“检测位相机”。逻辑名称与物理设备分离，以便 IP 改变、设备替换和流程迁移。

```text
逻辑设备：检测位相机
    ↓
物理身份：Hikvision + SerialNumber
    ↓
当前连接地址：192.168.1.20
```

### 4.3 采集配置

采集配置描述某个工作流工具如何使用相机，不等于设备全局状态：

```csharp
public sealed record CameraCaptureProfile(
    string CameraRef,
    CameraTriggerMode TriggerMode,
    TimeSpan FrameTimeout,
    IReadOnlyDictionary<string, object?> ParameterOverrides);
```

工具保存的是 `CameraRef` 和参数覆盖，不保存厂商句柄，也不直接保存不可迁移的连接对象。

## 5. 品牌与接口兼容策略

### 5.1 标准协议优先

第一优先级支持标准采集接口：

- GenICam / GenTL；
- GigE Vision；
- USB3 Vision；
- Camera Link 和采集卡接口；
- DirectShow / Media Foundation；
- 文件、序列图像和模拟图像源。

标准接口是品牌兼容的基础。品牌不是最适合的第一层抽象，协议和能力才是。

### 5.2 厂商 SDK 兜底

对于标准接口无法覆盖的功能，再通过独立适配器支持：

```text
HikvisionAdapter
BaslerAdapter
DahuaAdapter
DahengAdapter
FLIRAdapter
KeyenceAdapter
```

厂商适配器负责：

- 设备发现；
- 设备连接和释放；
- 参数读写映射；
- 帧格式转换；
- 厂商特有触发能力；
- 厂商扩展参数。

厂商适配器不负责：

- 工作流调度；
- UI 逻辑；
- 全局变量；
- 工具面板；
- 多流程执行策略。

### 5.3 能力模型

不能假设所有品牌都支持相同参数。每台设备必须暴露能力描述：

```csharp
public sealed class CameraCapabilities
{
    public bool SupportsSoftwareTrigger { get; init; }
    public bool SupportsHardwareTrigger { get; init; }
    public bool SupportsContinuousCapture { get; init; }
    public bool SupportsExposure { get; init; }
    public bool SupportsGain { get; init; }
    public bool SupportsRoi { get; init; }
    public bool SupportsLineTrigger { get; init; }

    public IReadOnlyList<CameraFeatureDescriptor> Features { get; init; }
        = Array.Empty<CameraFeatureDescriptor>();
}
```

UI 和工具面板必须根据能力显示参数，而不是固定展示曝光、增益、伽马、硬触发等选项。

### 5.4 核心能力与扩展能力分离

统一接口只保留跨品牌的稳定能力：

```csharp
public interface ICameraAdapter : IAsyncDisposable
{
    CameraDescriptor Descriptor { get; }
    CameraCapabilities Capabilities { get; }
    CameraConnectionState State { get; }

    Task ConnectAsync(
        CameraConnectionOptions options,
        CancellationToken cancellationToken);

    Task DisconnectAsync(CancellationToken cancellationToken);

    Task<CameraFrame> CaptureAsync(
        CameraCaptureRequest request,
        CancellationToken cancellationToken);

    Task StartStreamAsync(
        CameraStreamRequest request,
        ICameraFrameSink sink,
        CancellationToken cancellationToken);

    Task StopStreamAsync(CancellationToken cancellationToken);

    Task<CameraParameterSnapshot> ReadParametersAsync(
        CancellationToken cancellationToken);

    Task ApplyParametersAsync(
        CameraParameterSnapshot snapshot,
        CancellationToken cancellationToken);
}
```

厂商参数通过能力扩展访问：

```csharp
public interface ICameraFeatureAccess
{
    bool Supports(string featureName);

    Task<object?> GetAsync(
        string featureName,
        CancellationToken cancellationToken);

    Task SetAsync(
        string featureName,
        object? value,
        CancellationToken cancellationToken);
}
```

这样既能支持统一工具，也不会为了最低公分母而丢失厂商高级能力。

## 6. 设备运行时管理器

内部必须有设备运行时管理器，但它不等于一个强制性的用户页面。

```csharp
public interface ICameraRuntimeManager
{
    IReadOnlyList<CameraRuntimeInfo> Cameras { get; }

    Task<CameraSessionHandle> OpenAsync(
        string cameraRef,
        CameraAccessMode accessMode,
        CancellationToken cancellationToken);

    Task CloseAsync(
        string cameraRef,
        CancellationToken cancellationToken);

    Task<CameraFrame> CaptureAsync(
        string cameraRef,
        CameraCaptureRequest request,
        CancellationToken cancellationToken);
}
```

运行时管理器负责：

- 设备发现和注册；
- 逻辑设备到物理设备的解析；
- 单设备会话生命周期；
- 独占/共享访问模式；
- 连接和断开；
- 断线重连；
- 采集流管理；
- 并发访问控制；
- 设备健康状态；
- 资源租约；
- 运行日志和诊断计数。

### 6.1 访问模式

相机工具打开设备时应声明访问模式：

- `Exclusive`：独占采集和参数控制；
- `SharedRead`：允许多个消费者读取同一个采集流；
- `Preview`：低优先级预览，正式运行时可被暂停；
- `Diagnostic`：设备测试和参数读取。

默认工作流采集使用 `Exclusive`，预览不得隐式抢占正式运行会话。

### 6.2 单设备串行化

每台相机必须通过一个串行操作上下文或等价锁保护 SDK 调用，禁止多个线程同时操作同一厂商句柄。连接、断开、触发、改参和停止采集之间要有明确的状态转换。

## 7. 状态机、重连与异常策略

建议状态：

```text
Offline
  ↓
Connecting
  ↓
Connected
  ↓
StartingCapture → Capturing
  ↓                    ↓
StoppingCapture   Reconnecting
                       ↓
                 Connected / Faulted
```

重连规则：

- 只对可恢复错误重连，例如网络断开、设备暂时不可用；
- 参数不支持、驱动缺失、设备身份不匹配等错误不盲目重连；
- 使用指数退避，例如 `1s、2s、5s、10s、30s`；
- 重连前停止旧采集循环并释放旧句柄；
- 重连成功后重新应用运行期参数快照；
- 如果原来正在连续采集，按策略恢复采集；
- 重连过程向 UI 和工作流发布明确状态，不伪装成正常连接。

统一错误码建议包括：

- `CameraNotFound`；
- `ConnectionTimeout`；
- `ConnectionRejected`；
- `DeviceBusy`；
- `TriggerTimeout`；
- `FrameTimeout`；
- `ParameterUnsupported`；
- `StreamStopped`；
- `DeviceDisconnected`；
- `DriverUnavailable`；
- `OperationCancelled`；
- `Unknown`。

所有操作都必须支持取消和超时。日志至少带有 `DeviceId`、`RunId`、`WorkflowId`、`NodeId`、操作名称、重试次数、超时时间和厂商错误码。

## 8. 触发与连续采集

软触发、硬触发和连续采集必须是明确的采集模式，不能允许同一设备同时执行互相冲突的操作。

```text
Idle
 ├─ SoftwareTrigger → AwaitFrame
 ├─ HardwareTrigger → Streaming
 └─ Continuous      → Streaming
```

每一帧必须携带：

- `DeviceId`；
- `FrameId`；
- 时间戳；
- `TriggerId`；
- `RunId`；
- `WorkflowId` 和 `NodeId`；
- 宽、高、像素格式；
- 曝光、增益等实际参数；
- 丢帧、超时、重连等诊断信息。

连续采集必须使用可取消、可等待的异步任务。停止采集必须等待采集循环退出，不能只设置一个布尔值后立即释放设备句柄。

帧所有权必须明确：驱动创建后交给帧接收器，队列或消费者完成处理后释放；事件订阅者不得随意释放共享帧。

## 9. 参数快照和工作流集成

相机参数分成三类：

1. 设计期配置：保存到方案或设备配置；
2. 运行期快照：工作流启动时复制；
3. 设备实际状态：从硬件读取，仅用于诊断和 UI 展示。

工作流启动时创建：

```text
Solution
 ├─ GlobalVariableSnapshot
 ├─ CameraRuntimeSnapshot
 ├─ WorkflowRunRequest
 └─ CancellationToken
```

运行规则：

- UI 在运行中修改参数，不影响已开始的运行；
- 工作流节点只读取本次运行快照；
- 设备实际状态不自动回写设计期全局变量；
- 需要回写时，必须经过显式输出绑定或运行结果提交动作；
- 参数覆盖必须记录来源：设备默认值、设备配置、工具覆盖或运行期覆盖。

推荐模型：

```csharp
public sealed record CameraRuntimeSnapshot(
    string CameraRef,
    CameraTriggerMode TriggerMode,
    CameraCaptureSettings CaptureSettings,
    IReadOnlyDictionary<string, object?> Properties,
    DateTimeOffset CapturedAt);
```

## 10. 相机工具设计

相机工具负责业务语义，不负责物理设备生命周期。

工具职责：

- 选择逻辑相机；
- 配置触发方式；
- 配置曝光、增益、ROI 等采集参数；
- 执行单次采集或进入连续流；
- 输出 `IVisionImage`；
- 输出帧元数据、时间戳和设备状态；
- 支持输入绑定、输出绑定和运行期取消。

工具不负责：

- 注册厂商驱动；
- 创建 SDK 句柄；
- 管理所有系统设备；
- 启动独立后台线程；
- 写入全局静态状态；
- 访问 WPF 控件。

工具只保存类似以下配置：

```json
{
  "cameraRef": "inspection-camera",
  "triggerMode": "Software",
  "timeoutMs": 3000,
  "parameterOverrides": {
    "ExposureTime": 10000,
    "Gain": 2.5
  }
}
```

## 11. Plugin.SDK 接口

插件 SDK 只提供相机无关契约，不引用 UI、厂商 SDK 或 `CameraRuntimeManager`。

建议接口：

```csharp
public sealed record CameraCaptureRequest(
    string CameraRef,
    CameraTriggerMode TriggerMode,
    TimeSpan Timeout,
    IReadOnlyDictionary<string, object?> Parameters);

public sealed record CameraFrame(
    string CameraRef,
    long FrameId,
    DateTimeOffset Timestamp,
    IVisionImage Image,
    IReadOnlyDictionary<string, object?> Metadata);

public interface ICameraCaptureService
{
    Task<CameraFrame> CaptureAsync(
        CameraCaptureRequest request,
        CancellationToken cancellationToken);
}
```

当前 `ExecutionContext` 可增加受控服务访问能力，但不应直接暴露 DI 容器：

```csharp
public interface IExecutionServices
{
    T? Get<T>() where T : class;
}
```

宿主负责注入 `ICameraCaptureService`，插件只依赖 SDK 契约。

## 12. UI 边界与设备管理器界面

### 12.1 当前没有用户管理系统时的原则

当前不应在 UI 中硬编码“普通用户”和“工程师”两类权限，也不应因为未来可能增加权限系统而拆出两套设备管理界面。建议采用以下方式：

- 所有用户使用同一设备管理页面；
- 页面默认展示发现、添加、连接、测试和绑定等常用操作；
- 厂商高级参数、协议诊断、原始属性和危险操作放入“高级设置/诊断”区域；
- 高级区域当前可以通过展开按钮进入；
- 将来接入权限系统后，用 `IPermissionService` 控制按钮和区域是否可见、是否可编辑；
- 业务层仍通过同一套运行时服务校验操作，不能只依赖 UI 隐藏按钮。

设备管理器不是账号管理器。它管理设备资源、驱动和连接状态；未来用户系统只负责决定谁可以执行哪些操作。

### 12.2.1 复用 SDK 图像显示能力

相机预览可以复用平台现有的图像显示能力，但不能直接复用带“图像源选择”语义的工作流控件。当前项目已有：

- SDK 层 `IVisionImage` 图像抽象；
- SDK 层 `IVisionImageDisplayBridge` 图像显示桥；
- UI 层现有图像显示面板和 `IVisionImage → BitmapSource` 转换实现；
- 工作流场景的 `ImageSourceSelector`，该控件负责选择节点/文件等图像源，不适合直接作为相机预览控件。

推荐新增一个很薄的 `CameraPreviewHost` 或 `CameraPreviewControl`：

```text
CameraRuntimeManager
        ↓ CameraFrame / IVisionImage
CameraPreviewViewModel
        ↓ CurrentImage
CameraPreviewHost
        ↓ 使用 IVisionImageDisplayBridge
SDK/UI 图像显示控件
```

预览控件只负责显示，不负责选择图像源：

```text
CameraPreviewHost
  ├─ Image：当前相机帧
  ├─ IsStreaming：是否正在预览
  ├─ FrameRate：当前显示帧率
  ├─ FrameSize：图像尺寸
  ├─ Zoom / Fit / ActualSize
  └─ StatusOverlay：连接、等待帧、超时、断线
```

不应在该控件中加入：

- 图像源下拉框；
- 工作流节点选择器；
- 文件图像选择器；
- 相机连接逻辑；
- 厂商 SDK 调用；
- 预览线程和设备句柄。

相机帧的所有权仍由运行时和预览会话管理。UI 只接收用于显示的图像引用或显示副本，不能在 UI 线程直接释放驱动正在使用的原始缓冲区。

实时显示还需要增加两个运行约束：

- 采集帧率和显示帧率解耦，例如相机 120 fps 时 UI 只显示 15～30 fps；
- UI 使用 Dispatcher 更新当前显示帧，旧帧未显示时可以丢弃显示副本，但不能影响工作流采集队列。

因此，设备管理器预览不会引入第二套图像格式或显示体系：相机适配器只负责产出统一 `IVisionImage`，SDK/UI 显示层负责显示，`CameraPreviewHost` 只负责把两者连接起来。

### 12.2.3 自动发现、接口识别与品牌识别

自动发现应由多个 `ICameraDiscoveryProvider` 并行执行，而不是让 UI 先询问用户品牌或接口：

```text
CameraDiscoveryCoordinator
        ├─ GenTLDiscoveryProvider
        ├─ GigEVisionDiscoveryProvider
        ├─ Usb3VisionDiscoveryProvider
        ├─ CameraLinkDiscoveryProvider
        ├─ HikvisionDiscoveryProvider
        ├─ BaslerDiscoveryProvider
        └─ SimulationDiscoveryProvider
```

每个发现器只负责发现和返回设备描述，不负责决定最终 UI，也不直接创建长期运行会话。发现结果至少包含：

- `DeviceIdentity`：序列号、MAC、协议 ID 等稳定身份；
- `Manufacturer` 和 `Model`；
- `Transport` 和 `Protocol`；
- 可用的 `AdapterId` 列表；
- 连接地址、网卡或采集卡通道；
- 是否已被现有逻辑设备绑定；
- 发现来源和错误信息。

适配器选择顺序：

```text
设备支持标准协议？
  ├─ 是 → 优先使用标准适配器
  └─ 否 → 尝试已安装的厂商 SDK 适配器

标准适配器能力不足？
  ├─ 否 → 使用标准适配器
  └─ 是 → 在同一设备上提供厂商适配器作为可选后端
```

同一个设备可能同时出现多个候选后端，例如：

```text
Hikvision MV-CA050
  ├─ GigE Vision / GenICamAdapter
  └─ Hikvision SDK / HikvisionAdapter
```

普通用户看到的是一台设备，系统内部记录候选适配器，并默认选择优先级最高且能力完整的适配器。只有标准适配器无法提供必要能力，或用户在高级诊断中明确选择时，才使用厂商适配器。

品牌不需要用户手工选择：

- GigE/USB 设备通过协议发现响应、GenICam 信息和设备身份识别品牌；
- 厂商发现器通过厂商 SDK 枚举设备并返回品牌；
- UI 结果列表提供品牌筛选，而不是品牌选择向导；
- 发现异常时，设备行显示“发现来源”和“适配器错误”，便于诊断。

普通流程只保留三个动作：

```text
添加设备 → 自动发现 → 选择设备并保存
```

接口、品牌和适配器选择都由系统完成；接口筛选、网卡选择、厂商 SDK 强制选择和手动 IP 等功能属于高级诊断，不进入普通添加流程。

### 12.3 不同品牌参数的真正适配方式

“统一设备详情外壳”不代表所有品牌使用同一组固定字段，也不代表只显示曝光、增益和触发三个参数。正确做法是：

```text
设备连接
   ↓
读取协议/厂商参数描述
   ↓
转换为 CameraParameterSchema
   ↓
参数编辑器根据 Schema 动态生成控件
   ↓
读回、校验、应用、显示错误
```

相机参数适配分为三种情况。

#### A. 标准参数：使用统一语义

对于不同品牌都存在、且语义稳定的参数，映射到统一参数名：

```text
ExposureTime
Gain
Width
Height
OffsetX
OffsetY
PixelFormat
AcquisitionFrameRate
TriggerMode
TriggerSource
TriggerActivation
```

例如海康、Basler、大恒都支持曝光时间，但底层名称可能不同：

```text
统一名称：ExposureTime

Hikvision SDK：ExposureTime
Basler Pylon：ExposureTime
GenICam：ExposureTime
大恒 SDK：ExposureTime
```

UI 只依赖统一参数描述，适配器负责把统一名称映射到真实 SDK 或 GenICam 节点。

#### B. 标准协议中的动态参数：读取设备节点描述

GenICam/GenTL 设备不能假设固定参数集合。适配器应读取设备的节点树或参数描述，得到：

- 参数名称；
- 显示名称；
- 数据类型；
- 最小值、最大值、步长；
- 枚举项；
- 是否只读；
- 当前访问条件；
- 依赖参数；
- 所属分组；
- 是否需要停止采集后才能修改。

因此，标准相机的参数页应该由节点描述动态生成，而不是在 XAML 中写死。

#### C. 品牌专属参数：扩展参数页或扩展控件

对于以下参数，不应强行塞进统一字段：

- 海康的 UserSet、LineDebouncer、Chunk 数据；
- Basler 的 Pylon 特有触发延迟和事件配置；
- 大恒的特定白平衡、锐化和降噪参数；
- 采集卡的 CameraLink Tap、时钟和线路参数；
- 3D 相机的曝光序列、投影器和深度参数。

这些参数通过厂商扩展分组或独立参数页提供。核心 UI 不需要知道具体品牌，但品牌适配器可以提供参数 Schema 或专属编辑器。

### 12.4 参数 Schema 与动态编辑器

建议定义与 UI 无关的参数描述模型：

```csharp
public enum CameraParameterKind
{
    Boolean,
    Integer,
    Double,
    String,
    Enumeration,
    Command,
    StringList,
    Rectangle,
    Custom
}

public sealed class CameraParameterDescriptor
{
    public string Name { get; init; } = string.Empty;
    public string DisplayName { get; init; } = string.Empty;
    public string Category { get; init; } = string.Empty;
    public CameraParameterKind Kind { get; init; }
    public object? Value { get; init; }
    public object? Minimum { get; init; }
    public object? Maximum { get; init; }
    public object? Increment { get; init; }
    public IReadOnlyList<CameraEnumValue> EnumValues { get; init; }
        = Array.Empty<CameraEnumValue>();
    public bool IsReadOnly { get; init; }
    public bool IsAvailable { get; init; }
    public bool RequiresStopped { get; init; }
    public string? VisibilityExpression { get; init; }
    public string? Description { get; init; }
}

public sealed class CameraParameterSchema
{
    public string AdapterId { get; init; } = string.Empty;
    public string SchemaVersion { get; init; } = "1.0";
    public IReadOnlyList<CameraParameterDescriptor> Parameters { get; init; }
        = Array.Empty<CameraParameterDescriptor>();
}
```

设备适配器提供参数 Schema：

```csharp
public interface ICameraParameterProvider
{
    Task<CameraParameterSchema> GetSchemaAsync(
        CancellationToken cancellationToken);

    Task<IReadOnlyDictionary<string, object?>> ReadValuesAsync(
        IReadOnlyCollection<string> names,
        CancellationToken cancellationToken);

    Task ApplyValuesAsync(
        IReadOnlyDictionary<string, object?> values,
        CancellationToken cancellationToken);
}
```

UI 根据 `CameraParameterKind` 选择编辑器：

```text
Boolean      → CheckBox
Integer      → NumericUpDown
Double       → NumericUpDown / Slider
Enumeration  → ComboBox
Command      → Button
Rectangle    → ROI 编辑器
String       → TextBox
Custom       → 厂商扩展控件
```

这样，新增品牌通常只需要新增适配器和参数 Schema，不需要修改设备管理器主窗口 XAML。

### 12.5 三层参数 UI

设备管理器中的参数 UI 建议分成三层，而不是把所有参数一次性堆在同一页面：

```text
第一层：采集常用参数
  曝光、增益、分辨率、像素格式、触发方式、帧率

第二层：标准高级参数
  黑电平、伽马、白平衡、ROI、触发延迟、线路配置

第三层：厂商/设备原生参数
  从适配器 Schema 动态生成，或加载厂商专属编辑器
```

第一层服务于大多数工作流；第二层服务于调试和工程配置；第三层保留品牌能力，不为了统一界面而牺牲功能。

### 12.6 何时需要品牌专属 UI

不是每个品牌都必须开发一套完整的 WPF 页面。采用以下判断规则：

```text
参数可以用标准类型表达？
  ├─ 是 → 使用通用动态参数编辑器
  └─ 否 → 是否存在复杂交互或实时预览？
             ├─ 否 → 使用 Custom 参数描述
             └─ 是 → 加载品牌专属编辑器
```

品牌专属 UI 只处理复杂交互，例如：

- 多区域曝光配置；
- 3D 深度和投影器配置；
- 复杂触发时序图；
- 厂商白平衡校准向导；
- 相机 UserSet 管理；
- 采集卡线路和时钟拓扑。

品牌专属编辑器应实现统一宿主接口：

```csharp
public interface ICameraVendorEditor
{
    string AdapterId { get; }
    bool CanEdit(CameraDescriptor descriptor);
    object CreateViewModel(ICameraParameterProvider parameters);
}
```

如果厂商页面需要 WPF 类型，应放在 UI 扩展程序集，不得让核心设备驱动程序集引用 WPF。没有专属编辑器时，统一 Schema 编辑器仍然可以显示和编辑该设备的标准及动态参数。

### 12.7 相机接口与品牌适配矩阵

```text
┌──────────────────┬────────────────────────┬──────────────────────────────┐
│ 接入类型         │ 主要参数来源           │ UI 适配方式                   │
├──────────────────┼────────────────────────┼──────────────────────────────┤
│ GenICam / GenTL  │ 设备节点树             │ 动态 Schema 编辑器            │
│ GigE Vision      │ GenICam + 网络参数     │ 通用参数 + 网络诊断            │
│ USB3 Vision      │ GenICam + USB 状态     │ 通用参数 + 连接状态             │
│ Camera Link      │ 采集卡/相机文件/SDK    │ 通用参数 + 线路扩展页           │
│ 厂商 SDK         │ 厂商 API 和能力查询    │ 映射 Schema + 可选厂商编辑器    │
│ DirectShow       │ 媒体能力枚举           │ 有限通用参数编辑器              │
│ 模拟/文件        │ 模拟配置模型           │ 测试源参数编辑器                │
└──────────────────┴────────────────────────┴──────────────────────────────┘
```

品牌和接口的关系不是一对一的：同一个品牌可能同时支持 GenICam 和自己的 SDK；同一个 GigE Vision 接口也可能连接多个品牌。因此适配器选择顺序建议为：

```text
优先选择可用的标准适配器
        ↓ 标准能力不足时
选择厂商 SDK 适配器
        ↓ 仍有复杂专属交互时
加载厂商 UI 扩展
```

### 12.8 参数变更的运行约束

参数 Schema 还必须描述运行限制：

- 是否只读；
- 是否需要停止采集；
- 是否需要重新连接；
- 是否只能在硬件触发模式下修改；
- 是否会影响当前工作流快照；
- 是否允许在预览中实时应用。

设备管理器应用参数时，先由运行时管理器检查会话和资源租约，再由适配器执行。UI 不能因为控件可编辑就直接认为设备一定允许修改。预览和参数编辑也不能隐式创建新的设备连接，必须复用或申请明确的运行时会话。

### 12.9 相机工具中的参数适配

设备管理器和相机工具使用同一个参数 Schema，但展示范围不同：

```text
设备管理器：展示设备完整能力、诊断参数和厂商扩展

相机采集工具：
  展示与当前采集节点相关的参数
  保存为工具级 ParameterOverrides
  运行时合并到 CameraRuntimeSnapshot
```

相机工具不应复制一套独立的品牌参数模型。它应复用设备适配器提供的 Schema，并通过工具元数据声明过滤条件，例如：

```text
仅显示：触发、曝光、增益、ROI、像素格式
隐藏：网络地址、UserSet 保存、设备固件、采集卡时钟
```

### 12.10 相机工具面板

面向流程开发者，负责：

- 选择逻辑相机；
- 设置采集行为；
- 显示能力支持情况；
- 预览和单次采集；
- 显示工具级错误；
- 配置结果输出。

### 12.11 设备与驱动页面

面向设备维护场景，当前所有用户可访问，未来可接入权限控制，负责：

- 发现设备；
- 建立或修复逻辑设备绑定；
- 查看驱动和协议；
- 测试连接；
- 查看健康状态；
- 诊断丢帧和重连；
- 访问厂商扩展参数。

设备页面不是普通工作流操作的必经入口。工作流开发者通常从相机工具进入；相机工具发现不到设备、需要重新绑定或需要诊断时，再跳转到设备页面。

### 12.12 未来权限系统的兼容方式

不把权限判断写死在 ViewModel 中，建议预留抽象：

```csharp
public interface IPermissionService
{
    bool Can(string permission);
}
```

权限名称可以先作为字符串契约预留：

```text
camera.view
camera.discover
camera.connect
camera.configure
camera.vendor-advanced
camera.diagnostics
camera.delete
camera.force-disconnect
```

当前没有用户系统时，可使用允许全部操作的默认实现。未来接入用户、角色或组织权限时，只替换权限服务和登录上下文，不修改相机驱动、运行时管理器和工作流契约。

### 12.13 UI 密度控制与测试原则

动态参数不等于把设备的全部参数一次性展示出来。如果直接展开完整节点树，会导致：

- 设备管理器界面拥挤；
- 不同品牌的参数分组差异过大；
- 用户难以找到真正需要的参数；
- 参数依赖和禁用状态难以解释；
- UI 测试矩阵变成“品牌 × 型号 × 参数 × 状态”的组合爆炸。

因此 UI 采用渐进式披露，而不是全量展开：

```text
设备详情
  ├─ 概览：身份、连接、健康状态、常用操作
  ├─ 采集配置：当前工作流真正使用的参数
  ├─ 高级参数：按参数类别和能力按需展开
  ├─ 厂商扩展：只在适配器声明存在时显示
  └─ 诊断：原始节点、日志、统计和错误信息
```

设备管理器的默认页面只显示：

- 设备身份；
- 当前连接状态；
- 采集状态；
- 常用参数摘要；
- 测试采集；
- 最近错误和丢帧统计。

相机工具只显示当前节点需要的参数，不显示网络配置、固件、UserSet 管理和完整厂商节点树。完整参数浏览器属于诊断功能，不属于日常工作流配置。

#### UI 展示模式

建议提供三个展示模式，而不是三套实现：

```text
简洁模式：通用采集参数，面向日常流程配置
高级模式：标准能力和动态参数，面向设备调试
原生诊断模式：完整厂商节点和原始值，面向问题定位
```

三个模式复用同一个 `CameraParameterSchema`、同一套读写服务和同一套校验逻辑，只改变参数过滤、分组和编辑器选择。

#### 测试策略

测试不能穷举每个品牌的每个字段，而应分层测试：

```text
第一层：Schema/参数模型测试
  参数类型、范围、步长、枚举、只读、依赖、可用性

第二层：适配器契约测试
  所有适配器都验证连接、读参数、写参数、触发、连续采集和错误映射

第三层：通用 UI 测试
  使用固定的 Schema Fixture 验证控件生成、校验、禁用和分组

第四层：代表性适配器测试
  模拟适配器、一个标准协议适配器、一个厂商 SDK 适配器

第五层：真实设备验收
  每个协议和关键品牌选择代表型号进行现场验证
```

通用 UI 不需要为每个品牌重复编写页面测试。应准备若干稳定的 Schema Fixture：

- 只有核心参数的简单黑白相机；
- 带硬件触发、ROI 和枚举依赖的 GigE 相机；
- 带动态节点树的 GenICam 相机；
- 带厂商扩展页的相机；
- 参数只读、参数不可用和设备断线场景。

适配器测试重点验证“设备能力是否正确转换成 Schema”，UI 测试重点验证“给定 Schema 是否正确展示和编辑”，两者不应互相耦合。

建议增加以下自动化验收：

- Schema 序列化快照测试，防止参数名称和类型意外改变；
- 参数编辑器视觉回归测试，验证简洁/高级/诊断模式布局；
- 适配器错误码映射测试；
- 设备断线后 UI 状态转换测试；
- 运行中修改需要停止采集的参数时的阻止提示测试；
- 模拟设备故障注入下的重连和超时测试。

最终原则是：

> UI 不测试“所有真实设备的所有页面”，而测试“统一 UI 对参数契约的正确解释”；真实设备测试只验证适配器和代表性设备。

### 12.14 主题适配要求

设备管理器、动态参数编辑器、预览面板和厂商扩展控件必须接入现有主题系统，不能使用固定黑色、白色、灰色或硬编码品牌色。当前项目已有 `ThemeKeys`、Light/Dark 主题字典、SDK 主题语义资源和 `DynamicResource` 机制，新控件应沿用这套语义资源。

主题适配分为四层：

```text
主题语义 Token
        ↓
通用控件样式
        ↓
设备管理器布局
        ↓
厂商扩展控件
```

设备管理器至少需要使用以下语义资源类别：

- 页面和卡片：`PanelBackgroundBrush`、`ControlBackgroundBrush`、`WorkspaceBackgroundBrush`；
- 输入控件：`InputBackgroundBrush`、`InputBorderBrush`、`BorderBrush`；
- 文字：`TextPrimaryBrush`、`TextSecondaryBrush`、`TextDisabledBrush`；
- 状态：`SuccessBrush`、`WarningBrush`、`ErrorBrush`；
- 交互：`AccentBrush`、`ControlHoverBackgroundBrush`、`ControlSelectedBackgroundBrush`；
- 表格：`TableHeaderBackgroundBrush`、`TableRowBackgroundBrush`、`TableRowHoverBackgroundBrush`、`TableRowSelectedBackgroundBrush`；
- 预览：`ImageAreaBackgroundBrush`、`ThumbnailBackgroundBrush`、`ThumbnailBorderBrush`；
- 分隔和布局：`DividerBrush`、`SplitterBackgroundBrush`、`SplitterHoverBrush`。

XAML 控件必须使用 `DynamicResource` 或 SDK 主题控件样式：

```xml
<Border Background="{DynamicResource ThemePanelBackgroundBrush}"
        BorderBrush="{DynamicResource ThemeBorderBrush}">
    <TextBlock Foreground="{DynamicResource ThemeTextPrimaryBrush}" />
</Border>
```

禁止：

- 在设备管理器 XAML 中直接写 `#FFFFFF`、`#000000` 或固定灰色；
- 用品牌色表达成功、警告和错误状态；
- 为每个厂商复制一套 Light/Dark 页面；
- 让厂商扩展控件绕过宿主主题资源；
- 使用只在深色主题可读的图片、图标或文字颜色。

设备状态必须同时使用颜色、文字和图标表达，避免只依赖颜色：

```text
已连接  → SuccessBrush + “已连接” + 连接图标
连接中  → AccentBrush  + “连接中” + 进度图标
未连接  → TextSecondaryBrush + “未连接”
故障    → ErrorBrush   + “故障” + 错误图标
警告    → WarningBrush + “警告” + 警告图标
```

预览区域单独使用 `ImageAreaBackgroundBrush`，不能直接使用窗口背景。预览中的等待帧、断线和错误遮罩也必须使用主题语义资源，并保证暗色主题下的文字和图标对比度。

动态参数编辑器不能由品牌适配器直接返回已经绑定固定颜色的 WPF 控件。适配器只返回参数 Schema；通用 UI 根据参数类型创建控件，控件样式由宿主主题系统提供。确实需要品牌专属编辑器时，编辑器必须通过主题资源或宿主提供的主题服务获取颜色、字体、间距和状态样式。

主题验收至少覆盖：

- Light 与 Dark 两套主题；
- 设备列表选中、悬停、禁用状态；
- 连接中、已连接、断开、故障状态；
- 参数只读、不可用、校验失败和范围错误；
- 预览等待帧、实时帧、暂停、断线和释放会话；
- 厂商扩展页在两套主题下的可读性；
- 动态参数数量较多时的滚动条、分组和折叠状态。

主题测试应优先使用 Schema Fixture 和固定状态 Fixture，不需要为每个真实品牌重复验证整套颜色逻辑。

## 13. 模拟设备与测试

旧版基于 `BaseDeviceDriver` 的模拟驱动不应继续作为新架构基础。应实现统一的 `SimulatedCameraAdapter`，支持确定性故障注入：

- 连接失败；
- 连接延迟；
- 首帧超时；
- 连续采集丢帧；
- 运行中断线；
- 重连成功或失败；
- 参数设置失败；
- 固定帧率；
- 固定图案、序列图像或随机噪声；
- 帧号连续性检查。

测试分层：

1. 契约测试：所有适配器必须满足统一接口语义；
2. 模拟设备测试：连接、触发、连续采集、取消、超时、断线和重连；
3. 运行时测试：多工具争用、预览与正式运行、资源租约；
4. 工作流测试：相机帧进入 `ImageQueue` 并驱动算法节点；
5. 真实设备测试：至少覆盖一种标准协议设备和一种厂商 SDK 设备。

## 15. 旧相机契约迁移策略

现有以下类型视为 Legacy，不再作为新架构的目标接口：

```text
ICameraService
CameraDeviceInfo
CameraFrameInfo
CameraCaptureSettings
CameraPoolManager
```

当前版本采用一次性切换，不保留运行时兼容桥。旧代码由 Git 历史保存，需要查看旧实现时通过版本管理检索，不进入当前编译产物：

```text
CameraRuntimeManager
    ↓
ICameraAdapter
```

具体规则：

1. 新代码只依赖 `CameraRuntimeManager`、`ICameraAdapter` 和 Plugin.SDK 相机契约；
2. `ICameraService`、`CameraPoolManager`、旧帧模型、旧相机发现服务和旧厂商包装从当前源码删除；
3. 旧 `SimulatedCameraDriver` 不迁移为新核心，而是重新实现 `SimulatedCameraAdapter`；
4. 删除完成后必须通过 `rg` 检查生产代码不再引用旧契约；
5. 需要回溯旧实现时使用 Git 版本管理，不通过运行时 Facade 承担兼容责任。

迁移顺序：

```text
M0 新 SDK 契约
  ↓
M1 RuntimeManager
  ↓
M2 SimulatedAdapter / 标准适配器 / 厂商适配器
  ↓
M3 Workflow 和相机工具迁移
  ↓
M4 UI 迁移
  ↓
M5 插件迁移验证
  ↓
M6 真机验收与发布
```

## 16. 最终架构决策

SunEyeVision 不采用“只有设备管理器”或“只有相机工具”的极端方案。

最终决策如下：

1. **内部必须有设备运行时管理器。** 否则无法可靠处理多流程、多工具、预览、重连和设备资源争用。
2. **当前不建立普通用户/工程师权限前提。** 所有用户使用同一套设备管理能力，通过默认视图和高级展开区控制复杂度。
3. **相机工具是工作流场景的主要入口。** 相机选择和采集行为在工作流上下文中完成；设备页面用于发现、绑定、诊断和维护，不是工作流操作的必经步骤。
4. **未来用户管理通过权限策略接入。** 页面可见性和危险操作可受权限控制，但不改变相机运行时和适配器接口。
5. **物理设备、逻辑设备、采集配置和运行快照必须分开。**
6. **标准协议优先，厂商 SDK 兜底。** 品牌不是核心接口，能力模型才是核心接口。
7. **相机工具不得直接管理物理设备。** 工具只引用逻辑设备并提交采集请求。
8. **工作流负责业务执行，运行时负责设备资源。** 两者通过明确的服务和帧契约连接。
9. **先冻结契约和模拟测试，再接入真实品牌。** 不应继续在现有占位类上直接堆功能。

该方案能够同时覆盖低代码工作流体验、工业现场设备维护、多品牌兼容、多流程并发和未来插件化扩展，是当前 SunEyeVision 更稳妥的长期架构方向。
