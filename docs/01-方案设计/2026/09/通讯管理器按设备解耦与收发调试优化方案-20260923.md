# 通讯管理器按设备解耦与收发调试优化方案

- 日期：2026-09-23
- 状态：M1 状态解耦已实现并 Debug 构建通过，待人工验收；其余阶段待继续实施
- 范围：通讯设备配置、设备属性编辑、运行时会话、收发调试状态及其 UI 边界

## 1. 背景与目标

当前通讯管理器已经具备按设备保存配置和按设备 ID 管理运行会话的基础，但主界面的编辑状态与收发调试状态仍集中在管理器级 ViewModel。设备切换时，输入内容、收发历史、HEX 模式及忙碌状态没有完整的设备隔离。参数编辑也直接绑定到当前选中的设备对象，取消操作无法天然回滚。

本方案目标：

1. 每台设备的配置草稿、收发历史、发送输入和显示/发送模式互相隔离。
2. 管理器负责设备导航和窗口路由，不承担设备参数编辑和收发状态。
3. 新增和编辑设备均采用独立草稿，只有保存后才提交配置。
4. 收发链路保留原始字节，支持独立的文本/HEX 接收显示和文本/HEX 发送输入。
5. 支持多个设备会话并行，不因切换设备而丢失或串用状态。

## 2. 当前实现判断

### 已有的设备隔离

- 每个 `Communication` 实例有独立的 `Id` 和 `Settings`，设备配置在数据对象层面按实例区分。
- `CommunicationRuntimeManager` 使用设备 ID 管理运行时会话。
- 新建设备时通过单独的 `CommunicationDeviceEditorViewModel` 持有新建表单状态。

### 尚未隔离的状态

- `CommunicationManagerViewModel` 集中持有 `SendText`、`ReceivedText`、`SentText` 和 `IsBusy`。
- 收发数据显示依赖当前选中设备；当前视图模型不是每设备一个工作区，因此切换设备不能保证历史、输入和忙碌状态独立。
- 参数区直接绑定当前选中的 `Communication`，缺少编辑草稿与保存/取消事务边界。
- 接收 HEX 开关当前不可用且只有接收侧入口；发送侧没有 HEX 原始字节输入能力。

因此当前属于“配置模型部分按设备隔离、界面状态和编辑生命周期仍集中耦合”。

## 3. 目标架构

```text
CommunicationManagerViewModel
├── ObservableCollection<CommunicationDeviceViewModel>
├── 当前设备选择 / 新建设备 / 打开设置 / 打开调试工作区
└── 不持有单台设备的参数草稿、收发输入或消息历史

CommunicationDeviceViewModel（每个设备一个）
├── Communication 配置引用 / 当前编辑草稿
├── 运行状态与连接/监听命令状态
└── CommunicationWorkspaceViewModel
    ├── 接收消息历史（原始字节 + 时间 + 方向）
    ├── 发送消息历史（原始字节 + 时间 + 方向）
    ├── 发送输入与 Text/HEX 模式
    ├── 接收显示 Text/HEX 模式
    └── 操作忙碌状态 / 错误状态

CommunicationRuntimeManager
└── Dictionary<DeviceId, ICommunicationSession>
```

职责边界：

| 组件 | 负责 | 不负责 |
|---|---|---|
| `Communication` | 持久化协议、端点和设备参数 | UI 输入缓冲、消息历史、临时编辑状态 |
| `CommunicationManagerViewModel` | 设备集合、选择与窗口/工作区路由 | 单设备收发记录和参数草稿 |
| `CommunicationDeviceEditorViewModel` | 单设备新建/编辑草稿、校验、提交或取消 | 建立真实连接、承载长期消息历史 |
| `CommunicationWorkspaceViewModel` | 单设备收发历史、编码模式、输入和操作状态 | 直接操作其他设备的视图模型 |
| `CommunicationRuntimeManager` | 按设备 ID 创建、管理、关闭真实协议会话 | WPF 控件和窗口生命周期 |

管理器可以拥有多个设备工作区对象；相同设备的设置视图和调试视图可以复用控件模板，但不能共用 ViewModel 实例或临时状态。

## 4. UI 方案

### 4.1 通讯管理器

主窗口聚焦设备导航：设备名称、协议类型、运行状态、连接/监听开关，以及“设置”和“调试”入口。参数表和收发输入不再作为管理器级共享区域常驻。

```text
┌────────────── 通讯管理器 ─────────────────────────────┐
│ 设备列表                                  [＋ 新建设备] │
│ ┌───────────────────────────────────────────────────┐ │
│ │ TCP 客户端 · 设备 A          ● 已连接   [开关] [⚙] │ │
│ │ UDP · 设备 B                 ● 已绑定   [开关] [⚙] │ │
│ │ TCP 服务端 · 设备 C          ● 未启动   [开关] [⚙] │ │
│ └───────────────────────────────────────────────────┘ │
│ 选择设备后可打开该设备的设置或收发调试工作区           │
└────────────────────────────────────────────────────────┘
```

### 4.2 独立的设备设置对话框

- 新建与编辑复用同一视图，但每次打开都创建独立的草稿 ViewModel。
- 新建时草稿从协议默认值创建；编辑时从设备配置复制。
- “保存”执行校验并整体提交到目标设备；“取消/关闭”丢弃草稿，不应让未保存值提前写入原对象。
- 协议参数区按协议/模式显示差异化字段；不能编辑的运行态参数应说明原因。
- 多个设备的设置窗口若允许同时打开，必须分别绑定对应设备 ID 和草稿。

```text
┌──────────── 设备设置：设备 A / TCP 客户端 ────────────┐
│ 协议类型   [TCP 客户端]       设备名称 [设备 A]       │
│ 目标 IP    [127.0.0.1]        目标端口 [7920]         │
│ 自动重连   [开关]             接收结束符 [开关]       │
│ 接收结束符编辑区（开启后显示）                        │
│                                        [取消] [保存]  │
└────────────────────────────────────────────────────────┘
```

### 4.3 每设备独立的收发调试工作区

工作区标题必须包含设备名称、协议和当前状态。设备 A 的历史、输入和格式选择不能被设备 B 覆盖；切换回设备 A 时应恢复其工作区状态。

```text
┌──────────── 调试：设备 A · TCP 客户端 · 已连接 ───────┐
│ [接收数据] [发送数据]                                  │
│                                                        │
│ [时间戳 / RECV / UTF-8 或 HEX / 字节内容……       ]     │
│ [接收格式：文本 ▾ / HEX ▾]                [清空接收]   │
│                                                        │
│ [发送格式：文本 ▾ / HEX ▾]                             │
│ [输入数据……                    ] [发送]               │
│ Enter 发送；Shift+Enter 换行                           │
└────────────────────────────────────────────────────────┘
```

接收和发送历史可以用选项卡分开呈现，也可提供统一时间线并用方向标记区分；无论 UI 选择哪种形式，底层记录必须属于单台设备。

## 5. 数据与编码模型

每条消息以原始字节为事实来源，避免收到数据后立即转字符串而丢失 HEX 展示能力：

```text
CommunicationMessage
├── Timestamp: DateTimeOffset
├── Direction: Receive | Send
├── Payload: byte[]
├── Display/Send Mode: Text | Hex
├── EncodingName: UTF-8 / ASCII / Raw
└── Result: Success | Failed + optional error
```

- 接收侧“文本/HEX”是显示选择，不应改变收到的原始数据。
- 发送侧“文本/HEX”决定如何把编辑内容解析成字节；文本模式当前以 UTF-8 为默认，HEX 模式将十六进制文本解析成原始字节。
- HEX 解析需校验非法字符、奇数个半字节、分隔符及空输入，并在发送前给出可定位错误；不可静默修正用户输入。
- 时间戳记录收发动作时间；发送失败也应在发送历史中记录失败状态，但不能误标为成功发送。
- 显示字符串由 formatter 根据消息记录的模式生成，例如 `[2026-09-23 13:02:40.521]# RECV UTF-8>` 或 `# SEND HEX>`。

建议把协议收发的编码/显示转换抽到无 UI 依赖的 formatter/parser 服务，并为 HEX 解析器添加纯单元测试。

## 6. 状态流与生命周期

1. 管理器加载配置，按每个 `Communication.Id` 创建设备 VM 和独立 Workspace VM。
2. 用户打开设置时，从对应配置创建 draft；保存才写回该设备，取消丢弃 draft。
3. 用户启动设备时，运行时管理器按设备 ID 建立会话；会话事件携带设备 ID 和原始字节。
4. 设备 VM 仅将事件追加到自己的 Workspace 历史，不以当前选中设备过滤或丢弃数据。
5. 关闭/删除设备时，先停止对应会话，再释放该设备工作区和订阅；其他设备保持不变。
6. 关闭整个管理器时，按策略逐个关闭所有仍由本窗口拥有的会话，并解除事件订阅。

## 7. 分阶段实施

### M1：状态解耦

- 创建每设备 `CommunicationDeviceViewModel` 和 `CommunicationWorkspaceViewModel`。
- 将 `SendText`、`SentText`、`ReceivedText`、`IsBusy` 迁移到对应设备工作区。
- 移除“只处理当前选中设备的接收事件”逻辑，改为按设备 ID 路由。
- 验收：两个设备并行收发，切换设备不会串历史、丢消息或阻塞另一个设备操作。

### M2：编辑事务

- 设置对话框支持新建/编辑模式，使用独立草稿。
- 编辑参数不直接写入活动配置对象；保存提交、取消回滚。
- 验收：同时编辑不同设备不会交叉写入；取消后配置完全不变；保存后只影响目标设备。

### M3：收发格式

- 引入消息记录模型，保存原始字节和收发元数据。
- 接收区实现 Text/HEX 显示；发送区实现 Text/HEX 输入与校验。
- 验收：ASCII、UTF-8 中文、空格分隔 HEX、无效 HEX、接收分包和发送失败均有正确结果。

### M4：窗口与样式验收

- 对齐主题控件、焦点态、禁用态和空状态；配置对话框与调试工作区分别验证布局。
- 验收：多设备窗口生命周期、缩放、主题切换、断连、删除和管理器关闭无残留订阅或数据串扰。

## 8. 非目标与约束

- 本方案不改变协议驱动的职责边界，也不让 UI 直接操作 Socket/串口对象。
- 不把运行时连接状态写入持久化配置。
- 不把 HEX 仅做成文本着色或静态显示开关；发送 HEX 必须真正发送解析后的原始字节。
- 不在协议尚未实现时展示会造成误解的可用编辑控件或伪成功状态。

## 9. 实施前需确认

- 设备调试工作区采用独立窗口，还是在管理器中按设备切换的独立 Tab？两种方式都必须维持每设备独立 ViewModel 和历史。
- 文本发送默认编码是否统一 UTF-8？当前真实 TCP 实现使用 UTF-8，建议首期保持这一默认值。
- 接收“结束符”应只影响帧边界/显示，还是也要按设备驱动实际改变读取组帧逻辑？需要与各协议驱动能力一致，不能只做 UI 假象。
