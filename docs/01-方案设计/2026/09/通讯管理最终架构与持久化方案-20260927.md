# 通讯管理最终架构与持久化方案

日期：2026-09-27  
状态：A–D 核心实现已落地，待用户运行时/真机验收；E 的协议专用工作流契约须在明确消费场景后增补  
基线：`313f2457`  

## 1. 目标与范围

通讯管理沿用相机管理的分层和方案级生命周期：通用通讯契约位于 `src/Plugin.SDK/Devices/Communication/`；通讯运行时、驱动内部契约和所有协议实现集中在 `src/DeviceDriver/Communications/`，与 `src/DeviceDriver/Cameras/` 并列；应用级服务拥有运行时，UI 负责配置、调试和呈现，方案模型留在 Workflow。首批 SDK 不预建 Modbus/S7/CIP/OPC UA 专用接口，协议专用契约在明确的工作流或插件调用需求出现时再提升。统一的是架构边界，不是相机的“发现—采集”业务接口；TCP、串口、Modbus 等协议仍保留各自的操作语义。

本文整合设备配置、协议扩展、持久化、Modbus 地址空间、轮询、数据同步、发送测试和工作流接入。旧设计文档保留作演进记录；实施以本文的分层与数据边界为准。具体落地状态以协作记录和交接单为准。

### 1.1 当前事实

- `Solution.Communications` 已保存通讯设备，`Communication.Settings` 保存协议参数，`ModbusAddressPoints` 保存地址块；所以不是“完全没有持久化”。
- `CommunicationManagerViewModel` 自行创建运行时，关闭窗口时停止轮询并释放连接；相机运行时由应用级组合对象持有，关闭管理窗口不释放方案级连接。
- `CommunicationRuntimeManager` 位于 Workflow，以 `ProtocolKey switch` 创建内置协议会话；会话接口为内部私有接口。工厂注册和动态 DLL 协议插件均未实现。
- `ModbusAddressPoint.CurrentValue`、`ReceiveRecords` 当前会进入方案序列化；它们属于运行数据，不应长期混入配置文件。
- 通讯界面的保存命令调用 `SaveSolution` 后未检查布尔结果；方案仓库使用直接写目标文件。保存可靠性和失败反馈需修正。
- 当前可选协议为 TCP 客户端、TCP 服务端、UDP、普通串口、Modbus、S7、CIP、OPC UA；HTTP 在模型中有遗留判断，但不属于已接入运行时的协议。

## 2. 目标依赖与所有权

```text
Plugin.SDK/Devices/Communication：通用设备引用、状态、错误、能力与事件契约
                      ▲                   ▲
                      │                   │
Solution/Workflow：配置持久化与快照     DeviceDriver/Communications：工厂/会话/协议驱动
                      │                   ▲
                      └── 应用级通讯服务 ─┘
                              ▲
                              │
                         UI 管理与调试

工作流/插件需要具体协议操作时：只把该操作的稳定契约增补到 SDK。
```

依赖规则：Plugin.SDK 不引用 DeviceDriver、Workflow 或 UI；DeviceDriver 只依赖 SDK 公共模型，不引用 UI、方案模型或 WPF 控件；Workflow 执行层不直接引用 DeviceDriver 或具体协议 SDK；第三方驱动类型不得暴露在 SDK 公共签名中。相机已有 `Plugin.SDK/Devices/Camera/` 通用契约和 `DeviceDriver/Cameras/` 具体驱动，通讯采取同样的两层目录布局。现有 SDK 项目虽启用 WPF，新通讯契约本身不得使用 `Window`、`Dispatcher` 等 UI 类型。

应用级通讯服务的概念责任必须明确，但首阶段不必为它单独创建新项目。可以由现有应用组装入口持有 `CommunicationRuntimeComposition`，将方案模型转换为不可变快照，再调用 DeviceDriver；不得把恢复、保存及方案切换逻辑塞进通讯管理窗口或协议适配器。

## 3. SDK 通用契约与 DeviceDriver 集中目录

以下是第一阶段的目标目录，不表示文件当前存在。SDK 保存跨层稳定的通用通讯语义；通讯驱动代码全部收敛在 `src/DeviceDriver/Communications/`，和相机目录并列。方案模型与 WPF 界面仍各守原层。这里纠正上版误解：用户要求把通讯**驱动**放在一起，并未要求删除 SDK 层。

```text
src/Plugin.SDK/Devices/Communication/
├── CommunicationDeviceRef.cs       # 稳定逻辑设备引用
├── CommunicationState.cs           # 跨层连接状态
├── CommunicationError.cs           # 分类错误与可操作诊断
├── CommunicationCapabilities.cs    # 原始收发/读写/订阅等能力描述
├── CommunicationDataEvent.cs       # 设备ID、时间、方向、关联请求ID
└── ICommunicationStatusService.cs  # 只读状态入口；不授予断连权限

src/DeviceDriver/Communications/
├── CommunicationRuntimeComposition.cs  # 唯一组合入口，注册工厂
├── Contracts/
│   ├── ICommunicationProtocolFactory.cs # 根据协议 ID 创建适配器
│   ├── ICommunicationAdapter.cs         # 驱动内部连接/释放契约
│   └── IProtocolConfigurationValidator.cs
├── Runtime/
│   ├── CommunicationRuntimeManager.cs   # 按设备 ID 持有唯一会话
│   ├── CommunicationSession.cs          # 会话生命周期与在途请求
│   └── CommunicationPollingCoordinator.cs # 连接期间的可取消轮询
├── Raw/
│   ├── TcpClient/
│   ├── TcpServer/
│   ├── Udp/
│   └── Serial/
├── Modbus/
│   ├── ModbusProtocolFactory.cs
│   ├── ModbusTcpAdapter.cs
│   ├── ModbusRtuAdapter.cs
│   └── IModbusOperations.cs       # 驱动内类型化操作，不先放 SDK
├── S7/
├── Cip/
└── OpcUa/
```

SDK 通用目录不是协议驱动目录：它只定义设备引用、状态、错误、能力、事件及只读状态查询这些跨层语义。UI 通过应用级服务调试设备，不因为 UI 需要调用 Modbus 就把 Modbus 操作 API 放进 SDK。DeviceDriver 内部的工厂和适配器由组合对象显式注册。第一阶段只做内置协议工厂，不宣称支持任意外部 DLL 热插拔。若工作流工具或外部插件确实需要调用某一协议，才把该协议的请求/结果和能力接口提升到 SDK；Modbus、S7、CIP、OPC UA 遵循同一准入规则。公共接口不返回 socket、串口对象或协议 SDK Session。

未来若有明确的协议操作消费者，在现有 SDK 通用目录下增加协议专用的最小请求/结果与接口；不能把 DeviceDriver 的内部适配器和工厂整体搬进 SDK。DeviceDriver 可以依赖 SDK 模型，SDK 不能反向引用驱动模型。

NModbus、S7netplus、OPC UA Client、`System.IO.Ports` 等依赖应由实际使用它们的驱动项目声明并随构建/发布输出部署。初期保持单一 DeviceDriver 项目；仅在依赖冲突、独立发布或规模明显增加时拆分协议项目。

### 3.1 SDK 准入规则与接口边界

| 问题 | 决策 |
| --- | --- |
| 设备引用、状态、错误和能力需要在层间共享？ | 放在 SDK 通用通讯目录；Driver 和宿主共用同一模型，不复制同名类型。 |
| 只有通讯管理 UI 需要某协议操作？ | 专用操作留在 DeviceDriver；UI 通过应用级服务调用。UI 使用不等于协议专用 SDK 接口需求。 |
| Workflow 工具需要稳定地调用某协议？ | 在 SDK 定义最小的类型化请求、结果与能力接口；驱动实现由宿主提供。 |
| 第三方插件也需要调用？ | 在 SDK 契约上补兼容性约束、取消语义与版本测试，通过受控执行服务注入；不得暴露驱动实例。 |
| 只是想提前为将来的协议留文件？ | 不创建。避免 SDK 每加协议都变化，也避免抽象先于用例。 |

SDK 公共类型采用稳定的逻辑设备引用，不持有连接、线程、套接字和可变的方案对象。控制设备连接/断开的管理权限与工作流的读写能力分开：普通工具不应只因为能读寄存器，就自动拥有断开全局设备连接的权限。SDK 事件只定义语义，运行时应提供限流/背压，不能把无界的高速数据事件直接推给 WPF。

### 3.2 DeviceDriver 内部契约

`ICommunicationProtocolFactory` 负责声明稳定协议 ID、能力、配置验证，并用已经冻结的配置快照创建适配器。`ICommunicationAdapter` 负责连接、断开、资源释放和基础状态事件；协议专用操作另由驱动内部的能力接口实现。运行时以设备 ID 查找会话，先验证协议能力，再调用专用操作。禁止使用包含 `object` 或任意 JSON 载荷的“万能 Execute”来替代强类型读写。

工厂选择必须确定：同一协议 ID 不能注册多个同优先级实现而随机选中；没有匹配工厂要返回可诊断的“驱动不可用”。组合对象负责显式注册，注册时检测重复 ID。适配器不得直接读取 `Solution`、`Communication`、`ModbusAddressPoint` 等可变方案模型；应用层负责转换为快照。

## 4. 配置、运行数据与持久化

| 数据 | 所有者/位置 | 规则 |
| --- | --- | --- |
| 设备 ID、稳定协议 ID、协议配置版本、端点、超时、启用状态 | 方案文件 | 列表中启用的通讯设备在方案加载时连接，不另设自动连接开关 |
| Modbus 首地址、寄存器数量、地址块、整数位数、字节序、访问权限、轮询设置 | 方案文件 | 保存定义，不保存测量值 |
| 密码、私钥、证书信任 | 系统安全存储 | 方案仅存受保护引用，不存明文 |
| 会话状态、当前寄存器值、最近轮询时间、错误和短期收发记录 | 应用运行时 | 重启后重新连接/读取；默认不写方案 |
| 长期追溯的收发或测量历史 | 独立历史存储（若确需） | 明确容量、保留期和查询方式 |

配置模型使用稳定 `ProtocolId` 与协议配置 `SchemaVersion`。迁移器兼容现有 `protocolKey`、旧 `ConnectionType` 和旧 Modbus 字段；未知协议或驱动不可用时保留原始配置，显示原因，不阻断整份方案加载。加载旧方案中已有的 `CurrentValue` 和 `ReceiveRecords` 时不得因此丢失地址块配置；正式移除历史字段前应备份旧方案，并明确历史数据是导出还是废弃。

保存路径应先校验配置，写入同目录临时文件并校验，再以可恢复方式替换目标文件；失败不得覆盖原件。调用方必须检查保存结果，界面只在真正成功时提示“已保存”。新增、删除、重命名和参数修改应有统一的脏状态/提交规则，不依赖用户猜测哪些操作自动保存。

### 4.2 迁移、保存与未知协议

加载顺序：解析旧方案 → 读取设备身份/原始协议配置 → 按协议与版本迁移 → 校验 → 构造运行快照 → 注册运行时。迁移不应在只读加载时立刻覆盖原文件；只有用户保存方案时才写入新版本。迁移失败应保留原始配置并将该设备标记为不可连接，允许查看、导出或删除，不牵连其他设备。已经写入旧方案的运行值和接收记录默认不再回灌到当前状态；需要保留时先提供一次性导出或备份路径。

保存顺序：以当前编辑版本形成不可变配置副本 → 校验设备 ID 唯一性、地址范围及协议参数 → 序列化到同目录临时文件 → 重新解析验证 → 原子替换/可恢复提交 → 更新“已保存版本”。保存失败时保留未保存状态和原文件。多个编辑入口同时保存须经过同一保存服务；不得由某个窗口把过时的完整方案快照覆盖另一个窗口的新修改。

## 5. 会话、轮询与方案生命周期

- 应用级运行时按逻辑设备 ID 维护唯一会话。UI 调试、手动同步、发送测试和工作流共享会话，不重复打开同一端点。
- 打开/关闭通讯管理窗口只改变视图订阅，不决定方案级连接生死。
- 打开设备连接成功后，持续轮询已启用且可读的地址块；用户主动断开、异常断开、连接失败、删除设备、切换方案或退出应用时取消轮询。无轮询次数上限。
- Modbus 请求应按会话的协议约束串行化；读取和写入有超时、取消及部分成功反馈。高频结果后台汇总、限频通知 UI；不能在每次回写时重建地址表或无界追加记录。
- 修改端点、串口、站号等连接参数生成新的配置版本，提示重新连接；在途请求只允许回写到仍匹配其设备 ID 和配置版本的目标。方案切换后旧请求结果必须失效。
- 方案加载时读取、迁移、校验、注册设备；根据通讯设备列表连接已启用设备，不另设 `AutoConnect` 开关。旧方案中的 `autoConnect` 字段不再参与判断，后续保存时移除。连接失败不阻止打开方案，但状态和原因可见。工作流执行开始时持有配置快照，不访问 WPF 控件。

相机可通过发现器按设备身份重新绑定；TCP/串口/Modbus 多数依靠用户配置端点，不能强制套用相机的发现步骤。统一的是生命周期与所有权，不是发现和操作模型。

### 5.1 会话状态机及窗口行为

```text
Disconnected ──Connect──▶ Connecting ──成功──▶ Connected
     ▲                         │                 │
     │                         └──失败──▶ Faulted│
     │                                            │主动断开/异常
     └────────────── Disconnecting ◀─────────────┘
```

连接操作对同一设备互斥；并发点击“连接”不能创建第二条会话。异步断开要先禁止新请求，再取消轮询/订阅与在途操作，最后关闭协议适配器。状态变化以运行时为唯一事实源，窗口重开后重新订阅并读取快照，不从保存的 `IsEnabled` 推测“已连接”。异常断开后是否重连由该设备已保存的策略和驱动能力共同决定；若启用自动重连，应有可取消的退避与明确的故障状态，不能无限快速重试。

### 5.2 并发、背压与过时结果

- 同一 Modbus 会话上的自动轮询、手动同步、发送测试和工作流请求进入受控操作队列；保留超时和取消，不允许长轮询阻塞用户操作无上限。协议支持并发时由适配器明确声明，不用一个全局锁限制所有设备。
- 读取结果带设备 ID、方案代次、配置版本、地址块 ID 和请求时间；回写时检查这些身份及地址范围。关窗只影响 UI 订阅；删除地址块、改范围或切换方案使旧结果失效。
- 运行时当前值缓存按设备与地址块索引，历史记录为有界缓冲；UI 按可见区域和限频节奏读取。丢弃策略、最大长度和计数指标可观察，日志不会对每次成功轮询都写 UI。
- 写操作不因为编码成功就提前更新读值；收到协议成功响应后记录写入结果，必要时由下一次读取确认。分批写入出现失败要报告已成功前缀，不能宣称整批原子成功。

## 6. Modbus 地址空间与操作规则

维持已确定的 VM 风格地址空间：首地址和寄存器数量用 SDK NumericUpDown，表头 0–9，按实际容量生成地址行；最后不足十格只允许有效单元交互。已配置地址块按真实交集绘制连续归属色条，同一块跨行分段，未配置格悬停显示 `＋`；寄存器单元格查看接收数据，归属色条编辑地址块。表格内部单独滚动，操作栏保持可见。16/32bit、字节序和访问权限属于地址块配置，而不是设备级通用“数据类型”。

修改首地址或寄存器总数前计算对已分配地址块的影响：未受影响的块保留；越界、重叠或需要删除的块逐项列出并要求确认；不自动平移、不静默截断。清空所有分配地址应独立确认，并在原子更新后让在途轮询结果失效。

自动轮询只读取开启轮询且可读的块；“数据同步”是独立的一次性读取，覆盖所有已配置且可读的块，不依赖轮询开关。“发送测试”只写实际输入数量，其余寄存器保持原值；超出块容量按现有完整值/UTF-8 字符截取规则处理，超出单次协议写入上限分批，并明确提示部分成功。回写前校验地址块仍存在且范围、数量、配置版本与请求快照一致。

## 7. 新协议接入流程

1. 分配稳定协议 ID；定义角色、能力、参数、默认值、范围、SchemaVersion 与旧配置迁移。
2. 在 DeviceDriver 的协议目录实现工厂、适配器和类型化操作；封装第三方协议 SDK、取消、超时、重连语义和错误映射。
3. 在组合对象注册工厂；UI 增加配置编辑器和匹配协议能力的调试面板。若工作流或插件需要调用，才在 SDK 增加相应公共契约。
4. 声明依赖、许可、平台和部署文件；完成配置往返、断连、超时、取消、并发、释放、模拟器及真实设备测试。
5. 驱动缺失或版本不兼容时保留配置并显示“驱动不可用”，不得使整个管理器或方案加载失败。

### 7.1 以新增协议为例的最小变更集

假设新增 `vendorx.foo`：

```text
DeviceDriver/Communications/VendorX/
├── VendorXProtocolFactory.cs      # 支持的协议 ID、配置验证、创建适配器
├── VendorXAdapter.cs              # 建连/断连/释放、请求处理
└── VendorXOperations.cs           # 驱动内部类型化操作

UI/Features/CommunicationManager/
└── VendorXConfigurationEditor...  # 仅此协议需要的配置和调试 UI
```

还须在 `CommunicationRuntimeComposition` 注册工厂，补该协议配置的版本迁移和依赖部署清单。若目前仅 UI 调试，SDK 不新增 `IVendorXService`；若工作流工具已提出明确操作，再设计最小公共请求/结果与服务接口，并用 DeviceDriver 实现。注册成功不代表有完整 UI：配置编辑、运行诊断与错误提示均要验收。禁止以协议的中文显示名称作为持久化 ID。

## 8. 分阶段实施与验收

| 阶段 | 工作 | 退出条件 |
| --- | --- | --- |
| A 数据边界 | 配置版本、旧方案迁移、运行数据退出方案、保存结果反馈和安全写入 | 旧方案无损加载；保存失败不误报；轮询不使方案文件持续膨胀 |
| B 生命周期 | 应用级通讯运行时，连接和轮询移出窗口 | 关窗不断连；重开显示真实状态；断连/切换方案正确取消与释放 |
| C 最小驱动契约 | 建立 SDK 通用通讯契约与 DeviceDriver/Communications 内部工厂，先迁移原始 TCP 和 Modbus；不预建协议专用 SDK 接口 | 现有地址空间、轮询、同步、发送测试无回退；同设备唯一会话 |
| D 其他协议 | 迁移串口、UDP、S7、CIP、OPC UA | 各协议校验、操作、失败及依赖部署可验证 |
| E 工作流与发布 | 工作流通过 SDK 服务和配置快照调用；独立验证发布依赖 | 无 WPF/厂商 SDK 类型泄漏；取消、并发、方案切换正确 |

日常实现按用户要求只做相关 Debug 构建和测试，不将 Release 检查作为每次变更的门槛；涉及发布规则时另行安排发布验收。Visual Studio 设计时、运行时界面和真实设备行为仍需人工验收。任何跨 AI 交接遵守 `AGENTS.md`：记录基线、更新协作文件，必要时创建明确的临时提交；同一工作目录不并行写入。

最终验收不是“目录和接口齐全”，而是方案级会话所有权统一、配置可可靠恢复、运行值不污染方案、UI/工作流共享会话、新协议能通过工厂接入、既有 Modbus 交互与操作不回退。

## 9. 逐批落地清单与回归矩阵

### 9.1 建议提交批次

1. **持久化修复**：先给配置添加版本与迁移测试，再使 `CurrentValue`、`ReceiveRecords` 退出方案写入，修复保存结果判断与安全写入。此批不改变连接生命周期。
2. **最小运行时骨架**：在 DeviceDriver 引入工厂、适配器与组合对象；先以 TCP 和 Modbus 验证。应用级服务持有它，并保留旧调用的兼容门面，避免 UI 一次性大改。
3. **迁移所有权**：将连接、轮询和状态事件从窗口移入应用级服务；关闭窗口只解除订阅。补方案加载、切换和应用退出的清理链路。
4. **迁移剩余协议**：串口、UDP、S7、CIP、OPC UA 逐个迁移；每迁移一个协议即删除该协议的旧分支，避免双实现长期并存。
5. **工作流消费和 SDK 扩展**：先确定具体工作流操作；确需跨层调用时在已有 `Plugin.SDK/Devices/Communication/` 下新增最小协议契约。未明确消费场景的协议不要预留空接口。

每批提交前记录基线及工作区现状；同一目录只有一位 AI 写入。跨 AI 交接时按 `docs/collaboration/HANDOFF_TEMPLATE.md` 记录未完成项和验证结果，不为每个细小改动制造无意义提交。

### 9.2 必测场景

| 类别 | 核心用例 |
| --- | --- |
| 持久化 | 旧方案加载、新方案往返、未知协议保留、迁移失败隔离、保存失败不误报、轮询后文件大小不增长 |
| 生命周期 | 重复连接拒绝/复用、关窗不断连、重新开窗状态一致、主动断连停轮询、方案切换隔离、退出释放 |
| 竞态 | 轮询期间编辑/删除地址块、手动同步与发送并发、断连时请求取消、旧结果不回写新方案 |
| Modbus | 非整十地址表、跨行色条、同步不依赖轮询、短写保留后缀、超量截取、分批部分成功 |
| 协议扩展 | 缺驱动可见、重复协议 ID 报错、配置版本迁移、协议错误映射、第三方依赖部署 |
| UI | 高频轮询仍可点击和滚动、关闭记录窗口后无后台 UI 更新、VS 设计时与运行时布局 |

自动化构建和测试按本轮用户约束使用 Debug；真实 TCP/串口/PLC/OPC UA 设备及运行时视觉效果由人工验收。发布依赖的 Release 检查作为明确的发布阶段，不混入日常 Debug 验证。
