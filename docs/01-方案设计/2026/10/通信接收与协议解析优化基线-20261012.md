## 2 两条路径与输出关系

```text
通信设备／地址
      |
      +--> 通信管理接收事件：解析／比较／组装
      |             |
      |          事件 out
      |             |
      |      触发条件、流程输入／运行参数赋值
      |
      +--> 工作流接收数据工具：获取来源载荷
                    |
              本次节点接收输出
                    |
              协议解析工具
                    |
              类型化节点输出
```

事件out属于EventId／FieldId，节点输出属于NodeId／稳定字段键；同名out1不表示同一字段，不进行隐式复制。触发时若使用事件参数，值通过执行快照交付，不让执行层读取管理器控件。

事件与工具复用连接、轮询和样本，不建立第二套设备连接。用户确认本次设备数据与工作流一致：触发运行使用触发那条报文，手动执行使用执行开始时的有效已收样本；本次执行锁定快照，新报文不能替换。事件解析不能消耗工具样本。没有有效数据则失败，模块结果和分析展示真正使用的样本及接收时间，不偷偷沿用上次结果。此服务路径仍待R3实施。

## 3 来源适配和架构

| 来源 | 接收工具目标输出 | 边界 |
| --- | --- | --- |
| TCP客户端／服务端、UDP、串口 | 一份完整业务报文BinaryPayload | HEX只是展示；复用现有分帧，不能把TCP读取分块直接保证为完整业务报文 |
| Modbus地址块 | 寄存器数据区BinaryPayload | 不含协议帧头，保留寄存器原始数据顺序，不提前按int／float解码 |
| S7／CIP目标 | 由目标读取能力决定 | 不假定全部转字节；工具链未适配前不宣称可用 |
| OPC UA数据点 | 原生类型值及对应有效性 | 原生数值直接用于下游；字符串需要拆分时进入文本解析，不伪造报文 |
| 变量、队列 | 来源实际类型 | 队列仍属计划，未完成前不能提供可运行占位 |

共用解析核心应是无WPF、无设备副作用的算法层，统一HEX输入、严格字符转换、区间、顺序、数值规则和错误。通信事件负责比较、状态、历史和触发；工具负责本次执行结果。插件不能引用UI宿主或直接调用CommunicationReceiveProcessor。

共享改动覆盖SDK、执行服务、设备样本和事件解析，编码前需评估主项目影响。本工作区不开发标定、不自行同步主项目，不恢复SDK旧契约兼容。

### 接收输出与下游类型

TCP本身传输字节，不保证内容是字符串；UTF-8等编码把字节解释成文字，HEX只是另一种显示。接收工具对TCP／UDP／串口业务报文和Modbus寄存器数据区统一输出BinaryPayload，SDK词目为Binary，不自动追加String副本，也不提前拆字段。Modbus寄存器按原顺序保留，高字节在前，不夹带协议帧头；例如寄存器92的数据区为00 5C。此处为工具输出约定，不声称所有驱动底层都直接返回BinaryPayload。

OPC UA及变量／队列保留实际类型。原生Integer／Double等可以直接绑定兼容的下游参数，不必先转成String／Binary，也不必经过协议解析。接收插件仍待实现，不能把该约定描述为已有设备交付能力。

### 解析输入和绑定过滤

解析内容不是固定String输入，而是兼容String和Binary的单项载荷输入；输出字段的int／float／string不决定输入过滤。文本与字节两种模式都必须能看到上游接收节点的Binary out，也能看到String来源。

- 绑定候选只允许String／Binary兼容来源，复用现有树形路径、稳定输出键与索引选择，增加最小范围的多类型筛选能力。
- 不以空DataType或object放行所有候选，不把全局ParamBinding改成任意类型互通；不能只配置DataType=String而隐藏Binary。
- 来源声明用于候选过滤与条件UI，实际执行仍校验值类型、来源有效性和单项输入。手工填写不兼容路径必须报错，不能靠ToString把数值、图像或几何对象伪装为报文。
- 一份BinaryPayload包含完整报文；选择其中一个载荷不是选择一个字节。遵循现有单项tuple取值，多个载荷或多项String列表需显式选择一项，不自动拼接。
- 切换模式保留兼容的来源绑定，由解析方式改变解释过程，不更换设备来源、绑定键或底层载荷类型。

| 实际输入 | 文本解析 | 字节解析 |
| --- | --- | --- |
| String | 直接按分隔符拆分，不做字符解码 | 按明确的HEX文本或字符文本规则转换为字节，再解析 |
| BinaryPayload | 按所选字符编码严格解码，再按分隔符拆分 | 直接读取原始字节，不需要输入格式选择 |
| Integer／Double／Boolean／图像／几何等 | 不支持，过滤并在执行时拒绝 | 不支持，过滤并在执行时拒绝 |

### 文本与字节的转换规则

```text
文本解析
String ----------------------------------+
                                         +--> 按分隔符拆分 --> 配置字段转换
Binary --> 按字符编码严格解码为文字 ------+

字节解析
Binary ----------------------------------+
                                         +--> 按闭区间、类型与顺序解析
String --> 明确HEX文本或字符文本转字节 ---+
```

例如Binary载荷41 42 43 2C 32表示ABC,2：文本解析用逗号和string／int字段得到ABC及2，不需要接收节点额外输出String。字节模式直接读取原始位置；例如00 5C 41 44，int区间0～1得到92，string区间2～3得到AD。

文本Binary输入的编码目标为UTF-8／ASCII，默认UTF-8，放在高级设置；String输入已经是文字，不显示无效编码项。当前文本Binary解码固定UTF-8，条件编码选项与执行适配尚未实施。HEX展示字符串不自动还原为字节：String进入文本解析仍按文字拆分，进入字节解析才由输入格式决定转换。

字节模式ASCII数据表示字段按ASCII字符解释。例如39 32可按字符转换为整数92；二进制整数00 5C则关闭ASCII数据。它不等于HEX显示，也不等于输入格式。ASCII字符解释不使用数值字节重排。非法HEX、编码错误、所需片段不足、区间越界、类型转换失败及取消不发布部分业务值，不复用历史成功结果。

### 高级设置及条件显示

文本模式仅在Binary输入需要解码时显示高级设置的字符编码：

```text
|  v 高级设置                                              |
|  字符编码    [UTF-8                   v]                 |
```

字节模式按条件显示以下项目，而不是无条件全部展开：

```text
|  v 高级设置                                              |
|  输入格式    [HEX文本                           v]       |
|  字符编码    [UTF-8                             v]       |
|  当前字段    [out0                              v]       |
|  数值解释    [按统一规则                         v]       |
```

- 输入格式仅在字符串进入字节解析时显示；真实BinaryPayload不需要识别格式，不猜字符串含义。
- 字节编号固定从0开始，起止均包含，不再展示0／1选择框。这是本项目约定，不断言VM全部实现。
- 字符编码在文本Binary解码、字节字符文本编码或字节string字段解码时显示；String进入文本解析无需编码。字节ASCII解释使用ASCII规则，该设置不参与时隐藏。声明类型无法确定时不能默默猜格式，执行仍按实际值严格校验。
- 数值解释仅对当前二进制int字段显示，当前行切换同步该字段。选项为按统一规则、有符号、无符号，已按字段持久化；字段重排保留设置与身份。
- 默认统一规则为1～3字节非负、4字节有符号，允许显式覆盖。无符号值仍须落入协议int32范围，不因此放宽SDK承载范围。
- float仍为有限32位浮点、4字节；string按配置编码解释。输入格式、编码和符号是项目扩展，不伪称VM主界面已有对应参数。

### 当前实现与待验收范围

协议解析和组装已能用常量或变量独立测试，但不能因此声称真实通信已贯通。下一批优先取得接收节点真实数据，再按第7节联合验收；输入框宽度等可独立后续优化。

解析算法已接受String／Binary，文本Binary目前固定UTF-8；解析内容控件未指定DataType，候选未限制为这两类，且宽度仍铺满。联合候选过滤、文本编码条件显示与执行适配、约260宽度和路径省略Tip属于本次确认的待实施优化。列表重排修复已完成277项相关回归及常用Release验证，不把这些历史结果算作新优化验收。

新实现至少覆盖：两类输入与两种模式的四种组合；UTF-8／ASCII及无效编码；非法HEX；手工错误路径、实际类型不符、单项／多项tuple与显式索引；切换模式和绑定重载；失败清空输出；长路径Tip及深浅主题、高DPI和可读列宽。共享筛选变更必须回归其他算法节点，确保原有单类型限制不放宽。接收服务实施后再验证设备样本到节点out到解析的同次快照整链。

## 6 接收运行时契约

用户已确认所见即所得，采用触发样本锁定和手动当前样本快照，不隐式等待新消息。模块结果、解析和下游须对应同一份数据。具体有效期数值、会话失效、TCP服务端客户端身份、跨目标策略以及队列不足和消费行为仍需落实，不能无限沿用旧会话最新值、另建轮询或让执行层读取WPF控件。上述是项目决策，不是VM官方默认值。

配套入口：[接收数据方案](./接收数据工具方案与沟通基线-20261010.md)、[协议解析方案](./协议解析工具方案与沟通基线-20261010.md)、[实施计划](./通信工具链实施计划-20261010.md)、[结果统一约定](./通信工具链模块结果与数据分析统一约定-20261010.md)。

## 7 协议组装来源与联合验证

组装列表每行是一个独立文本片段，主要订阅本次已有成功结果的上游节点字段，不限于紧邻上一节点；也可绑定全局变量快照或直接填写字符串常量。不是从设备再次读取，不固定接收全局触发out，也不默认复制接收事件out。

当前文本组装支持String／Integer／Double单项值，数值按固定文化明确格式化。Binary、Boolean、图像、几何等不自动转文字；多项集合需明确选取一项。组装绑定候选目标限制为String／Integer／Double，实际校验不能仅依赖下拉过滤，当前筛选尚未接入。

```text
设备业务报文／寄存器数据区
          |
     接收数据 out：Binary
          |
     协议解析 out：String／Integer／Double
          |
     组装列表：上游字段 + 变量快照 + 字符串常量
          |
     组装结果：String + 对应UTF-8 Binary
          |
     宿主模块结果／主界面数据分析
```

原始Binary接收out不能直接进入当前文本组装项，必须先取得解析后的标量；原生数值或String来源可直接绑定兼容组装项。全局触发只有明确映射到流程输入或模块参数且执行接线具备后才可能参与，仍属独立路径，不是第一批联合验证的前置。

首批实例：TCP对端发ABC,2，接收out保持41 42 43 2C 32，文本解析得到ABC和2，组装常量RESULT与两字段得到RESULT,ABC,2。Modbus数据区00 5C 41 44经字节解析得到92和AD，组装为RESULT,92,AD。两例均从本次上游结果取值，检查下一报文到达不覆盖当前执行、无数据与失败清空、会话及设备隔离、重排／改名／保存重载后的绑定身份。

第一批终点为模块结果，不发送回设备；发送插件、队列及完整收发验收仍按后续计划实施。详见[组装来源方案](./协议组装工具方案与沟通基线-20261010.md)及[实施计划](./通信工具链实施计划-20261010.md)。
