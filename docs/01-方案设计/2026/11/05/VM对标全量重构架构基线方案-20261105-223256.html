创建：2026-11-05 22:32·代码基线：71da36329（main）·对标对象：D:\MyWork\参考项目\VisionMaster\Source·现行结论落点：09-现行文档/框架架构总览.html

一句话结论

重构目标是与 VisionMaster 原件的四层一一对应，不是按现有工程名继续加固。已核实的结论是：接口三分层（Plugin.Contracts / Plugin.Runtime / Plugin.Wpf）和工具两段式（Runtime + Wpf）方向正确，不需要推翻；不对标的地方只有三处——①算法层反向依赖旧 Plugin.SDK、②节点/参数/结果模型存在新老两份、③UI 平台被打散在四处。因此第一批要做的不是继续迁工具，而是让旧 Plugin.SDK 整体退场；它不退，后面每个工具的迁移都会做两遍。

改前用户看到什么

  • 工具箱里只有两个工具是新的（图像加载、Blob 分析），其余 18 个仍是旧形态，界面风格与操作手感不一致。
  • 开发一个新工具时，明明只想调算法，却必须同时处理旧 SDK 的模型，因为算法适配层（CvAdapter）就建在旧 SDK 上。
  • 同一个"参数/结果"在不同工具里长得不一样、字段也不完全对得上，因为底层有两份等价模型。
  • 公共控件的行为取决于它落在哪个界面里——控件分散在四个工程，样式来源不止一处。
  • 第三方想独立开发工具，拿不到一份干净、稳定、只含必要依赖的 SDK。

改后应该是什么样

场景 期望行为
开发一个新工具 只需引用 Plugin.Contracts + 所需算子库，不需要知道旧 SDK 存在
新增一种参数或结果 只改一处模型，工具箱、参数页、结果页、保存重开全部跟着生效
原件控件升级 改 Plugin.Wpf 一处，所有界面同时生效
用 CvEngine 写算法 不会被动拖入设备驱动、脚本、旧 UI 之类无关依赖
第三方独立开发 仅凭发布 DLL + 模板工程即可构建、部署、外部附加调试

依据：VM 原件 Source/ 下 Zoo.* 算子库不依赖 UI 平台与应用；WPF-Control 是唯一 UI 平台且自带 NugetTemplates；NodeData 是唯一节点数据模型。三条都由工程清单实测，不是推断。

判据：什么叫"设计正确"

后续任何改动都用这五条判定，不满足就先补设计，不做优化：

  1. 依赖单向无环：层与层之间只允许向下依赖，禁止出现"算法层反过来依赖 SDK / 宿主"。
  2. 算子库独立：算子库只暴露算子语义，不依赖 UI、不依赖应用、不依赖工具插件模型。
  3. 模型单份：同一个业务概念（参数、结果、几何、节点数据）在全仓只有一处定义。
  4. 工具隔离：工具 Runtime 不碰 WPF、不碰 UI、不碰持久化；工具编辑器只依赖自身 Runtime + 公共控件。
  5. UI 平台唯一：公共控件、模板、样式只有一处来源，宿主只做组装。

两套架构实证

VM 原件：4 层 + 算子库旁挂（依赖方向按 csproj 实测）

我们的现状：22 个 src 工程 + 20 个工具

逐层处置清单

处置只有三种：保留 / 重写（改依赖或改实现）/ 退出（迁移后删除）。删除前必须按三类引用核实：源码引用、反射字符串、配置或工具箱字符串常量。

证据分级与不卡死机制

重构必然遇到原件证据不足。原则是证据只影响实现细节，不影响接口与结构，因此任何一级都不阻塞主线。

级别 判定 处置 阻塞主线
A 充分 原件源码可读、行为可核对 直接按原件实现 否
B 部分 有契约 / 依赖 / 资源，缺实现细节 按契约实现，内部标注「待原件核对」 否
C 不足 只有名称或空目录 先定接口，实现最小可用并标「未实现」 否
D 缺失 参考库无此程序集 按本方业务需求设计，记录决策依据 否

三条硬规则

  1. 接口先行：C/D 级也先冻结公共契约（签名、数据形状、错误语义）。补证回来后只改内部实现、不改接口，因此不返工。
  2. 占位可见：未实现的功能保留明确入口，界面或日志至少一处标注「未实现」，不得静默可用、不得计为完成。
  3. 补证集中化：所有缺口汇成一个队列一次索取，等待期间照常推进 A 级工作，不设等待门。

批次计划

顺序按"设计正确性依赖"排，不按工作量排。前两批不做完，后面的工具迁移会返工。

批次 目标 完成判据 依赖
R1 旧 SDK 退场 把 Plugin.SDK 中被框架层真实使用的类型归位（模型 → Plugin.Contracts，日志 → Foundation），使 Core / Plugin.Infrastructure / CommonControl / DeviceDriver / UI 不再引用它 全部宿主工程对 Plugin.SDK 的引用清零（含 UI 对 SDK.UI.Controls 的直接引用）；全量 Release 0 错误 无（前置）
R2 算法层解耦 CvAdapter、HalAdapter 去掉 Plugin.SDK；Tool.Kernels 依赖方向纠正 算法层只依赖 Plugin.Contracts / Plugin.Runtime / 算子引擎；两个已准入工具执行结果与改前一致 R1
R3 UI 平台收拢 CommonControl 迁入脚本工具；Plugin.Editing.Wpf 归并核实；宿主自造控件逐步换原件 公共控件来源唯一；宿主 XAML 引用原件比例提升并记录 R1
R4 工具分族迁移 18 个旧工具按族拆 Runtime/Wpf 迁入新链，迁完删旧工程 每族：工具箱可见、拖入画布、执行出结果、保存重开、取消释放 R2
R5 开发包与最终目录树 PluginDevKit 模板与 SDK 由源码同步；旧入口与旧命名清零 第三方仅凭发布 DLL 可构建、部署、外部附加调试 R3 + R4

验收方式

  • 每批必做：dotnet build SunEyeVision.slnx -c Release 0 错误，记录警告数与耗时。
  • 依赖判据可机检：每批结束用项目引用导出核对五条判据，任一违反即该批不通过。
  • 功能链验收（R3/R4 适用）：工具箱出现 → 拖入画布 → 执行出结果 → 保存重开 → 取消与释放。
  • 不混淆三种状态：代码同步、构建通过、人工验收分别记录，不互相替代。

未取证缺口（不臆造）

  • Zoo.Halcon 内部算子组织方式（是否按功能族分文件、是否统一算子抽象）——决定测量工具怎么写，未读。
  • Domain / Workflow / Persistence 与 VM 的 Project / DiagramData / NodeData 是否职责等价——只比了工程名，未比类型清单。
  • Plugin.SDK 各子目录的真实消费者清单——只核到命名空间级，未到类型级。
