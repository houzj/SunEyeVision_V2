0. 用户功能性视角（必读）

改前用户看到什么

① 双击节点 → 先白窗约 0.5 秒，窗口出来了但里面是空的，等一会儿控件才出现。
② 第一次点「运行参数」Tab 卡 2~4 秒（实测 3.7s），点「结果显示」卡 1.7s；第二次起就快了。
③ 和原厂 VisionMaster 对比差距明显：VM 双击立刻出完整参数页，切 Tab 没有首次/后续的区别。

改后用户看到什么

① 双击节点，窗口出现的瞬间参数内容就在（目标 ≤100ms，与 VM 一致）。
② 切 Tab 首次和后续一样快（目标 ≤80ms），没有"第一次慢"现象。
③ 参数页外观与交互保持不变——联动显隐、范围配对、高级分组、枚举选项全部照旧。

2. Bug 模式分析

当前 bug

双击节点开窗空白约 0.5s；首次切参数 Tab 卡 1.7~3.7s，二次起正常。

真因分类：设计缺陷

不是"写得慢"，是生成方式选错了：把"参数 UI"当成了要在运行时用代码装配的对象，而不是"数据 + 模板"的渲染结果。这一层架构决定了卡顿必然出现，调参（缓存、异步）只能缓解，不能消除。

同类潜伏点

#位置描述优先级
1src/UI/Shell/Windows/MainWindowRuntimeEditing.cs:107Show 后 Background 优先级组装 — 同 pattern（低优先级延迟装配）P0
2src/Plugin.Wpf/Fields/DeclaredFieldsView.cs:463-472二次延迟构建死代码 — 同 pattern（延迟构建叠层）P0
3src/UI/Services/Editing/Nodes/RuntimeNodeConfigurationControl.cs:145-155CreateSettingsView 在 UI 线程同步完成整页创建 — 同 patternP0
4src/Plugin.Wpf/Fields/DeclaredFieldsView.cs:133每次 AddRow 都触发 UpdateVisibility 全量求值 — 同 pattern（O(n²) 倾向）P1

治本点

修复 「UI 生成层：命令式装配 → 数据树 + DataTemplate」（DeclaredFieldsView 的装配链）， 而非「当前症状点」（给 BorrowRow/UpdateVisibility 调优或把 Background 换成别的优先级）。 声明层（BlobParameters.xml → fields）保持不变——它已经和 VM 同构。

证据缺失警告

VM 同版本、同机型的开窗/切页耗时未取得实测值（反编译源码可读但无法运行原程序做对照）。本方案的 VM 侧数值按"无感"体验目标设定（≤100ms / ≤80ms），上线后用 PerfProbe 与用户体感复核。此缺口不影响架构结论——链路差异（数据树 vs 控件装配）有源码实证。

6. 防御机制

防御机制 #1：契约测试（字段覆盖一致性）

目的：防止模板化实现漏掉任何字段类型/布局能力。
落地形式：新增测试 DeclaredTemplateFieldsViewContractTests——对每个现有工具的 fields 声明，断言新实现与旧实现产出的 RealizedPageKeys / RealizedFieldIds 集合一致；对每种字段类型（数值/枚举/布尔/文本/引用/ROI/图形/文本表达式）各有渲染断言。
验收方法：dotnet test 全绿；缺一个字段 id 即红。

防御机制 #2：端到端冒烟（生产链手动验收）

目的：覆盖"启动 → 双击节点 → 看到内容 → 切页 → 联动 → 确认保存 → 重开"完整路径。
落地形式：Blob 分析工具全参数页手动脚本（含 visibleWhen 联动、pairWith 范围、advanced 分组、引用绑定、调试执行、关闭释放）。
验收方法：手动步骤表逐项打勾 + PerfProbe 日志无 EXCEED。

防御机制 #3：Fail-Forward（未知类型显式报错）

目的：模板选择器遇到未覆盖字段类型时，禁止静默跳过或空渲染（rule-015）。
落地形式：DeclaredTemplateSelector.SelectTemplate 未匹配即抛 NotSupportedException("未支持的字段类型: ...")；页构建失败按现有会话清理路径释放。
验收方法：单测构造未知类型字段断言抛异常；不出现"少了一行但没报错"。

防御机制 #4：性能守护（探针长期保留）

目的：自动发现未来重构造成的性能退化。
落地形式：P1 修复后的 PerfProbe 覆盖 open/tab/close 三场景全链路，阈值 open=300ms / tab=80ms / close=150ms，超阈值 Warning。
验收方法：验收运行日志中三个场景均无 EXCEED。

11. 评审结论（2026-11-07）

有条件通过架构方向，不批准按当前文档直接替换生成层。“数据树 + 模板”可以作为 VM 对齐目标，但文档把静态结构差异直接等同于性能根因，并把未经 VM 实测的 80ms/100ms 写成验收目标，需要修正。

保留项

  • VM 的声明/参数树承接 Tab、分组和触发关系，作为目标模型。
  • Tab 选择不应重复触发页面组装。当前本方重复切换已证明有页面复用。
  • 隐藏页的全量数值回读不应阻塞打开。该项已由本方实测确认，并移到 DispatcherPriority.SystemIdle。
  • 固定主题资源，不设计运行时主题切换。

必须修正项

原判断评审结论
“命令式装配是根因，模板化可彻底消除首切卡顿”过度结论。DataTemplate 仍会创建 WPF 控件树，不能由静态结构推出 ≤80ms。当前 BlobAnalysis 第2/3页首次仍为 2021/2562ms，重复切换为 24/60ms。
“VM Tab 切换零构建”静态代码只证明选择属性处理，不能证明视觉树、绑定和模板已在打开时全部生成。应改为“静态未见 Tab 处理器主动重建，运行时复用方式未确认”。
“五类宿主职责导致重复构造”没有实例计数或调用次数证据。当前 DeclaredFieldsView 已有按页 builder 和 built-page 缓存，不能直接认定每次切页重建。
“声明层已经与 VM 同构”本方 page/section/visibleWhen/pairWith 与 VM Tab/Category/Triggers 只是结构相似，父链、触发和保存语义仍需逐项映射。
“新字段零装配代码”Blob 的 ROI、阈值、显示组合、运行参数和外部锚点仍需要专用接缝，必须保留模板槽和资源所有权合同。
“VM 同版本性能目标 ≤100ms/≤80ms”目标值是推算，不是 VM 实测。先取得同场景原厂基线再定预算。
