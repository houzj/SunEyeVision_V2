## 一、一句话结论

工具调试窗口「打开慢、切换慢」的**根因尚未被任何实测数据证明**；目前能确定的是 VM 参数 UI 为**声明驱动装配**，以及我方窗口职责被拆散在 5 个类中导致**重复构造**。解决方案分两步：先用真实数据取证，再按证据改；在此之前不允许预设缓存、虚拟化或异步。

---

## 二、问题现象

| 现象 | 用户感受 |
|---|---|
| 控件较多的工具，调试窗口首次打开明显等待 | 点了没反应，怀疑没点中 |
| 在参数 Tab 之间切换有顿感 | 调参节奏被打断 |
| 切到另一个节点再切回来 | 需要重新等待 |

## 三、分析结论（分三层，不是一句话定论）

### 3.1 可确认（VM 静态证据）

VM 参数 UI 走**声明驱动组装链**：

```
工具入口
  → IToolPresentationFactory / IToolSettingsView
  → ModuleParam / AlgorithmTabRoot     ← 页签、分组、外部参数、左右/底部命令、选中页、窗口尺寸、订阅、ROI 桥接
  → ParamsConfigControlBase
  → ParamsTabUserControl
  → ParamListView / ParamUserControl
  → UserTempConverter + paramusercontroldatatemplate.xaml   ← 202 类参数分发到真实 DataTemplate
  → Tab / GroupLinkItem（克隆公共组并设父链）/ 底部命令 / 外部槽
  → 执行回调 → 关闭退订与资源释放
```

结论：**控件数量差异来自 XML/Group 声明量，装配工作量由声明驱动**。这是「控件多就慢」的直接怀疑对象。

版本锚点：VisionMaster 4.4.0 Build20250516@1555331，7 个控件/资源程序集 SHA 已在 `docs/07-工具逆向/decompiled/README.md` 固定。

### 3.2 可推断但未证（待测假设）

首次打开慢可能来自四处：

1. XML / Group 展开
2. DataTemplate 选择（202 类分发）
3. 控件树构造
4. 资源合并

**这四条只是假设，不能写成 VM 的机制。**

### 3.3 目前未知（必须承认的空白）

- 是否一次性创建全部 Tab 内容，还是按需装配
- 同节点切 Tab 是否复用视图 / 模型 / 模板，还是销毁重建
- 跨节点切换是否先销毁旧树再建新树
- 是否存在缓存、异步、虚拟化、延迟装配
- 首帧瓶颈到底在 XAML 解析、绑定、资源合并还是算法执行
- 关闭顺序：退订 → 等待在飞 → 拒收迟到回调 → 释放 reader / 图像，VM 的真实顺序未闭合

### 3.4 两条纪律

1. **不能把我方实现当 VM 事实**。`ToolDebugSession`、`ToolEditorHost`、`ModuleExecutionScope` 的关闭等待链是本方实现，不能反推 VM 行为。
2. **VM 原厂没有运行时主题切换能力**，SunEyeVision 不再设计运行时主题切换，只保留与 VM 装配链一致的固定主题资源。

## 四、解决方案

### 4.1 第一步：先取证（不改架构、不上优化）

固定两个样本：一个普通 XML 工具、一个含 `GroupLinkItem` 的工具，采集五个场景：

| 场景 | 采集项 |
|---|---|
| 首次打开 | 窗口/视图/模型**实例数**、模板解析次数、绑定次数、资源加载数、**首帧 UI 线程耗时** |
| 同节点切 Tab | 视图/模型是复用还是重建（实例数增量）、模板是否重解析 |
| 跨节点切换 | 旧树是否销毁、旧模型是否释放 |
| 返回原节点 | 是否重建、是否命中任何缓存 |
| 关闭 | Loaded/Unloaded 顺序、绑定回调、reader 与图像资源释放时点 |

落点：复用已有 `ILogService`，在关键节点输出结构化耗时，跑一遍出数据。

### 4.2 第二步：按证据决定（有证据才动）

| 证据指向 | 对应动作 |
|---|---|
| 每次重建视图/模型 | 做实例复用 |
| 模板/资源重复解析 | 做模板缓存与资源合并 |
| 一次性装配全部 Tab | 改按需装配 |
| 关闭时资源未释放 | 按 Owner 合同收紧生命周期 |
| 什么都没指向 | 不改 |

**未取得证据前，禁止新增缓存 / 虚拟化 / 异步 / 延迟加载**，也禁止以 VM 行为名义验收。

### 4.3 架构侧同步动作（不依赖性能证据）

把窗口宿主收拢到 VM 那条组装链上。这是结构问题，可以先行。

## 五、现状差距（问题真正的来源）

VM 的 `AlgorithmTabRoot` **一处**承担：页签管理 + 分组 + 外部参数 + 底部命令 + 选中页 + 窗口尺寸 + 订阅 + ROI 桥接。

我方拆成五个类各承担一段：

```
ToolEditorHost
ToolConfigurationHost
ToolDebugWindow
ToolConfigurationProvider
ToolConfigurationState
```

后果：同一次打开可能走多轮初始化，同一份状态被多处各算一遍。**这是结构性重复构造，不是渲染慢**，所以性能补丁无法根治。

此外我方已有 `ThemeManager`、`PreviewBitmapCache`、`EnhancedBatchUpdateManager`、`CachedNodeConverters` 等设施，按证据纪律只能算**候选实现**，不得以 VM 行为名义验收或继续扩展。

## 七、对 Codex 审计意见的回应

### 7.1 认同的部分

1. **静态组装链梳理扎实**，`AlgorithmTabRoot` 职责、`GroupLinkItem` 父链、202 类 DataTemplate 分发是可施工的声明式契约。
2. **「不能把本方实现当 VM 事实」**这条纪律必须保留。
3. **性能不预设机制**，不先测就加缓存基本等于白干，完全同意。

### 7.2 不认同的部分

| 问题 | 说明 |
|---|---|
| 全篇结论为「未确认」，无行动出口 | 统一验收矩阵 7 个场景全为未确认，优化方案第一步是「建立测量」，但未写谁测、测到什么数算过、测不出怎么办。所有缺口共享同一闸门 = 全部停工 |
| 证据缺口未分档 | 「缺运行证据」不影响「按已确认静态链组织代码」；「缺 NodeData 语义」不影响「删除已定性为过渡结构的旧代码」。不同缺口不该互相阻塞 |
| 定性落后于仓库现状 | 审计称「旧 Plugin.SDK 退场属候选、不能放行删除」，但 `Directory.Build.targets` 早有 `RejectRetiredSdkToolBuild` 闸门（`IsToolPlugin=true` 直接报错拒绝构建），旧工具在审计前已退出产品构建 |
| 冻结顺序倒置 | 要求「四批证据 + 全量映射 + 主线评审」后才允许批量重构，而审计自身已认定旧 SDK 属过渡结构。已定性为过渡的清理不该被 NodeData、保存重开等无关缺口拉住 |

### 7.3 我方该认的问题

1. **动手前没先出迁移映射表**。R1 一次改动 146 个文件，虽有构建与测试实证，但顺序违反「先完成整体实现设计，再按设计成片实施」。
2. **目标分层不该单方面定稿**。`Plugin.Editing.Wpf`、`Plugin.Tooling` 两个层的判断依据是依赖方向（算法层不该依赖 UI 模型层），方向成立，但 VM SDK 结构尚未确认，应标为候选。
3. **唯一可定稿的判断**：删除 `IVisionImageDisplayBridge` 属纯代码事实（零实现、零调用、零注入）。

### 7.4 建议的证据分档（替代单一闸门）

| 档 | 允许动作 | 覆盖范围 |
|---|---|---|
| **A 档：静态证据即可施工** | 按已确认链实现、删除已定性过渡结构、删死代码 | `AlgorithmTabRoot`/`GroupLinkItem`/模板分发组装语义；旧 SDK 清理；死契约删除 |
| **B 档：必须有运行证据** | 性能机制、复用边界、销毁顺序、SDK 目标分层定稿 | 缓存/虚拟化/延迟装配；Tab 复用 vs 重建；跨节点释放顺序；新层归属 |

## 十、验收口径

本篇为**分析结论与方案**，不含功能交付。判定标准：

- 取证数据出来后，能明确回答「慢在哪一段」，并据此形成带预算的优化项
- 窗口宿主收拢后，同一次打开只走一轮初始化，实例数与模板解析次数可量化下降
- 任何优化项落地时，必须在提交中附前后数据，不以「感觉快了」验收

## 十一、2026-11-07 实际探针回执与本轮立即调整

本轮 `tests/RuntimeEditorProductionProbe` 在当前工作区直接构建并运行，覆盖 ImageLoad、BlobAnalysis 的真实 Session、节点、参数视图、Tab、提交和关闭释放。结果如下。

| 阶段 | 调整前基线 | 绑定全量数值回读移出打开路径后 | 结论 |
|---|---:|---:|---|
| ImageLoad 参数页绑定返回 | 634ms | 348ms | 绑定阶段下降约 45%，当前仍在 UI 线程但不再同步读取隐藏页全部数值 |
| BlobAnalysis 参数页绑定返回 | 2464ms | 1313ms | 下降约 47%，证明同步 `ReadNumericModels(All)` 是打开路径中的真实额外成本 |
| BlobAnalysis 首个已选页呈现 | 396ms | 304ms | 首页面控件树仍有成本，但资源字典不是主因 |
| BlobAnalysis 第 2 页首次切换 | 2907ms | 2021ms | 仍是首次页面控件树和绑定装配成本，不能把它归因于 Tab 控件本身 |
| BlobAnalysis 第 3 页首次切换 | 3031ms | 2562ms | 同上 |
| BlobAnalysis 重复切第 2/3 页 | 24/34ms | 24/60ms | `_pageBuilders` + `_builtPages` 已产生稳定复用，重复切换不是当前主要瓶颈 |

本轮代码将 `DeclaredSettingsView` 的全量数值模型同步改为 `DispatcherPriority.SystemIdle` 调度，并保留显式 `ReadNumericModels(NumericModelReadScope.All)` 的即时合同。重绑定和释放通过 generation guard 拒绝迟到读取。这样先完成窗口和当前页装配，隐藏页的宿主回读在 UI 空闲时补齐。该行为是当前实现的性能修复，不写成 VM 已确认机制。

这组数据把 CodeBuddy 文档中的“根因未证”收敛为两个层次。全量数值回读已经由本方实测证明是可移除打开阻塞的实现问题。首次生成 BlobAnalysis 第 2/3 页仍需继续与 VM 同场景取证，当前不能擅自新增缓存、虚拟化或把页面预构建到后台线程。主窗口已先呈现再执行参数页绑定，当前探针仍是直接绑定控件，不能代替主窗口人工首帧测量。

验收出口保持三项。第一，首次打开窗口可见后不被隐藏页回读阻塞。第二，同节点首次 Tab 只装配一次，重复切换复用既有页面。第三，提交、重绑定、关闭释放和迟到回调测试继续通过。下一步只针对首次页面装配做 VM 与当前实现的逐段实例数、模板分发、绑定和 UI 线程耗时对照。
