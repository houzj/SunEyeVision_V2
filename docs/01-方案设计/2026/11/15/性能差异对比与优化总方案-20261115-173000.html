本方 300ms 分解：batch-capture 70ms + batch-run 200ms（其中算法仅 40ms，160ms 为框架）+ result-publish 10ms + 其他约 20ms。
结论：即便把 Blob 从 38ms 优化到 15ms（省 23ms，占 8%），总耗时也只到约 275ms；而把 260ms 框架压到 80-120ms，可让总耗时进入 130ms 级别（省 57%）。主战场是框架开销，对应 VM 的"模块常驻 + 只发请求"设计。

环节VM本方
算法引擎归属独立 Server 实例/进程UI 进程内（HALCON 75MB）
装载时机启动时（BeforeStartPart 后台最高优先级线程，与 UI 并行）首次执行时（IsDeferredPlatformDependency 延迟装载，new HImage(address) 隐式触发）
成本可预期性确定（启动付一次，之后恒定）随机（20ms~3100ms，取决于 OS 文件缓存是否命中 75MB DLL）
点方案时的行为只加载方案（流程/模块描述）；算法本体已在 Server全托管新建对象；算法仍冷
执行时行为向常驻 Server 发请求每轮 new 引擎/会话/全量快照
定性："时快时慢"是设计问题，不是环境问题——一次性成本（HALCON 平台装载）没有确定归属，被隐式绑定在"第一次 new HImage"上，因此成本大小取决于系统当时缓存状态。VM 把这个成本固定在启动阶段，所以稳定。
佐证：本机可用内存 2.9GB/15.8GB、Standby 缓存 2.5GB，75MB DLL 易被回收 → 冷/热交替 → 随机表现。环境只决定随机值大小，设计决定随机性存在与否。

六、设计对齐路线（L1-L4）

L1 预热：补上缺失的初始化阶段（对齐 VM 的 StartNewInstance 时机）

做法：HandleStartupDecision returned 之后，后台 LongRunning + BelowNormal 线程执行一次：HOperatorSet.GetSystem("version") + 内存生成小图 → HImage 构造 + 一个阈值算子。不 await、不进启动关键路径、不读用户图像、不写方案；失败只记日志。
预期：首次 image-read-decode 1107ms（冷态可达 3134ms）→ ≤10ms；首次流程 1532ms → 约 450ms。
验收：新进程首次执行探针 ≤10ms；启动 HandleStartupDecision returned 耗时不变（±0.2s）。

L2 执行链常驻化：消除每轮 260ms 框架开销（主战场）

对齐对象：VM 的"模块/流程对象常驻，运行只发请求"。
候选四刀（须先量化后再动，见第 7 节）：
#候选现状预期风险
L2-a执行引擎池化/复用DocumentRunBatch 每批 new WorkflowExecutionEngine()省数 ms低（需确认无状态残留）
L2-b工具会话按节点复用每节点每轮新建 IToolSession（BlobSession 等）省数 ms + 避免 HALCON 作用域重建中（会话状态/生命周期）
L2-c参数绑定物化缓存每轮 binding-settings 重新物化（3-6ms/节点）省 10-20ms中（配置版本失效）
L2-d输入/参数快照按需每轮 batch-capture 全量捕获 70ms省 20-50ms中高（快照是执行隔离语义，须逐端口核实消费方）
预期：框架 260ms → 80-120ms。
底线：不得以放弃"执行快照语义"换性能；只优化"没被消费的端口/重复物化"。

L3 Blob 算法确定性（消除内容相关抖动）

B4 先测入口 24ms → B1 灰度统计按需（每 blob 一次 GrayHisto，-10~15ms）→ B3 per-blob SelectObj 批量合并（-3~5ms）→ B2 区域快照按需（per-blob + final/ok/ng 三次深拷贝，-6~8ms）。
预期：Blob 25-57ms → ≤15ms，且不再随 blob 数量线性抖动。

L4 渲染/发布（可选）

场景差量更新（同 publication 只更新变化图层）；result-publish 惰性化。预期省 10-20ms。
综合预期：流程总耗时 ~300ms → 约 100-130ms；首次 ≈ 后续（确定性达成）。
诚实边界：仍约为 VM（7.32ms）的 15 倍，根源是架构（进程内 HALCON + 托管边界 + 快照隔离设计）。要完全追平需算法迁独立进程 + 模块全常驻 + 渲染常驻，属执行层重写，本方案不承诺。

七、执行稳定性与效率底线

稳定性是性能优化的前置约束。执行引擎、节点会话、输入快照和结果发布的生命周期必须形成完整合同，不能因为改动范围大而停止优化，也不能用删除隔离语义换取耗时下降。
每个优化批次必须同时验证冷启动首次执行、同一流程后续执行、连续执行、取消、异常、节点切换、方案切换、参数编辑后再次执行和关闭释放。结果数量、数值、图形、文本、结果表、历史记录和资源归属必须保持一致。
执行引擎复用、工具会话复用、参数物化缓存和图像缓存都必须有明确的身份键、配置失效条件、取消边界、异常回滚和退役释放路径。任何复用对象在下一轮执行前都必须完成上一轮的资源结算。
性能验收同时记录首轮耗时、稳定态耗时、耗时方差、失败率和资源增长，不能只看平均耗时。优化结果必须在 Release 程序中按统一执行 ID 留存探针证据。

九、明确不做

项理由
移除执行/参数快照机制快照是执行隔离语义（同输入必同结果、执行期不受编辑影响），不以正确性换性能；只做"按需捕获"
ReadyToRun 全量对 HALCON 原生装载无效；JIT 非本次主因
ImageSource 解码优化非首次已 4-7ms，接近 VM 4.05ms
算法迁独立进程（本轮）工程量≈执行层重写，需单独立项评估
