> 只读分析，未改任何代码。基线 `1716fe79f` + 57 个未提交改动。

## 0. 一句话结论

**问题不在某个工具写错，而在“声明没有单一真源 + 平台装配器零强制”。**

三个数字说明现状：
- 18 个工具共 **32,295 行**，其中 **52% 是声明/样板、33% 是编辑器手工装配、只有 14.7% 是算法**；
- 平台最强装配入口 `ToolEditorCommit` / `ProductionEditorContext` 在工具层 **0/18 复用**，`NativeStandardBasicPage` 只有 **4/18**；
- 同族工具的声明文件已出现**逐字相同**：`GrayMatch/MarkFind/ContourMatch` 的 `*ResultGeometry.cs` 各 84 行且 `Capture(...)` 签名一致；`BlobLabels/GrayMatch` 的 `*ResultDisplay.cs` 各 176 行、字段块逐行同文。

原厂边界一句话：**平台 = 声明解释器 + 通用交互 + 私有序列化；工具 = XML 元数据 + 原生算法。**
（`R1\decompiled\WpfControls\VMControls.WPF\ParamsConfigControlBase.xaml.cs:206-269`、`AlgorithmTabRoot.cs:577-593`）

## 4. 问题根源（四条结构性缺口）

**R1 声明没有单一真源。**
同一份“参数/IO/显示/ROI”语义被拆成 4–6 个 C# 静态类（`*Fields.cs`、`*Schema.cs`、`*ResultDisplay.cs`、`*Roi.cs`、`*Parameters.cs`），每个都要手写、手对齐。原厂是 4 份 XML 由平台解释，只有一份真源。

**R2 平台装配器没有强制入口。**
`ToolEditorCommit`、`ProductionEditorContext` 存在但 **0 工具使用**；`NativeStandardBasicPage` 4/18；`NativeRoiEditHost` 2/18。平台能力“可选”，工具自然各写各的。

**R3 没有工具脚手架。**
新建工具的复用手段是“复制一个最像的工具再改”。这是 `*ResultGeometry.cs` 三份 84 行逐字相同、`*ResultDisplay.cs` 两份 176 行同文的直接原因。

**R4 没有契约门禁。**
没有架构测试阻止“工具引用 UI 层”“工具自写渲染”“同一份声明出现第二份”。漂移只能靠人眼发现——这次就是靠对比文件行数发现的。

### 影响传导

```
R1 声明分散
  → 每处都要人写 → 漂移（同一语义 3 种写法）
  → 新人只能复制 → R3 放大
R2 装配可选
  → 工具各自装配 → UI 行为不一致（ROI/结果显示/参数页反复出同类 bug）
R4 无门禁
  → 上面两者可以长期存在而无人告警
```

**结论**：过去反复修的 ROI 显示、结果显示、参数页问题，都是 R2 的表象；改一个工具只修好一个工具，所以“反复出现同样问题”。

## 6. 统一方案（5 个改造包）

### P1 工具清单（ToolManifest）——解决 R1

一份 `tool.manifest.json`（或 C# 声明式 builder）承载：
- 身份：`id/name/category/icon/keywords`
- 输入：`image/roi/fixture/mask` 标准端口组合（平台提供常量组合，工具选装）
- 参数：`id/label/type/default/range/step/visibleWhen`
- 输出：结果行字段、标量输出
- 显示：显示项（检测区域/匹配框/轮廓点/文本）
- ROI：形状集合、上限、继承方式

平台在构建期生成：`SettingsSchema`/`ResultSchema`/`DisplaySchema`/`ResultDisplayDescriptor`/`RoiEditDeclaration`/`RequiredOutputs`。
**收益**：消灭 52% 的声明样板；四个声明文件合一。

### P2 平台装配器（ToolPageComposer）——解决 R2

平台提供唯一参数页装配入口：
```
ToolPageComposer.Compose(manifest, inputs, draft) → FrameworkElement
```
内部统一完成：页签/分组/行、ROI 宿主、结果显示字段、上传/撤销（`ToolEditorCommit`）。
工具不得再 new `NativeRoiEditHost`、不得自己排 `DeclaredInputFieldsView`。
**收益**：消灭 33% 的编辑器装配；UI 行为天然一致。

### P3 工具基类（ToolDefinitionBase）——解决 R1/R2

提供默认实现的抽象基类，覆盖 18/18 的四个必备接口 + 常用的 `RuntimeInitialization`/`ParameterBindingNames`/`ManualReferenceSources`：
```
abstract class ToolDefinition<T> : IToolDefinition<T>, IToolSettingsFields, IToolCatalogProvider, ...
```
工具只 override：`Manifest`、`CreateSession()`。
**收益**：接口样板从 ~200 行/工具降到 ~20 行。

### P4 几何/显示基座——消除“84 行 ×3”

平台提供 `GeometryCapture.FromRegion(region, role, options)` 与 `DisplayFields.Graphic(group, label, defaults)`：
- 光栅组、`OutlineOnly`、预算、空域语义由基座决定；
- 显示字段 visible/ok/ng/opacity/width 由基座生成，工具只给标签与默认色。
**收益**：消除 3 份 84 行 + 2 份 176 行的逐字重复。

### P5 同族合并——解决“重复工具”

| 族 | 成员 | 合并方式 |
|---|---|---|
| 模板匹配族 | GrayMatch / MarkFind / ContourMatch | 共享“模板 + 搜索域 + 匹配结果”内核，差异只在算法入口与训练窗 |
| Blob 族 | BlobAnalysis / BlobLabels | 共享阈值/连通域/筛选/输出，差异只在“是否输出标签” |
| 测量族 | CircleCircle / PointPoint / LineLine… | 共享“两个几何体 → 测量值”框架 |
| 输入源族 | ImageSource / DivideImage / FrameMean | 共享图像输入输出包装 |

估算：匹配族可消除 **8,000–9,000 行**重复声明（以 GrayMatch 2,302 + MarkFind 2,361 + BlobLabels 2,856 的同构部分为上限）。
**不可合并**（真实差异，保留）：ContourMatch 模板训练窗（`TemplateConfigData.cs` 1,759 行）、BlobAnalysis 的 HALCON 阈值内核（1,219 行）。

### P6 契约门禁（架构测试）——解决 R4

新增测试项目 `SunEyeVision.Architecture.Tests`：
1. 工具项目**不得**引用 `Plugin.Wpf.Presenters.Parameters` / `UI`（除已登记例外）；
2. 每个工具必须有 `manifest`，且生成物与 manifest 一致（快照比对）；
3. 禁止 `new Port(` / `new ResultDisplayDescriptor(` 出现在 `tools/`；
4. 同族工具的声明文件哈希不得与另一个工具相同（检测复制粘贴漂移）。

| **工具脚手架**（新增 skill `工具脚手架`） | 按 manifest 生成完整工具项目骨架（csproj/manifest/session/测试），不生成编辑器与声明文件 | `dotnet new suneye-tool` 等价物 + 模板 |

技能体系的定位：**技能不是文档，是可执行的生成器 + 门禁**。否则又变成“写在文档里、没人执行”。

## 10. 未闭合项（不得当成结论）

1. `VM.Core`/`ModuleFrame.dll` 未入库，`ModuBase`/`VmModule`/`VmIO` 类体无证据，执行基座只有原生地址级证据。
2. `ParameterManager`/`ValueManager`/`ValidateParam`/`ReferenceManager`/`ModuAlgorithmTab` 在库内 0 命中，本文用功能等价物替代。
3. XML 到页签归属、显隐条件、值联动、像素级布局未取证（XML 只给 `type`+`name`）。
