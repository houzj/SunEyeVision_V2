一、改前 / 改后 / 依据

改前，用户看到什么

  • 节点上一共只有 4 个端口，拖线时才冒出来，鼠标一移开就消失，悬停没有任何提示。
  • 只有"图像源"节点长得像胶囊，别的节点都是统一卡片，原因是代码里按工具 ID 写死了一个圆角特例。
  • 连线是灰蓝色（#666666），VM 里是橙色（#FFA70F），一眼就能看出不是同一套。
  • 节点右键只有"复制、重命名"两项，VM 里有六项。
  • 参数配置窗口的分页样式是自己画的，VM 用的是带页签背景和橙色下划线的那套。

改后，用户看到什么

  • 节点照样 4 个方位，但鼠标一进节点就四个端口一起出现，命中哪个哪个变粗变大；拖线走向与 VM 一致。
  • 节点填充、底边橙线、边框、投影与 VM 逐值一致；连线是 VM 的橙色，拖线是 VM 的 5/2.5 虚线节奏。
  • 右键菜单与 VM 同样六项：断开连接 / 删除 / 复制 / 重命名 / 禁用 / 启用。
  • 参数配置窗口用 VM 原件那套页签外观。
  • 节点形状后续按 VM 的"显示类型"（普通/图像/条件/功能/定时/壳/通讯）自动选择，不再按工具 ID 写死。

依据（不是自创，是照做）

  • 端口几何：VM 原件 diagramitemtemplate.xaml 第 167-190 行的四个 Connector 实例（20×30、Margin −20/−25、ScaleX=-1、RotateTransform ±90）。
  • 端口视觉：VM 原件 Connector.xaml（橙条 5×8、命中放大 8.5×12、#FF444444 边框）。
  • 节点填充：VM 原件 NormalModulePathStyle（#FAF7F5→#F3F6F5→#ECEDF0→#EBE6E2→#EB6600 五段渐变）。
  • 节点形状：VM 原件 6 个 PathGeometry（ImageModulePath / IfBranchPath / FunctionModulePath / TimerModulePath / ShellModulePath / CommuncationDataPath）。
  • 连线配色：VM 原件 connectionstyle.xaml（Col_EditProcess_Ligature = #FFA70F，Selected = #E76900，线宽 2/3）。
  • 右键菜单：VM 原件 diagramitemtemplate.xaml 的 InteractionContextMenu 六项。

四、Bug 模式分析（治本，不打补丁）

真因分类：实现偏差（迁入未接通）+ 契约漏洞（跨程序集资源无校验）。

第 1 类：迁入未接通（占问题 6、7 的全部，问题 5 的一半）

原件代码已经复制进仓库，但停在 .pending 或存在却无人消费。结果就是"仓库里看着有、界面上用不上"，开发者每次都要重新判断"到底有没有"。

同类潜伏点（已实测）：

  • 521 个 .pending：内容含 namespace SunEyeVision.Plugin.Wpf.Native...，是迁移草稿而非垃圾；任何 csproj 都没有引用它们。
  • ConfigurationShell.xaml/ConfigurationControls.xaml：已合并进 Generic.xaml，但 UI 侧无窗口使用。
  • colorstyle1/2/3.xaml：已注册为 Resource，但 UI 未合并，158 个键零消费。
  • ImageViewBox 等原件控件：存在于 Native/Display，使用面待核对。

治本点：不逐个修补，而是建立"原件资产必须有消费者"的校验——每个迁入的原件字典/控件，要么有明确消费位置，要么在台账里标注"未接通 + 原因"。没有台账就不算完成。

第 2 类：跨程序集资源无契约（问题 5 的直接原因）

WPF 的 Themes/Generic.xaml 只对**本程序集内定义的自定义控件**自动生效，对宿主里 TabControl 这类框架控件不生效。因此 UI 要用原件样式，必须显式合并字典。

本次实施已踩到真实代价：把配置窗口样式改为依赖 App.Resources 后，RootCollectionMainWindowTests 立即失败（测试环境没有 Application 级资源），改为窗口级合并才恢复。

治本点：原件样式一律在消费者所在作用域合并（窗口级/控件级），不依赖全局 Application 资源；同时把这条写成契约测试。

推荐 C，理由：

  1. 实测证明整批启用 B 不可行——启用 24 个原件文件即产生 100 个编译错误、去重 18 类缺失契约（IExtensionItem、IDecorate、ExtensionItemDecorator、DragDropAdorner、StatusBar 等），而这些类型的来源程序集 WindowUtilities 在全部反编译产物中 0 命中，属未逆向证据缺口。
  2. A 已被本次实测否定——节点外观与端口的真实差异是结构与取值，不是样式微调；补丁式改法会留下两套端口实现。
  3. C 的每一批都能独立构建、独立跑单元测试、独立人工验收，符合"每批 0 错误"的硬约束。

十、防御机制（≥2 项）

1. 端口契约测试（单元）

断言：每个节点端口数 = 4；锚点位于节点视觉边缘中点（与原件的 AnchorPoint(i) 一致）；IsHited 由 IsMouseOver 驱动；端口层随节点悬停显示。

落在 tests/CanvasLayout.Tests，与现有 27 个用例同批运行。

2. 原件资源消费台账 + 校验（防"迁入未接通"复发）

对每个迁入的原件字典/控件登记：消费位置（文件:行号）或"未接通原因"。校验脚本在构建后运行，发现"字典存在但零消费且无原因"即失败。

这一条直接封堵本次发现的第 1 类 bug 模式（ConfigurationShell/colorstyle/521 个 .pending）。

3. 资源合并作用域规则（防跨程序集失效）

原件样式一律在使用者作用域合并（窗口级/控件级）；契约测试覆盖"脱离 Application 资源仍能构造窗口"，等价于本次已修复的 RootCollectionMainWindowTests。
