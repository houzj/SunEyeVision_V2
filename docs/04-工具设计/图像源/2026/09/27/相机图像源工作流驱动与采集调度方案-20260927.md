# 相机图像源工作流驱动与采集调度方案

日期：2026-09-27  
状态：后续沟通与实施基线；已开始实施，真实相机工作流验收尚未完成  
范围：工作流运行调度、相机帧输入、相机调试预览隔离、超载和 UI 响应

本文补充并覆盖同目录《图像源工具 UI 与执行设计方案》中**相机工作流每轮主动取帧、相机预览/工作流并发取帧**的设计描述；本地图像预览器的可见性、来源切换 UI、输出契约等未冲突部分继续有效。VM 的实际内部实现未知；本方案只参考用户观察到的交互，不宣称复刻 VM 架构。

## 1. 现状、问题与待验证事实

- 当前连续运行是一轮工作流完成后再启动下一轮；相机图像源节点执行到自身时调用 `CaptureAsync` 主动取一帧。按钮驱动工作流，帧不是统一调度器的输入事件。
- 相机设置窗口的预览只为调试相机参数，不是工作流图像来源，不得将预览图像直接送入图像源节点或由预览回调启动工作流。
- 当前预览流与工作流单次取帧可访问同一相机适配器；有取帧锁，但没有清晰的采集所有权和并发使用规则。
- 用户观察到本地图像连续运行不卡 UI，而相机软件触发连续运行时 UI 响应变差；触发关闭的工作流还有读取失败现象。现有日志证明部分软件触发和工作流执行成功，但**尚未确定** UI 卡顿及触发关闭读取失败的具体根因。不能把两者直接归因于相机出图过快或 SDK 缓冲。
- 工作流逐轮执行不等于 UI 逐轮刷新完成。节点状态、结果树、图像转换、统计属性、日志等仍可能造成 UI 线程耗时或异步投递积压；此项须通过对照测量验证。

## 2. 职责边界

```text
用户单次/连续/停止命令 ──→ 工作流运行调度器 ←── 相机帧事件
                                  │ 仅调度器决定是否启动一轮
                                  ↓
                           本轮不可变帧快照
                                  ↓
                         图像源节点 → 后续工具

相机设置窗口 → 参数调试预览（独立用途；不进入工作流）
```

按钮只修改运行意图和状态；相机采集服务只提交带相机 ID、帧号、时间戳的帧就绪事件。这里的“帧事件”不要求厂商 SDK 提供回调：后台采集循环通过 SDK 等到完整帧后再发布事件，同样符合设计。按钮和帧事件不能各自直接调用工作流执行入口。同一工作流同时最多运行一轮。图像源消费本轮开始时确定的图像快照，不在执行到节点时重新向相机请求另一张图。运行时负责连接、采集和帧所有权；工作流执行层不访问 WPF 控件，UI 不承担调度职责。关闭预览或图像源调试窗口不改变设备原有连接状态。

### 2.1 图像源节点的两阶段角色（避免循环依赖）

1. **开始运行之前**：运行协调层从工作流定义的图像源配置读取来源类型和稳定相机 DeviceId，形成配置快照，供调度器决定监听哪台相机。此时没有执行该节点，也不由插件注册回调或操作 SDK。
2. **帧到达之后**：只有调度器确认工作流处于单次等待或连续运行状态、当前没有冲突轮次，才把该帧作为本轮输入快照启动一次执行。
3. **本轮执行到图像源节点**：节点读取本轮上下文里的图像，转换/输出统一图像契约供下游使用；不再次取帧、不再发触发命令、更不递归启动工作流。

因此驱动一轮的是被运行状态接受的**帧事件**，不是正在执行的图像源节点；节点配置只是让运行协调层知道帧来自哪里。相机运行时对图像内存的所有权必须清晰：移交给本轮前完成必要的复制或引用计数，覆盖待处理帧、停止或执行结束时释放相应资源，不得让下游持有已归还 SDK 的缓冲区。单次模式只接收启动后符合条件的一帧；旧缓存帧不得误作为本次输入。

### 2.2 与未来通讯事件的边界

调度器接收的是抽象的“启动一轮请求/输入快照”，而非写死的图像参数。相机事件携带帧，未来若需通讯触发可携带设备 ID、报文和时间戳，并通过同一执行租约与取消机制启动一轮；无图像源工作流不依赖相机事件。通讯事件触发**当前尚未实现，也不是本轮实施范围**：本轮不设计通讯事件配置、匹配规则或跨源优先级，只保证调度入口不与相机 SDK 或 WPF 绑定。未来出现同一工作流有多种触发源的需求时，必须先定义仲裁和去重规则，不允许多个入口分别直接执行。

## 3. 无需普通用户手动选驱动方式

当前工程实施约定通常由一个工作流使用一个图像源，多相机任务优先拆成多个工作流。这只是现阶段的使用约定，**不新增“每个工作流只能放一个图像源”的编辑器或运行时限制**。多个图像源的自动驱动、同步和配对不属于本轮方案，不在此预设主触发相机或强制拒绝执行；若后续确有业务需求，再基于具体场景单独设计。

| 工作流配置 | 单次执行 | 连续运行 |
| --- | --- | --- |
| 无图像源 | 立即执行一轮 | 沿用逐轮运行；避免无间隔忙循环 |
| 本地图像源 | 读取当前本地输入快照并执行一轮 | 沿用现有预览器序列/逐轮运行语义 |
| 常规单相机图像源 | 进入等待一帧状态，收到帧后只运行一轮并退出 | 进入接收帧状态，收到帧后按超载策略安排运行 |

界面可只读显示自动判定的运行状态，例如“等待相机1帧”“相机1帧驱动”“等待硬件触发”，不增加普通场景的常驻启动方式开关。相机持续出图但工作流处于未运行状态时，不执行工作流。没有图像源或使用本地图像源时，按钮仍按现有逐轮语义运行，不等待相机帧；因此“工作流启动”不被图像源或相机回调垄断。

## 4. 相机触发与状态机

- **触发关闭（自由运行）**：运行调度器订阅指定相机的帧；单次模式仅认领一帧，连续模式对到达帧安排后续轮次。相机帧到达之前不执行空轮次，也不每轮重复向 SDK 发取帧请求。
- **软件触发**：单次模式发一次命令并等待对应帧。连续模式默认上一轮处理完成后再发下一次命令、再等对应帧，不主动制造积压。应以帧号/请求序号和超时跟踪对应关系，避免旧缓存帧误配。
- **硬件触发**：等待外部信号产生的帧；无帧时显示等待，不空转执行。新触发超过处理能力时进入统一超载策略。
- **停止**：立即撤销订阅/待触发请求并请求取消当前轮；迟到帧不得启动新轮。停止确认、运行租约释放和按钮状态必须走单一路径。
- **断线、超时、触发配置变化**：分别报告设备故障、等待超时或重新配置；不能把正常等待硬件触发视为采集失败，也不能悄悄把单次模式变成连续模式。

调度器状态至少区分 `Idle`、`WaitingForFrameOnce`、`WaitingForFrameContinuous`、`Processing`、`Stopping`。新一轮只能由调度器在确认当前运行状态、帧归属和执行租约后启动，防止按钮与帧事件双重启动。状态转移示例：空闲点击单次 → 等待帧 → 接收并认领一帧 → 处理 → 空闲；空闲点击连续 → 持续等待帧 → 处理/待处理帧 → 持续等待；任一运行态点击停止 → 停止中 → 空闲。未处于运行态的自由运行帧只在采集层处理，不产生工作流执行记录；停止后迟到的帧用运行代次或等效标识排除。

## 5. 采集所有权、超载及日志

同一相机必须有明确采集所有者。首版规定“相机参数调试预览”和“工作流采集”互斥：启动其中一方时提示先停止另一方；不以关闭预览窗口为由断开设备列表所持连接。若以后要求两者同时运行，另行设计单采集者、独立订阅者的帧分发，不让两个消费者直接竞争 SDK 图像缓冲。预览订阅即使存在也绝不驱动工作流。

处理慢于帧到达时不得无限排队。默认实时模式最多保留一张待处理的**最新帧**，替换掉的帧记录帧号和跳帧数；工作流实际处理过的帧不得计为跳帧。对于每工件必检场景，禁止默认覆盖策略，应使用受控触发/设备握手及容量明确的有界缓存；满载时报警或停止，不能静默丢图。软件触发默认按处理完成节拍发命令。

采集成功、进入工作流、处理成功、跳帧、采集失败/超时、工作流处理失败应分别计数和记录。普通状态采用聚合统计，异常包含相机 ID、工作流 ID、帧号、触发模式和错误码，避免逐帧高频日志再次拖慢 UI。VM 截图中的“失败数”语义未核实，不直接照搬。

## 6. UI 响应与结果呈现

工作流每轮产生结果，不要求 UI 每轮完整重建结果树、转换全尺寸图像或计算全部像素统计。执行结果与 UI 展示分离：结果缓存保留工作流实际处理的帧及其状态；UI 可合并展示最新结果，过时的**显示任务**可跳过，但不得由此改变工作流的处理/跳帧计数。全图统计按需或在非 UI 线程计算；停止与打开节点调试窗口须保持可响应。限流展示是呈现层优化，不是相机丢帧策略，也不能替代根因定位。

## 7. 实施顺序与验收门槛

1. **先定位当前具体故障**：保持同一节点选择和相近图像尺寸，对照本地图像、相机触发关闭、相机软件触发各运行约 20 秒；以聚合指标测取帧/触发耗时、单轮处理耗时、UI 投递等待、结果树和图像转换耗时、响应延迟。核对触发关闭时取帧错误码和是否存在预览争用。不得先用限流或重构掩盖失败原因。
2. **调度器与帧快照**：从工作流定义读取图像源配置快照，把运行命令和帧事件收敛到唯一执行入口；实现上述状态机、取消、帧身份、运行代次、帧所有权和超载策略；保持无图像源和本地图像源的现有语义，并留出非图像输入事件的抽象边界而不实现通讯触发。
3. **相机采集适配**：按触发关闭/软件/硬件三种模式产出帧事件；图像源消费本轮快照；制定预览与工作流互斥规则，复用应用级连接，不让插件持有 SDK 句柄。
4. **UI 呈现隔离**：结果缓存与显示更新分离，移出昂贵 UI 计算；显示聚合计数和等待状态。
5. **验证交付**：单次恰好一轮；连续不重复执行同一帧；未运行时不因自由运行帧自动执行；停止后迟到帧不重启；图像源节点取得本轮预先绑定的帧号而非重新取帧；触发关闭/软触发/硬触发等待与超时正确；处理过载计数准确且帧内存无泄漏；预览图不进入工作流；无图像源与本地图像回归；真实海康相机下停止和双击保持响应。涉及执行、SDK、UI、插件和发布，按项目规则做跨模块影响评估、全量 Release 构建、Release 程序验证、VS 设计时及用户运行时人工验收；未完成项不宣称已交付。

## 8. 本次决策与未决问题

**已确认**：预览仅调参；按钮是运行授权，帧事件在相机模式下提供本轮输入；图像源配置在运行前供调度器选择相机，节点在运行中消费已绑定的帧而不自行驱动工作流；单次/连续不能与帧事件形成双重执行；无图像源不能依赖相机帧；相机处理不过来须有明确、有界且可追溯的策略。通讯事件驱动仅是未来假设，不在本轮实现。

**待实测/业务确认**：触发关闭读取失败的真实原因；UI 卡顿的具体热点；每工件必检工作流如何识别与配置。多个图像源的驱动和配对留待将来有实际业务场景时讨论，本轮既不实现也不增加数量限制。上述未决项不应被默认实现悄悄替用户决定。

## 9. 2026-09-27 实施进度

- 已建立运行前相机帧绑定通路：相机帧经运行请求按节点 ID 传到图像源，节点消费帧并复制为自有图像；旧工具单次采集入口保留兼容。
- 常规单相机工作流的单次、连续和解决方案级单次执行已在节点执行前接入相机帧采集。自由运行/硬触发使用后台取流和最新待处理帧；软件触发使用同一取流通道，每轮仅发一次触发，前一轮完成后才请求下一帧。停止取流不关闭设备列表所持连接。
- 相机设置预览与工作流采集增加同一设备的采集租约互斥；预览窗口关闭时只停止其自己启动的取流，不能停止工作流取流。
- 相机结果逐轮写入运行缓存；UI 将图像/结果树展示合并到约 200 ms 的刷新节奏。相机像素统计移到工具工作线程；增加 UI 排队或展示超时的低频诊断和收到/进入工作流/跳帧计数。
- 定向自动测试已覆盖设备采集互斥、预绑定帧不重复采集、运行请求帧映射、模拟自由运行和软件触发供帧、连续停止旧回归。全量 Release 构建与 Release 启动冒烟已执行；具体结果以协作记录为准。
- **仍未验收**：真实海康相机在触发关闭、软件触发、硬件触发下的完整工作流执行；触发关闭原有读取失败的实际根因；连续运行时停止/双击的手感和 UI 耗时；VS 设计时；每工件必检策略。多图像源不新增数量限制或自动配对逻辑。不得将本阶段视为整份方案全部交付。
