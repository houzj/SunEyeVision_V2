切换主题：有合同校验，缺失败原子性

是什么

颜色不是每个窗口各改一遍；宿主提供主题资源，SDK控件按资源键取值。

实际链路

ThemeManager.ApplyTheme → _currentTheme赋值 → 移除旧字典 → 创建/校验新字典 → 加入 → 标题栏/偏好/事件

已实现及具体不足

已实现Light/Dark、SdkThemeKeys逐键校验。问题是状态先变、旧字典先删；新字典加载或校验抛错时，没有对应回滚。相同theme再次调用又会提前return。

最终取舍

必须整改局部切换事务；不因此推翻全部主题体系。

具体改法

先构造并校验候选字典，再在UI线程替换；成功后提交_currentTheme。失败保留旧字典/状态，标题栏和事件也按成功阶段更新。

验收标准（未执行）

缺资源、错误URI、偏好保存失败分别验；失败后可重试，所有已开窗口和新开窗口一致。未运行VS设计器或产品。

        public void ApplyTheme(AppTheme theme)
        {
            if (theme == _currentTheme)
            {
                return;
            }

            _currentTheme = theme;
            ApplyThemeDictionary(theme);
            // 刷新所有已打开弹窗的系统标题栏（切主题瞬间即时跟随）
            WindowTitleBarThemer.UpdateTheme(theme == AppTheme.Dark);

            // 持久化用户选择
            try
            {
                _settings.SetPreference(PreferenceKey, theme.ToString());
            }
            catch (Exception ex)
            {
                _logger.Log(LogLevel.Error, $"主题偏好持久化失败: {ex.Message}", "ThemeManager", ex);
            }

            _logger.Log(LogLevel.Info, $"主题切换为: {theme}", "ThemeManager");
            ThemeChanged?.Invoke(theme);
        }

插件依赖：有独立目录，但运行时共享优先

是什么

工具带自己的依赖清单；宿主已有同名程序集时优先共用，因此不是每个插件都用自己的版本。

实际链路

PluginManager → PluginLoadContext → 宿主合同/已加载同名/宿主目录同名 → 插件deps.json/目录

已实现及具体不足

共享可避免跨边界类型身份分裂；但按simpleName和宿主文件存在回落，不等完整版本/公钥/API兼容验证。插件主程序集单独认本目录。

最终取舍

局部兼容准入整改；第三方版本隔离优劣暂缓。

具体改法

声明必须共享的边界合同和版本范围；加载前检查插件依赖/宿主版本并报差异。仅不跨边界的私有依赖可隔离，不承诺ALC安全沙箱。

验收标准（未执行）

同名不同版本、缺依赖、BAML控件解析、序列化类型身份分别验；失败给出真实选择路径与版本。

        protected override Assembly? Load(AssemblyName assemblyName)
        {
            var simpleName = assemblyName.Name;
            if (string.IsNullOrEmpty(simpleName))
                return null;

            // ① 插件主程序集：只认本插件目录内那一份 —— **绝不回落宿主**，
            //    避免 dev/Debug 根的历史残留同名 dll 被误用（方案 §十 清理清单第 5 条）。
            if (string.Equals(simpleName, _mainAssemblySimpleName, StringComparison.Ordinal))
            {
                var selfPath = Path.Combine(_pluginDirectory, _mainAssemblySimpleName + ".dll");
                return File.Exists(selfPath) ? LoadFromAssemblyPath(selfPath) : null;
            }

            // ② 契约与框架模块（SunEyeVision.*）→ 交回宿主，类型身份唯一
            if (PluginAssemblyPolicy.IsHostProvided(simpleName))
                return null;

            // ③ 宿主**已加载**的同名程序集 → 共用（跨边界类型必须同源）
            if (IsLoadedInHost(simpleName))
                return null;

            // ④ 宿主**运行目录可解析**的同名程序集 → 共用。
            //    这是"共享优先"的兜底事实判定：与构建期行为天然一致（构建期剔除的正是宿主已有的那批），
            //    故加载期**不需要**再维护第二份平台清单（消除构建期/加载期清单分叉的可能）。
            if (IsResolvableFromHostDirectory(simpleName))
                return null;

卸载：当前清注册表，不是释放程序集

是什么

工具实例、后台任务、事件订阅、原生句柄和程序集是不同层；清掉工具列表不会自动销毁它们。

实际链路

PluginManager.UnloadPlugins → _plugins.Clear / _toolCatalog.Clear；PluginLoadContext isCollectible:false

已实现及具体不足

不可回收ALC是明确源码事实；UnloadPlugins没有调用逐实例Dispose或在途等待。不能据此断言一定泄漏，但不得把日志“卸载完成”解释为热更新/资源已全释放。

最终取舍

明确当前仅进程生命周期加载；热卸载作为新增专项，不能包装为已实现。

具体改法

若产品不需热更，改文档/状态为注销并要求重启；仍需逐工具实例退役。若需热更，先建停派发/排空/退订/Dispose合同，再评可回收ALC和WPF/native限制。

验收标准（未执行）

注销后不再创建新实例；在途任务结局被观察；热卸载未开发，不能用GC调用当验收。

部署：构建规则已有，干净机器仍待验收

是什么

工具私有库随插件，大件平台由宿主供给；文件复制规则和运行依赖闭合是两件事。

实际链路

Directory.Build.targets → 插件OutDir/PackagingRoot → 保留deps → 剔除HALCON/OpenCV → 宿主部署native

已实现及具体不足

真实规则保留工具自身依赖，集中大件；宿主缺HALCON会构建报错。SuppressNativeRuntimesForToolPlugins按Link包含runtimes宽泛移除，未按私有原生依赖区分；不能保证新增插件私有native完整交付。

最终取舍

构建规则局部整改＋干净环境发布矩阵；不照搬未知VM发布包。

具体改法
