架构师对照｜两套系统把“执行责任”放在哪里，换来了什么代价？
架构决策轴
VM：托管层维护方案/流程模型→PlatformManager 做消息分发→ModuleProxy 做协议与回调适配→ModuleFrame 加锁准入并投递 worker→worker 按连接关系激活候选；模块级后继计数归零后分派；精确状态语义/并发/取消仍在追
自研的对应选择
托管层显式构造 DAG→GraphValidator 产出确定性顺序→GraphExecutor 逐节点 await 并管理生命周期
VM 的架构收益 / 代价
收益
ModuleFrame 收束流程运行 API多个宿主/API 面可共用 native 执行能力ModuleProxy 解耦协议与后端 API 表
代价
调度决策要跨 PlatformManager/Proxy/Frame 追踪多层契约增加状态同步与故障定位成本并发与停止语义依赖 native 内部契约
本轮确认 ModuleFrame 有连接关系触发的流程重调度；精确就绪判据、多个候选的并发程度及取消收尾仍未闭合。
自研的架构收益 / 代价
收益
调度规则可读、可诊断、可做差分错误/取消/释放可在一个执行闭环中检查无需 native SDK 才能运行算法图
代价
串行 await 限制就绪节点并行度框架需自担调度器演进与兼容与 VM 的执行次序/停止等价性尚无原机差分
以上自研描述来自当前框架源码，不是对 VM 行为的类比推测。
架构判断：执行控制权的边界，比“有没有 Runtime/WPF 分层”更决定系统行为、可调试性和演进成本。
设计评估：迁移哪些设计是既定前提？
自研工具层以 VM 工具设计为迁移基线，因此工具定义/资源参数、运行参数、输入输出与绑定、接管判断、结果/图形/文本显示及宿主适配属于兼容目标。显式 DAG、独立校验、运行上下文和生命周期实现可保留为内部实现，但前提是它们没有改变这些可观察工具行为；VM 的协议代理和重复运行状态不是仅因工具迁移就必须照搬。
设计评估：哪些执行差异必须核实？
VM 已证实流程 worker 收尾后扫描连接候选并重投；流程对象内部按结果码更新模块后继状态、锁保护依赖计数并在归零后分派。自研预先生成 ExecutionOrder 并串行 await。对于 VM 工具迁移，这个差异不能先验地判为“内部细节”：需对齐模块次序/准入、失败与跳过状态、结果完成屏障、停止/连续运行及保存恢复；若这些会影响迁移工具的输入输出或 UI 行为，就需要改自研执行语义。
修正后的架构结论：工具层迁移 VM 设计是约束，不代表 native 分层必须原样复制；但也不能仅以自研 DAG 更易审计为由预设不改执行器。先逐项建立“VM 工具行为 → VM 执行语义依赖 → 自研对应行为”的追踪矩阵。当前串行拓扑模型只能列为待兼容性核实的自研选择；若差分发现可观察语义冲突，应调整执行器。VM 的准确计数含义、失败传播和真实并发度仍待闭合。
证据支撑：VM managed 调用链及 SDK/native opcode→流程接口映射见下方各图和 native-sdk-boundary-evidence.md；自研调度与生命周期见 GraphValidator.cs、GraphExecutor.cs、SolutionExecutor.cs。标注为未知的 VM 行为不参与架构优劣定论。
迁移边界图｜VM 工具设计迁移后，哪些框架行为成为兼容约束？
架构师取舍前提：工具层的 VM 设计是目标；框架内部实现可以不同，但工具可观察行为必须闭合
VM 工具链｜需要还原的设计面
工具定义
工具参数 / 资源模板→基础/运行参数与持久化
运行接线
输入输出 / 参数绑定 / 触发关系→ModuleFrame 节点执行

这些工具面是迁移目标。每项要以原厂源码/资源/二进制证据建立字段和生命周期合同，不能仅依据窗口外观推定。
自研迁移｜工具合同与执行引擎分两层验收
工具合同层
工具资源 / 参数 / 输入输出→绑定、接管判断、显示适配→按 VM 可观察行为差分
执行器层
GraphValidator + GraphExecutor↔VM 连接态调度、失败/跳过、stop/continuous、完成屏障仍须逐项映射
决策门
差异不影响已迁移工具行为→可保留自研实现/差异改变工具行为→需调整执行语义并复核工具
这把“工具迁移”和“框架内核照搬”拆成两个可审核问题：工具合同必须兼容；执行器只在行为差分证明安全后才可视作实现自由度。
因此，前面“保留自研 DAG”的结论修订为条件结论：保留它的可诊断性和单一执行所有权，同时把 VM 调度差异列为工具迁移的兼容性缺口来验证；如果确认影响被迁移工具的输入/输出、状态、接管/显示、停止或恢复行为，就不能以“只是框架内部实现不同”关闭问题。
VM 工具迁移目标来自当前项目明确约束；本页 VM 执行调用链与自研 GraphExecutor 事实分别见后续控制流图和证据索引。此图是决策边界，不替代逐工具源码级参数/绑定/显示矩阵。
架构决策对照｜VM 与自研如何把“依赖关系”变成执行？
比较单位：一个节点完成后，系统如何确定哪些后继可进入执行
VM｜完成态驱动的关联状态传播与后继分派
节点入口/执行
流程对象取出关联后继列表→读取当前节点结果码→调用模块对象 vtable + 0x08
状态传播
按结果码分支→FUN_18001E400 写入后继状态标记→节点进入时锁内复制 +0x24 → +0x20；后继完成时锁内递减 +0x20
后继分派
计数归零→按后继类型分支→FUN_1800FFD00 递归路径 / FUN_1800FFAA0 准入后递归或按类型提交
流程级闭环
worker 常规收尾→连接候选状态更新→候选 gate=0 时重新准入 ModuleFrame
已证实模块级后继列表、结果码到标记的分支、受锁计数归零分派，以及流程级候选重投。新增静态证据已闭合基准计数来源：节点构造时 +0x24=0；关系加入 owner 的后继表时对 target +0x24 加一，删除关系时减一；节点入口把它复制到活动计数 +0x20。因此这里是目标节点的入边/依赖计数。状态位业务名、所有失败/跳过分支与真实并发度仍需核实。
自研｜运行前求出全序，运行中串行消费
图与准入
ExecutionLinks / Connections 派生边→GraphValidator 校验并计算拓扑序
执行计划
生成 ExecutionOrder→执行期按列表遍历
后继推进
await 当前模块→解析绑定 / 记录状态→进入下一个序号
并行特征
拓扑序固定+当前 GraphExecutor 串行 await同层 ready 节点不并发启动
自研把调度计划显式化，便于日志、复现和审计；代价是并发策略若要演进，需要改变执行器和状态汇总契约。
架构评估：动态触发 vs 预计算全序；分派策略的灵活度 vs 可观察性/复现成本
VM 的取舍
每次节点进入时从基准字段恢复活动计数，后继完成路径传播结果标记并递减活动计数；归零后按节点类型分派。这允许按节点类型走不同分派路径，也把调度状态藏在 native 对象中。优势是原生运行内核可集中管理；代价是需要跨 native 对象、字段与事件追因果，精确重放和外部诊断更难。当前静态证据还不能量化真实并发度。
自研的取舍
完整拓扑序提前可见，错误可定位到节点序号，执行易复现；代价是串行策略牺牲可并行的吞吐机会。它不是 VM 的文件结构差异，而是调度状态何时计算、由谁持有，以及并发语义如何呈现的差异。
架构决策（不是最小改动决策）：保留 DAG 作为显式流程模型、校验/持久化/诊断边界；不把预先算出的单一全序继续当作执行器的唯一策略。目标执行模型应以依赖计数和节点状态驱动 ready 集合，调度器负责准入、失败/跳过传播、取消和完成屏障，并提供有界并发策略。当前 VM 静态证据支持依赖触发与后继分派，但尚未证明真实并发度或完整失败语义；因此先按串行 ready 调度落地可观察合同，再依据 native 运行取证和工具线程安全/共享资源合同开启并发。这样保留自研显式 DAG 的可审计性，同时避免把“串行全拓扑序”误当成架构目标，也不盲抄 VM native 黑盒。
静态证据：module-frame-dependency-predicate/output/1800ffd00.c（结果码处理、模块对象调用、后继列表与状态分支、计数归零后分派）；module-frame-dispatch-paths/output/1800ffaa0.c（准入判断与按类型提交分支）；module-frame-module-graph-core/output/18001e310.c（从对象 +0x48 取关联列表）；module-frame-module-graph-core/output/18001e400.c（锁保护的状态位 OR/记录）；流程级关系重投见 module-frame-worker-inner-calls/output/1800e4080.c、1800e4330.c。二进制原件及自研源码锚点见本页证据索引和 native-sdk-boundary-evidence.md。
架构总图｜两种执行系统如何分层、控制流穿过哪些边界？
VM 原厂｜三层控制面 + native 执行框架
构建 / 配置
managed：Solution / Procedure / Module 对象→VM.PlatformSDKCS→iMVS Platform SDK façade
命令 / 协议
PlatformManager：handle、流程记录、opcode handler→ModuleProxy：同步命令解析、状态/事件/结果组装
执行所有权
ModuleFrame：流程运行 API→按流程记录准入 / 加锁 / 复位事件→提交 worker closure 至两条执行队列之一→worker 周期后扫描关联候选并重投；连续模式可按 interval 循环→ 模块后继计数归零后按类型分派；状态含义/并发度仍核实
反向结果流
ModuleFrame 结果/事件→ModuleProxy 回调适配与结果协议→Platform SDK / managed callback / UI
这是跨 managed/native 二进制的组件化执行系统。ModuleFrame 的导出表直接包含流程运行、停止、连接、参数绑定、状态查询和结果回调接口；ModuleProxy 解析协议并调用这些 API。各层的准确依赖由二进制调用与导出/动态解析点支撑，已恢复模块后继结果状态传播和受锁依赖计数归零分派；是否并行以及与固定拓扑序的语义对应仍未证实。
自研｜单一托管工作流执行闭环
构建 / 配置
Solution / Procedure / Module workspace→持久化模型与框架契约
准入 / 计划
SolutionExecutor：资源、子流程、Group 生命周期→GraphValidator：结构校验 + 拓扑序
执行所有权
GraphExecutor：逐节点 await→Module.ExecuteAsync：算法调用与输出记录
反向结果流
节点返回值 / 状态→执行记录与工作流输出→UI 展示 / 持久化边界
当前自研把验证、调度、取消和节点执行放在同一托管调用链，避免需要跨 native 协议查找运行决策。其现状是串行 await；这描述自研实现，不是 VM 的等价模型。
架构师比较轴：执行所有权 → 跨层契约数量 → 可观察性与故障定位 → 并发演进成本 → 部署 / ABI 成本
责任边界
VM：API 编排与结果适配在外层↔运行能力聚合在 ModuleFrame↔自研：策略与节点执行在托管 GraphExecutor 边界内
复杂度转移
VM 降低 SDK 消费者对执行内核的直接耦合→但诊断、兼容和状态一致性跨协议 / native 边界↔自研更易审计和差分→但调度扩展、隔离和并发治理由自研框架承担
可迁移结论
借鉴 VM：稳定的运行 API、运行参数/策略/控制参数分域、事件与结果契约→不照搬：额外代理协议层、重复运行状态、不可见 native 调度边界
架构判断：VM 的优势不是“层多”，而是把可被多个宿主调用的流程运行契约收束到 ModuleFrame，再由 ModuleProxy/SDK 承担集成和返回适配。自研当前无需为了外形增加代理层；更值得对齐的是明确运行控制契约并保持执行所有权唯一。只有当多宿主、进程隔离或独立部署成为真实需求时，才评估拆出独立 Runtime/协议进程。
新增依据：ModuleFrame.dll（SHA-256 45c57bc46f72fd1f9e0b3a6f9183ff974d14590cfd05ecf4e9fa97a4ff95ae9b）导出 VM_M_RunProcedureOnce/OnceEx/Continuously/StopRunProcedure、ConnectModule、SetModuleParamBinding、SetResultCallback、QueryModuleRunningState；反编译入口分别转发到 ModuleFrame 内部操作函数。ModuleProxy 动态解析并保存这些 API 函数指针，命令解析器随后调用对应槽。实现细节见 module-frame-execution-exports/output、module-proxy-entrypoints/output、module-proxy-command-core/output 与 native-sdk-boundary-evidence.md。未知部分仍以虚线显示。

架构师结论：两边都有连接关系，但 VM 证据指向“运行中更新关联候选状态并重新提交”，自研是“预先计算完整顺序后串行 await”。VM 已证实 native 节点按依赖计数和状态传播触发后继，并在流程层更新候选后回投；自研保留显式 DAG，但当前把它压成固定全序并串行 await。VM 不是因此更差：它把依赖触发和类型分派放在 native worker 中，具备运行时调度结构；自研在图校验、确定性和诊断方面更强。VM 的真实并发和失败语义仍未知，不能把潜在吞吐优势说成已证实。决策是保留 DAG 表达和自研可审计边界，演进为状态/依赖驱动调度；串行 ready-set 是当前兼容基线，有界并发需等工具线程安全、资源冲突、回调顺序和停止屏障被证实后启用。该判断按长期架构质量作出，不是为少改代码而保留现状。

⑥ 哪些架构事实可以直接用于理解“拓扑执行”差别？
VM 已确认
图边写入 SDK绑定写入 SDK每过程线程数/CPU 亲和性策略接口native work-status / module-result 回调

所以，“我们当前好像是拓扑执行”对自研可具体表述为：先由 GraphValidator 求 DAG 顺序，再由 GraphExecutor 单线程序列 await；对于 VM 只能确认“连线关系与参数绑定被提交给 native 引擎”，不能把它描述成已证实的相同拓扑执行器。
架构师视角的判断
VM 的架构特征
后端执行权在 native SDK。托管层偏对象模型、参数/连线提交、API 适配、状态同步、结果投影与 UI 通知。优点是 managed 层无需暴露调度实现；代价是执行策略和停止语义难以仅凭 VM.Core 还原。
自研的架构特征
显式 DAG、运行前验证和结果记录让行为更容易复现与诊断；但当前固定拓扑序 + 串行 await 把图与调度策略绑得过紧，不能直接消费 ready 节点并发。与 VM 的关键差异是调度状态如何推进及其是否可并发，不是文件摆放。
架构决策：保留 DAG 作为权威执行关系模型；将执行器拆成依赖状态机与可替换调度策略。先实现与 VM 已证触发规则兼容的串行 ready scheduler，状态传播、取消/停止和结果完成屏障作为独立合同；只有工具可并发安全和 native 运行证据确认后，再开启有界并行。这样是以可验证性为基础的目标架构，不是单纯选择最少改动；VM 目前也没有足够证据被判定为整体优于或劣于自研。
