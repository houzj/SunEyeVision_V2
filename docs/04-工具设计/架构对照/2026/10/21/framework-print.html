结论与范围

框架层设计对比与目标架构

执行、数据、发布和生命周期放在同一条链上比较。目标是完善自研平台公共机制，不是功能数量对比，也不把工程图丰富程度当质量评分。

分析范围：当前自研源码＋已有VM反编译产物。全部目标类型和改法为设计提案，未改产品、未构建、未运行VM或设备。VM原生调度/停止排空/最终析构未闭合，不把未知写成不支持。
核心判断

自研已有任务执行与强类型工具基础，但批次数据、运行身份、结果有效性和退役没有贯穿公共层；VM已恢复代码在模块IO与批次发布方面组织更集中。应保留可证的执行基础，借鉴VM重做公共数据与发布机制，并优先补停止和Owner合同。不是默认保留自研，也不是整套迁移VM。

自研当前已证主路径

  1. 运行请求 → Session / Scope
  2. 定义校验与执行快照
  3. 依赖就绪 + profile + 局部lease
  4. Task执行 → ToolResults
  5. Context按节点保存 → 多入口UI投影

VM当前已证结果路径

  1. 平台返回模块结果（内部调度待证）
  2. nModuleID定位模块
  3. VmIO按执行计数/循环整理字段
  4. 事件门控制与回调入队
  5. 后台分发给消费者（显示最后读者待证）
领域决定必须保持的边界
执行器保留基础，整改终态/资源仲裁不认当前排空完整，不迁未知原生调度
数据层借鉴VM重做统一字段/值访问保留工具强类型，不复制私有格式
结果发布借鉴VM批次与通知分层，融合现有投影发布、显示完成与资源释放不同
生命周期自有Owner/lease/退役合同必须整改复制已证边界保留，零拷贝/热更先不选型

阅读顺序：执行 → 数据 → 发布 → 寿命 → 目标架构 → 实施验收。每张卡均给双方事实、优缺点、推荐理由和源码入口。

执行架构

执行架构：调度选择与终态保证分开

不能把Task队列与native平台二选一作为全部设计判断。首先需要明确谁能派发、谁能停止、谁证明完成、共享资源在哪个范围互斥。

E1 调度与派发

差异：高保留整改

自研：实际实现及缺口

自研ReadyQueue扫描前驱，按并发profile与局部资源lease派发Task；未声明profile用LegacyExclusive，并发上限计算后不超过4。

VM：已恢复事实及边界

VM已证模块结果由平台回传，再进入托管模块/IO层；原生队列、线程池、抢占和全局资源仲裁未闭合，不能据回调代码还原调度器。

双方收益与代价：自研规则可直接审查和定制，代价是自己保障公平性、跨根仲裁和停止收尾；VM桥接层职责集中，但原生内部诊断和变更成本高。未测吞吐/延迟，不判性能优胜。

采用判断与具体改法（未实施）

复用当前依赖图、profile和派发器；先补全根/子运行的资源域与可等待终态，再按实际瓶颈定调度优化。不以反编译信息不足为理由替换后端。

为什么不直接选另一条：不整体迁移VM调度器：其内部调度和停止保证未恢复，迁移收益无测量；也不认当前队列已经完整。

源码依据：engine · session · vm-values

E2 停止、取消与完成

差异：高必须整改

自研：实际实现及缺口

队列finally对仍在running中的任务只释放lease，未在此await所有任务；发出取消或登记退出不单独证明原生调用/回调结束。

VM：已恢复事实及边界

导出注册接收端验证记录后转helper；此代码不证明注销、停止完成或在飞回调排空。VM停止终态仍待原实现证据。

双方收益与代价：CancellationToken是请求，Task终态和资源排空是保证；现有结构能接入，但提前归还lease有重入冲突风险。不能把VM界面停止成功当内部排空证明。

采用判断与具体改法（未实施）

一个RunHandle提供Completion与StopAsync；停派发→取消→观察所有在途及回调→资源退役→终态。超时进入隔离并保留占用，不能成功释放。

为什么不直接选另一条：此整改来自自研可证路径，不需等待VM；强杀native或仅延时不是排空协议。

源码依据：engine · feed · vm-register

E3 根运行、子调用与循环身份

差异：高保留整改

自研：实际实现及缺口

已有Session.RunId、子Scope.RunId、ParentRunId和ConsumerScope；子结果向RootContext按裸节点ID回填，身份在展示层可能拍平。

VM：已恢复事实及边界

结果带nModuleID/nExecuteCount，循环按条件合并或重置；不能据此宣称其拥有与自研等价的Scope调用栈模型。

双方收益与代价：已有Scope值得复用；裸NodeId便捷但不足区分两个调用者/多轮结果。VM执行计数利于区分批次，仍需明确计数作用域、回绕及历史策略。

采用判断与具体改法（未实施）

把Run/调用Scope/节点/迭代/帧身份贯穿存储、绑定和投影。目标ScopeId映射现有WorkflowRunScope.RunId，不再新增一份不一致身份。

为什么不直接选另一条：不抄nExecuteCount当全局唯一ID；不推倒已有Scope，只修丢身份的边界。

源码依据：session · scope · engine · context · vm-values

X1 跨根资源仲裁和外部副作用

差异：高必须整改

自研：实际实现及缺口

ReadyQueue的资源lease管理器在每次调用内new，不能独自保证两个根运行/两个子队列共享设备互斥；已有相机用途lease是另一层准入。

VM：已恢复事实及边界

本批资料尚不足证明原平台全局设备资源锁、优先级及事务回滚。

双方收益与代价：局部lease简洁但易与设备层不同步；全局协调增加等待、死锁和故障隔离设计成本。外部设备写入失败也不等可回滚。

采用判断与具体改法（未实施）

定义资源键、访问模式、作用域和获取次序；应用级协调共享设备，运行内协调计算资源。等待可取消；已执行的触发/发送按副作用记录，不自动重放。

为什么不直接选另一条：保留已有设备门禁并合一准入语义，不一把全局锁串行所有算法，也不猜VM全局锁实现。

源码依据：engine · feed

数据与数据流

数据结构与数据流：值、身份、有效性和Owner一起传

Dictionary复制、强类型结果、模块IO分别解决不同问题。目标并非统一成object容器，而是在工具类型之上建立统一可校验的数据合同。

D1 定义数据与运行快照

差异：高保留整改

自研：实际实现及缺口

执行前校验定义并生成执行用流程；GlobalVariables用新Dictionary包装但值仍可能可变；子调用路径全局参数传null。

VM：已恢复事实及边界

本批恢复证明运行IO持有状态，不证明完整配置快照、编辑并发隔离和全局变量继承规则。

双方收益与代价：自研有快照入口便于隔离编辑，浅复制不能保护图像/数组等值；VM集中对象不自动等不可变快照，不能推断更安全。

采用判断与具体改法（未实施）

冻结定义版本与参数来源；逐类型Clone/Retain/借用策略，普通全局快照显式继承到子Scope，局部覆盖及写回政策独立。

为什么不直接选另一条：复用已有准备路径，禁止把new Dictionary当深快照；不凭VM界面反推配置线程安全。

源码依据：engine · context · resolver

D2 工具结果与通用字段模型

差异：高借鉴VM重做公共层

自研：实际实现及缺口

ToolResults有强类型派生，GetOutputValues生成字典；Context、变量和参数解析另有容器，公共字段访问缺少统一的身份/版本/有效性合同。

VM：已恢复事实及边界

模块结果按ID定位模块；SetValue以字段名哈希定位叶VmIO，更新执行计数、值、列表与事件门。此片段是字段层，不证明原生算法数据布局。

双方收益与代价：强类型工具利于编写和静态检查；字典适配轻但迁移/动态字段成本分散。VM统一IO便于公共工具消费，却增加动态类型、字段映射和事件状态复杂度。

采用判断与具体改法（未实施）

保留强类型结果，在框架新增统一FieldDescriptor与只读ValueRecord适配层：稳定FieldId、schema版本、值类型/形状/坐标域、质量状态、来源与所有权。

为什么不直接选另一条：重做的是公共数据访问机制，不是所有工具类；不持久化GetHashCode，不直接使用VM二进制或私有数据格式。

源码依据：result · context · resolver · vm-values

D3 绑定与跨节点数据流

差异：高混合优化

自研：实际实现及缺口

ParameterResolver实际只分派Constant/Binding，动态读取结果并做转换；NodeOutput枚举存在不等此分派支持，C#脚本不等参数表达式引擎。

VM：已恢复事实及边界

VmIO由公共层接收字段值；此处尚不能证明完整订阅图、类型转换、失败来源与循环反馈实现。

双方收益与代价：自研反射/属性路径接入方便，易受重命名、数组形状和默认值政策影响；VM公共载体可统一读取，订阅政策仍需证据。

采用判断与具体改法（未实施）

绑定定义使用生产者Scope相对地址+NodeId+FieldId；编译预检类型/数组/环/坐标域，运行通过统一读取门返回值或明确失败，不偷偷回到设计初值。

为什么不直接选另一条：复用当前类型/路径适配，逐步迁稳定字段ID；暂不按未知VM订阅细节重写全部解析器。

源码依据：resolver · result · context · vm-values

X2 兼容、持久化和可诊断性

差异：中到高混合优化

自研：实际实现及缺口

当前节点/结果类型、绑定路径与SDK资源已有存量；直接替换全部类型会影响插件、方案、UI树和标定。

VM：已恢复事实及边界

VM原版实现、恢复模型与重建工程不等价；不能把重建文件结构当原厂部署架构。

双方收益与代价：增量适配降低一次迁移风险，但双读协议过久会增加复杂度；整体重写表面统一，代价与回归面更大。

采用判断与具体改法（未实施）

先加新合同适配器与双读、单写迁移；按版本登记schema/FieldId映射，日志贯穿Run/Scope/Node/Frame和Owner。测量后再收敛旧路径。

为什么不直接选另一条：不采用“既然不同就全迁VM”；以已证问题和兼容矩阵决定替换边界。

源码依据：sdk · resolver · context

拟议合同（不是现有类）建议结构/复用关键字段与规则生产/消费职责
身份ExecutionAddress（拟议）RootRunId + ScopeId + NodeId + Iteration + FrameId + DefinitionVersion；ScopeId映射现有子Scope.RunId，保持现有序列号与GUID分工。引擎生产，绑定/结果存储/投影消费；帧可无值，需显式NotApplicable而非伪造。
字段FieldDescriptor（拟议公共层）稳定FieldId、schema版本、ValueKind、数组形状、单位/坐标域、可空性；从ToolResults元数据生成适配，不照抄VM名哈希。插件声明，加载准入和绑定编译校验；重命名不改变身份，删除字段显式迁移。
值与有效性ValueRecord（拟议）地址+FieldId+Quality+Value/ResourceRef+版本；Quality区分Valid/Missing/Failed/Cancelled/Stale，不用null包办所有含义。发布层一次采用；结果树可显示缺失，执行读取按明确策略拒绝无效值。
执行结局RunHandle / NodeOutcome（拟议扩展）Completion、RequestedStop、实际终态、错误/诊断、已提交批次；取消请求不是完成，发布失败不抹掉已执行副作用。执行会话持有，宿主等待；订阅者异常不反转已经确认的结局。
资源ResourceLease（拟议统一合同）OwnerId、资源键/代际、Borrow/Retain/Clone、活动读者、退役结局；句柄引用和值快照分开。资源Owner负责最终释放，使用者归还lease；超时隔离而非宣布释放成功。
通知ResultBatch / ResultChanged（拟议）批次ID+地址+schema版本+变更字段；通知是索引，消费者读取已提交版本，不广播所有大数组像素。Publisher提交，显示/记录/通信分队列消费；容量、丢弃/拒绝、过期及错误可见。

P1 批次整理与结果发布

差异：高借鉴VM重做公共层

自研：实际实现及缺口

完成任务后依次SetNodeResult、NodeExecutionFinished、节点状态事件；结果和状态不是一个原子批次，UI回调抛错可能影响执行层分支。

VM：已恢复事实及边界

SetValue按ExecuteCount/自执行/循环条件重置或合并；循环结束恢复通知并Enqueue回调。数据整理与后续事件分发有层次。

双方收益与代价：VM的公共机制便于多消费者共享一致批次，但可变IO、默认化及事件门同样需严谨维护。自研直接通知简单，入口变多后易半更新与事件影响调度。

采用判断与具体改法（未实施）

ResultPublisher先完成本轮Outcome与字段批次提交，再发轻量通知。消费者读同一版本；事件处理异常隔离，不能改变已经提交的执行事实。

为什么不直接选另一条：借鉴职责分层；不照抄缺项默认化作为失败结果，也不承诺全进程数据库式原子性。

源码依据：engine · ui · vm-values · vm-queue

P2 显示投影、历史与背压

差异：高混合优化

自研：实际实现及缺口

相机待显示结果按节点合并后定时刷新选中显示并通知调试窗；普通、调试、分析另有分支；同尺寸位图池返回可变共享对象。

VM：已恢复事实及边界

后台接收/发送数组交换后分发；队列开关与溢出有代码，非每次原生结果立即完成显示。没有据此证明无损/无限容量。

双方收益与代价：最新值合并保护UI响应但会跳帧；历史和逐帧业务不能用同一政策。VM分发层便于统一通知，但不自动解决显示线程、背压及像素寿命。

采用判断与具体改法（未实施）

UI只消费投影，不调度工作流。实时显示latest-only、业务记录有界不可默丢、历史独立快照分通道；Run/Scope/Frame门禁拒收迟到结果，Dispatcher统一采用。

为什么不直接选另一条：保留相机合并机制并明确损失政策；不拿显示通知丢帧当算法少执行，也不默认换渲染后端。

源码依据：ui · bitmap · vm-queue

拟议发布顺序

  1. 工具结束 → 捕获NodeOutcome（成功/失败/取消）
  2. 构造完整字段批次（含缺失和失效项）
  3. 在定义边界内提交版本化结果视图
  4. 发布只读变更索引；异常订阅者单独诊断
  5. 树/图像/分析/通信按用途读取同一版本
  6. 旧版本无读者后退役资源

批次提交仅保证框架定义的结果视图一致；设备触发、网络发送和文件耐久性不自动成为同一事务。失败后的补偿与重试须另有副作用合同。

L1 图像生产与传递所有权

差异：高保留整改

自研：实际实现及缺口

ImageLoad接收外部frame时借用，自己Capture时持有；像素复制后创建结果图像。CameraWorkflowFrameFeed旧pending被替换会Dispose。

VM：已恢复事实及边界

VmIO清_value/_valueList只证明撤掉这一层引用，未证明ImageData像素或共享映射释放；原注册函数不证明最后读者。

双方收益与代价：自研复制边界容易理解且隔离厂商缓冲，成本为内存带宽与分配；没有测量不宜改零拷贝。VM可能跨native载体，当前不能承诺其无拷贝或更省内存。

采用判断与具体改法（未实施）

每种图像载体登记唯一Owner；跨线程/历史使用显式Retain/Clone，ValueRecord仅持句柄与帧身份。消费者先取得使用lease再读，最后lease退役后释放底层。

为什么不直接选另一条：保留已证复制安全边界；共享图像协议需按实际消费者补齐，不把到处Dispose当优化。

源码依据：image · feed · bitmap · vm-values

L2 工具、分析控件与插件退役

差异：高必须整改

自研：实际实现及缺口

分析入口CreateToolInstance后创建控件，旧高亮有退订但工具实例Owner未形成等待会话；SDK运行类型与WPF控件同包。

VM：已恢复事实及边界

模块/IO/回调对象有平台组织，但本批代码没有闭合实例最终析构、原生最后读者与热卸载。

连续运行：StartContinuousAsync返回Controller；每轮具有独立Iteration/Frame身份和输入请求。InputProvider每轮提供数据，重复固定图像必须显式选择；StopAsync停止新轮并等待所有在途。结果通知不可代替controller.Completion；事件未订阅也要有运行结局与可查询结果。

避免完成与取结果循环等待：Completion等待执行任务、回调和本轮临时资源收尾，不等待未来才会获取的ResultLease。RunHandle活着时固定本轮结果版本；handle释放后禁止新Acquire，已取得的ResultLease继续持有自身资源引用。最终像素释放发生在结果Owner及所有使用权退出之后，不因Completion立即销毁。

二开 / 事件及错误

事件、并发与失败：不把内部回调责任推给客户

订阅句柄持有过滤器、有限队列及handler。实时UI允许LatestOnly，业务记录/ACK按有界可靠投递或拒绝准入；缓冲满、过期、失败和丢弃都有计数。通知只给地址/状态，读取像素必须另获取lease。handler异常不改变已提交的RunOutcome。通知地址不承诺无限保留结果：单次由RunHandle固定版本；连续按有界保留窗口，过期返回ResultExpired。可靠记录订阅可由分发队列内部保留至交付，handler需另Acquire才能跨回调持有；UI只转发地址时必须处理过期并跳过旧帧。

故障/竞争场景拟议处理与诊断
加载中取消或缺插件候选退役，当前项目不替换，返回缺少工具/版本/资源清单；不发布Ready。
schema或定义修订过期拒绝接纳或提交；客户重新GetSchema，不按旧名称猜绑定。
同项目并发Start首期MaxConcurrentRoots=1，明确Busy；能力接口保留未来扩展，不冒称已支持多租户。
等待者取消只取消WaitAsync等待；调用者若要停运行必须StopAsync并观察Completion。
工具失败或结果缺失Outcome失败+字段Quality，输出不冒充上次成功；读失败结构化返回。
结果handler慢/抛错不影响调度终态；队列超容量按通道拒绝/丢弃并记录计数，ACK和业务记录不可无声合并。
停止超时/外部lease未还Quarantined/ClosePending，保留资源占用及Owner诊断；不能继续重连或卸载native。
许可失效/拔自有狗各入口统一准入，自有策略决定拒绝新Run并安全退役；狗型号/宽限未定，不能承诺发行。
主异常与收尾异常并发保留主异常，单独聚合清理错误；示例中的await using不代表Dispose失败可以覆盖原错误而丢失诊断。

错误模型：SdkError包含Code、Operation、Project/Run/Scope/Field地址、可读信息、原始内部异常链和阶段。参数/版本/缺依赖是接纳失败；工具业务失败是RunOutcome；关闭失败是CloseOutcome，不统一吞成false。

回调线程：默认SDK分发worker，不保证UI线程；UI控件自行Dispatcher投影。禁止客户在回调内同步等待自身Drain/Stop造成互锁，提供异步退出路径及重入错误诊断。官方同样提示避免同步渲染阻塞，见doc-events · sdk-doc-events。
