P1 批次整理与结果发布

差异：高借鉴VM重做公共层

自研：实际实现及缺口

完成任务后依次SetNodeResult、NodeExecutionFinished、节点状态事件；结果和状态不是一个原子批次，UI回调抛错可能影响执行层分支。

VM：已恢复事实及边界

SetValue按ExecuteCount/自执行/循环条件重置或合并；循环结束恢复通知并Enqueue回调。数据整理与后续事件分发有层次。

双方收益与代价：VM的公共机制便于多消费者共享一致批次，但可变IO、默认化及事件门同样需严谨维护。自研直接通知简单，入口变多后易半更新与事件影响调度。

采用判断与具体改法（未实施）

ResultPublisher先完成本轮Outcome与字段批次提交，再发轻量通知。消费者读同一版本；事件处理异常隔离，不能改变已经提交的执行事实。

为什么不直接选另一条：借鉴职责分层；不照抄缺项默认化作为失败结果，也不承诺全进程数据库式原子性。

源码依据：engine · ui · vm-values · vm-queue

P2 显示投影、历史与背压

差异：高混合优化

自研：实际实现及缺口

相机待显示结果按节点合并后定时刷新选中显示并通知调试窗；普通、调试、分析另有分支；同尺寸位图池返回可变共享对象。

VM：已恢复事实及边界

后台接收/发送数组交换后分发；队列开关与溢出有代码，非每次原生结果立即完成显示。没有据此证明无损/无限容量。

双方收益与代价：最新值合并保护UI响应但会跳帧；历史和逐帧业务不能用同一政策。VM分发层便于统一通知，但不自动解决显示线程、背压及像素寿命。

采用判断与具体改法（未实施）

UI只消费投影，不调度工作流。实时显示latest-only、业务记录有界不可默丢、历史独立快照分通道；Run/Scope/Frame门禁拒收迟到结果，Dispatcher统一采用。

为什么不直接选另一条：保留相机合并机制并明确损失政策；不拿显示通知丢帧当算法少执行，也不默认换渲染后端。

源码依据：ui · bitmap · vm-queue

拟议发布顺序

  1. 工具结束 → 捕获NodeOutcome（成功/失败/取消）
  2. 构造完整字段批次（含缺失和失效项）
  3. 在定义边界内提交版本化结果视图
  4. 发布只读变更索引；异常订阅者单独诊断
  5. 树/图像/分析/通信按用途读取同一版本
  6. 旧版本无读者后退役资源

批次提交仅保证框架定义的结果视图一致；设备触发、网络发送和文件耐久性不自动成为同一事务。失败后的补偿与重试须另有副作用合同。
