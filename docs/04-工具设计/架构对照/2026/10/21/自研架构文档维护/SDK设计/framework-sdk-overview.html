S1 工具扩展与应用二开不是同一种能力

差异：高借鉴VM重做应用SDK边界

自研：实际实现及缺口

已有IToolPlugin、IAsyncToolPlugin和独立IToolEditorFactory接口，可开发工具；公开WorkflowExecutionEngine也有执行方法，但构造需WorkflowEngine/IPluginManager等内部装配，SDK与Workflow包均UseWPF。不能说自研完全不能二开，也不能把插件接口当完整应用SDK。

VM：已恢复事实及边界

VmSolution暴露Instance、索引器、Load/Save/Run/SyncRun等公共入口，模块IO和回调为集成提供统一表面；这里证明公共API形状及部分实现，不代表其无UI依赖、跨平台或每种嵌入场景已验。

双方收益与代价：自研工具扩展门槛相对低，宿主装配和数据读取知识仍可能外泄给应用集成者；VM公共入口减少集成者拼内部对象的成本，但单例/全局状态有多实例隔离和许可部署约束。

采用判断与具体改法（未实施）

保留工具开发合同，另建面向应用集成的RuntimeHost/ProjectSession门面，提供Open、参数设置、输入绑定、RunAsync、StopAsync、结果读取/订阅、CloseAsync。公共数据/生命周期合同必须能脱离主窗使用；WPF控件作为可选扩展。

官方开发指南：二开是独立产品能力

安装目录名4.4.0、文档标题4.4.2和反编译样本版本不自动视为一致；公开API说明与内部实现证据分开。以下是官方声明，不提高原42原生检查点核实率。只核对8个选定主题，不声称读完两套API全部条目。

官方SDK定位

方案/流程/模块按对象级封装，数据交互与运行控制、可组合配置/渲染控件为对外能力。

官方文档来源 doc-overview

C++与C#二开

官方列C++和C#接口及示例，C++有VC/Qt示例；不能由示例存在推断所有UI无关或跨平台。

官方文档来源 doc-cpp

API与控件依赖分开

官方明确纯接口无控件方式引用VM.Core.dll和VM.PlatformSDKCS.dll；WPF/WinForm另加接口/渲染/对应控件库，具体模块再加模块DLL。

官方文档来源 doc-packages

流程级运行合同

Run有等待结束、响应UI及执行计数等重载；流程对象暴露参数/结果与类型化输出读取，说明外部调用合同是独立设计面。

官方文档来源 doc-flow

事件与消费者负担

官方列加载、工作状态、运行结果、通信、相机及服务事件；结果/结束回调可读数据，但不应同步渲染等耗时操作阻塞后续运行。事件名不证明所有原生在飞任务排空。

官方文档来源 doc-events

WPF嵌入及平台限制

该V4.4.2文档要求.NET Framework 4.6.1及以上，不支持.NET Core；退出前调用资源释放，避免在析构函数调用。不可直接将其WPF二进制迁入自研net9.0-windows。

官方文档来源 doc-wpf

可嵌入渲染组件

公开模块/图像源绑定、立即绘制/保留图形、原图/渲染图保存、渲染间隔和Dispose；这是控件API设计证据，不是像素最终释放与性能证据。

官方文档来源 doc-render

外部图像输入

官方说明SDK图像源经SetImagePath/SetImageData输入，Mono8/彩色及灰度输出使能分别有规则；外部输入需要明确格式和输出字段，不能仅传object。

官方文档来源 doc-input

对自研的直接影响：应用Runtime API、工具开发合同、可选UI控件应按消费方式分层交付；不要求客户通过主窗控制流程。SDK必须有独立入门样例、部署/许可说明、错误和异步完成合同、输入输出schema及资源释放规范。自研采用现代.NET可保留，但不因此推导架构或运行质量优于VM。
