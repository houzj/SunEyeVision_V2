## 1. 一句话

**干活的地方把东西放全（工具自己的 `bin`），交出去的地方只放缺的（`plugins\<工具>\`）；判断"缺不缺"只有一句话：宿主有的就不带。**

---

## 2. 为什么要改（现状四个问题）

| # | 问题 | 直白说明 | 证据 |
|---|---|---|---|
| ① | **VS 设计器看不到工具界面**（黄框 / "程序集缺失" / 控件空白） | 两个独立成因：**(a)** 产物被构建规则挪到 `plugins\`，而设计器按"项目输出路径（`TargetPath`）"找程序集 → 找不到；**(b)** SDK 程序集没有声明"我的样式字典在哪" → 设计器里 SDK 控件渲染为**空白** | `Directory.Build.targets:39-41`（OutDir 覆盖）；`src/Plugin.SDK/AssemblyInfo.cs`（补 `ThemeInfo` 前的状态） |
| ② | **工具离不开本仓库** | 构建规则**故意剔除**工具的依赖，靠主程序临时提供 → 别人没有主程序源码就没法开发工具；做完拷进 `plugins` 也不保证能跑 | `Directory.Build.targets:56-74`（Step 1 剔除清单，已反转为只剔大件） |
| ③ | **一个目录兼两职，必然打架** | 设计器要求"输出目录里依赖齐全"，运行只要求"有主程序集"；压在同一个目录 ⇒ **要么目录变脏（塞满宿主已有的库），要么设计器就是坏的** | 实测：`plugins\Tool.PointLineMeasure` 试点后 9 文件 / 4.09 MB（其中 78% 是 pdb+xml） |
| ④ | **（事故）两份同名库 → 功能悄悄失效** | 工具目录自带一份 `System.Text.Json`，插件被隔离加载后，宿主"看不见"插件里定义的 JSON 判别符 → 打开解决方案报 `Read unrecognized type discriminator id 'Script'` | 事故档案见原方案 §18.5；治本规则见 `PluginAssemblyPolicy.cs` / `PluginLoadContext.cs` |

## 3. 怎么算成功（验收标准）

| # | 标准 | 验证方式 |
|---|---|---|
| 1 | **设计器可用**：VS 打开工具界面文件能正常渲染、能补全 | 手动（VS 打开工具 XAML） |
| 2 | **F5 能跑**：工具工程 F5 → 起真实主程序，里面跑刚编的工具 | 手动 |
| 3 | **拷进即用**：把 `plugins\<工具>\` 文件夹拷到别人主程序即可用 | 手动 + 启动日志「发现 N == 注册 N」 |
| 4 | **坏插件不拖垮主程序**：版本不匹配 / 依赖缺失 → 明确报错 + 只跳过它自己 | 自动（守卫测试）+ 手动 |
| 5 | **插件目录干净**：`plugins\<工具>\` 只放"宿主没有的东西" | 目录清单核对（脚本） |
| 6 | **不存在"两份同名库"**：运行期一律用宿主那份 | 自动（端到端冒烟 + 加载日志"隔间内解析依赖 N 个"） |

## 4. 方案核心

### 4.1 两个目录，各干一件事

| 目录 | 角色 | 里面放什么 | 谁在看它 |
|---|---|---|---|
| `tools\<工具>\bin\<配置>\...\` | **厨房** | **完整**：主程序集 + SDK + HalAdapter + 工具私有库 + 调试符号 + 依赖清单 | **VS 设计器**、代码补全、F5 |
| `dev\Debug\plugins\<工具名>\` | **外卖盒** | **最小**：主程序集 + 调试符号 + 依赖清单 + **宿主没有的**私有库 | **运行时加载器**、交付 |

> 要点：**设计器看的目录（输出目录）运行时不需要；运行时读的目录不需要依赖齐全** —— 把这两件事分开，才同时满足"设计器可用"和"目录干净"。

### 4.2 唯一的规则：「宿主有的不带」

- **构建期**：向 `plugins\<工具>\` 复制时，凡是**宿主目录已有同名文件**的项，一律不复制；
- **运行期**：加载插件时，凡是宿主有的库（契约 / 框架 / 大件 / 框架自带）一律**回宿主取**；
- ⇒ 两边是**同一句话** ⇒ 不需要人工维护"该带什么"的清单，也不会"带了却不用"。

### 4.3 三条支撑（**已完成并已提交，本次复用，不再改动**）

| 支撑 | 作用 | 落点 |
|---|---|---|
| **契约版本（"证件"）** | 插件声明其编译期 SDK 版本；宿主启动核对，不匹配则明确报错并只跳过该插件 | `src/Plugin.SDK/Core/ToolContract.cs` |
| **每插件隔间加载 + 共享优先** | 每个插件在独立 `AssemblyLoadContext` 中加载；契约/框架/大件**回落宿主** ⇒ 全平台类型身份唯一 | `PluginLoadContext.cs`、`PluginAssemblyPolicy.cs` |
| **依赖清单 `deps.json`** | 工具私有库的解析依据，随插件一起复制 | `Directory.Build.targets:89-99`（由"删除"改为"保留"） |

### 4.4 依赖归属判据（谁的东西放谁那儿）

> **主程序装"所有工具都要的"（平台能力）；工具装"只有我要的"（业务依赖）。**
> 自问一句：**"这是平台能力吗？"** —— 是 → 宿主；不是 → 跟工具走。

| 归属 | 放哪 | 例子 |
|---|---|---|
| **平台能力** | 宿主一份（`dev\Debug\` + `runtimes\native\`） | 契约 SDK、HalAdapter、Halcon/OpenCV、框架自带 `System.*`、公共几何/日志 |
| **业务依赖** | 该插件文件夹（`plugins\<工具>\`） | 相机/PLC/打印机/加密狗 SDK、条码/推理/图表库、工具私有算法 dll |

**契约（SDK）规定的是"工具能看见哪些平台能力"，不规定"工具能带什么私人物品"** —— 两者不可混。

### 4.5 插件目录的精确内容（= 宿主能力的补集）

`plugins\<工具>\` 装的是**"该工具运行时在宿主里找不到的那部分"**：

| 必须有的 | 说明 |
|---|---|
| 工具主程序集 | 文件名必须 **==** 目录名（加载器发现约定） |
| **依赖清单 `deps.json`** | 私有库的解析依据 —— **不是 dll 但必须带**，缺它私有库解析不到 |
| 工具私有依赖 dll（宿主没有的） | 如 `System.Data.SQLite`、`SharpVectors.*`、相机 SDK 等 |
| 调试符号 `.pdb`（可选） | 供在宿主中运行时断点 |

**不该有的**：宿主已有的（契约 SDK、HalAdapter、框架模块、大件与原生、框架自带 `System.*`）—— 全平台只留一份，保证**类型身份唯一**（否则即 §2④ 事故）。

**边界情况（必须遵守）**

| # | 情况 | 约定 |
|---|---|---|
| 1 | `deps.json` | **必须随插件走**（它是私有库的"地图"） |
| 2 | **同名但版本不同**的库 | **以宿主为准**（"宿主有同名即回宿主"，不看版本）。这是刻意取舍：跨边界类型只能有一个来源。**真要新版本** → 走正规通道：升级宿主版本，或把该库**提升为平台件**（进宿主依赖清单 + 契约版本纪律）。**禁止**工具私自带一份不同版本 |

**当下实况**：18 个工具**均无私有库** ⇒ 今天 `plugins\<工具>\` = **3 个文件**（主 dll + pdb + deps.json）；私有库出现时（接硬件/第三方算法/外部开发者）由构建规则**自动带上**，规则不需改变。

### 4.6 依赖分层与归属判定（四类，不是两类）

| 层 | 实例 | **放哪** | **工具怎么引用它** |
|---|---|---|---|
| **契约** | `Plugin.SDK` | 宿主一份 | 工具引 SDK（源码工程 **或** 包） |
| **平台适配层** | `HalAdapter` / `CvAdapter` / `CvEngine` / `halcondotnetxl`（托管+原生）/ OpenCV 运行时 | **宿主一份**（体积与类型身份双重要求） | 工具引**包**（仅编译引用）；运行期由宿主提供 |
| **通用能力（源码层）** | `Workflow`（如 `Solution` 上下文）、公共控件等 | **应提升为契约**（进 SDK：接口 / 只读投影） | 工具引 SDK 契约，不直连宿主实现 |
| **业务私有** | 相机/PLC/加密狗 SDK、条码/推理/图表库 | **`plugins\<工具>\`** | 工具自带；构建规则自动复制 |

**判定标准（三问，避免凭"谁在用"误判）**

> ① 工具**运行期**是否真的需要它？ ② 是否**多个/未来工具**都需要它？ ③ 它的**类型会跨插件-宿主边界**吗？
> - 三"是" → **提升为契约**（进 SDK）；
> - 只有 ① 是 → 属宿主实现细节 ⇒ 用**契约接口**隔离（工具不直连实现）；
> - ① 否 → **移除引用**。

**明确否定两种错误判据**：❌"谁在用"（一个工具用 ≠ 该私有）；❌"不在 SDK 层"（源码层通用能力只是**尚未契约化**，处置是"送进 SDK"，不是"禁止引用"）。

**超出平台能力怎么处理（直白版 · 三分支）** —— 判据只问一句：**"宿主需不需要认识它？"**

```
工具的一个需求
├─ 宿主已有该能力 ──────▶ 用宿主那份（工具不带、SDK 不动）
│                          例：Roslyn / AvalonEdit / Halcon / OpenCV / 公共控件
├─ 只有工具要、宿主不认识 ─▶ 工具自带（构建规则自动复制进 plugins\<工具>\）
│                          例：ZXing 条码 / ONNX 推理 / 相机SDK / LiveCharts / Excel 导出
└─ 两边要对接（宿主必须认识）▶ 在 SDK 加**一张接口**（不是那个库本身）
                           例：读全局变量 / 操作画布节点 / 取"当前解决方案上下文"
```

| 工具要做的事 | 宿主认识吗 | 放哪 | SDK 动吗 |
|---|---|---|---|
| ZXing 读条码 / ONNX 推理 / 相机 SDK / LiveCharts 画曲线 | 不认识 | **工具自带** | **不动** |
| 跑用户脚本（Roslyn）/ 用编辑器控件 | 宿主自己也要用 | **共用宿主那份** | **不动** |
| 读写全局变量 / 操作画布节点 / 取当前方案上下文 | **必须认识** | SDK 加接口（十几行），宿主给实现 | **动一次（仅接口）** |

**重要澄清**：**"超出平台能力" ≠ "进 SDK"**。绝大多数超出部分是**工具私货**（进插件文件夹，SDK 零改动）；进 SDK 的通常只是**一张接口**；**SDK 增长很慢**（只有"必须与宿主对接"时才动一次）。

**AvalonEdit / Roslyn 的对齐口径（它们属"宿主已有能力"，不需重做）**

| # | 对齐项 | 现状 | 目标 |
|---|---|---|---|
| 1 | 引用语义显式化 | Script 声明包（默认复制）+ 旧 Step 1 拦截 | 明确"**仅编译引用**"（§4.7）；运行期一律宿主提供 |
| 2 | 注释口径 | `SunEyeVision.UI.csproj:24` 写"宿主统一加载, Script 工具 csproj 不再声明"（与实测矛盾） | 改为"**宿主自身需要（编辑器控件），顺带共享；工具声明仅用于编译**" |
| 3 | 归属定性 | 未明确 | 定为"**平台能力（编辑器 / 编译基础设施）**"，未来同类工具直接复用 |

> 真正需要**契约化 / 下沉**的不是 Roslyn/AvalonEdit，而是 Script 直连的两处源码层依赖：
> ① `SunEyeVision.Workflow.Solution`（类型直连宿主源码层 ⇒ 破坏独立性）；
> ② `CommonControl.ScriptEditorCore` 控件（公共控件 ⇒ 宜**下沉 SDK**，与"公共控件归 SDK、显示编辑器归工具层"的既有决策一致）。
> 两者与"谁在用"无关 —— 判据是 §4.6 的三问。

### 4.7 引用形态（双场景同一份 csproj）

**运行期共享** ≠ **开发期可以引仓内工程源码**。无宿主源码时 `..\..\src\...` 根本不存在 ⇒ 必须可分发布形态：

```xml
<!-- 场景 A：有宿主源码 → 引工程，仅编译不复制 -->
<ProjectReference Include="..\..\src\SunEyeVision.HalAdapter\SunEyeVision.HalAdapter.csproj"
                  Condition="Exists('..\..\src\SunEyeVision.HalAdapter\SunEyeVision.HalAdapter.csproj')">
  <Private>false</Private>
</ProjectReference>

<!-- 场景 B：无宿主源码 → 引开发包里的适配层包，只取编译引用、不复制 -->
<PackageReference Include="SunEyeVision.HalAdapter" Version="1.0.3"
                  Condition="!Exists('..\..\src\SunEyeVision.HalAdapter\SunEyeVision.HalAdapter.csproj')"
                  ExcludeAssets="runtime" />
```
两种写法语义一致：**仅拿到编译引用，不复制到输出；运行期一律由宿主提供**（与 §6.5「同一份 csproj + 条件引用」一致）。

## 5. 具体形态

### 5.1 数据流

```
工具源码
   ↓ 编译
tools\<工具>\bin\<配置>\...\        ← 厨房：完整依赖闭包（设计器看这里）
   ↓ 过滤：凡是宿主目录已存在同名的项，一律剔除
dev\Debug\plugins\<工具名>\         ← 外卖盒：最小集（运行时读这里 + 交付物）
```

### 5.2 实际内容（按现有产物实测预估）

| 工具 | 现状 | 新方案下 `plugins\<工具>\` |
|---|---|---|
| 一般工具（如 CircleDetect） | 1 文件 / 0.17 MB，**但设计器黄框** | **3 个文件 / 几十~百 KB**：主 dll + pdb + deps.json |
| **Script** | 34 文件 / 26 MB | 其 **28 个 dll 中 27 个宿主已有**（Roslyn/AvalonEdit 宿主自己在用）→ 被过滤 ⇒ **仅 1 个 dll，≈417 KB** |

### 5.3 构建规则（草案，待实施）

```xml
<PropertyGroup Condition="'$(IsToolPlugin)'=='true'">
  <!-- 单一外部输入：宿主运行目录（本仓 = dev\Debug；场景 B = DevKit 的 host\） -->
  <HostRoot Condition="'$(HostRoot)'==''">$([System.IO.Path]::GetFullPath('$(MSBuildThisFileDirectory)dev\Debug\'))</HostRoot>
  <PluginDeployDir>$(HostRoot)plugins\$(MSBuildProjectName)\</PluginDeployDir>
</PropertyGroup>

<Target Name="DeployToolPlugin" AfterTargets="Build" Condition="'$(IsToolPlugin)'=='true'">
  <ItemGroup>
    <_Core Include="$(TargetPath)" />                                                  <!-- 主程序集 -->
    <_Core Include="$(TargetDir)$(TargetName).pdb" Condition="Exists('…')" />          <!-- 调试符号 -->
    <_Core Include="$(TargetDir)$(TargetName).deps.json" Condition="Exists('…')" />   <!-- 依赖清单 -->
    <!-- 工具自带依赖：只留"宿主没有同名"的（与加载期同一条规则） -->
    <_Private Include="@(ReferenceCopyLocalPaths)"
              Condition="!Exists('$(HostRoot)%(Filename)%(Extension)')" />
  </ItemGroup>
  <MakeDir Directories="$(PluginDeployDir)" />
  <Copy SourceFiles="@(_Core);@(_Private)" DestinationFolder="$(PluginDeployDir)" SkipUnchangedFiles="true" />
</Target>
```

**配套（防目录重新变脏）**：把"本次复制了哪些文件"写入一个清单文件（manifest）；下次构建时**只删"上次复制、本次不再需要"的项**，不触碰其它文件。

### 5.4 与加载器的接口（均已就绪，无需改动）

| 环节 | 靠什么保证 |
|---|---|
| 加载器找到插件 | 文件名 **==** 目录名（`PluginAssemblyPolicy.DiscoverPluginAssemblies` 的约定） |
| 工具私有库能解析 | `deps.json` 一并复制（隔间解析依据） |
| 共享依赖不重复带 | "宿主有的不带"（与加载期"回宿主"同源） |

## 6. 四个要求如何同时成立

| 要求 | 靠什么成立 |
|---|---|
| **设计器能用** | 设计器看工具的 `bin`（厨房），依赖**完整** ⇒ 控件可渲染、提示可补全 |
| **运行能用** | 从 `plugins\<工具>\` 只加载主程序集；SDK / HalAdapter / 框架 → **回宿主取**；工具私有库在插件目录内就地解析 |
| **独立开发** | 工具工程**只认两个外部输入**（SDK + 宿主目录）；本机 F5 起真实宿主跑刚编的工具；交付 = 把 `plugins\<工具>\` 文件夹发回 |
| **目录干净** | 只放"宿主没有的" ⇒ 一般工具 3 个文件、几十 KB 起 |

## 7. 业界对标（本机参考库 `D:\MyWork\参考项目\`，不随 git 分发）

| 维度 | MAGE3D 实测 | 本方案 | 结论 |
|---|---|---|---|
| 插件输出目录 | **≥3 个**：`bin\x64\Debug\MCTools\`、`Mage3DGeneration\win64d\MCTools\`、`MGen2_Plugs\`，且 `ControlLib` 等**直接输出到宿主根** | 一个 `plugins\` 根 + **每工具一子目录** | 本方案更可归因、可 drop-in |
| 插件目录内容 | `MCTools` = **47 dll** / 91 文件；`MGen2_Plugs` = **117 dll**（含 `EntityFramework` 4.9 MB、`halcondotnetxl` 1.5 MB） | 一般工具 **3 文件**，Script 仅 1 dll | 本方案更干净 |
| 依赖策略 | 人工逐条标 `<Private>False</Private>`，**已漂移**（抽查 `ControlLib.csproj` 29 项未标、`ImageTypleConverter.csproj:35-37` 漏标 halcondotnet） | 构建期与运行期**同一条事实规则**（宿主有的不带/回宿主） | 本方案无人为漂移空间 |
| 加载方式 | MEF `DirectoryCatalog`（`MAGE3D_2ndGen_Base\MC_Tools\Plugins.cs:44-69`），.NET Framework 4.6.1 单 AppDomain | 每插件隔间 + 只认同名主程序集 | **不可照搬**：`DirectoryCatalog` 会载入目录内所有程序集，在自包含目录下即 §2④ 事故的同款成因 |
| 设计器可解析机制 | 旧式 csproj + `HintPath` 直指宿主目录（仓库私有路径） | 输出目录内含完整闭包（标准做法） | **不可照搬**：硬编码仓库路径会使"无宿主源码开发"不成立 |

**可借鉴**：① "框架模块与大件不复制"（MAGE3D 亦如此）；② 插件产物置于**宿主目录子树内**（本方案已是）。
**不可照搬**：多输出目录/平铺共享目录/人工逐条 `Private`/`DirectoryCatalog` 全目录扫描/`HintPath` 指仓库路径。

### 7.1 实测分布：MAGE3D 只做对了一半

| 插件目录 | dll 总数 | **宿主也有（重复副本）** | 插件独有（工具自身 + 私有库） |
|---|---|---|---|
| `MCTools` | 47 | **29（62%）** | 18（2.89 MB） |

- **做对的一半**：工具私有库确实跟插件走 —— `System.Data.SQLite(.EF6/.Linq)`、`SharpVectors.*`（8 个）等**宿主根没有**的库都只存在于插件目录（与 §4.5 一致）。

## 9. 风险与回退

| 风险 | 应对 |
|---|---|
| 产物分两处（bin 与 plugins） | 复制是**构建规则**（非手工），每次 `Build`/F5 自动执行；验收固定为"plugins 目录内容清单" |

| 出问题如何回退 | 改动集中在构建侧（工具 csproj + `Directory.Build.targets` + 一个新 target），`git` 整体回退即可 |
