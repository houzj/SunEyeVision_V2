# 插件接口与参数模型架构审查

日期：2026-09-18  
范围：`src/Plugin.SDK/Core`、`src/Plugin.SDK/Execution/Parameters`、工具注册与执行链  
结论：当前设计可以支撑现有工具运行，但插件接口和参数模型存在结构性耦合。继续增加工具时会放大 UI、绑定、执行器和算法之间的相互影响，应在继续大规模迁移工具前完成接口收口。

## 一、当前设计的合理部分

1. `IToolPlugin<TParameters, TResult>` 提供了泛型入口，工具实现可以获得编译期参数和结果类型检查。
2. `IToolPlugin` 作为注册中心使用的非泛型入口，解决了插件程序集动态加载的问题。
3. `ToolExecutionRequest` 已经开始表达本次运行的输入图像、上游结果、全局变量和取消令牌，这是运行数据与设计数据分离的正确方向。
4. `IAsyncToolPlugin`、`IToolExecutionProfileProvider`、`IToolInputReader` 分别覆盖异步执行、并发资源声明和只读输入访问，方向是合理的。
5. 输出变量使用 SDK 固定词汇，能够支持模块结果绑定和全局变量类型校验。

这些部分可以保留，但需要把它们收敛到一条统一的执行契约上。

## 二、插件接口的主要问题

### 1. 同步和异步接口不是同一个执行模型

同步插件是 `Run(ToolParameters)`，异步插件是 `ExecuteAsync(ToolExecutionRequest)`。两者的输入对象不同，导致执行器必须维护两条路径，调试运行和工作流运行容易出现行为差异。

应统一为：

```csharp
ValueTask<ToolExecutionResult<TResult>> ExecuteAsync(
    ToolExecutionContext context,
    TParameters parameters,
    CancellationToken cancellationToken);
```

同步工具由 SDK 提供适配器包装成 `ValueTask`，工具作者不需要同时理解两套入口。

### 2. `IToolPlugin` 仍允许执行器把运行数据写回参数对象

`ToolExecutor` 会把 `ResolvedInputImage`、`NodeResults`、`Context` 写入 `ToolParameters`。这使一次运行的状态进入了设计参数对象，破坏了快照隔离，也使同一个参数对象不能安全地并行执行。

最终接口应让工具从独立的 `ToolExecutionContext` 或 `IToolInputReader` 读取运行输入。参数对象只保存可持久化的设计值。

### 3. 非泛型接口承担了过多职责

当前 `IToolPlugin` 同时暴露参数类型、结果类型、输出变量、执行方法和默认参数创建。注册、元数据、执行、结果契约应分开：

```text
IToolDescriptor       注册与静态元数据
IParameterContract    输入槽位和运行参数
IResultContract       输出字段和绑定能力
IToolExecutor         执行入口
IToolEditorFactory    可选的桌面编辑器
```

非泛型适配器只存在于插件发现边界，不能成为算法层主要接口。

### 4. SDK 层直接引用 WPF

`IToolEditorFactory` 位于 Plugin.SDK，却直接返回 `Window` 和 `FrameworkElement`。这会让算法插件依赖桌面 UI，阻止无界面运行、服务端运行和独立测试，也使 SDK 与 UI 版本绑定。

建议拆成两个包：

```text
Plugin.SDK              纯运行时契约、参数、结果、图像和几何类型
Plugin.SDK.Wpf          IToolEditorFactory、调试窗口和控件
```

工具插件的算法程序集只引用 Plugin.SDK；需要编辑器的程序集额外引用 Plugin.SDK.Wpf。

### 5. `ToolAttribute` 混入 UI 行为

`ToolAttribute` 同时保存 ID、显示名、分类、图标、调试窗口样式和是否有窗口。图标和窗口样式属于宿主展示策略，不应成为算法插件的核心身份契约。

应保留稳定的 `Id`、版本和能力声明；显示名称、图标和窗口工厂通过独立的 UI 元数据提供。

### 6. 注册中心通过反射创建实例并提取元数据

`ToolRegistry.RegisterTool` 会创建工具实例、注册参数多态类型并提取输出元数据。注册阶段执行构造函数可能触发资源初始化或 UI 状态，增加加载副作用。

建议注册阶段只读取类型和静态描述；真正的工具实例在执行会话开始时由工厂创建。工具实例应明确是无状态、会话级还是可复用实例，避免并行执行时共享可变字段。

### 7. 并发安全和资源生命周期没有成为插件契约

`IToolExecutionProfileProvider` 能声明并发类别，但没有同时声明：

- 实例是否可复用
- 是否允许同一实例并行调用
- 图像/ROI/算法句柄由谁创建和释放
- 取消是否可响应
- 超时后是否需要销毁实例

`ParallelSafe` 只能作为调度提示，不能替代这些生命周期契约。

## 三、参数类设计的主要问题

### 1. `ToolParameters` 同时是数据模型、绑定模型和 UI ViewModel 基类

它继承 `ObservableObject`，并包含 `Context`、`NodeResults`、`ResolvedInputImage` 等运行时字段，还提供反射式绑定查询。这使参数对象既是方案文件的一部分，又是执行中的可变对象。

建议拆成：

```text
ToolDefinition          工具静态契约
ToolConfiguration        设计期纯值参数，可序列化
ParameterBindingSet      参数到上游结果/全局变量的绑定关系
RuntimeParameterSnapshot 解析绑定后的本次运行纯值
ToolExecutionContext     图像、上游结果、日志、取消令牌和资源
```

算法只接收 `RuntimeParameterSnapshot` 和 `ToolExecutionContext`。

### 2. `ParamValue<T>` 把值和绑定状态绑在一个属性里

`ParamValue<T>` 当前包含值、绑定配置、绑定常量、来源文本和通知机制。参数解析器也通过反射专门寻找 `ParamValue<>`，这会导致 SDK 的所有新设计都围绕该包装器展开。

最终参数应是纯 CLR 属性：

```csharp
public int Threshold { get; set; }
public double Sigma { get; set; }
```

绑定由外部结构保存：

```csharp
public sealed record ParameterBinding(
    string ParameterName,
    BindingSource Source,
    string SourcePath,
    string TargetType);
```

执行前由绑定解析器生成快照，工具执行期间不修改设计参数。

### 3. 当前 `ParameterResolver` 与具体包装类型耦合

`ApplyBindings` 只处理 `ParamValue<>`，并通过泛型参数取得目标类型。参数类型一旦改为纯 CLR，解析器就必须改变为“读取契约 + 写入运行快照”，而不是反射修改参数对象。

### 4. 反射式 `GetBindableInputProperties()` 不是可靠契约

当前规则是“没有 `IgnoreBind` 就可以绑定”。这会把派生属性、运行时属性、显示配置和结构性集合误认为业务输入。输入槽位必须由契约明确声明，并包含角色、类型、集合性、可空性和是否允许绑定。

### 5. `CopyFrom` 是浅复制

当前反射复制会直接复制 `ParamValue`、ROI 集合、结果显示配置和其他可变引用。复制后的节点可能共享同一绑定配置或集合，造成“修改一个节点，另一个节点变化”的隐性问题。参数快照必须使用明确的深拷贝或不可变记录。

### 6. 参数类包含派生显示属性和 UI 状态

例如 `IsBinary`、`PositionCorrectionBindingDisplayText`、结果显示配置等不应成为算法运行参数。它们应由 UI 状态模型或结果呈现模型承担，避免进入参数契约和全局变量树。

## 四、建议的最终接口

```csharp
public interface IToolDefinition<TParameters, TResult>
    where TParameters : class
    where TResult : class
{
    ToolDescriptor Descriptor { get; }
    IParameterContract Parameters { get; }
    IResultContract Results { get; }
    ValueTask<ToolExecutionResult<TResult>> ExecuteAsync(
        TParameters parameters,
        ToolExecutionContext context,
        CancellationToken cancellationToken);
}
```

宿主侧可以提供 `IToolPluginAdapter`，负责把动态加载、非泛型发现和泛型执行接起来，但适配器不进入算法代码。

## 五、实施顺序

1. 先新增 `ParameterBindingSet`、`RuntimeParameterSnapshot` 和统一的 `ToolExecutionContext`，让执行器具备不修改设计参数的路径。
2. 将 `ParameterResolver` 改为“绑定定义 → 运行快照”，删除对 `ParamValue<>` 的特殊处理。
3. 把 Blob、图像二值化、图像滤波、形态学四个工具的参数改成纯 CLR 值；工具内部所有 `.Value` 访问改为直接属性访问。
4. 将契约校验改为要求纯 CLR 参数，删除自动解包逻辑。
5. 将输入参数树和目标参数树改为读取契约，不再从反射排除规则推断可绑定性。
6. 把 WPF 编辑器接口移动到 `Plugin.SDK.Wpf`，再迁移其他工具。
7. 最后收紧插件实例生命周期、取消、超时和并发声明，并补充跨工作流运行测试。

## 六、架构结论

当前接口设计可以作为现有系统的过渡层，但不适合作为长期插件 SDK。最需要优先修复的是参数模型：只要 `ParamValue<T>` 仍是工具参数属性，绑定解析、执行快照、UI 编辑和算法逻辑就没有真正分离。插件接口的最终形态应以“纯值参数 + 外部绑定定义 + 独立运行上下文 + 统一异步入口”为核心。
