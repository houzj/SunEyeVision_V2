# 工作流与执行引擎架构审视

## 评审结论

当前系统的执行算法、依赖图和运行快照已经具备重构基础，但工作流定义的所有权仍然不统一。`WorkflowTabViewModel`、`WorkflowEngine`、`Solution.Workflows` 和序列化模型在不同路径上都可能持有一份工作流对象或工作流集合。这个问题会直接影响节点、连接、参数绑定和全局变量，属于核心架构风险。

日志已经给出明确证据：2026-09-19 13:14:18，工作流 2 的节点 `0d0cc817-e907-45b2-82e1-7fc2a2e4e160` 出现在 UI 画布；13:14:34 执行时，执行管理器从引擎读取工作流，却抛出该节点 ID 不在字典中；13:19:18 保存诊断显示该节点 `ui=WorkflowNode`，而 `engine=null、solution=null`。因此当前异常不是字典访问缺少保护，而是节点写入了 UI 投影却没有写入工作流定义。

## 当前架构的主要问题

1. **工作流定义存在多个事实源。** UI 节点集合可以变化，引擎工作流节点集合和方案工作流集合却不一定同步。切换标签页时自动创建空引擎工作流会把生命周期问题隐藏到执行阶段。

2. **节点和连接的修改入口分散。** 创建节点、删除节点、建立连接、删除连接、修改参数和绑定可能分别直接操作 UI 集合、引擎对象或方案对象。调用顺序不同就会产生不同结果。

3. **执行边界虽然有快照，但快照来源不稳定。** 引擎在运行开始复制节点和参数是正确方向，但如果复制的源工作流不是当前 UI 定义，快照会稳定地执行错误内容。快照解决的是运行期间不被编辑污染，不能解决定义源不一致。

4. **保存和加载仍承担对象拼接职责。** 反序列化、UI 转换、引擎注册和方案登记之间存在复制转换；历史上已经出现过 `ParamSettings` 漏复制。只要字段新增，就可能再次产生“界面有、执行没有、保存丢失”的问题。

5. **全局变量边界需要和工作流定义分开。** 全局变量是方案级定义，输入来源和目标输出是定义期绑定；一次运行的值必须属于 `RunContext` 快照。设计值、运行值、上一批次值不能共享同一个可变字典。

6. **子程序依赖容易被对象引用混淆。** 子程序应通过稳定的 `WorkflowId` 和节点 ID 引用定义，不能通过 UI Tab、控件或临时工作流对象引用。父子运行应共享一次运行会话，但使用各自的局部上下文。

7. **UI 参与了过多生命周期协调。** UI 可以发起命令和展示状态，但不应负责把节点补写到引擎、猜测当前工作流、延迟修复定义，或在执行中修改引擎对象。

## 目标架构

引入方案级 `WorkflowDefinitionStore` 作为唯一真相源。Store 持有完整的工作流定义：稳定的工作流 ID、节点、连接、参数值、参数绑定、子程序引用和版本号。`Solution` 只持有这个定义集合；`WorkflowEngine` 通过 Store 查询定义，不再维护一份可独立修改的节点集合。

`WorkflowTabViewModel` 只做 UI 投影。画布上的节点 VM 通过稳定 ID 映射到定义节点；所有增删节点、连接和参数修改都通过 `IWorkflowDefinitionService` 命令完成。服务先修改定义，再发布领域事件，UI 根据事件刷新。这样 UI 关闭、切换标签和重新打开不会改变定义的所有权。

运行时使用三层对象：定义对象、运行快照、运行上下文。定义对象可编辑并可持久化；运行开始时根据工作流 ID 编译出不可变的 `WorkflowExecutionSnapshot`，其中包含节点参数快照、绑定快照、连接快照、依赖图和执行画像；`WorkflowRunContext` 保存本次运行的图像、全局变量值、节点状态和结果。算法插件只能读取运行上下文和运行参数副本，不能访问 UI 或定义对象。

全局变量分为方案级定义和批次级值。定义包含名称、类型、初始值、生产者绑定和消费者绑定；运行开始为每个 Run 建立 `GlobalValueSnapshot`。跨工作流依赖由方案依赖图编译为工作流级生产者/消费者边，生产者完成后提交本批次值，消费者只能读取该批次快照。并发写入必须通过生产者唯一约束或显式合并策略解决，禁止多个工作流无序覆盖同一变量。

执行引擎只接受已编译的运行快照。它先校验节点 ID 唯一、连接引用有效、绑定来源存在、子程序引用存在、跨工作流依赖无环，再建立就绪队列。并行窗口由连接依赖、参数绑定依赖、全局变量依赖、资源租约和工具并发画像共同计算。单个节点等待信号或超时只影响它的后继链；无依赖的节点可以继续运行。超时、取消、失败和跳过都写入同一运行上下文，并由快照事件通知 UI。

## 生命周期规则

新建工作流必须一次性完成“创建定义、注册 Store、建立 UI 投影、选中 Tab”四步。切换标签页只能切换投影，不能自动创建空的引擎工作流。

添加节点必须通过定义服务完成。服务生成稳定节点 ID，把节点和默认参数写入定义，再发布 `NodeAdded`；UI 监听事件生成或更新节点 VM。连接也遵循同一规则，服务在写入前校验两端节点存在。

保存时只序列化 Store 中的定义；加载时只反序列化一次，完成校验后注册 Store，再由 UI 创建投影。禁止“UI 对象转引擎对象转方案对象”的多次复制。若需要执行类型化节点，应由运行快照编译器创建运行副本，不能回写定义。

参数绑定保存的是稳定引用：`SourceWorkflowId`、`SourceNodeId`、`SourceProperty` 和目标参数名。显示名称是缓存字段，加载后可以根据定义重新计算。参数控件的显示值由绑定状态投影生成，不能把绑定值覆盖回设计期常量。

## 实施顺序

1. 先冻结不变量并增加自动化测试：同一个工作流 ID 在 Store、Solution、Engine 查询到同一份定义；新建工作流添加节点后立即执行；连接后执行；保存重启后节点、连接和绑定数量不变；子程序和全局变量路径可解析。
2. 建立 `WorkflowDefinitionStore` 和 `IWorkflowDefinitionService`，先接管节点、连接的增删改，保留现有 UI 作为投影。
3. 移除 `OnSelectedTabChanged` 中“引擎不存在就自动创建空工作流”的逻辑，改为只从 Store 选择定义。
4. 让 `WorkflowTabViewModel` 的节点和连接命令全部经过定义服务，清理直接操作多个集合的路径。
5. 将执行入口改为 `CompileRunSnapshot(workflowId, runRequest)`，执行引擎不再从 UI 或可变方案对象读取节点。
6. 把保存、加载、子程序注册和全局变量编译统一迁移到 Store，并删除重复转换路径。
7. 最后再做并行性能优化和 UI 快照展示；性能优化必须建立在定义和快照一致的前提上。

## 必须保留的架构验证

- 新建工作流后，不关闭窗口，添加两个节点并连接，立即执行成功。
- 切换到其他工作流再切回，节点、连接和参数仍来自同一个定义。
- 保存方案、关闭软件、重启、加载后，节点 ID、连接、参数绑定和全局变量绑定完全一致。
- 一个节点等待相机信号时，无依赖节点继续执行；依赖它的节点按超时策略跳过。
- 两个工作流同时读同一全局变量得到同一批次值；同一变量多写入按唯一生产者或显式合并策略处理。
- 子程序执行结果能通过稳定的父节点/子节点路径回传，UI 只接收事件，不参与调度。

在这套架构落地前，任何针对 `KeyNotFoundException` 的局部 `TryGetValue` 只能改变错误表现，不能视为修复。当前应优先完成定义所有权和生命周期统一，再继续扩展执行器功能。
