GEX26 · 自研 SunEye · 计算完成、调度器收集、UI缓存提交是三个不同的时刻

慢工具完成本身不直接调用 Context.SetNodeResult：正常根就绪队列在完成任务收集环节写 Context 并触发 NodeExecutionFinished；取消离开后未继续收集的工具结果，不能仅凭工具成功返回就认定已写入根结果。管理器在 await 引擎后先 await InvokeOnUIAsync 更新执行快照，随后逐节点调用 OnNodeExecutionCompleted。该方法用 InvokeOnUI 投递事件；普通入口在这里使用 CancellationToken.None，通信入口才捕获通信取消 token。MainWindowViewModel 收到节点事件后调 NodeResultManager.UpdateNodeResult，后者按节点 ID 写入 _getContext() 当时返回的上下文；构造时该委托为 () => CurrentWorkflowContext，而该属性按执行事件被接收时的 SelectedTab.Id 调用 GetOrCreate；不是从本事件携带的工作流 ID 选择缓存上下文。节点事件参数携带 Node、Result、Timestamp、相机标志与排队耗时，在该类型中没有 RunId/SolutionEpoch。另一个执行快照事件仅按当前 Tab 的 RootWorkflowId 过滤状态栏，不能把此过滤推广成节点缓存提交的执行代次门。

这是已取源码的具体提交链，不是完整产品 UI 的迟到写回复现。还需验证停止／方案切换与已排队普通事件的实际先后、上下文替换时机及其它接收者是否另有门；不能仅因当前几个方法没检查代次就称整个产品无保护。
