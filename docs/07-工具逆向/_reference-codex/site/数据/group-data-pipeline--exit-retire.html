GEO32 · VmModule.Dispose → InnerDispose / CommonDispose → 集合移除、IO退役与IMVSGroup.CloseModuleInterface → DeleteGroupModule

source-confirmed

现有托管原体中Dispose交InnerDispose：先IsOnDispose=true，已disposedValue则return；Group先收变量绑定范围再ClearVarBindResultRelation，按Undo服务可能Export。VmModuleSet.DeleteInnerModules只递归从AllModules移除子模块记录，所选方法没有逐child.Dispose调用，不能写成已逐层析构全部子payload。随后退前驱NextModules链接、删参数绑定、CommonDispose，再从父Modules及AllModules移除本对象，CloseModuleInterface后才disposedValue=true。IMVSGroup override CloseModuleInterface明确交DeleteGroupModule(ID)。CommonDispose清NextModules、解内部订阅并逐Inputs/Outputs.Dispose。整个InnerDispose异常catch仅恢复IsOnDispose=false并包装重抛，不等于finally补完剩余清理。

从模型索引移除、IO对象Dispose、native DeleteGroupModule请求是独立动作；不把TryRemove等同native free。

Undo Export可能额外持有删除前对象信息；已disposed与异常后的字段不同。

托管正常顺序可证；DeleteGroupModule最终native资源释放、child最后持有者和异常后未执行部分仍未知。

待核：明确下一缺口是ModuleManager.DeleteGroupModule的实际SDK/native接收体及原Group子模块最终payload退役，不能以字典移除补足。

待核：所选已有反编译体未新做CIL逐指令或原版运行验证。

GEC16 · 每轮scope.Enter/ForProcedure与solution关闭 → 跨轮state/有效参数持有，closing后等租约再释放

independent-implementation

GraphExecutor每次RunAsync using scope.Enter；body与父run沿用同root scope。模块context的Scope为ForProcedure(p.Id)借用view，State缓存键为(procedure,module,node)，因此同body多轮同键复用state而非每轮Dispose。RememberExecutionParameters在模块入口前对seed/applied逐JsonElement.Clone，覆写该键缓存。scope.Dispose对借用view无动作；root先closing=true并Cancel stopping，取消完成且leases==0才TryRelease，最后Exit也可触发。Release先快照distinct states+ownedServices，再清states/effectiveParameters/services/ownedServices，再逐IDisposable.Dispose，异常记录并保留failedResources。

运行租约、跨轮node state、参数JSON克隆缓存和结果session payload分别持有；非owned服务只从字典移除，不由Release列入dispose值。

结束一次Group只退出它的Graph租约，不自动关闭solution root或清node state；RemoveNode另按procedure键移除state与参数，并在锁外Dispose该state。

root释放是IDisposable路径，不await IAsyncDisposable-only state；清字典不证明外部引用消失，cleanup失败对象被failedResources继续持有。Lease.Interlocked.Exchange保证一次Exit。

待核：谁创建/最终Dispose宿主root scope需在具体solution lifecycle入口另追；本页不把局部Group结束等同应用关窗。

待核：当前源码的参数缓存不是native SDK SetParam已确认值；cleanup异常、外部state引用和具体图像原生资源由实现另证。
