返回专题总览

③ 删除节点：节点不在画布上，旧图像就释放了吗？

原版：已证片段与未知父级桥

模块Dispose会断IO关联并关闭SDK模块；IO值与旧显示的最后持有者还要分别追。

谁持有：所选装饰器、图像列表、结果仓库和已排队通知可能分别持有载荷。

已确认的收尾：VmModule.Dispose经CommonDispose逐IO.Dispose、移出模块集合并请求CloseOneModule；VmIO.Dispose移出父集合并断RelateIO，却不直接清_value/_valueList。装饰器退役与显示清空是另有条件的路径。IsDisposeNotify的已证SearchDryPopup消费者只退搜索事件，不能当作清图触发器。

此后仍可能存在：这些方法不能单独证明删除模块后所有异步读者和native像素已退出。

待核：尚未把具体删除入口、同一模块实例、显示退役和生产者最终回收连成完整已证链；不把Dispose片段当成删除全过程。

RC04 · ClearDisplayStore / Init / DeInit → 仅清当前display、清三仓及迟到回调的边界

source-confirmed

ClearDisplayStore仅Clear当前display图像/图形字典，不改buffer/spare、三个计数、两个固定标志或SelectedImage等选择引用。Init只设isInit=true。DeInit则设isInit=false，Clear三套图像/图形字典，清计数和固定标志，置CheckImagesName/SelectedImage/SelectedInputImage为空；没有逐图Dispose或像素free。SetRenderDataToStore以isInit阻止继续入值，但SetDataToStore本身并未先检查isInit：反初始化后迟到的有效回调仍可更新仓库计数和走Clear，然后在下层不存值。所以DeInit不等同所有生产回调已经停止或排空。

representation：清仓、清选择身份、禁止下层存值、原生像素释放是四个不同层次；A链ModuleResultView另持有的ImageData不由此字段写入直接清掉。

cache：ClearDisplayStore仍保留两待写仓里的旧图；DeInit删除三仓持有，但已交给装饰器、视图或扩展消费者的对象可继续可达。

CSR02 · RemoveNode与RetainProcedureNodes批量裁剪 → 删除记录在Dispose之前完成；首个异常中断剩余裁剪

independent-implementation

RemoveNode在root.gate内先删除effectiveParameters键，再从states.Remove取出value；离锁后仅当value实现IDisposable才Dispose，没有catch和RecordCleanupFailure。Dispose抛错时该node状态及参数已从这些字典移除，调用直接失败；重复RemoveNode找不到state就return，不自动重试旧对象。RetainProcedureNodes先批量删除不在keep中的全部参数键，再快照待移state键并foreach RemoveNode；其中一项抛错将中断剩余foreach，后续state仍可留在states，而其参数键可能已在第一阶段删除。
