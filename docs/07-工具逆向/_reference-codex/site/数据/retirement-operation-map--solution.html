④ 切换方案：为什么不能只清右侧图像？

原版：已证片段与未知父级桥

方案属性变更先条件关闭参数窗，再换方案装饰器；此处不直接清旧图像。

谁持有：A链三套仓库/选择引用与B链临时仓库独立，不能合并成一个缓存。

已确认的收尾：OnSolutionChanged仅在参数窗尚未关闭时Close，再替换DecoratorSolution；旧方案分支没有直接Dispose旧装饰器。Release包装控件Dispose已证会调用内部MainViewControl.Dispose再清Content；但具体切方案/关主窗谁触发包装控件Dispose仍未知。A/B链DeInit是另外已证的局部退役体。

此后仍可能存在：A链DeInit不等于生产回调停止：迟到回调仍可能进入上层计数逻辑；B链已排队任务也未由这些体排空。

待核：整方案切换的父级调用顺序、同一实例对应关系和最后读者需要额外证据。

已确认的收尾：ReplaceExecutionScope使旧owner失效并取消请求，清调试/配置/流程结果等，再Dispose旧scope并创建新scope；旧scope等待取消完成且租约归零后Release。

待核：这不证明外部历史、消费者和托管像素都在同一时刻消失。

CSR03 · root closing置位与API准入 / 租约 → 立即拒新状态与租约，不等于所有查询/删除都禁用

independent-implementation

CSR04 · 取消或资源Dispose异常后的root Dispose / Lease.Exit → root清理是一次性尝试；failedResources保留不等于排队重试

independent-implementation

Dispose设置closing后，stopping.Cancel抛Exception会RecordCleanupFailure(cancel,stopping,error)，finally仍设置cancellationComplete并TryRelease；不是因取消回调异常就跳过该finally。TryRelease要求closing、cancellationComplete、leases==0且!releaseStarted，在真正Release前置releaseStarted=true。Release对各IDisposable的Exception分别记录后继续下一资源，并单独尝试stopping.Dispose；这点现有CR06已有，本事实新增明确重试边界：root重复Dispose因closing立即return，后续Exit也因releaseStarted不再启动第二遍，failedResources只保留对象，所选类没有重试/清空该表的方法。

representation：CleanupFailures getter返回失败记录数组副本；内部failedResources保存真实资源引用。诊断快照与资源持有是两层。

cache：失败对象及其Exception可继续使资源图可达；保留到root仍可达不等于资源已释放，也不等于有后台重试任务。

release：Release前先清states/有效参数/services/ownedServices，失败不会把原索引恢复。普通单项Dispose抛Exception不会阻断后续项；但分配快照、RecordCleanupFailure自身异常或进程级故障等未被这一逐资源catch覆盖。
