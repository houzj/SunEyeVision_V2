收尾失败怎么办？四个容易误判的异常分支

替换服务时，旧服务Dispose抛错会怎样？

旧owned标记可能已撤，但services仍指旧对象，新服务未登记；这条失败不走root的CleanupFailures。

CSR01 · ModuleExecutionScope.RegisterService<T>替换旧owned服务 → 先撤owned标记，再Dispose；抛错可留下未回滚的旧映射

independent-implementation

条件必须同时满足：同T已有previous、新service不是同引用、ownedServices.Remove(previous)返回true且previous实现IDisposable。该条件链先从ownedServices删除旧对象，再调用previous.Dispose；只有其正常返回才写services[typeof(T)]=新service及按owned标记登记新对象。旧Dispose抛异常时方法无catch/finally回滚：services仍映射旧previous，旧owned标记已移除，新service未写入，异常直接向调用者传播，也不调用RecordCleanupFailure。不能把注册失败描述为原状态完全不变。

representation：services以Type为key保留对象引用；ownedServices是按ReferenceEquality比较的跨Type集合。新旧服务引用与该集合标记分开。

cache：Service<T>()仍可能查回旧previous。后续root Release的服务候选来自ownedServices而非services全值，所以若旧对象没有另在states等候选中，它不再因这个服务映射获得自动Dispose重试。另有state/服务别名时不能据这一条断言永不再被Dispose。

release：这是服务替换入口的异常合同，区别于root Release逐资源catch/记失败后继续；服务注册并未采用同样的失败资源保留策略。

一批节点里，第一个Dispose抛错会怎样？

节点state与参数先移除才Dispose；首个异常可打断后续state裁剪，不能沿用root逐资源继续清理的保证。

CSR02 · RemoveNode与RetainProcedureNodes批量裁剪 → 删除记录在Dispose之前完成；首个异常中断剩余裁剪

independent-implementation

RemoveNode在root.gate内先删除effectiveParameters键，再从states.Remove取出value；离锁后仅当value实现IDisposable才Dispose，没有catch和RecordCleanupFailure。Dispose抛错时该node状态及参数已从这些字典移除，调用直接失败；重复RemoveNode找不到state就return，不自动重试旧对象。RetainProcedureNodes先批量删除不在keep中的全部参数键，再快照待移state键并foreach RemoveNode；其中一项抛错将中断剩余foreach，后续state仍可留在states，而其参数键可能已在第一阶段删除。

representation：节点状态字典移除、参数字典移除、对象Dispose完成分别发生，不能用一个成功/失败标记代替。

cache：没有被循环走到的state仍由root.states持有，可在之后的裁剪或root关闭进入其它清理；已移除但Dispose失败对象不由本分支自动放入failedResources。若它另被owned服务/外部持有，则还需单独判断。

release：单节点Remove/批量Retain与root Release有不同异常屏障；root Release的逐项继续保证不能外推到这两个入口。

closing是不是所有入口都关闭？

State/Enter和参数入口有自己的拒绝门；Service查询等入口不一定共用该门。租约只保护root Release，不能外推所有Remove。

CSR03 · root closing置位与API准入 / 租约 → 立即拒新状态与租约，不等于所有查询/删除都禁用

independent-implementation

root Dispose在gate下先设置closing=true再调用stopping.Cancel；State<T>、RegisterService、Enter与参数Parameters入口均以closing抛ObjectDisposedException。与之不同，Service<T>只锁gate查询，无closing检查：若活跃租约阻止Release清字典，它仍可在closing期间返回旧服务；Release清空后则返回null。ForProcedure只验证procedure字符串，可以继续生成borrowed view；RequestRun/RequestRefresh在closing直接返回。RemoveNode与RetainProcedureNodes没有closing或leases门，故root完整Release等待租约不能被概括成任何节点移除/替换都受同一租约保护。

representation：closing是操作级准入状态；cancellationComplete与leases控制root Release时机。借用view的存在本身不证明其API可继续使用。

cache：在Release前states/services可能仍保留；State即使只是想取已有值也先拒绝，Service查询则未使用同样策略。

release：Enter取得的Lease仅参与root TryRelease；Lease自身Interlocked.Exchange确保一次Exit。它不替代调用者在RemoveNode等入口的并发协调。

再调用Dispose会自动重试失败资源吗？

不会。closing/releaseStarted已置位，failedResources保留失败对象供诊断，源码没有把它作为自动重试队列。

CSR04 · 取消或资源Dispose异常后的root Dispose / Lease.Exit → root清理是一次性尝试；failedResources保留不等于排队重试

independent-implementation

Dispose设置closing后，stopping.Cancel抛Exception会RecordCleanupFailure(cancel,stopping,error)，finally仍设置cancellationComplete并TryRelease；不是因取消回调异常就跳过该finally。TryRelease要求closing、cancellationComplete、leases==0且!releaseStarted，在真正Release前置releaseStarted=true。Release对各IDisposable的Exception分别记录后继续下一资源，并单独尝试stopping.Dispose；这点现有CR06已有，本事实新增明确重试边界：root重复Dispose因closing立即return，后续Exit也因releaseStarted不再启动第二遍，failedResources只保留对象，所选类没有重试/清空该表的方法。

representation：CleanupFailures getter返回失败记录数组副本；内部failedResources保存真实资源引用。诊断快照与资源持有是两层。

cache：失败对象及其Exception可继续使资源图可达；保留到root仍可达不等于资源已释放，也不等于有后台重试任务。

release：Release前先清states/有效参数/services/ownedServices，失败不会把原索引恢复。普通单项Dispose抛Exception不会阻断后续项；但分配快照、RecordCleanupFailure自身异常或进程级故障等未被这一逐资源catch覆盖。
