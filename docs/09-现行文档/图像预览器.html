图像预览器部分未验

最后更新：2026-11-05·状态：部分未验·代码基线：71da36329·合并来源：10 篇历史方案与实施总结（清单见文末「历史演进」）

一句话结论

缩略图列表用节流并行加载（SemaphoreSlim 控制并发），不是用 lock 串行；滚动时取消离开视口的请求、优先当前视口；每个格子必须给出三态反馈（加载中 / 成功 / 失败可见可重试），不能留白块。持久化走内存实时同步 + 保存时统一落盘，不靠退出时一次性写。方案状态（打开/关闭）与预览器状态必须是同一份数据。

改前用户看到什么

  • 打开一个几百张图的方案，缩略图列表一片白块，往下滚才慢慢出来，滚动时卡顿明显。
  • 滚过去的缩略图还在后台加载，滚回来反而要重新等。
  • 某张图解码失败，格子永远是空白，既没图标也没提示，不知道是没加载完还是文件坏了。
  • 图像预览器里删掉的图，方案里还记着；或者方案里状态改过，预览器不刷新。
  • 关闭程序后重开，删除/新增的图又回来了。

改后应该是什么样

场景 期望行为
快速滚动长列表 离开视口的请求被取消；当前视口优先加载，不卡
并发 有限并发（不是串行，也不是无限并发）
单张解码失败 显示失败态 + 可重试，不留白
大图/异常图 降级解码，不整体崩溃
删除/新增图 内存立即反映，保存时统一落盘
方案状态变化 预览器同步刷新，不各存一份
重开程序 与上次保存一致

关键结构

缩略图加载流水线

关键点：失败必须可见。 白块是最差的状态——用户无法区分"没加载"和"坏了"。

持久化模型

  • 运行时只有内存一份状态，界面读它
  • 落盘统一在保存时发生，不在每次操作时零散写
  • 避免"界面一套、磁盘一套"导致的重开后回退

关键决策与理由

决策 理由 依据
用 SemaphoreSlim 节流并行，不用 lock 串行 lock 把解码串起来，列表越长越慢；无限并发则会打满线程池 20260818 ImageGlass 对齐 Phase A
滚动取消离开视口的请求 不取消就白做，用户滚回来还得重来 Phase B
当前视口优先 用户看哪里就先出哪里，这才符合直觉 Phase B（对齐 GalleryControl）
失败必须可见 + 可重试 + 降级解码 白块让用户无从判断；不降级会让一张坏图拖垮整列 Phase C
三态反馈放 XAML 加载中/成功/失败由视觉状态机表达，不靠代码临时改颜色 Phase D
内存实时同步，保存时统一持久化 边操作边写盘会产生大量中间态和不一致 20260818 持久化方案
失效资源允许清理 缺失资源若每次打开都报错，用户无法自救 20261008 §4

未验

  • 几百~上千张图的实际滚动流畅度无实测数据（没有帧率或加载耗时记录）。
  • 大图（数十 MB）、异常图（截断/损坏）的实际表现未记录。
  • 高 DPI、深浅主题下缩略图与三态图标的可读性未目视验收。

风险与遗留

  1. 三态反馈依赖每个格子都实现。 新增列表位置（例如结果视图里的图像列表）如果没接三态，就会重新出现白块。
  2. 取消语义要贯穿到底。 只在发起处取消、解码仍在跑的话，滚动快时仍会堆积任务。
  3. 内存实时同步意味着"未保存的改动"是真实存在的。 必须保证所有退出路径都会触发保存，或者明确提示用户已丢弃改动。
  4. 失效文件清理是手动入口。 且清理后方案里的引用要同步更新，否则下次打开又报缺失。
  5. 性能优化没有量化基线。 "不再卡顿"是主观判断，无法回归验证。
