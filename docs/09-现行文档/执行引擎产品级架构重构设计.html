ExecutionServer 产品级架构重构设计

目标：依据 VM 已确认的常驻服务、流程/模块会话、请求式 Run、结果回流和 UI 行为，重构 SunEyeVision 执行引擎。算法使用 HALCON，算法外的生命周期、数据、结果和显示语义尽量与 VM 一致。

版本：2026-11-15　唯一现行方案　范围：启动、方案会话、ExecutionServer、ExecutionCoordinator、Run/Trigger、输入工作区、结果投影、取消/异常/关闭和 UI 适配。

设计决策：这不是在旧 CaptureRunBatch → WorkflowExecutionEngine → ResultPublication 链上继续加缓存，而是建立新的深模块。外部只暴露请求、状态和结果订阅；执行模型由证据决定，拓扑只是候选内部实现，不作为原厂事实前提。
整合阅读主线：本文件依次包含原厂证据、VM/当前/目标差异、启动与方案加载、目标主链、目标 Run、执行引擎深模块、四类 UI 投影、数据/结果/关闭合同、实施顺序和验收矩阵。旧启动执行链文件仅为摘要入口，不再维护另一套目标描述。

第一部分：对比分析与重构决策

先看双方证据和差异，再进入目标设计。这里的“目标”是决策结果，不是把未经证实的 VM 内部实现当成事实。

核心问题VM 原厂SunEyeVision 当前自研决策
执行服务在哪里？Server/Proxy 常驻，UI 只提交请求和读取结果。宿主、工作流、工具会话和结果发布在单进程内协作。执行生命周期收回 ExecutionServer；UI 不拥有执行器。
Run 做什么？Run 是进入服务的请求入口。Run 入口还承担批捕获、快照、资源组织和调度准备。Run/Trigger 只提交请求；真实输入在服务内按代次冻结。
调度是什么？已证实服务异步执行、流程策略、触发入口和结果缓冲；内部拓扑尚未证实。当前使用自研执行器和依赖队列。采用中性 ExecutionCoordinator，不预设拓扑。
结果如何显示？结果对象按 ExecuteCount 回流，UI 分别投影。结果快照、Owner、Presenter、表格和图形曾有耦合。模块结果、当前结果、历史结果、帮助四条 UI 链独立管理。
为什么首次执行更慢？公共运行环境和模块服务提前常驻准备。更多每轮准备和宿主接缝在正式 Run 中发生。公共服务常驻，真实输入和算法资源按需准备并复用。
为什么关闭容易出问题？Server 统一排空、退订和释放。窗口、方案、运行、结果和插件资源分散。统一取消/排空/Owner 归还/服务退役顺序。
对比结论：真正需要重构的是服务边界、Run 入口、结果所有权和关闭生命周期；不是继续在旧 CaptureRunBatch 上叠加更多缓存。算法层仍使用 HALCON，算法外行为按 VM 对齐。

一、原厂对标基线

VM 证据产品级含义本次迁移对应
VisionMasterServer、ModuleProxy 独立常驻UI 不拥有算法执行生命周期，模块运行态由服务持有。ExecutionServer 拥有执行器、模块会话和结果存储；是否持有拓扑计划由后续原厂证据决定。
PreLoadOption=1、PreInitMVDOption=1启动阶段准备模块运行环境，不在每次 Run 重新建立。启动准入执行服务目录和必要公共初始化；不做模拟图像、ROI 或算子预热。
VmSolution.Load、VmProcedure.Run方案加载流程对象；Run 只是提交请求。方案加载建立 SolutionRuntime；Run 只提交 RunRequest，内部执行模型不预设拓扑。
模块结果和 UI 结果视图分离结果对象由运行服务持有，UI 读取结果。ResultStore 持有发布快照，UI 通过订阅取得投影。
VM 内部具体使用哪种入度队列、调度线程或 IPC 协议尚未全部恢复。本设计迁移的是已证实的职责和生命周期，不声称私有实现逐字等价。

二、目标分层

UI / Shell提交 RunRequest、订阅状态

ExecutionCoordinator按原厂模型协调 Run/Trigger

深模块职责不负责什么
ExecutionServer持有运行目录、流程会话、编译计划、模块宿主、调度器和结果存储；接收 Run、Cancel、Subscribe、Retire。不访问 WPF 控件、不解释 UI 选择、不直接读磁盘方案文件。
StructureModel保存流程、节点、端口和连接身份；只有原厂证据确认结构编译时，才由其生成不可变执行计划。不读取当前图像、不创建结果资源、不启动工具算法；不把拓扑编译当作已确认原厂行为。
ExecutionCoordinator根据取证确认的原厂模型协调流程 Run、全局脚本、外部触发和单模块入口；内部是否使用拓扑、事件或过程引擎暂不预设。不构造工具定义、不发布 UI 场景、不持有方案编辑对象。
ModuleRuntimeHost按模块身份持有工具定义和可复用会话，提供顺序/并发能力声明。不保存本轮输入、不持有结果发布 Owner。
InputWorkspace为一个 Run 代次冻结图像、ROI、屏蔽区、变量和宿主输入，节点按端口借用。不决定拓扑顺序、不发布结果。
ResultStore按原厂边界持有已完成结果代次和资源 Owner，并分别供模块结果视图、当前结果 Tab、历史结果 Tab 和帮助 Tab 的独立投影使用。不重放工具、不访问编辑器草稿、不把三个下方 Tab 合并成一个状态。

三、核心接口与候选内部计划

1. ExecutionServer

interface IExecutionServer : IAsyncDisposable
{
    ExecutionServerGeneration Generation { get; }
    SolutionRuntimeHandle OpenSolution(SolutionExecutionDescriptor descriptor);
    ValueTask RunAsync(RunRequest request, CancellationToken cancellation);
    ValueTask CancelAsync(RunId runId, CancellationToken cancellation);
    ResultSubscription Subscribe(ResultSubscriptionRequest request);
    ValueTask RetireSolutionAsync(SolutionRuntimeHandle solution, RetirementReason reason);
}

接口只暴露方案运行句柄、Run、Cancel、Subscribe 和 Retire。拓扑编译、模块会话、输入工作区和结果 Owner 都是内部实现，调用者无需知道其组合。

2. 结构计划（候选，不代表原厂已证实）

sealed record CompiledWorkflowPlan(
    WorkflowIdentity Workflow,
    StructureGeneration Structure,
    IReadOnlyList Nodes,
    IReadOnlyList Edges,
    IReadOnlyList Dependencies,
    IReadOnlySet InputConsumers,
    IReadOnlySet OutputProducers);
计划身份失效条件不失效的变化
方案会话 + 流程身份 + 结构代次 + 工具目录代次 + Schema 指纹节点增删、连线变化、流程变化、端口合同变化、插件目录退役。当前图像、变量值、ROI 数值、参数值和显示选择。

3. RunRequest

sealed record RunRequest(
    RunId RunId,
    SolutionRuntimeHandle Solution,
    IReadOnlyList Workflows,
    ConfigurationGeneration Configuration,
    HostInputRequest HostInputs,
    RunMode Mode,
    CancellationToken Cancellation);

RunRequest 只携带身份、运行模式和输入捕获请求，不携带 UI 控件、可变 NodeDefinition、已发布结果或 HALCON 对象。ExecutionServer 在接收后创建本轮 InputWorkspace 和轻量 RunState；是否绑定结构计划由原厂调度证据决定。

4. ResultSubscription

interface IResultSubscription : IDisposable
{
    ResultSubscriptionId Id { get; }
    event Action Event;
    ResultSnapshot? Current { get; }
    ValueTask AckAsync(ResultVersion version, CancellationToken cancellation);
}

UI 分别订阅模块结果视图、当前结果数据、历史结果查询状态和显示来源。相同 ResultVersion 的导航、缩略图、高亮和显示设置不退役结果；新执行产生新版本才原子替换。帮助内容不属于结果订阅，不触发执行或结果清理。

四、生命周期合同

对象创建存活释放禁止行为
ExecutionServer插件准入完成后创建。覆盖整个应用运行期。应用退出时停止接收新请求，等待所有方案和 Run 归还。不由 UI 页面创建或销毁。
SolutionRuntime方案安装成功后创建。方案会话存活期。方案切换/关闭时先排空 Run，再退役计划和模块。不持有编辑器草稿和 UI 控件。
CompiledWorkflowPlan结构变化时编译。结构代次有效期间。结构失效、方案退役或目录代次退役。不携带当前图像和结果资源。
RunState/InputWorkspace接受 RunRequest 后创建。本轮执行和结果提交期间。成功、取消或异常终态后释放。不跨 Run 保留旧 Frame、旧 ROI 或旧 Owner。
ResultSnapshot所有必需节点终态完成后创建。订阅者和历史记录仍需要时。所有订阅、显示和历史引用归还后释放。编辑或导航不能隐式清空仍显示的结果。

目标 Run：从入口到四类 UI 投影

阶段目标行为独立边界
1. 入口归一流程单次、全局脚本、连续运行、外部触发、单模块调试分别转换为 RunRequest/TriggerRequest，不假定它们共享同一原厂内部调度算法。入口来源与内部调度模型分离。
2. 输入准备图像源缩略图切换形成新的输入请求；冻结图像、ROI、变量和配置身份，记录输入批次。缩略图选择不是显示游标状态。
3. 服务执行ExecutionCoordinator 将请求交给原厂模型对应的服务执行路径；工具运行只产生模块输出，不直接操作 UI。算法由 HALCON 适配，调度语义不由算法决定。
4. 结果提交为本轮生成 ExecuteCount/ResultVersion，提交模块结果、当前数据、历史记录和可显示对象引用。模块结果、当前结果、历史结果不是同一个集合。
5. 模块结果视图按显示来源和 ExecuteCount 更新图像、图形、文本和结果树。不因当前结果 Tab 清空而销毁。
6. 当前结果 Tab只更新当前执行代次的数据表；行选中时按当前代次重新读取显示对象并执行高亮投影。行选中是显示投影动作，不重新运行流程。
7. 历史结果 Tab按页查询历史结果，使用独立 native 缓冲和释放流程。历史查询不覆盖当前结果，也不清空模块结果视图。
8. 帮助 Tab按模块类型/语言刷新静态帮助内容。帮助切换不触发 Run、结果查询或结果清理。

六、迁移策略

阶段实施内容退出条件
S1 合同和骨架新增四个深模块接口、身份类型、RunState/ResultVersion、取消/退役语义；建立内存 ExecutionServer。不接 UI 时可用测试 RunRequest 完成一次 ImageSource→Blob。
S2 原厂模型对应的执行协调在调度模型证据闭合后，把现有执行入口迁入 ExecutionCoordinator；只有原厂证实拓扑时才引入拓扑计划，否则按事件/过程/混合模型落位。同一入口重复 Run 不重复创建不必要的服务状态；模型和计划身份与证据一致。
S3 模块宿主和输入工作区把 RuntimeDirectorySnapshot、ToolSessionLease 和输入捕获接入 ModuleRuntimeHost/InputWorkspace。会话按能力复用，取消/异常/方案切换无租约泄漏。
S4 结果与 UI 投影把结果提交迁入 ResultStore，但分别接入模块结果视图、当前结果 Tab、历史结果 Tab 和帮助 Tab；四者不共享清空/更新触发器。图形、文本、当前结果行、高亮和缩略图切换按各自合同更新。
S5 UI 切换主窗口 Run、连续执行、取消、关闭和方案切换改用新 ExecutionServer；删除旧执行路径。旧 WorkflowExecutionEngine 不再作为生产入口，单一执行链完成全场景验收。
S6 进程隔离将内存 ExecutionServer 替换为独立进程/IPC 适配器，保留同一四个接口。UI 与算法服务可独立重启，RunRequest/ResultSubscription 合同不变。

七、验收矩阵

场景必须证明
首次 Run / 后续 Run首次只支付原厂模型要求的服务/会话/输入创建；后续复用边界必须由证据确认，不能预设拓扑计划。
参数/ROI 编辑不执行编辑生成新配置代次，当前 ResultVersion 和显示保持。
结构变化拓扑计划失效并重编，旧 Run 停止，旧结果按身份清理。
连续运行同一 SolutionRuntime 和原厂确认的执行协调状态复用，RunState/输入/结果按代次隔离。
取消/异常不再入队的新节点停止；在途会话、InputWorkspace、ResultOwner 全部结算。
节点/方案切换旧 SolutionRuntime 退役，迟到事件不能写入新会话。
关闭程序batches=0 / engines=0 / sessions=0 / resultOwners=0，ExecutionServer 正常退役。
不保留双轨：S1–S4 迁移期间允许通过 Adapter 接入现有工具，但生产入口一旦切换到 ExecutionServer，旧 CaptureRunBatch → WorkflowExecutionEngine → ResultPublication 路径必须删除或降为测试 Adapter，不能长期并行维护两套执行语义。

八、实施前的原厂执行引擎逆向前置门槛

当前状态：本设计已经固定目标职责和接口方向，但 ExecutionServer 的实现不得在原厂执行引擎闭包取证前开始。现有 VM 证据足以确认服务常驻和 Run 入口，尚不足以确认私有调度器、拓扑编译、数据传播、回调和关闭状态机的完整行为。
取证层必须闭合的原厂问题最小证据出口对目标设计的影响
启动/服务VisionMasterServer、ModuleProxy、模块服务的创建顺序、线程/进程归属、失败重试和就绪信号是什么？启动日志 + 入口反编译 + 服务/代理调用闭包。决定 ExecutionServer 是否需要独立进程、何时接受 RunRequest。
方案/流程对象VmSolution.Load 后创建哪些 Solution、Procedure、Module、Port 和连接对象？哪些对象跨 Run 常驻？Load 调用链、对象构造/注册/退役和方案切换证据。决定 CompiledWorkflowPlan 和 SolutionRuntime 的持有者。
拓扑编译流程图何时编译；节点、连接、输入输出端口如何转换为运行计划；结构变化如何失效？Procedure/Graph/Module 相关类型、构造者和结构变化调用链。决定是否有独立 WorkflowCompiler 及其计划身份。
拓扑调度Run 后按什么规则入队、解除依赖、处理独立分支和模块触发？是否有固定序、优先级或并发上限？Run→调度器→模块执行的完整调用闭包或动态运行日志。决定 TopologyScheduler 的状态机、并发合同和结果顺序。
输入/数据传播图像、变量、ROI、模块输出如何从上游传到下游；是借用、复制、共享内存还是序列化？端口绑定、数据容器、模块输入设置和释放证据。决定 InputWorkspace、借用租约和跨进程传输策略。

取消/异常停止/取消是立即终止、协作排空还是服务级中止；失败后模块和流程如何回到可运行状态？Stop/Cancel/Exception/Retry 调用闭包及状态日志。决定 RunState 终态、资源退役和重试合同。

取证完成判定

  • 每个层次都有同版本原厂证据、调用入口、消费者和释放出口。
  • 拓扑调度的未知项必须标成“未证实”，不能用本方实现反推 VM 语义。
  • RunRequest、ResultSubscription 和 ExecutionServer 的最终接口要在取证矩阵收口后定稿。
  • 取证阶段只读原厂材料和运行证据，不修改产品执行代码；取证闭口后再按 S1–S6 实施。
因此当前动作顺序调整为：原厂执行引擎完整取证 → 依赖闭包/状态机/数据所有权矩阵 → 定稿四个深模块接口 → 建立可替换 ExecutionServer 骨架 → 迁移拓扑计划和调度 → 迁移工具/结果/UI → 删除旧生产入口。

十、总一致性原则：算法可替换，算法外行为尽量一致

目标不是“保留现有自研执行链再做局部优化”，而是按 VM 的产品级行为重建 SunEyeVision 的宿主与执行基础。唯一允许存在稳定实现差异的主边界是算法执行：SunEyeVision 通过 HALCON 适配层实现工具算法，VM 使用其自研算法库。算法之外，除必要的程序集、品牌、文件路径和 HALCON 类型适配外，应尽量保持原厂的生命周期、状态、数据所有权、调度、结果和 UI 语义。

领域一致性要求允许的最小适配禁止的偏离
启动与常驻服务按原厂的启动页、欢迎页、方案会话和常驻执行服务边界组织。SunEyeVision 自有进程名、品牌和插件目录。把服务初始化下沉到窗口、节点或每次 Run。
方案/流程/节点身份保持方案会话、流程、节点、端口和连接的稳定身份及生命周期。映射到 SunEyeVision 自有合同类型。用 UI 对象或临时字典代替运行时身份。
拓扑执行保持结构计划、依赖传播、就绪调度、并发策略和取消语义。节点执行体内部调用 HALCON。以当前自研队列的偶然顺序反推原厂语义。
输入与数据保持输入快照、端口传播、结果代次和资源所有权边界。图像/区域在 HALCON 与公共合同间转换。在 UI、工具或结果表之间隐式复制、清空或跨 Run 持有。
结果与显示保持执行代次、当前结果、历史结果、图形/文本、高亮和订阅更新语义。用 SunEyeVision 展示控件承载同一结果合同。切换缩略图、Tab 或参数时隐式清空上一次结果。
关闭与异常保持取消、排空、结果归还、模块退役、服务关闭顺序。适配 .NET/WPF 资源释放。窗口关闭直接等同于方案/服务销毁。
实施门槛：只有当原厂执行引擎的拓扑调度、数据传播、结果提交和关闭生命周期证据闭合后，才按上述一致性原则定稿 ExecutionServer；HALCON 只替换算法内核，不替换算法外的产品级执行语义。

十一、调度模型不得预设：拓扑只是待证伪假设

修正前提：现有材料证明了流程、模块、端口、触发配置和 Run/结果回调的存在，但还没有证明原厂内部以“拓扑计划 + 就绪队列”作为唯一或主要调度模型。因此 TopologyScheduler 只能作为候选职责名，不能作为已确认的原厂架构结论。

候选模型现有证据线索尚缺的判别证据当前状态
拓扑/数据流驱动流程拥有模块和连接，存在 IO/Link 类型，结果按流程回调。Run 后是否建立节点依赖图、何时解除依赖、分支是否并发、连接是否直接驱动下游。候选，未证实
事件/触发驱动存在 Execute_Procedure、Execute_Module、全局触发流程配置和输入 IO/边沿信号。外部触发是否直接进入服务事件总线；事件如何选择流程、模块和输入批次。候选，未证实
过程脚本/命令驱动VmSolution.Run 进入 GlobalScriptStartRunOnce，而流程单次入口另有 VmProcedure.Run。脚本是总调度器、触发器还是仅包装 native 请求；脚本与模块依赖的边界。候选，已见入口未闭包
服务内部混合模型ServerSDK 同时暴露流程策略、可重入、模块结果缓冲和异步状态回调。这些合同在 Server/Proxy/native 内部如何组合，是否按流程、触发和模块分别走不同路径。最需要验证

取证顺序调整

  1. 先固定每个入口：流程单次、全局单次、连续运行、外部触发、单模块调试。
  2. 对每个入口沿同一 Run 实例追踪：请求进入、输入绑定、模块调用、状态回调、结果提交、结束和释放。
  3. 只有观察到“连接/依赖解除驱动下游执行”的证据，才把拓扑调度确认为核心；否则按事件/脚本/服务混合模型设计。
  4. 在模型定稿前不命名、不实现 TopologyScheduler 为生产核心；目标接口先使用中性的 ExecutionCoordinator 语义。
当前结论：原厂执行引擎的核心仍需从入口动作反向追到 Server/Proxy/native 的真实调度机制。现阶段只能确认“服务化、流程级策略、异步结果回流”三类外部合同，不能确认“拓扑驱动”这一内部模型。

十二、最新取证判断：当前更接近“入口/事件 + 服务异步执行”，尚不能称为拓扑调度

继续检查现有原厂证据后，出现了比“拓扑调度”更直接的线索：全局脚本入口的 StartOnce 将编译/初始化和 CodeRun 放入 Task.Run，提交后立即返回；外部触发配置把输入 IO、边沿信号和目标流程写入光源模块参数；另有独立的 Execute_Procedure、Execute_Module 和 Execute_Module_Action 消息结构。这些证据支持“命令/事件进入常驻服务，服务异步执行”的判断，但仍不能证明服务内部没有拓扑或依赖调度。

已观察到的事实对模型的影响仍需证明
全局脚本 StartOnce 异步提交任务，任务体等待编译/初始化后进入 CodeRun，上游命令立即返回。执行入口不是 UI 线程上的同步拓扑遍历；存在服务/任务层异步边界。CodeRun 内部是否调用流程依赖调度、模块消息链或 native 过程引擎。
全局触发可编码执行流程、执行模块和模块参数动作；光源触发把 IO、边沿和目标流程写入模块参数。原厂至少存在事件/命令驱动入口，不能把“点击 Run”视为唯一驱动源。事件进入服务后的排队、去重、并发和与流程 Run 的合并规则。
流程策略包含线程/CPU、可重入和模块结果缓冲。执行服务具有独立于 UI 的资源和并发控制面。策略如何作用于单流程、模块和触发批次，以及是否由同一调度器落实。

显示链也必须单独取证

显示不是结果提交的同义词。现有原厂证据显示，ModuleResultView 订阅流程异步状态和模块回调；ExecuteCount 决定取哪一代结果；RenderDataCenter 以 display/buffer/spare 三个仓交换图像与图形；Dispatcher 再更新图像、图形、数据列表和结果树。参数或显示选择变化时，视图可按已有执行代次重新取值，不必重新运行。这条“结果提交 → 显示投影 → 导航/高亮”的链必须与执行调度分开验证。

显示阶段已确认行为待补证据

显示投影Dispatcher 更新所选图像、形状、数据列表和结果树；非运行参数变化可主动刷新当前结果。结果表行与图形高亮的身份映射、历史结果选择和跨 Tab 保持规则。
显示关闭Dispatcher 关闭开始时停止 RenderThreadPool，RenderDataCenter.DeInit 清仓并清选择引用。显示订阅者释放与 Server/Proxy 结果 owner 退役之间的先后关系。
因此暂不定性：现阶段的最稳妥抽象不是“拓扑执行器”，而是“常驻执行服务 + 多种 Run/Trigger 入口 + 内部未知调度器 + 分代结果提交”。内部调度器可能使用拓扑，也可能使用过程引擎、消息驱动或混合机制；必须继续取证后再决定重构模型。

十七、VM 原厂、自研现状与目标执行引擎对照

维度VM 原厂设计SunEyeVision 当前自研设计目标设计

方案会话VmSolution 持有 Procedure、Module、IO 和服务状态，方案加载/切换有独立回调。DocumentSession、工作流和 UI 状态之间承担了部分会话职责。SolutionRuntime 统一持有方案、流程、节点、端口和运行身份；编辑器草稿与运行会话分离。
运行入口流程 Run、全局脚本、连续运行、外部触发、模块命令等多入口进入服务。Run、连续执行、调试和图像源操作存在多条宿主入口。统一转换为 RunRequest/TriggerRequest；入口差异保留，服务内部合同统一。
调度模型外部证据确认服务异步执行、流程策略、可重入和结果缓冲；内部是否拓扑尚未证实。以自研工作流执行器和批捕获链组织运行。ExecutionCoordinator；内部按原厂证据接入事件、过程、拓扑或混合模型，不预设拓扑。
算法执行模块服务调用 VM 自研算法。工具运行时直接组织 HALCON 调用及参数适配。ModuleRuntimeHost 管理工具会话，HALCON 只替换算法内核，算法外执行语义保持一致。
输入传播由 Server/Proxy/Module IO 合同传递图像、变量和模块输出，具体复制/共享边界待 native 闭包确认。输入快照、宿主请求和工具输入由多层对象协作。InputWorkspace 在 Run 开始冻结真实图像、ROI、变量和配置；工具不读取 UI 可变状态。
结果提交结果带 ExecuteCount，通过异步回调和结果缓冲回流。结果发布、表格、图形和显示层之间存在多条适配路径。ResultStore 生成 ResultVersion/Owner；提交与显示投影分离。
模块结果 UIModuleResultView 显示图像、图形、文本和结果树，按 ExecuteCount 投影。模块结果和显示状态曾与执行刷新、Tab 切换发生耦合。模块结果视图独立订阅结果代次，不因当前结果/历史结果切换而清空。
当前结果 UICurResultTabItem 独立绑定当前结果集合；选行后按当前 ExecuteCount 重绘并高亮图形。当前结果表更新与结果显示曾存在混用风险。CurrentResultProjection 独立更新；选行只触发显示投影和高亮，不重新执行。
历史结果 UI独立查询历史结果，分页处理并显式释放 native 缓冲。历史结果与结果发布缓存曾存在清理边界混淆。HistoryResultProjection 独立查询/释放，不覆盖当前结果和模块结果 Owner。
帮助 UI按模块类型和语言生成帮助内容，不参与执行和结果查询。帮助显示与模块视图生命周期绑定。HelpProjection 独立刷新，只随模块/语言变化更新，不触发 Run 或结果清理。
关闭生命周期停止运行、退订回调、关闭渲染线程、释放历史/结果缓冲，再退役 Proxy/Server。窗口、方案、运行和结果资源存在交叉释放风险。停止接收请求 → 取消/排空 Run → 退役结果订阅 → 释放显示投影 → 退役模块会话 → 关闭 SolutionRuntime/ExecutionServer。

十八、启动执行链差异摘要（现行基线）

本节取代独立的启动执行链现行方案。启动、方案加载、Run、结果发布和关闭的差异统一在本文件维护；原启动执行链文档仅保留为摘要入口，不再承载第二套目标设计。

阶段VM 原厂SunEyeVision 当前自研目标设计
启动EXE → 启动页 → Server/Proxy → 模块准备 → 欢迎页。EXE → 启动页 → 插件准入/公共初始化 → 欢迎页。EXE → 启动页完成服务与插件准备 → 欢迎页；不读取用户图像、不执行工具。

输入准备服务/模块对象读取当前帧、变量和模块输入。每轮组织输入快照、ROI、变量和宿主请求。InputWorkspace 按执行代次冻结真实输入；编辑不会污染在途 Run。
结果与显示常驻结果对象异步更新，UI 读取结果。结果快照、Owner、Presenter 和表格/图形显示由多层协作。ResultStore 提交 ExecuteCount/ResultVersion；模块结果、当前结果、历史结果、帮助分别投影。
关闭停止运行 → 退订回调 → 关闭渲染 → 释放历史/结果 → 退役 Proxy/Server。窗口、方案、运行、插件和结果资源需要显式排空。停止接收请求 → 取消/排空 Run → 退役四类 UI 投影 → 释放结果/会话/方案 → 关闭 ExecutionServer。

统一差异结论

  • 最大的架构差异是 VM 将执行器、模块会话和结果对象放在常驻服务内，而当前自研链把更多准备和发布职责放在宿主进程中。
  • 目标不是增加更多用户可见步骤，而是把必要的生命周期和所有权边界收回 ExecutionServer 内部。
  • 拓扑不是已确认的原厂内部模型；目标使用中性 ExecutionCoordinator，待证据确认后接入真实调度方式。
  • HALCON 只替换算法内核，启动、方案、输入、结果、显示和关闭语义按 VM 对齐。

关闭停止、退订、渲染关闭、历史/结果释放、Proxy/Server 退役。窗口、方案、插件、运行和结果资源需要显式排空。按 ExecutionServer 统一退役顺序，最终计数归零。
