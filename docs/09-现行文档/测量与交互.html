测量与交互部分未实施

最后更新：2026-11-05·状态：部分未实施·代码基线：71da36329·合并来源：58 篇历史方案与测试报告（清单见文末「历史演进」）

一句话结论

测量是6 张独立工具卡（点-点 / 点-线 / 点-圆 / 线-线 / 线-圆 / 圆-圆），每张卡固定 2 个卡尺槽，卡尺各自独立配置、默认绘制模式、可订阅上游几何。工具本身不调 Halcon / OpenCV，只做纯 C# 几何运算。位置修正是测量的地基：绑定不改坐标、切图不改坐标、只有用户真正编辑图形才逆变换写回参数。工程链已跑通，但运行轮次 / 基准版本、统一撤销历史、其他 ROI 编辑器推广尚未完成。

改前用户看到什么

  • 量点距、点线距、线线夹角、圆心距，要靠写脚本或串多个检测工具再人工换算，没有统一 UI，没有 OK/NG，也没有可视化。
  • 位置修正场景下：打开工具窗口、什么都不改、直接点执行，结果就错位。同一个工具走工作流入口是对的，走工具调试入口是错的。
  • 先绑定位置修正再画 ROI，图形会突然跳走；先画再绑定，坐标也被偷偷改了。
  • 已经跑完的历史结果，改了当前参数之后重新绘制，历史结果跟着变，看起来像"测量结果不稳定"。
  • 顺时针 / 逆时针、旋转 90 度、2 倍缩放的圆，拖动中心会落到错误位置（要 X=360 却落到 330）。

改后应该是什么样

场景 期望行为
量点距 / 圆心距 / 线线夹角 选卡片、图上画两个图形（或订阅上游）、直接出数值 + OK/NG
先绑位置修正再绘制 在当前图像绘制，按矩阵逆变换存为参考坐标，画面不跳
先绘制再绑定 保留已画的位置参数作为参考坐标，按当前矩阵更新显示；不弹转换选择、不自动逆转换
打开窗口 / 刷新 / 切图 不改任何 ROI 位置参数（中心、角度、尺寸全都不动）
用户拖动图形 才按逆变换写回参考参数，且整体事务提交、失败全不变
上下游矩阵更新 更新运行上下文，不迁移参数
临时关闭位置修正 保留参考 ROI，显示未修正位置，开启后恢复
矩阵无效 / 未匹配 / 图像帧不匹配 明确拒绝修正编辑并说明原因，不用单位矩阵或旧矩阵伪装有效
改当前参数重绘历史结果 历史结果几何不变（引导圆、卡尺半宽/半长/数量已冻结）
拖动中切图或换基准 取消未提交编辑，不出现按下一套矩阵、松手另一套

关键结构

测量卡片形态

卡片 ToolId 项目 输入
点-点 SunEyeVision.Tool.PointPointMeasure 点 + 点（点只走订阅，不可绘制）
点-线 SunEyeVision.Tool.PointLineMeasure 点（订阅）+ 线（订阅/绘制）
点-圆 SunEyeVision.Tool.PointCircleMeasure 点（订阅）+ 圆（订阅/绘制）
线-线 SunEyeVision.Tool.LineLineMeasure 线 + 线
线-圆 SunEyeVision.Tool.LineCircleMeasure 线 + 圆
圆-圆 SunEyeVision.Tool.CircleCircleMeasure 圆 + 圆

ROI 坐标三层归属（核心契约）

三个不变量（违反任一条就是 bug）：

  1. 绑定不改 ROI 位置参数
  2. 打开窗口、刷新、切图不改 ROI 位置参数
  3. 只有用户实际编辑图形才通过逆变换更新参考参数

位置参数包含中心、角度、尺寸及相关几何数据，不只是 X/Y。

对象 归属与转换
未启用位置修正的 ROI 按原参数直接显示和使用；关闭修正不转换数值
已建立修正关系的 ROI 保存参考坐标 + 参考关系身份
算法使用的区域 / 引导 参考几何经本轮有效矩阵转换到当前图像
交互图形、卡尺、手柄、命中 同一上下文与形状规则
鼠标编辑写回 当前图像坐标逆变换为参考坐标
拟合结果、测点 已属当前图像坐标，禁止再次修正
视口缩放 / 平移 独立显示变换，不写入 ROI 参数

执行侧取证口径（最容易出错的地方）

  • 预览值不作执行权威数据。圆查找曾经的错位根因就是：工作流入口执行前主动填了 CurrentValue，而调试入口从绑定恢复的对象只有路径、没有当前值，算法把「启用的修正」当成「无修正」静默执行。
  • 图像帧谱系由 SDK 以弱关联保存（帧标识 + 结果实际输入帧标识），不序列化、不加可绑定输出、不持有图像。它是帧谱系，不是运行轮次也不是模板版本。
  • 帧身份不一致 → ImageFrameMismatch，禁止修正编辑与算法执行并提示重新匹配；来源结果在查询中被替换则等待，不接受跨代值。

未做

  • 运行轮次与模板基准版本：结果只带帧谱系，没有轮次身份与基准版本，同一帧不同轮的结果无法区分。
  • 统一事务历史（撤销/重做）：目前只有"编辑中矩阵变化就回滚"这一局部保护，不是统一撤销栈；多 ROI 编辑的事务提交未闭环。
  • R4 完整参考几何与图像/轮次上下文：圆—圆只补齐了引导/卡尺片段。
  • R5 推广：共享 MeasureEditorControl 的不可用保护当前只有圆—圆接入，检测区、屏蔽区与其他 ROI 编辑器仍按旧逻辑。
  • 把所有拟合输出改为不可变类型。
  • 历史结果图层的混帧治理（当前编辑与历史结果不混帧已做，跨工具推广未做）。
  • 非等比缩放/剪切的明确拒绝在全部工具上落地（目前是契约层要求）。
  • 正式执行在无源结果时的兼容回退（读绑定缓存）未移除，属已知残留路径。

风险与遗留

  1. "跑通了"不等于"三层同源"。 多轮批次都是"圆—圆先行验证"，其他 ROI 编辑器尚未接入公共保护入口。看到圆—圆正确就认为测量全体正确是误判。
  2. 预览与执行是两条取值路径。 已用同一份 NodeResults 快照收敛，但调试侧仍走实时查询、且保留了无源结果时回退绑定缓存的兼容分支。这条回退是旧矩阵误配的入口，需要后续清理。
  3. 帧谱系不等于运行轮次。 同一帧被两轮使用时，现有机制无法区分，历史结果可能被误解为同一轮。
  4. 直接 Bitmap 旁路与未接入谱系的插件不在保障范围。 这类插件仍可能出现"显示的图和参数里的图不是一张"。
  5. 无统一撤销。 多 ROI 编辑取消、失败的原子性依赖各编辑器局部实现，跨工具行为可能不一致。
  6. 构建环境问题曾经卡住验收。 中间目录写入拒绝这类环境问题会被误当成代码问题，需要单独记录排查入口（隔离 WorktreeBasePath、关 XML 文档生成）。
