相机与采集部分未实施

最后更新：2026-11-05·状态：部分未实施·代码基线：71da36329·合并来源：14 篇历史方案（清单见文末「历史演进」）

一句话结论

相机走五层分离：Plugin.SDK 只定契约，DeviceDriver.Camera 实现厂商对接，App 负责装配，UI 只管管理和展示，Workflow 只用统一采集服务。当前实际只有一条工业相机通道（内部对接海康 MVS，#if MVS_SDK_AVAILABLE 条件编译），模拟相机只在测试里用。新增第二家厂商只需加适配器，不动上层。

改前用户看到什么

  • 相机管理、预览、工作流各自持有设备对象，同一台相机被重复打开，第二个入口报占用失败。
  • 关掉设备管理器或预览窗口，连接莫名其妙断了，正在跑的工作流取不到图。
  • 保存方案重启后，相机按名称匹配重新绑定，改名或换台同型号机器就绑错。
  • 参数一律当字符串/布尔处理，PixelFormat 这类枚举被 Convert.ToBoolean 弄错。
  • 换一家厂商的相机，要改 UI、改工作流、改业务流程。

改后应该是什么样

场景 期望行为
同一台相机被预览和工作流同时使用 复用同一个连接会话，不重复打开
关闭设备管理器 / 预览窗口 连接保持，只有退出、切方案、主动断开、删除设备才释放
保存方案后重启 按 DeviceId / 序列号 / MAC 重新绑定，改名不影响
相机离线或 SDK 缺失 明确报错，主界面照常进入（不卡启动）
参数读写 按声明类型（Boolean / Integer / Float / String / Enumeration / Command），不猜
触发源枚举 读当前值 + 设备枚举符号名归一化；符号名缺失或未识别拒绝采集，不猜
新增厂商 只加发现器 + 适配器 + 工厂，UI 和工作流零改动

决策 理由 依据
契约层不出现任何厂商类型 一旦泄漏厂商类型，UI/工作流就会被绑死，新增厂商必须改上层 20260925
同一 CameraDeviceRef 只允许一个会话 预览、工作流、管理器共用一台相机，重复打开必然冲突 20260925 §3

持久化只存身份 + 配置 连接对象不可序列化，且状态属于运行时 20260925 §4.2

风险与遗留

  1. #if MVS_SDK_AVAILABLE 是编译期开关。 未定义时适配器行为需要明确：必须报"未启用工业相机支持"这类可辨识错误，不能表现成"扫描不到任何相机"让用户以为设备坏了。当前文档未记录该分支的实际表现，属待验项。
  2. 只有一条厂商通道，没有第二家验证中立性。 现在的"契约中立"是设计上的，没有第二家厂商跑过，可能仍有隐藏的厂商假设（例如参数默认值、传输方式枚举）。
  3. 加载等待 10 秒是固定值。 相机数量多或网络慢时会拖慢启动；反之设备很快连上也要等满才继续（若实现是串行等待）。需要按实际体验确认是否改成并行 + 提前返回。
  4. 方案重绑依赖三种身份之一。 若某厂商既不提供稳定序列号也没有 MAC（例如纯 IP 连接的虚拟相机），重绑会退回不稳定匹配，需明确该场景的策略而不是默默按名称。
  5. 模拟相机不在装配中。 想在无相机环境演示，需要改代码注册 SimulatedCameraDiscoveryProvider，没有配置开关。
