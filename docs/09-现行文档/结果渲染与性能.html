结果渲染与性能部分未实施

最后更新：2026-11-05·状态：部分未实施·代码基线：71da36329·合并来源：28 篇历史方案与实施总结（清单见文末「历史演进」）

一句话结论

结果呈现走的是契约驱动路线：插件通过 ResultDisplayDescriptor / ResultProjectionDescriptor / ResultGeometrySnapshot 描述"该怎么显示"，UI 侧 ResultWorkspacePresenter / ResultPresentationPresenter / ResultDispatchQueue 负责渲染与调度。但 2026-09 那批「统一空间索引 + 批量 Geometry 提交 + Tile 候选索引」的大批量渲染方案，在当前工作区没有对应实现——ResultRenderLayer、ContourRecord、RenderGeneration、Tile 索引均 0 命中。性能指标也没有实测记录。

改前用户看到什么

  • 结果图形一多（几千条轮廓）就卡、掉帧，缩放平移明显滞后。
  • 调试预览的结果和正式工作流的结果混在一起，清掉调试预览后正式结果也没了。
  • 同一份结果在不同窗口显示不一致（工具调试窗、结果视图、全屏预览各画一套）。
  • 切换图像或重新执行时，旧结果图形还留在画面上一会儿。

改后应该是什么样

场景 期望行为
几千条轮廓 缩放/平移无卡顿；同一轮廓一次渲染只画一次
一次结果刷新 只启动一次有效缓存构建，不因连续两次 Set 触发两轮
调试预览 vs 正式结果 分开管理；清理调试预览后正式结果仍可恢复
结果呈现 各窗口读同一份描述符，不各自解释
缓存未完成时 不静默回退到逐轮廓阻塞路径
图像/轮次不匹配 明确不混帧、不混轮次

方案设计的目标模型（未落地）

设计中的统一渲染链是：

结果提交 → 建立 ContourRecord + 空间索引 → 视口查询候选
        → 按 ID 去重 → 按 OK/NG·颜色·线宽·填充分组
        → 每组合并 StreamGeometry → 少量 DrawGeometry

核心思想：Tile 只负责找轮廓，Geometry Batch 负责合并，DrawingContext 只提交少量批次，全视口与局部视口共用同一套逻辑。

当前工作区实测：ResultRenderLayer、ContourRecord、RenderGeneration、TileKey、SetDisplayCollector、SetRegionItems 全部不存在。存在的 UI/Services/Rendering/ 只有画布相关：CanvasRenderer（工作流画布节点/连线）、GeometryOptimizer（连线几何缓存）。

关键决策与理由

决策 理由 依据
结果呈现用描述符 + 快照契约，而不是让工具直接画 工具不该依赖 WPF；同一份结果要能在多个窗口显示 结果呈现契约
历史结果携带几何快照 否则改当前参数会让历史结果跟着变，看起来像"测量不稳" 20261014 / ResultGeometrySnapshot
调试预览与正式结果分开管理 混在一起时清理调试预览会误删正式结果 20260921
结果分发走队列 + 租约 直接回调会在 UI 线程堆叠，且难以取消 ResultDispatchQueue / ResultDispatchLease
缓存构建按代次取消旧任务 连续两次 Set 会启动两轮构建，前一轮白做 20260922 §5
Tile 只做候选索引，不做绘制单位 以几何块为绘制单位时，视口只要覆盖一小块就整块绘制 20260922 §2
全视口与局部视口共用同一套查询/去重/分组 两套算法必然行为不一致 20260922 最终原则
暂不引入 GPU 后端 先用空间索引和提交次数解决量级问题，再按真实数据决定 Direct2D/D3D11 20260922 §9

未做

以下均为 2026-09 系列方案的核心内容，当前工作区未找到实现：

  • ResultRenderLayer 统一渲染层
  • ContourRecord + TileKey → ContourId 空间索引
  • RenderGeneration 代次取消与合并刷新
  • 按 OK/NG / 颜色 / 线宽 / 填充分组合并 Geometry
  • 少量 DrawGeometry 批量提交
  • 点/十字/矩形/圆/文字的轻量空间索引
  • SetDisplayCollector / SetRegionItems 刷新合并（这两个 API 本身也不存在）

这些方案可能落在其他 worktree（例如 20261014 文档提到的 SunEyeVision_V2-comm）或已被后来的契约化路线取代。在确认之前，不能把"批量渲染已优化"当结论。

未验

  • 3000 / 10000 条轮廓在适配窗口、放大、缩小、平移、切图像时无明卡顿——无实测记录。
  • 候选轮廓数 / 去重后轮廓数 / 最终批次数 / 缓存命中率 / 绘制耗时没有指标输出。
  • 双渲染层幂律缩放治理的最终效果无复测记录。
  • GPU 相关方案（D2D/D3D11）仅为评估，无结论。

风险与遗留

  1. 方案与代码脱节（最高）。 28 篇文档里最核心的一批（空间索引、批量提交、代次取消）在当前基线找不到实现。任何基于这些文档的"性能已优化"判断都不成立，必须先确认代码在哪个分支。
  2. 结果呈现分散在多个 Presenter。 ResultWorkspacePresenter、ResultPresentationPresenter、MainWindowResultPublication、ResultImagePane 各自处理一段，容易出现"某个窗口没跟上新契约"。
  3. 几何快照是逐工具接入的。 圆—圆已冻结引导与卡尺几何，其他工具是否都产出快照没有逐个确认，未接入的工具改参数仍会让历史结果变化。
  4. 调试预览隔离依赖队列与租约的正确使用。 绕过队列直接发布的结果不受生命周期管理。
  5. 没有性能指标。 没有耗时/批次/命中率输出，就无法判断是"已经够快"还是"还没优化"。
