通讯工具链部分未实施

最后更新：2026-11-05·状态：部分未实施·代码基线：71da36329·合并来源：21 篇历史方案（清单见文末「历史演进」）

一句话结论

通讯分成两条互不合并的路径：设备收发在「通信管理」里配事件、流程内用「接收数据 / 协议解析 / 协议组装 / 发送数据」四个工具拼链。核心链路（TCP 四工具闭环）已跑通并部署 Release；被动报文已改为一条报文只能被同一节点成功接收一次，不再复用最新报文。统一变量传递（U1~U3）与六项设计优化未实施，排在工具链之后。

改前用户看到什么

  • 同一个接收节点连续执行，反复读到同一条最新报文，看起来"有数据"，其实早就是上一条；对端不再发新数据时无法区分「没数据」和「有数据」。
  • 等待期间继续显示上一轮的成功结果，看不出这一轮还在等。
  • 接收到的原始字节被当成字符串 Hex 显示，字符串、字节两种输入混在一起，配置时不知道该选哪个。
  • 变量绑定和接收订阅各记一份，界面上改了绑定，编译器用的还是旧的。
  • 直接绑定全局变量时，等待时机对了但取到的是启动时的初值，不是本轮结果。

改后应该是什么样

场景 期望行为
第二轮不再发数据 接收节点保持执行中等待，不复用上一轮报文
第二轮发同样的值（连发两次 7） 识别为两条新报文，分别满足两次接收
执行前已到达两条 按顺序各取一条，不是只留最新
等待中 节点显示「等待中」，不把上轮结果显示成本轮有效结果
下游解析/组装/发送失败 不自动回滚消费、不重放旧报文，避免重复业务副作用
缓冲溢出或坏报文 明确报告缺口/失败，不静默跳过后仍宣称逐条交付
接收原始数据 TCP/UDP/串口与 Modbus 都输出 BinaryPayload，Hex 只是显示
OPC UA 读数值 保留原生 Integer/Double，可直接绑定下游，不必先转字符串

关键结构

两条路径（不合并）

同名 out1 不表示同一字段，两条路径不隐式复制。事件只决定流程是否启动；工具按所选来源在节点执行时取数。两者共用底层解析核心与网络连接，不建第二套连接、不争抢数据。

各来源的执行契约

来源 每次执行的取数方式 无新数据 / 异常
TCP / UDP / 串口 顺序取本节点尚未消费的完整报文 无未消费报文 → 保持执行中；来源失效 → 明确失败
Modbus / OPC UA 主动读 复用连接实际读一次当前值，相同值仍有效 按协议超时/质量/错误规则处理
无生产者的全局变量 读节点执行时的当前集合 校验存在性与类型
有生产者的全局变量 取生产者本轮成功结果 不回退上轮值或设计初值

被动报文的消费身份

  • 消费身份 = 稳定工作流 ID + 稳定调用节点路径 + 子流程 ID；不用显示名、不用每轮 RunId
  • 报文新旧依据会话 + 递增序号，不看载荷内容
  • 各节点是独立订阅关系：一个节点消费不推进别人的游标
  • 消费者上限 4096；新身份不继承其他节点进度

关键决策与理由

决策 理由 依据
事件与工具不合并为一条路径 输出身份（EventId/FieldId vs NodeId/字段键）、执行时机、用途都不同，合并会引入隐式复制 20261012 基线
被动报文改为逐次消费 复用最新报文会让"没数据"伪装成"有数据"，无法判断真实触发 20261014 方案（取代旧规则）
原始载荷统一 BinaryPayload，Hex 仅展示 TCP 传的是字节，不保证是字符串；提前转 String 会丢原始信息并误导配置 20261012 §3
解析输入同时接受 String 与 Binary 上游可能是接收节点的 Binary，也可能是原生 String，过滤掉任一类都会断链 20261012 §3
取消「报文年龄」参数与隐藏超时 年龄限制会静默丢数据，且与"等新报文"语义冲突 20261014
坏报文不静默跳过 跳过等于吞数据，用户无法知道丢了什么 20261014 §4
一个变量只有一个生产来源 多生产者会产生不确定的赋值顺序，冲突必须提示而非覆盖 20261012 变量传递
字节编号 0 基、区间闭合 与配准一致性，避免 0/1 基歧义 20261012 §4
默认数值规则：1~3 字节非负、4 字节有符号，可显式覆盖 贴近常见 PLC 约定，同时允许工程覆盖 20261012 §4
接收成功后下游失败不回滚消费 回滚重放会造成重复业务副作用（例如重复写 PLC） 20261014 §4
事件 ASCII 与模块 ASCII 解释刻意不同 事件先严格校验 ASCII 字节再按二进制字段规则；模块按字符转换（字符 1 得到 49 和 1）。这是项目定义，不冒充复现 VM 内部算法 20261012 §5

风险与遗留

  1. 逐次消费是运行时状态，不写回设计参数。 程序重启或方案重载后不恢复旧报文，用户会看到"重启后要重新发数据"，属预期行为，需在帮助里写清。
  2. 坏报文会一直阻挡该消费者。 这是刻意的（不静默跳过），但没有显式"丢弃并继续"入口，现场遇到持续坏帧会卡住，需要后续补一个明确的丢弃/调试入口。
  3. 溢出恢复只能重载方案。 达到消费者上限（4096）或缓冲容量后没有优雅恢复路径。
  4. 事件 out 仍不会自动变成节点输出，用事件触发流程时若要在流程里用同一份数据，需要走接收工具另取一次，可能取到不同报文。
  5. U1~U3 未实施，所以「直接绑定」与「接收入口」两条取值路径行为仍不完全一致：等待时机可能正确但读到初值。
  6. 官方帮助只确认来源与轮询行为，未披露 VM 内部的依赖、快照与等待实现。本项目规则是自定契约，不能当作 VM 行为的证据。
