## 全平台重构的证据协作（2026-11-02）

适用于按目标源码树进行的全平台重构，与既有单元级取证和唯一写者规则一起执行。VM 原件是设计和行为对照的依据；目标源码树、接口及未证行为的自研处理分别标明为本项目设计，不把建议目录或静态条件路径写成原厂已实现或全场景事实。

1. **批次证据基线。** 每个实施批次先读取相关逆向资料的最新状态，登记 VM 版本和原件身份、文件/方法及必要哈希、参考文档路径与版本或可复核快照、本方基线和受影响消费者。动态更新的页面不以文件名或时间单独证明内容一致；首次取证与后续更新均保留可追溯记录。
2. **整链提问。** 本项目先查现有材料，把影响同一完整功能链的缺口合并、去重，写清要作的设计决定、已查范围、缺失证据、影响、所需交付及环境限制，按既有约定经逆向负责人集中协调。跨对话发送仍遵循用户明确授权；不把多个小问题逐项排队或要求逆向方替本项目设计。
3. **回件与采纳。** 逆向方提供对象版本及身份、源码/反编译/机器码或运行证据位置、入口到消费/退出的路径、成立条件、反例或未覆盖分支和限制；实机回件另记录版本、操作、样本及观察。本项目核对后，按“VM 已证、推断、未确认、自研假设”分开写入原方案与覆盖台账，并将设计、代码与测试的处理结果对应到具体条目。未回件或仅发送请求不能算取得证据。
4. **持续更新与变更影响。** 批次实施期间和正式集成前重新核对该批依赖的证据版本；新证据推翻原结论、改变调用条件或暴露遗漏时，集中记录旧结论、新证据、受影响合同/文件/消费者、占位替换位置和需要重新执行的验证，再按完整功能链修订。无关更新不触发重做，也不能把正在实施的产品代码当成逆向事实。
5. **并行和收口。** 逆向工作提供证据，不修改本项目产品代码或替本项目决定架构；本项目负责适配、实施、构建和自测。各工作区同一时间一个写入者，按已授权的独立 worktree 构建验证，不等待主仓日常构建窗口；主线集成验证与独立结果分别记录。证据充分且基础具备的工作继续，不因其他缺口或文档持续更新而全线等待。
6. **缺口与假设。** 当前 Windows 环境下已穷尽可用静态取证仍无法确认的具体行为，按既有“自研假设占位”规则标明假设、影响、替换位置和修正条件；缺基础入口不可误用。仅有某一方向尚未验证或未做实机测试，不足以认定静态取证已经穷尽；有具体可追的源码、机器码或可用替代环境时，针对该点继续取证。

全平台批次依赖与验收清单见 [全平台目标源码树重构计划](evidence/全平台目标源码树重构计划-20261102.html)。本补充不授权跨对话发送、运行原厂程序或替其他工作区写入；已有用户授权按其范围持续有效。

## 本项目与逆向项目怎么分工

### 设计取舍：开发阶段不背旧兼容包袱

产品尚未正式发布。不得为了兼容旧开发方案、旧接口或旧测试而牺牲合理架构；需要改变时直接替换或删除，并同步调整真实消费者与测试，不保留两套算法、合同或过渡产品路径。适配只为现行宿主集成、明确外部合同或用户指定需求服务，须说明实际用途和退出条件。旧代码、旧证据和失败记录保留在Git及文档历史中，不把它们变成必须维持的产品设计。

该原则同样用于VM对标：VM是设计和验收的第一基准；本方已有实现按与VM行为是否一致及实际用途判断去留，不因旧代码或旧接口存在而保留。用户明确要求的差异和平台必要适配须单独记录，不能静默改变VM行为。

| 对话 | 负责什么 | 交付什么 |
| --- | --- | --- |
| 本项目实施对话（技术总监） | 明确需求和取证问题；以VM为设计及验收的第一基准，依据证据确定本方必要适配；在主仓实施、测试、管理代码和交付。 | 可运行成果；原主文档中的阶段总结、效果、验证及剩余问题；向用户主动报告实际进度和预计时间。 |
| 工作流独立对话 | 在已授权独立worktree负责工作流、主界面及图像源消费/宿主接纳；共享接口与主仓按完整链协调。 | 本线候选、来源基线及消费者清单；同步、集成与验收状态分别记录。 |
| 逆向项目 | 由下列三个既有对话分别统筹、源码分析与实机验证。不修改本项目产品代码，不替本项目决定架构。 | 通过取证统筹对话集中交付可定位证据、已确认结论、未确认项及影响；详细材料留原处，仅交付必要记录。 |

逆向主程序保留三个既有对话，不能把项目间单一联络入口误解为逆向侧只剩一个角色：

| 逆向侧既有对话 | 职责 |
| --- | --- |
| 逆向负责人｜VM取证统筹 | 接收明确问题，复用现有证据，安排源码或实机取证，检查覆盖范围、矛盾和缺口，集中反馈成果与预计时间。 |
| 逆向工程师｜VM源码分析 | 查原件/反编译、控件和模板、依赖及完整消费链；给出具体源码位置和静态结论，不能以静态材料冒充实机行为。 |
| 验证工程师｜VM实机取证 | 在静态证据不足或实际行为影响决策时，用最小场景验证；记录版本、操作、样本、观察及限制，不能代替本项目 Release 验收。 |

本对话直接向取证统筹提出问题、核对回件并采用结论；本项目不恢复交付经理、文档岗或额外转发层。逆向任务须附用户授权原文和来源对话，避免把已授权协作误判为无权消息；如回复通道仍受限制，应明确报告限制并保存成果，不把“已发送请求”算作“已取得证据”。

以一个完整控件或用户指定的完整功能链为实施单元，先集中取得该单元所需VM证据和可执行方案，再统一实施并集中测试；测试发现未证分支或不一致时，针对失败补证、修复并重新验证。不同单元可在职责与写权不冲突时并行取证和准备，不将同一单元拆成单个小功能反复取证、改动和测试。缺少会影响完整方案的关键证据时标清范围与影响，不凭猜测补齐。

| 事项 | 约定 |
| --- | --- |
| 何时取证 | 单元实施前先集中复用已有材料，补齐影响该控件或功能链完整实施的证据；统一测试发现缺口时再定向补证，不重复全面逆向。 |
| 问题怎么提 | 明确完整控件或功能链范围、已有证据、缺口和所需方案；覆盖入口、原件及依赖、模板、组装、全部适用状态和交互、数据流、退出清理及验收，不能按单个小功能逐次派发。 |
| 方法怎么选 | 结构、接口、声明、依赖和组装链先查源码或反编译材料。交互、时序、动态选择、渲染和资源释放等实际行为，在静态证据不足、存在矛盾或结论依赖运行效果时做实机取证；静态证据足够的结论不强制重复运行。 |
| 什么算证据 | 标明对象与版本、原件位置及必要的文件身份、文件/类/方法或模板位置、调用或消费关系。实机证据补充样本、操作、预期和实际结果，以及必要截图或日志。注明原始源码、反编译、声明或运行观察，结论分为“已确认、推断、未确认”；截图不能单独证明内部实现。 |
| 何时停止 | 足以回答当前问题并支持决策即停止，不无限扩大范围。查不到时记录已查范围、缺口、影响和最小补证办法；不能把“尚未找到”写成“确认不存在”，也不能据此直接判定删除。 |
| 结果怎么用 | 新证据统一存主仓，沿用已有证据目录；正文用简明结论、理由、影响和未知说明，详细来源可定位。阶段性集中更新原清单、去留表和工程图，替换过时结论，保留历史材料；不每有小变化就重写整份文档。 |

## VM优先的实施与验收合同

- **先查现有能力并做复用决策。** 每条完整链列明VM证据、本方已有实现位置及行为对应、差异、复用／调整消费者／替换核心的决定和生产验收出口；原资料足够即实施，只有会影响决定的具体缺口才补证。不按类名判断能力，不重复逆向已明确内容，不以反复定位回调替代整批交付。
- **两种图像源回执分开。** 正式配置接纳与冻结图像实际读取接纳分别核身份、状态、资源寿命和失败取消；旧投影退役不代表正式配置未接纳，Task正常返回也不代表图像被消费。工作流独立线负责取用合同及完整执行链，可在其工作区先行实施并记录基线和消费者；双方在正式集成前共同核对，未确认内容不称为已集成或验收。主仓控件线继续处理视觉组合，不因等待即时回复停止独立工作。
- **只报告可证实进度。** 批次状态分列已验证、待集成、本批交付、未实现及依赖、待人工验收；没有源码盘点及依赖依据不承诺工期。试用版本冻结期间不关闭、构建或替换，反馈集中修复。
- **先核完整链路，整批交付。** 以完整控件或功能链为单位，实施前集中查清VM入口、原件和依赖、模板组装、状态与交互、数据流、退出与资源清理，并形成可执行方案和同态验收清单；然后统一实施、集中测试，测试不通过再针对失败补证和修复。不同单元可以并行取证，不把一个单元切成小功能轮流试错。对已确认、推断和未确认行为分别标注，不靠截图推断内部实现。
- **原件优先。** 控件、模板、图标、布局和交互优先复用或按VM原件实现；本方代码行为一致即可复用，局部不一致集中调整，核心机制不符才替换。不得用相似外观冒充原件完整交互。
- **宿主负责适配。** 通过非视觉适配连接现行字段、引用、执行和资源合同，保持原控件职责；不让VM交互迁就旧SDK可视控件或旧接口。适配涉及跨模块时按项目架构边界核对影响。
- **差异显式记录。** 用户确认的屏蔽区多形状支持、HALCON等平台必要差异，以及其他经确认的产品选择，记录差异内容、原因、影响和对应验收；其余未证行为区分具体可追证据与已穷尽静态手段的自研假设占位，不冒称VM事实。
- **先同态对照，再验本方链路。** 先核同一页面、状态和操作下的VM与本方表现，包括原件组装、交互和清理；再核本方实际执行、保存重开、取消及资源生命周期。静态证据、实机对照、自动测试、VS设计器和用户人工验收分别记录；没有实测的项目不代签。

该合同同时适用于控件库、Blob和工作流相关功能；各对话仍按既有唯一写者和独立分支边界工作。存在证据缺口时，仅对已有证据支持的范围作决定，并记录补证需求。

## 三岗成果如何核收

- 源码岗交具体文件、入口到消费/退出链、原件与恢复件身份、未证分支；区分本人本次成果、可复用历史材料和归属未确认材料。文件中的role元数据不能单独证明作者或本次交付。
- 实机岗交实际版本与窗口身份、操作、观察、截图/日志和限制；没有受支持通道时，明确未执行、缺什么及解除条件，不用安装文件身份、静态模板或准备清单顶替实机证据。
- 统筹逐项核收两岗实际回件，附路径、身份、作者/来源、结果与缺口；原任务未覆盖或回复偏题应退回。由本人补做的审计须注明，不能冒称两岗均已完成，也不用一个百分比合并静态和实机状态。
- 本项目总监独立核对后才采用并统一原方案。窗口/控件/样式调整先有视觉方案和对应证据；功能自动通过不代表UI达标，HTML原型也不代表WPF已实现。用户人工验收只记录真实反馈。

取证优先读取现有原件，不再复制整套项目或运行库。VM运行观察使用其原有程序；本项目的自动和手动测试仍统一使用主仓正式 Release，原始取证材料不等同于本项目验收通过。
