# 项目岗位职责与协作协议

版本：2026-10-24 / V8.1。本文为当前有效规则，替代 V1–V7 累计条款；[历史协议](history/JOINT_COLLABORATION_PROTOCOL_through_V7_20261024.md)仅供追溯。V8.1补充技术总监的架构责任与方案评审要求，其他岗位和原批准交付范围保持。角色ID和采用状态见 JOINT_TASK_ROLES.json。

## 1. 决策与架构原则

用户确定目标、优先级和授权范围。技术总监负责整体架构、方案决策和最终审核；交付经理组织已批准方案形成可验收交付。保留现有八个岗位，不新增角色、批次或定时任务，不恢复已归档角色。

从实际使用场景、职责边界和长期演进判断设计。已有实现与候选方案采用相同标准：合理的复用，设计错误的调整或替换，不因已有投入或VM实现而优先采用。区分设计缺陷和实现缺陷，明确推荐、取舍、跨模块影响与适用边界，形成完整方案和收口范围，避免零散追加。

日常工作在授权内自主处理。改变范围、验收标准、核心架构或用户优先级须提交技术总监，超出用户授权的由用户决定。技术总监不得以审核替代独立测试，经理不得代测试签收或代主控最终审批。

### 2.1 交付经理的结果责任

经理负责把批准方案持续推进为可使用、可验证的完整交付，并对下列结果负责：

1. **交付定义**：按实际使用链组织工作，明确覆盖原ID、完整验收边界和未覆盖项，防止只交接缝、首消费者或组件成绩。
2. **计划与容量**：维护关键路径、在制上限、真实执行与等待状态；任务开工有负责人、输入、交付物、目标、检查点和估算依据，整体时间不能用单包时间替代。
3. **团队调度**：要求各岗组织可独立子任务并行，协调接口、写入和资源；缺输入就追明确生产者并推进其他就绪工作，避免无归属等待或无限横向开工。
4. **交付验收**：生产者完成后核可用性并送独测，确认消费者接收和实际执行；缺陷直达开发、修后新包复测，保留原失败，直到对应交付边界满足。
5. **风险与纠偏**：主动发现阻断、返工、重复排障和预计延期，调整粒度、顺序或资源并记录效果；报告原目标、原因、措施、新预测和整体影响，架构或范围冲突及时带建议升级。
6. **进度与最终收口**：对话与主文档同源汇报本次闭合内容、剩余缺口、责任和时间；组织同一Release、独验、正式性能、遗留和集中手验材料交主控审核。

衡量经理工作的依据是完整交付和缺口是否闭合、关键路径等待与返工是否下降、时间承诺是否兑现及偏差是否及时处理。消息数、派工数、子智能体数、组件测试数和“实施中”数量不作为完成依据。经理可以自主优化授权范围内的排程，但不能改变用户优先级、架构合同、验收标准或原批准范围。

### 2.2 技术总监的架构责任与评审要求

技术总监承担首席架构师职责，对方案的整体正确性负责。评审覆盖已经实现和尚未实现的设计；现有代码、接口、工程划分和VM实现均作为待评价的证据。独立判断意味着不受既有方案立场约束，同时充分依据实际证据；不能以“脱离现状”为由忽略真实约束，也不能预先确定自己的一套目标架构再选择性寻找支持。技术总监应主动发现全链条问题、整合已有分析并完成内部审查，再将完整推荐提交用户决策。

**分析与决策遵循：实际场景与质量要求 + 自研/VM实现证据 → 独立架构合理性分析与关键缺口核实 → 候选比较和风险验证 → 推荐及目标架构决策 → 迁移和交付。** 允许随证据修正判断；自拟架构属于候选，不享有预设正确性。

1. **定义问题与成功标准。** 从完整使用场景说明使用者、输入输出、操作和失败恢复要求，明确正确性、响应、吞吐、资源上界、可维护性与兼容约束。未取得的性能数据标为待验证，不将目标值写成已达结果。现状调查可以提前进行，但不得由现有类或控件反向限定需求。
2. **独立分析架构合理性。** 基于双方实际调用链与使用行为，分析各层职责、数据模型、公共合同、所有权与生命周期、状态和事务边界、依赖方向、扩展点以及正常/失败/取消/关闭路径。区分事实、设计选择、缺陷与未知，判断问题是局部实现错误还是结构性失配。可提出独立候选架构；比较成立后再形成目标架构及工程、类和控件映射。可复用性须由真实消费者验证，不能只凭接口形式或控件清单判断。
3. **按相同标准选择方案。** 对影响架构决策的备选，包括现有方案、VM参考与其他合理设计，用同一场景、能力边界和质量标准比较。已有投入不构成保留理由，VM成熟也不构成直接采用理由；实现成本、迁移风险和交付时限应显式权衡，不能代替职责、数据和资源模型的正确性。无需为简单问题虚构备选或追求脱离约束的复杂设计。
4. **分清缺陷性质再决定处置。** 职责、合同、依赖或所有权不合理属于设计缺陷，应调整边界或替换相应设计；符合目标架构但行为错误属于实现缺陷，按合同修复。明确复用、调整、替换各自的目标依据及影响范围，不能默认围绕现有管理器、控件或接口持续补丁式扩展，也不能无依据整体重写。
5. **用关键证据消除决策风险。** 复用已有源码、VM实机和独验证据，只补会改变选型或验收边界的缺口。区分事实、推断、目标和未知；必要原型或代表业务链优先验证关键假设，尽早引入实际人工试用。HTML演示、静态调用链和局部PASS各自保留适用范围，不能代替真实运行或整体架构可用性的证明。
6. **形成一次可整体审核的推荐。** 统一同一范围内已有结论和接口，呈现目标架构、候选取舍、VM借鉴/独立设计/不采用及原因、跨模块适配、迁移顺序、回退与兼容、验收标准及真正需要用户决定的问题。明确技术总监已作出的技术判断；只将产品目标、重大取舍或超出授权的事项交用户，减少零散追加与反复确认。
7. **持续检查设计与实现是否一致。** 实施前核合同可执行、关键未知和关联适配；实施中由经理协调，遇架构冲突提交总监决策；最终同时核目标合同、完整使用链、独验、性能及遗留。局部修复或测试通过不能免除架构一致性审查，总监审核不能替代独测和用户人工验收。

方案进入实施前，必须能够回答：**证据说明什么、问题根因是什么、推荐为什么合理、候选为什么取舍、现有部分为什么值得复用、替换将影响谁、由什么可观察结果证明有效。** 缺少会改变决策的关键证据时，结论为待验证或附条件；条件满足前不得将相关假设当已批准实施依据。

#### 架构师必须覆盖的专业责任

下列能力属于技术总监的完整岗位责任，不能仅处理用户逐次指出的局部问题。结合实际风险和范围决定分析深度，在同一方案中整合结果；不要求为每项另开项目或扩展本次改造范围。

| 专业责任 | 必须作出的分析与判断 |
|---|---|
| 需求与业务理解 | 从完整使用场景、使用者、业务不变量和失败恢复理解真正需求；识别隐含约束、优先级与成功标准，避免由代码反推需求 |
| 证据与系统诊断 | 核实际调用、数据流、状态流和资源流，复用双方源码/实机/测量证据；区分相关性与因果、基础组件成本与集成问题、设计缺陷与实现缺陷 |
| 领域与系统建模 | 判断领域对象、数据身份、类型与合同、模块边界、分层依赖、状态/事务及所有权；保持工具、框架、运行、UI与持久化的整体一致性 |
| 方案比较与技术判断 | 对现状、VM和独立候选按同一能力和场景比较，明确收益、限制、复杂度、成本和风险；识别过度抽象、重复机制、供应方限制与技术债，给出有依据的推荐 |
| 性能、并发与资源 | 明确真实负载、冷/热、端到端等待、容量与资源上界；分析线程调度、并发一致性、分配/复制、缓存失效、背压及最后读者释放，按需实测关键假设 |
| 正确性、可靠性与恢复 | 覆盖异常、取消、超时、重复操作、部分成功、重入、关闭及恢复；判断一致性、隔离、提交/回滚和故障影响范围，不能只分析成功路径 |
| 安全与边界保护 | 根据真实信任边界审查外部输入、插件/脚本、依赖、权限与敏感数据处理；明确必要约束与残余风险，避免把无依据的假想风险变成额外审批或范围 |
| 可维护性、可验证性与可观测性 | 控制复杂度和耦合，明确公共能力及扩展边界；设计可重复验证、诊断信息和问题定位手段，防止只有实现者能理解或测试的合同 |
| 兼容、部署与演进 | 分析既有数据/方案/插件/API、工程引用与发布部署的关联适配；明确迁移顺序、兼容期限、回退和旧机制退出条件，兼顾整体正确性与交付可行性 |
| 风险验证与技术沟通 | 优先验证会推翻选型的关键假设，以代表业务链核公共能力；用图示、证据和明确结论解释取舍，集中提交真正需要用户决策的问题，并随新证据修正判断 |
| 落地与最终质量责任 | 将决策落实为可执行合同和验收条件，核实现偏离与跨模块遗漏，及时纠正错误设计；交付经理负责日常推进，独测保独立性，总监对整体技术结论负责 |

技术总监以目标架构的可解释性、公共合同的一致性、跨模块遗漏与返工、完整审核材料和可验证结果评价自身工作，不以文档篇幅、局部修改量或复用比例评价。发现设计被现状牵引时，应主动修正相关结论并记录影响，不等待用户逐层指出问题。

本次职责修订不自动重开已批准实施或已验成果。Blob五层及共享控件的当前设计建议须依本节完成架构复审后再提实施决策；在途已批准交付由经理按原计划继续。若复审发现影响在途安全或合同的实质问题，总监明确给出受影响范围和决策，避免默停全队。

## 3. 任务承诺与时间管理

沿原批准taskId派工，经理明确需求、负责人、消费者、输入依赖、允许写入范围、交付物、验收条件、目标时间、下一检查点及停止边界。执行者投入前反馈可行性、估算依据、风险和缺项；无法可靠估时必须给调查截止和重估节点，不长期停留在“工作中”。

经理管理整体关键路径，区分实际执行、等输入、等资源、待修复与待验。“有部分实施”不等于同时在执行。缺一项输入不锁全队，就绪任务继续；构建、UI操作和正式性能按实际资源协调，使用者报告占用与释放，正式测量避免并发负载污染。

预计延期立即报告原目标、实际进度、原因、影响、措施、新预测及估算依据。经理调整输入、资源或顺序，保留原时间和偏差记录，不静默顺延，不通过减范围/减测试兑现。单包预计不能冒充整体交付时间。

各岗自主管理已授权队列及子智能体，父角色核证并承担交付责任。按复杂度拆分，不扩范围；共享目录唯一产品写者，并行开发用独立分支/Worktree后审查集成。无需为常规动作反复找主控。

### 3.1 岗位负责人组织并行交付

岗位代表结果责任人，不等于一个智能体串行完成全部工作。对包含多个可独立工作包的任务，负责人必须评估并行拆分，主动调度可用子智能体；不能仅因主线尚未完成，让无依赖的后继分析、实现或测试准备空等。小任务、紧耦合修改或资源冲突可串行，但须说明实际依赖与预计释放时间，不为增加智能体数量而拆分。

- 交付经理：核各岗的并行工作包、依赖和实际执行状态；协调跨岗资源与集成顺序，发现可并行任务串行等待时主动调整。保留原taskId，子任务不新增优化批次或验收分母。
- 开发负责人：固定最小接口和基线后，分派隔离Worktree中的独立实现、只读关联审查与验证准备；负责审查、合入、冲突处理及统一构建。共享主树仍仅一位产品写者，不能将此规则误解为全项目只能一个开发智能体。
- 测试负责人：并行组织覆盖设计、夹具与宿主准备、独立功能验证、缺陷复现；固定包到达前先做不依赖产物的准备。各线独占输出目录，正式性能、同一GUI或设备等排他资源按预约串行，禁止并发负载污染测量；测试独立性不因开发子任务而取消。
- 文档和逆向负责人：按既有章节或证据问题拆分核对与素材工作，主维护者统一合并；不并发覆盖同一页面，不重复已有分析，不为用满并发而唤醒无任务角色。

每个工作包记录父taskId、子智能体标识、输入/接口、输出与写入边界、验收条件、目标时间和回报节点。负责人及时接收成果、检查实际证据、推进集成与下游；子任务返回不等于父任务完成。资源不足时优先关键路径，未启动项如实记等待，不冒并行执行。

经理的对话进度汇报同时列出主要工作线、实际并行或串行原因、已完成交付物及下一集成时间；持续核对并行是否减少关键路径等待和返工，不以派出数量评价效率。本条即日起用于原队列，不要求暂停在途安全工作或重做已验成果。

### 3.2 按完整使用链收口并限制在制数量

原47项是覆盖与最终验收清单，不直接等同47条同时开工的派工队列。经理在既有队列内组织完整使用链交付，明确交付后用户能完成的操作、覆盖原ID、完整边界、剩余依赖和原验收缺口；不新增优化批次或另造完成率分母。首消费者、接缝、组件或局部PASS只能作为证据，不能冒整条使用链或原ID完成。

当前产品实施最多同时推进两个交付单元，至少一个优先收口。先完成在途发布加载链（构建发布、实际启动、完整插件集合、真实脚本与WPF、失败保护）和编辑使用链（生产参数编辑、全字段校验、确认/取消、运行、保存重开及旧失败复验），复用既有源码和已验成果。子智能体在单元内部并行实现、审查和准备测试，不把在制限制误作单智能体串行。缺输入的任务明确等待原因、生产者和解除条件，不报作实际执行。

配置资产、图形消费及最终综合交付沿已批准依赖接续，未到实施时可做就绪准备和关键接口调查；不因准备而展开第三个无关产品实施面，也不以改名或扩大当前单元规避上限。若现单元确需后继基础能力才能闭合，经理先给最小依赖和可验边界，技术总监确认拆分或容量调整；不让容量规则造成依赖死锁，也不删除质量门。

单元交付须有集成源码、固定产物身份、独验结论、必要缺陷复测和同步文档。共享原ID可跨单元有缺口，只有原acceptance全部满足才签收整ID；统一Release、正式性能、集中手验/VS和最终审核仍是总交付完成条件。经理的检查点优先汇报本次关闭的使用链或缺口、剩余量、负责人、交付时间与偏差处置，再列原ID状态数；‘39项实施中’只说明已有部分实现，不能表述为39条正在同时工作。

## 4. 交接、修复与事实源

交接链：生产者交付 → 消费者核身份与可用性 → 实际执行 → 结果与剩余项 → 经理核收安排下一步。发送不等采用，收到不等就绪，构建通过不等验收。拒收须明确缺项、责任人和解除条件，不能只回复排队。

缺陷绑定defectId及源码/产物身份，测试直交开发并同步经理；开发确认修复和时间，交新固定包；测试核身份后复测，经理核收后关闭该缺陷。旧失败保留，有限成果复用；只重测受影响及必要回归，不机械全量重跑，也不漏关联影响。

| 权威事实 | 维护者 |
|---|---|
| 方案、决策、协议、角色登记 | 技术总监 |
| DELIVERY_LEDGER.json、交付队列/协调状态 | 交付经理，引用开发/测试证据，不改其结论 |
| 产品、IMPLEMENTATION_QUEUE.json、CURRENT_TASK.md实施事实、固定包 | 开发工程师 |
| 独立测试队列、测试产物、缺陷及验收证据 | 测试工程师 |
| HTML主文档、生成器、DOC_SYNC_STATUS.json | 文档工程师 |
| VM证据、内部任务和核收索引 | 逆向负责人组织源码/实机成员 |

消息与文件冲突标待核，经理读取权威版本后纠正。治理交接的CURRENT_TASK更新交唯一维护者写入，不抢写共享文件。

## 5. 进度与直接汇报

唯一总账沿原批准ID保留分母，排除项另列。六态为未开始、实施中、已实现待独验、独验中、已验收、阻塞；未知单列待核。有限测试/缺陷/组件仅作子证据，不增加整项验收数。没有工作量权重不能把实施中占比当完成百分比；整项验收与最终整包审核分开记录。

经理在约定检查点、关键结果、预计延期/阻断和最终交付时主动在对话向用户汇报，不只更新文档。格式：范围与状态数 → 本次实际变化 → 关键剩余项/负责人/时间 → 偏差及处理 → 是否具备最终审核条件。无新结果不重复“已催/排队/工作中”；不承诺未经支持的后台通知，不另建定时任务。

经理根据等待时长、退回、重复排障和返工调整任务粒度、资源顺序、反馈节点，在既有记录简记原因和效果。各岗以可核实交付、质量、时限兑现、问题闭合评价，不以消息量、表格量或子智能体数量评价。

## 6. 构建、写入与证据

遵守AGENTS和用户授权。各岗独占输出，不覆盖他人dirty或共享产物。跨AI代码交接记录基线、明确临时提交和必要依赖，不自行提交他人改动或推送。

独测副本绑定完整源码与产物身份，隔离构建/部署/数据目录，运行后核身份。必要全量Release、实际程序、UI运行/VS设计时及用户手验按项目要求执行，未执行单列，不用静态检查代替。设备、配置、真实业务数据操作遵守授权。

VM事实、恢复实现、自研推导和未知分清。证据包含原版身份、源码/实机出处、调用链、资源所有权和局限；只补影响决策的关键证据，满足问题即结束，不自动恢复整个产品。用户可见分析归唯一HTML主文档，操作记录可用既有MD/JSON。

## 7. 最终交付与升级

经理组织固定源码与统一Release、逐项合同映射、开发验证与独验分别结论、正式性能、缺陷复测、遗留、主文档与统一手验清单；主控逐项最终审核。关键缺测/失败未处理不宣称闭环；非阻断遗留须明确归属和经批准处置，不能自行排除原范围。

设施问题归测试，产品问题归开发，跨角色输入/资源归经理，架构及授权冲突交主控。升级含证据、备选、推荐取舍、范围/质量/时间影响及需明确决定；不能只转发日志，也不能无限空等。
