Blob 同构优化：最终方案

2026-11-19　·　目标不是"长得像原厂"，是"第 11 个工具接得进来"

一句话目标

让新工具接入 ROI 编辑的成本从 570 行降到 60 行，接入参数声明的成本从 200 行降到 10 行。

衡量标准不是"和 VisionMaster 文件一一对应"，而是"平台替工具承担了多少"。

一、先看清原厂有两条独立通道

这是 172 个类继承 NameValueItem 查出来的，不是猜的。

通道 A：参数总线

  • 承载：数值、字符串、ROI 二进制
  • 形态：string / byte[]
  • 取法：InnerGetStringParamValue(名字)
  • 写回：InnerSetStringParamValue(名字, 值)
  • 谁用：172 个 NameValueItem 子类

通道 B：桥接方法

  • 承载：图形、图像、结果列表
  • 形态：对象引用
  • 取法：GetDisplayObjectOperation(名字)
  • 谁用：Object / Feature（16 个显示对象）
ROI 属于通道 A。证据：ROISelecter.cs:1156 new MemoryStream(CurValueA) — CurValueA 就是参数值（byte[]）， 控件里的 RoiByteData 只是反序列化缓存。

二、我们和原厂的真实差距

不是"有没有总线"，是数据结构由谁定义。

#差距原厂本方证据
G1 ROI 记录结构定义在工具里 由平台定义（ROIType + ROIBox 等结构体），72 个模块共用 由 Blob 定义（BlobLocalRoi 四层类型在 BlobRoi.cs） BlobRoi.cs:58-90
G2 显示对象装配写在代码里 Display.xml 声明 16 个对象外观 + Tab_Image Display 声明挂载清单 BlobDisplayUi 40 行硬写 7 组；BlobDisplay.xml 被拿去装表格列 BlobParameters.cs:1424
G3 其余 9 个工具没有参数声明 每个工具都有 Algorithm.xml 参数全在 C# 里，0 个 XML 全仓扫描 0 命中
G4 UI 装配零测试覆盖 — 140 个测试全在数据层/执行层 测试清单
G5 参数值多份投影 一份（引擎参数表） 草稿 → 冻结 → InputValues 三次投影 FieldSettingsDraft / FieldSettings / InputValues

二·五、Blob 用的其他共享控件要不要都接总线

Blob 引用了 9 个平台命名空间、约 30 个类型，看起来很多。按职责分三类：

类别类型读写参数？怎么处理
参数字段 DeclaredInputFieldsView(15)、DeclaredFieldsView(5)、DeclaredFieldRow(6) 是 阶段 4 改统一入口，控件零改动
ROI 编辑 NativeRoiEditor、NativeRoiSession、RoiEditProposal/Snapshot/Acceptance、NativeRoiUiDraftControls、NativeAssistUiDraftControls、RoiDeclarations(11) 是 阶段 1 结构标准化解决
纯渲染 NativeIntegerRadioChoice(5)、NativeResultViewport(2)、DeclaredSettingsView(5，容器不存值) 否 不用接
结论：没有一个控件需要单独改。参数字段共用一个读写入口，ROI 走结构标准化，纯渲染类根本不碰值。

三、四个阶段

阶段 0：补测试地基（前置）

结果页装配现在零覆盖，改它没有兜底。先补 3 条冒烟：

  • 图形组数量与顺序 = 声明里的 7 组
  • 文本项绑定到正确的 7 个字段
  • 可见性项 = 2 项
规模：3 个测试风险：无产出：改 UI 的安全网

阶段 1：ROI 记录结构标准化（解 G1）

核心动作：把数据结构从工具搬到平台。不是搬 570 行代码，是把 4 个类型定义换个程序集。

现在（tools/…/BlobRoi.cs）改后（src/Plugin.Contracts）
BlobLocalRoi.ShapeTypeRoiShapeValue
BlobLocalRoi.ItemTypeRoiItemValue
BlobLocalRoi.GroupTypeRoiGroupValue
BlobLocalRoi.DeclarationRoiDocumentValue

连带来一起搬的：Root/Group/Item/Items/Coverage 构造与访问、Validate/ValidateShape/NormalizeDegrees/Point、Empty/Explicit/FullDomain/None 常量。

留在工具里的：InputId（字段名）、MaximumLocalInspectionCount/MaximumLocalMaskCount（Blob 特有容量）。

然后新建 NativeRoiEditHost（平台）管编辑器/会话/帧/选中/待提交/预览/释放，工具侧只剩一个声明：

public sealed record BlobRoiDeclaration : INativeRoiDeclaration { RoiDocumentValue Read(InputValues values); // 从字段读 void Write(RoiDocumentValue document, ...); // 写回字段 IReadOnlyList<NativeRoiEditGroup> Groups => ... // 两个组 }
平台 +350 行工具 −510 行风险：中（7 条基线兜底） 验收：ROI 基线通过 + 手工验证绘制/继承/屏蔽区/撤销/重开 方案格式：不变

阶段 2：显示声明标准化（解 G2）

BlobDisplay.xml 增加三段声明，只写组名不写 id：

<GraphicGroups> <Group key="display.blob" /> <Group key="display.inner-rectangle" /> ... </GraphicGroups> <VisibilityItems><Item key="display.text" /><Item key="display.outline" /></VisibilityItems> <TextItems><Item key="display.text" /></TextItems>

平台加 IDisplayDeclaration + DisplayOptionsFactory，把声明转成 GraphicDisplays/VisibilityDisplays/TextDisplays。工具侧 BlobDisplayUi 40 → 18 行（只留文本表达式解析）。

平台 +150 行工具 −22 行风险：中（阶段 0 兜底） 验收：3 条冒烟 + 目视结果页

阶段 3：9 个工具参数声明化（解 G3）

每个工具三步：

  1. 从现有 C# 参数定义导出 <Tool>Parameters.xml
  2. 接 DeclaredParameterSchema（已有，Blob 已验证逐字段等价）
  3. 删掉工具自己那份解析代码
每工具 −200 行风险：低 验收：参数逐项比对一致 + 参数页打开正常 + 方案读写正常

阶段 4：参数总线接入（解 G5）

所有字段控件都不用改。它们写值时都走同一个入口，换存储只改入口本身：

DeclaredInputFieldsView.ReadUnpresentedInput(id) ← 读，改这里 DeclaredInputFieldsView.WriteUnpresentedInput(id, 值) ← 写，改这里 DeclaredFieldRow(port, label, initial, Action<ParameterSetting> write) ← 注入源，改这里

控件照旧往入口塞值，不知道自己背后的存储换了。这和原厂一样——172 个 NameValueItem 子类共用基类的 InnerGet/SetStringParamValue，换存储不动控件。

真正要配套解决三件事：

配套问题
节点 ID仓库按「节点 + 参数名」存，得知道当前编辑的是哪个节点
变更通知Store 有 Changed 事件，要接到字段行的刷新链上
方案保存现在读 Fields.Capture()，改后读 Store.Snapshot()
控件改动：0 行核心改动：2 个方法 + 1 处注入 风险：中前提：阶段 3 完成收益：消除多份投影
为什么控件不用改：本方的 DeclaredFieldRow 在构造时收一个 Action<ParameterSetting> write 委托，所有字段行共用；DeclaredInputFieldsView 提供唯一的 ReadUnpresentedInput / WriteUnpresentedInput 通道。 控件与存储之间本来就隔着一层，换存储只换这层。

四、顺序不能反

阶段 0（测试地基） ↓ 阶段 1（ROI 结构标准化） ← 让新工具接 ROI 只写 60 行 ↓ 阶段 2（显示声明标准化） ← 让新工具接显示只写 0 行 ↓ 阶段 3（9 个工具声明化） ← 用新方式改造旧工具 ↓ 阶段 4（总线接入） ← 改 2 个入口，控件零改动
反过来会返工：如果先做阶段 3，9 个工具按"自带解析"的方式改造，等阶段 1、2 做完还得再改一遍。

五、明确不做的事

不做理由
拆成 Algorithm.dll + Bridge.dll全 C#，没有跨语言边界；原厂拆是因为 C++/C# 必须分
把 ROI 拆成散装数值参数原厂也没这么做——它也是 byte[] 整体存（Algorithm.xml 里 ROI 只有 RoiType/MulRoiType 两项）
拆 Algorithm.xml / AlgorithmTab.xml方案 6.2 明确合并，拆分只会增加 id 对不上的风险
补 BlobCount 显示项原厂自己都没给它定义外观；表格里几行 Blob 一眼可见
让控件直接传 HRegion原生句柄不能序列化、不能跨线程，覆盖不了保存/重开/无 UI
参数改回弱类型（字符串）全 C# 环境，强类型是优势；原厂弱类型是被跨语言逼的
