UI 装配逻辑：原厂与自研是两种不同的范式

本文对比 VisionMaster（原厂）与 SunEyeVision（自研）在"工具参数页如何被组装出来"这件事上的架构差异， 并说明该差异对"完整 UI 对齐"能达成到什么程度。

2026-11-18 对照对象：VisionMaster 4.4.0 · SunEyeVision 2.0.0.8 证据：反编译源码 + 实机截图

一句话结论

原厂是 每工具手写 XAML + 专属 ViewModel（像素级自由布局）； 自研是 元数据声明 + 通用渲染器自动生成（逻辑级结构）。 两者思路同为"声明 + 渲染"，但载体与控制粒度不同，因此结构可以对齐、像素级外观无法自动对齐。

1装配链路对比

同一个参数页，从"定义"到"控件树"走过的路径完全不同。

原厂 VisionMaster

手写视图
元数据 XML
AlgorithmTab.xml · uiControls · ToolItemInfo.xml
▼ 解析
专属 ViewModel（每工具一个）
Apps.XmlParser.ParamTab.DataClassificationParam
▼ 数据绑定
手写 XAML 视图（每工具一份）
DataClassificationParam.xaml · Config.xaml
▼ 样式合并
WPF 控件树
Apps.Style 全局样式 + 像素级布局

自研 SunEyeVision

元数据渲染
C# 声明（Runtime 层）
ToolSchema · FieldPresentation · FieldLayout
▼ 反射/只读消费
通用渲染器（唯一一套）
DeclaredSettingsView → DeclaredFieldsView
▼ 模板选择
控件模板注册表
DeclaredFieldTemplateRegistry · DeclaredFieldRow
▼ 扩展点
WPF 控件树
默认模板自动生成；复杂处经 InputContent 注入

3同一行控件的两种表达

以数据分类"输入变量行"为例，左边是原厂手写的像素级布局，右边是自研的声明。

原厂 DataClassificationParam.xaml 
<!-- 手写：列宽、行高、边框色全部固定 -->
<DataTemplate x:Key="InputVar">
  <Grid Height="32" Margin="0,0,5,6">
    <Grid.ColumnDefinitions>
      <ColumnDefinition Width="160" />
      <ColumnDefinition Width="80"  />
      <ColumnDefinition Width="*"   />
      <ColumnDefinition Width="75"  />
    </Grid.ColumnDefinitions>

    <Border BorderBrush="#CCCCCD"
            CornerRadius="2">
      <TextBox Text="{Binding Name}" />
    </Border>
    <!-- 类型列、订阅选择器、显示勾选… -->
  </Grid>
</DataTemplate>
自研 DataClassificationFields.cs 
// 声明：只说"是什么"，不说"长什么样"
new FieldPresentation(
    fieldId: "settings.source-select",
    displayName: "来源选择",
    group: "基本参数",
    order: 1,
    editor: FieldEditorKind.Choice,
    choiceKeys: new[] { "1", "2" },
    choiceLabels: new Dictionary<string,string> {
        ["1"] = "图像坐标系", ["2"] = "物理坐标系"
    })
{
    Layout = new("基本参数", "测量设置")
};

// 具体外观由 DeclaredFieldRow 模板决定，工具不参与
关键差别：原厂在 XAML 里能精确指定"这一列 160 像素、这个框 32 高、边框 #CCCCCD"； 自研只能声明"这是一个下拉，名字叫来源选择，排在基本参数页第 1 位"， 具体长什么样由 DeclaredFieldRow 的模板统一决定。

4逐维度差异

下表每一项都可在两侧源码中定位核实。

维度原厂 VisionMaster自研 SunEyeVision性质
视图载体 每工具独立 WPF 工程 + 专属 .xaml 无工具级 XAML，统一 DeclaredFieldsView 根本差异
ViewModel 每工具专属 VM（含 ObservableCollection / ICommand） 框架托管，工具无 UI 状态 根本差异
页面定义位置 XML 元数据 + XAML 布局 Runtime 里的 C# FieldPresentation 载体不同
布局精度 像素级（列宽/行高/边距/边框色手写） 逻辑级（名/组/序/编辑器类型） 能力差异
页签生成 XAML 中 TabControl 硬编码顺序 按 Layout.Page 首次出现顺序聚合 机制不同
分组生成 XAML 中 GroupBox / Border 手写 按 Layout.Section 自动聚合 机制不同
特殊交互 任意 DataTemplate、触发器、转换器 受模板注册表约束，超出需 InputContent 注入 能力差异
本地化 Lang:ResourceBinding 绑定资源键 zh-cn.xaml 资源键 + 工具内硬编码标签 载体不同
全局样式 Apps.Style 按工具引用合并 统一主题字典继承 等效
一致性保障 靠样式库 + 各工具自觉 同一渲染器强制统一 自研更优

5对"完整 UI 对齐"的实际影响

哪些能靠声明对齐，哪些必须写自定义控件——这是工作量预估的依据。

✅ 能自动对齐（改声明即可）

  • 页签名称与数量
  • 页签排列顺序
  • 字段显示名
  • 字段分组归属
  • 字段先后顺序
  • 默认值 / 取值范围
  • 枚举中文下拉（Choice + 标签）
  • 开关文案（启用/关闭）
  • 结果判断分组（Enable + 上下限）
  • 数值区间成对显示

⚠︎ 需装配（复用现有控件）

  • 基本参数页图像输入下拉
    ImageSources + InputSection
  • ROI 区域组
    NativeRoiEditor / RegionGeometryEditor
  • 输入区绑定与校验
    DeclaredInputFieldsView
  • 工具底部按钮组

✕ 必须写自定义控件

  • 数据分类"订阅关系"三列表格
    动态行 + 多选下拉 + 增删
  • ML 分类训练页
    +训练按钮 + 图像注册区 + 下载
  • 结果显示"眼睛图标 + 编辑弹窗"式显示项
    原厂为自定义 DataTemplate

6三条可选路线

取决于"要多贴近原厂外观"与"愿意付多少成本"。

路线 A

保持声明式
只做结构对齐

不动框架，仅调整 FieldPresentation 声明。页签、字段、默认值、枚举全部对齐，外观沿用自研统一风格。

成本 低 · 一致性 高 · 像素一致 达不到
路线 B

对齐原厂范式
改为每工具自定义视图

改造框架支持"工具级自定义视图"，复杂工具写专属 XAML + ViewModel，完全复刻原厂布局与交互。

成本 很高 · 一致性 下降 · 像素一致 可达成
建议
路线 C

混合
声明为默认 + 复杂处自定义

四个查找测量类用声明式结构对齐；数据分类订阅表、ML 训练页、结果显示交互走 InputContent 注入自定义视图。

成本 中 · 一致性 高 · 覆盖率 可满足要求
