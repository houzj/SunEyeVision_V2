5差距的四个根源

根源一：参数多了一份副本

原厂值在引擎，C# 无副本；我方值在 BlobSettings。这导致三件事必须由工具自己做：序列化、校验、保证界面与代码一致。原厂这三件都由引擎承担。

根源二：界面渲染的责任被下沉

原厂参数页由平台 Apps.XmlParser 解析 XML 生成；我方每个工具自己写 290 行解析器（BlobParameterDefinition + .Settings.cs）。

根源三：ROI 从「写值」变成了「搬控件」

原厂我方
ROI 代码量约 90 行（BlobFindRoiManager，2KB）约 650 行（RoiOwner 423 + Preview 145 + RoiUi 79）
做法设类型 → 写几何值 → 结束创建控件 → 交出控件行 → 再挂回去
后果不会出现父子冲突出现「控件已属于其他视图」崩溃

原厂 ROI 编辑器是平台级的：Apps.XmlParser 下有 ROISelecter.cs（58KB）、RoiStruct.cs（19KB）、ButtonSelecter.cs（15KB）。✅ 已证实

根源四：结果视图按「枚举选一种」，原厂按「数据类型自动分区」

原厂一个组件能吃下「图像+直方图+表格」；我方每种组合都要新写一套。这是亮度测量缺直方图的直接原因。

一句话概括：我们把原厂「平台承担的四件事」——参数存储、XML 解析、ROI 编辑、结果渲染——全部搬进了每个工具。 工具从 5 个文件变成 45 个文件，问题也就从「平台一处」变成了「18 个工具各一处」。

所以「XML 声明」和「C# 门面」是两处手写，靠人工保持一致。原厂能承受，是因为它有 SDK 兜底：参数名写错时 IMVS_GetParamValue 返回错误码并抛 VmException。

我方没有 SDK 兜底，因此必须补一道启动校验：

强制要求：平台加载工具时，比对「XML 声明的参数名集合」与「C# 门面登记的参数名集合」，不一致直接抛异常并列出差异。
否则会出现最坏情况——XML 里删了参数，CS 门面还留着，代码照常读写一个不存在的参数，静默失效。

这是「禁止兜底」原则的落地：宁可启动失败，也不要静默跑错。

为什么这决定了崩不崩

原厂参数页里每个元素都是数据节点，UI 由 DataTemplate 生成。WPF 每次应用模板都创建全新元素——同一个数据对象被多处绑定也没问题，因为元素从不共享。结构上不存在「元素有第二个父亲」这回事。

我方 NativeRoiUiDraftControls 是 StackPanel，靠 Children.Add 装外部传入的 DeclaredFieldRow。只要它是 Panel 且装外部元素，元素所有权就得靠代码正确性维护——一处疏漏就崩。

这解释了为什么之前的补丁只能缓解：把「传实例」改成「传工厂」后，参数页组装失败从 3 次降到 1 次，但控件本身仍是 Panel，模式没变，所以没有根治。
