# 架构层同构方案 + 十工具框架同构复核

> 日期：2026-11-21　状态：待确认　路线：逆向取证 + 同构迁移（非业界对标、非自主设计）
> 核心原则：架构层服务**所有工具**，不按单一工具定制。

---

## 0. 改前 / 改后 / 依据（说人话）

**改前**：本方框架已迁移了一批 VisionMaster 原厂控件，但很多停在 `.pending` 没启用；三个匹配工具的模板配置窗口是工具层各写各的近似品，缺图像工具条、样本列表、匹配中心/锁定底栏。我先前还照控件清单自研过一个 `Spec+Host` 壳——也是同类错误，已删。

**改后**：按原厂的**分层公共能力**重建架构——L0 通用显示/窗口、L1 输入与区域、L2 参数页/结果页、L3 匹配类训练框架、L4 工具专属算法。每层服务它的全部消费者，改一层就回归一层的所有工具。模板窗口（L3）是匹配类公共层，不是轮廓匹配专项。

**依据**：原厂反编译源码/配置（静态）+ agent-desktop 实机快照（实机）双链路；证据见 §1。

## 8. 防御机制

1. **契约测试**：框架每个公共件（L0-L3）绑 Evidence ID 指向原厂，无证据不新增。
2. **多消费者回归**：改 L0/L1 后回归该层**全部**消费者（18/4 工具），不只测改动的那个——体现"架构层服务所有工具"。
3. **端到端冒烟**：L3 迁移后 4 个匹配工具模板窗口逐页签截图对照原厂。
4. **Fail-Forward**：建模/编解码失败直接报错，不静默近似（rule-015）。

## 14. Tab 层对齐优先级（用户口径：先 tab 层，再功能窗口）

**双链路对照结论**：四页签集合已对齐（基本参数/特征模板/运行参数/结果显示）。差距在**基本参数页的 ROI 区域控件**：

| 原厂基本参数页（vm.../param-window.png） | 本方（contourmatch-ui-ours.../tab-basic-ours.png） |
|---|---|
| ROI区域：输出掩膜开关、ROI区域类型(图形/图像)、ROI创建(绘制/继承)、形状三按钮、屏蔽区创建(绘制/继承)、屏蔽区、位置修正 | 仅"输入ROI区域"引用行 + "位置修正"引用行 |

### 关键方案级差异（必须按此实现，勿再内联 composer）
- **平台 `NativeRoiGroupComposer` 的继承机制 ≠ 原厂 ContourMatch 的 InputROI 继承**：
  - 平台继承来源 = `RecordOf(形状)` 形状参数 record（rect/annulus），用于"按参数继承"；`ComposeInputEditor` 期望 `SequenceOf(Shape)`。
  - 原厂继承来源 = `InputROI`（`ResourceKind.Region` 资源连线，指向上游模块输出区域）。
  - 之前在参数页内联 composer 反复失败（Synthetic `roi.rectangle.hidden`/`roi.annulus.hidden` 无 presentation、`roi.annulus.hidden (Resource<Region>)` 类型不匹配）的根因就是这两套继承语义不同。
- **正确实现路径**：平台 composer 只承担"本地绘制"部分（形状按钮/屏蔽区/可见/删除/撤销重做，复用 NativeRoiEditHost + RoiDocumentStore）；"绘制/继承"单选与上游 Region 引用行用工具自己的字段 + 简单切换实现，不套 composer 的继承来源机制。上游 Region 引用行已存在（现显示"输入ROI区域"）。
- 数据+算法层已完成（`ContourMatchSearchRois.cs`：Local/Upstream 二选一进算法，默认 Upstream 保存量），本批只需把 UI 切换控件补到基本参数页。
