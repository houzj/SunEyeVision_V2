## Blob 低阈值

原 XML `LowThreshold` 的算法索引为 `0x0603`，CurValue/DefaultValue 是 `0x64`；这只是 XML 配置，并非已证明的解绑回读值。普通读取请求从 `IMVS_GetParamValue` 的 0x3f8、`Get` 分支经代理 0xbc0 到候选 ModuleFrame `VM_M_GetModuleParam`，正常对象调用 vtable `+0x10`。Blob 工厂/构造的 vtable `+0x10` 对应其 `GetParam`；该参数命中后转发 Blob 算法实例 `+0x58`，再通过句柄调用 `MVD_Algorithm_GetValueByString`。同名 Set 走 `+0x18 → +0x60 → MVD_Algorithm_SetValueByString`。实际加载映像身份和句柄内部存储/订阅注入仍按证据边界保留。

补核算法内核：句柄类型 `0x12d` 的虚表读写分别进入 `18004aed0` / `18004b360`，通过实例 `+0x510` 的运行时名称表进行分派。名称允许、非特殊分支、解析/回调成功且是同一实例时，Get 与 Set 通过 `180007c30` 定位同一按名树；Get 取节点值，Set 更新对应值并标脏。尚未证明 LowThreshold 在该表中的实际索引及是否命中该普通分支，不能用 XML 的 0x0603 代替运行时映射。之前全量 Ghidra 工程 OOM；本轮用 `-noanalysis` 定点取得相关导出及原指令，失败与新结果均保留在 Blob 分册。

回读与执行订阅是两个入口：`VM_M_GetString` 的特定查无订阅分支返回 `0xe000031b`，不能作为 `IMVS_GetParamValue` 的返回值，也不能直接判定算法消费的最终值。按文末真实 Blob 整数变量样本，成功执行写入后直接解除参数绑定、再执行、保存重开均保留最后写入的 173；这是有界原厂实测，不推广到 UI 异常回写、其他类型或失败分支。迁移此条件场景时应保留实际当前参数而非恢复订阅前的 37 或 XML 默认 100；失败、未确认解绑和参数回读仍分开处理。

解绑后续已进一步追证：[关系删除及通知静态边界](B08解绑关系删除和后续通知静态边界-20261030.md) 中 `1800bd7c0 → 1800be550/18009e470` 等已核直接路径处理关系及引用，未见对工具 SetParam 或通知的直接调用。`18007e960` 创建的关系控制块虚析构已核为释放记录及控制块，未直接调用参数 setter；其他控制块身份仍未闭合。托管 UI 的 `SetLinkWithVarNull` 可单独向类型 5/25 的来源变量模块发送 `ModifyVar`，其接收后果未闭合；参数回读校验失败还可能进入 `SetParamUnit`。所以不能把“原生删除体未直接写入”扩展成“整个解绑操作绝无写入”。

[UI 生命周期和类型边界](B08界面解绑生命周期和类型边界-20261030.md) 补证：`SetInit` 只清初始化状态和 SubData，不恢复常量；重置按钮是先解绑再 ResetParam 的独立入口。String 独立实现切换，回读后可按 UTF-8 字节长度截断并触发写回；标准 Boolean 模板没有订阅切换入口；Float 使用 CLR double 但订阅 ComType 为 float。整数直接 API 的实测不得自动推广到这些类型及 UI 异常分支。

执行注入的原指令补证见 [执行订阅注入边界](B08执行订阅注入边界-20261030.md)：`1800ffd00 → 1800b98c0 → 1800b9c70 → 1800ba0e0 → 1800bb4d0` 的整数来源成功读取后，经 `1800bc680 → 1800bc8a0 → 180043120` 在正常目标分支调用工具 vtable `+0x18`，对于该 Blob 实例即尝试 `SetParam` 并进入已证算法 setter；最终写入仍取决于 setter 成功及同实例。读取非零时该项跳过 setter，绑定处理返回错误，已核 `1800ffd00` 分支跳过任务对象虚调用；其他绑定项若此前成功并无回滚证据。`0xe0000314` 可由 `1800ca500` 外层键未命中返回，现场日志不能单凭错误码确定命中点或缺失身份。

变量来源类型 3 的内部记录读取中，`+0x8c` 是传给外层查找的来源项 ID，`+0x90` 是来源参数名；第一个管理器失败后可能尝试另一管理器，最终失败才返回并跳过该项 setter。该偏移属于转换后的内部记录，不能直接套用到 SDK 传入结构，见执行分册的原汇编。

[执行失败边界](B08执行订阅失败与已写参数静态边界-20261030.md) 区分：多绑定逐项处理，某项失败停止遍历，前面已成功写入项在该循环未见直接回滚；来源读取失败的当前项不进 setter。解析失败的已核分支发生在写缓存之前，但算法内核普通 setter 存在先成功写缓存再调用后续函数、随后返回非零的路径，因此不能把所有 setter 错误等同“未写入”。算法异常、停止后已读包装未见直接恢复旧参数，但间接调用和并发仍未证实，不能保证最终保留。

## 多绑定执行及保存顺序（2026-10-31）

原执行 `1800b98c0` 从管理器 `+0x28` 的模块链表 `head.next` 向后逐项处理。`1800be020` 在**来源类型非零、模块执行链表已存在且更新成功**的已核分支中，先移除同目标旧项，再将新项插入链表尾；因此此分支按 A、B、C 建立后改 A 为 B、C、A，删除 B 再重绑为 C、A、B。其他来源类型、空链表、失败和并发不能自动套用。原保存 `1800bf230` 遍历并过滤管理器 `+0x10` 的另一棵树生成记录；`1800bf800` 按记录次序调用 `1800bd110` 导入，遇失败停止。对于同一目标模块、通过过滤的名称树，原比较器是 `MSVCR120.dll!memcmp`，按所存字节比较、短前缀在前且不做大小写折叠；仅当经已核托管 UTF-8 入口且后续字节未变时可称 UTF-8 字节序。若重开导入每项均命中上述非零来源、已存在链表的成功尾插分支，队列会按导出记录顺序重建，而不是保留先前改源后的顺序；链表创建、其它分支和多绑定原机重开尚未证实，不能无条件泛化。单绑定原机样本已证保存和导入路径；不能把 schema/JSON 排序视作原执行队列。迁移需保留独立队列顺序、变更及失败的可观察状态。

## 触发文本

已核单次或连续允许分支将入参复制到流程对象 `+0xa8`；已核 GLOBAL=2 字符串 IO 从相应流程对象读取它。正常执行路径随后可将该字段复制到关联任务对象的 `+0x100`。另有 `##TriggerCmd##` 写入从具体任务输入对象的 `+0x100` 取值；尚未证实该对象就是上述关联列表中的对象，不能将名称、两个对象字段与写入点视为同一个存储。普通忙拒绝分支在复制前返回；特殊递归例外单列。停止、取消、关闭重开和所有间接清理不应推断为一律清空或保留。

| 入口或阶段 | 有界源码结论 | 仍未知 |
|---|---|---|
| 无参流程单次 | 托管 `VmProcedure.Run()` / `Run(bool)` 将 null 命令传入 SDK；候选 native 导出将空指针规范为空串，成功进入允许分支时复制 | 不能将整方案 `VmSolution.Run()` 或所有手动入口归为同一路径 |
