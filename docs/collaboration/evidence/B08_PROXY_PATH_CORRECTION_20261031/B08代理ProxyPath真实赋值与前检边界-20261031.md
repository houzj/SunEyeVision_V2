# B08 代理 ProxyPath 真实赋值与独占前检边界

目标 `ModuleProxy.dll` SHA-256 `76F09A40184B2B5F99B7173EDDE23A716D339E3C64955696D6927495EFDF68A9`；只读既有原汇编和私有 Ghidra 分析工程，没有启动 SDK/VM 或修改安装、共享清单及其他任务目录。本文纠正前次“`180018980` 仅用于诊断、未证明给 `+0x118` 赋值”的结论：该结论遗漏原 x64 指令保留的 R8 实参。

## 写入者与路径来源

1. `VM_PROXY_Init@180020a90` 构造全局对象并调用 `1800480c0`；后者在 init 参数非空分支 `180048123–126` 把自身传给 `18003c600`。`18003c600@18003c6c4–6ce` 将 `this+0x118` 地址放入 R8 后调用 `180018980`；该字段为后续资源线程使用的 ProxyPath。不能依赖把函数参数省略的伪代码判为无赋值。
2. `180018980@1800189ae` 保留 R8 到 RDI，`1800189b9` 把原二进制字面量 `ModuleProxy.dll` 放 RCX，调用 IAT `KERNEL32!GetModuleHandleA`，再以该句柄调用 `KERNEL32!GetModuleFileNameW`，容量 `0x104`。找到末级 `\\` 或 `/` 时截断文件名，将父目录经 `18000d030`（WideCharToMultiByte 代码页 65001，即 UTF-8）转换，`180018a6e–74` 将结果和先前保存的 RDI 分别传入 `18000fb70`，后者对目标字符串作赋值。这是 `+0x118` 的实际写入路径，而不仅是日志输出。
3. 限定正常成功路径、名称匹配已加载的目标 ModuleProxy 且路径未发生截断时，ProxyPath 是该模块的实际加载目录。若 `GetModuleHandleA` 返回 null，`GetModuleFileNameW` 的 null 句柄按 Windows API 是调用进程主程序路径，不能未经证据替换成 DLL 路径；GetModuleFileNameW 失败、未找到分隔符、超过固定缓冲等异常行为均不能被称为成功隔离。
4. 资源线程把 ProxyPath 与 `\\..\\..\\ModuleProxy\\ImageSourceTempPath.txt` 拼接后读取历史行。它不按当前 exe 的 app base 限制清单；也不能仅凭清单存放在自有目录保证清单里每个历史行目标属于该目录。使用原安装 DLL 的正常定位路径，静态链不显示此字段由正式路径参数赋值；并不能仅凭此一函数断言整个产品不存在其它公开配置或覆写入口。

## 一次性前检能说明什么

技术总监线只读观察该清单当前一行是其已退出测试进程的图像缓存，十份有事前 SHA 的产物未变；该观察是某一时点的内容，不等于未来资源线程读取时内容必相同，也不能补出缓存事前逐文件基线。SDK 检查进程快照失败（如 access denied）同样返回 false，之后该行可能被加入递归删除；不能凭失败当 PID 确实不存在。PID 复用、其他实例并发写清单、检查与读取之间的时间差、路径重解析点/junction、目标所有权与目录内容均须逐项处理。常规绝对路径字符串前缀比对不足以证明最终递归目标和子路径无重解析跳转。允许的运行仍需清单实际所有历史行和目录最终归属明确，并能可靠避免在检查后被其他实例改写；只检查 PID 或单次读取并不是对未来执行的原子保证。
