## 更正先前结论：存在确切的 +0x118 写入

原公开导出 `VM_PROXY_Init@180020a90` 在对象构造后，以 `RCX=&DAT_180198620`、`RDX=其输入参数` 调用 `1800480c0`。该 `MP_Init` 在初始化早期调用 `18003c600(this)`；该函数原指令 `18003c6c4 LEA RBX,[RDI+0x118]`、`18003c6cb MOV R8,RBX`、`18003c6ce CALL 180018980`，即把对象字段地址以 **第三参数 R8** 传入该帮助函数。

`180018980` 原指令 `1800189ae MOV RDI,R8` 保存目标指针；然后 `GetModuleHandleA("ModuleProxy.dll")`、`GetModuleFileNameW` 取得加载模块路径，使用 `wcsrchr` 查找最后的 `\\` 或 `/` 并截去文件名；`180018a5f–74` 由 `18000d030` 将宽字符串转换为 UTF-8，再以 `RCX=RDI`、`RDX=转换后字符串` 调 `18000fb70`。后者将目标旧字符串释放/清空并复制新字符串。**因此正常成功分支确实向对象 +0x118 写入加载模块所在目录；此前“仅日志，没有向该字段写入”的说法错误。** 原指令和参数寄存器是关键：错误忽略 R8 会漏掉这个写入。GetModuleFileNameW 失败及未发现分隔符有不同错误分支；路径截断、模块同名装载及运行身份未作动态观察。

在后续 `180036e40` 路径构造中，该字段会附加 `\\..\\..\\ModuleProxy\\ImageSourceTempPath.txt`；因此在 `GetModuleHandleA` 返回目标模块句柄且后续成功的条件下，历史清单的位置由 **该 ModuleProxy.dll 目录和相对路径解析**决定，而不是单由探针 EXE 工作目录决定。原调用没有检查 GetModuleHandleA 的返回值后再调用 GetModuleFileNameW；按该 Windows API 的 NULL 句柄语义，查不到模块时可能得到当前进程可执行文件路径，因此不把模块命中当成无条件事实。解析后每条历史路径本身仍可指向任意其他目录；即使清单位于专有目录，也必须证明其内容和所有递归删除目标也仅在专属范围。

## 正式入口、加载路径及未闭合边界

既有 `docs/plugins/CAMERA-MAPPING-B3-RETURN-SOURCE.md` 对 SP 路径的原指令追踪表明：PlatformManager `1805d3f00` 读取 `ProxyPath` 配置，默认 `../ModuleProxy/x64/ModuleProxy` 并加 `.exe` 保存到 manager `+0x7d438`；`1805d3570 → 18063bc40` 从配置字符串构造 DLL 路径并 `LoadLibraryW`。这说明存在影响 **加载目标** 的配置来源，但现阶段未证明对该 SDK/PF 调用可通过公开参数、而且不修改安装/共享配置就指定合规独占路径；原加载 DLL 的文件/链接与模块解析身份、同名重复加载和配置文件根还须明确。用户本次禁止复制厂商程序/算法库，也禁止修改共享清单或原二进制；不能在此基础上发明“自有目录加载副本/替换库”方案。

更重要的是，`180036e40` 根据历史清单中的原始整行构造清理目标，不是始终把目标限定在当前目录。独占历史清单位置只是**必要条件之一**：还需原路径解析、所有历史行与递归目标均约束在自有树，且避免快照失败被当作进程不存在。当前未证有正式支持的隔离配置使这些条件全部成立；因此保持不启动原 SDK，不将此结论扩大为“绝不可能配置”。
