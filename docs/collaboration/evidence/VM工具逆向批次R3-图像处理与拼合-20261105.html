0 结论摘要

问题档位结论
R3 实物模块数观察到 34 个有效模块目录，与批次计划的 34 完全一致（ImageProcessing 21 / ImageGeneration 4 / SplitCombination 6 / Collection 3）。
Collection 下另有 ImageSourceModule、ImageAcquisitionModule 两个模块，已在 R1 计数，本批不重复计入，仅作对照。
本批无空目录，与 R2 出现 1 个空目录的情况不同。
专用编辑器是否普遍观察到 带 *Control.dll 的仅 7/34 = 20.6%：AffineTransform、FrameMean、ImageCombineProcess、Normlize、ImgStitchCalib、LightModule、SaveImage。
图像处理的"滤镜族"（Enhance/Filter/Morph/Sharpness/ShadeCorrect/Binary）全部没有专有控件 —— 它们靠同一套"图像+ROI+参数页"通用壳驱动。
端口是否统一观察到 统一三层结构：Base(固定 7 项) → Input → Output → TransmitInfo(1 个无名节点)。
几乎每个模块的输出都自带 ModuRunTime:float + ModuStatus:int 这对"运行态"字段；图像处理族额外统一输出 BlindPolygonString:string[]。
ROI 形状能力来自哪里观察到 来自 AlgorithmTab.xml 的 <ROISelecter> 元素，不是来自端口。原文示例：
<ROISelection>Box SectorRing Polygon Sector</ROISelection> / <RoiMaxNum>16</RoiMaxNum> / <SelectType>Mul</SelectType>。
即：形状集合、数量上限、单选/多选，是每个工具的独立声明。
形状词目有几种观察到 本批共出现 9 种：Box、UroBox、SectorRing、Sector、OverSector、Polygon、Point、Line、CircleMes。
后 4 种仅出现在 GeometryCreate 的"几何创建类型"选择器 GeometryType（上限 128、多选），不是 ROI 形状，不可混用。
我方形状词目够不够观察到 我方 ShapeType 有 7 种（Point/Line/Circle/RotatedRectangle/Polygon/Annulus/Arc）。
缺 2 个：Sector（扇形，与 SectorRing 扇环并列声明，不可互相替代）、OverSector（PolarUnwarp 专用）。
多 1 个：Arc —— 原件没有独立弧 ROI，弧用 ROIANNULUS（扇环）表达。
Style 是否有唯一 schema观察到 没有。 Style 只约束"形状种类/字段基数"，字段名由各模块内联决定，且同一 Style 在不同模块字段名不同：
全局库 ROIANNULUS 用 DetectAnnulus* 前缀；IMVSBinaryModu 内联用 roiAnnulus* 前缀。
→ 绑定不能按键名硬映射，只能按 Style 语义 + 顺序或显式映射表。
全局库是否封闭观察到 不封闭。本批出现 2 个全局 Combination.xml 里不存在的 Style：ACQUIMAGE(17 字段)、DEBUG(3 字段)，均由模块 XML 内联定义。
即：全局库是可复用模板集合，不是封闭枚举。
参数页怎么分观察到 三段式页签：Tab_Basic Params / Tab_Run Params / ResultShow。页内用 Category + GroupLinkItem 做分组，GroupLinkItem 通过 <LinkName> 引用同名共享分组。
例外：GeometryCreate 无 Run Params；LightModule 只有 1 页；SaveImage 换成 Tab_Render Parameters/Tab_Render Settings。
本批对我方的最大校正观察到 三处：①Annulus 的角用 起始角 + 角跨度（AngleExtend），不是起止角；②Line 原件用两端点，我方用点 + 方向向量；③UroBox（声明为无旋转矩形）的端口仍给 roiangle 字段 —— 声明与端口不同步，不能拿声明当字段依据。

1.3 端口契约：三层 Category + 统一运行态输出 观察到

34 个模块的 <ParamRoot><Categorys> 结构高度一致：

运行态输出是统一约定，不是个别模块自定义：

  • ModuRunTime:float + ModuStatus:int：本批 32/34 模块成对出现。
  • 例外 2 个：ImageAcquisitionModule（只有 ModuRunTime，状态改用 4 个采集统计量 FrameNum/LostFrameCount/LostPacketCount/GetCameraFailCount）、ImageSourceModule（ModuStatus 在前，无 BlindPolygon）。
  • 图像处理族独有 BlindPolygonString:string[]：8 个模块（Binary / ImageCombineProcess / Enhance / Filter / Morph / Normlize / Sharpness / ShadeCorrect）。
对我方的直接含义：ModuRunTime/ModuStatus 是"每个工具的固有输出"，不是业务输出。 我方若逐工具手写这两个字段会重复 34 次。应作为框架统一注入的隐式输出（与业务 OutputVariable 分离）， 否则每个新工具都要记得补，漏了就是不一致。

全局 Combination.xml（SHA256 前 16 位 7A2B369154AC05EE，170,889 B）中，本批涉及的关键 Style 结构已逐层展开如下：

关键结构性事实：同名 Style 在不同模块内字段名不同。

全局 Combination.xml <Combination Name="ROIAnnulus" Style="ROIANNULUS"> Filter: DetectAnnulusCenterX / DetectAnnulusInnerRadius / DetectAnnulusStartAngle ... IMVSBinaryModu.xml:60 <Combination Name="InputROIAnnulus" Style="ROIANNULUS"> Filter: roiAnnulusCenterX / roiAnnulusInnerRadius / roiAnnulusStartAngle ...

两者 Style 相同、字段语义相同、字段名不同。同样现象见 CIRCLE（全局 centerx/centery，模块内联 CenterX/CenterY）、LINE（全局 LineStartPointX，模块用 ...）。

结论（对绑定契约致命）：Style 是"几何种类 + 基数"的声明，不是字段名 schema。 任何依赖"按字段名跨模块对齐 ROI 字段"的设计都会在原件上失败。 正确做法是按 Style + 位置序，或为每个模块维护显式映射 —— 与我方 RoiFieldSchema 按 ShapeType 生成固定路径（Center.X/Radius）的做法方向不同：我方是"内部统一模型"， 对我方自己的工具成立；一旦要读原件的 ROI 值，必须先按 Style 做一次语义归一。

全局库不封闭：ACQUIMAGE(17) 与 DEBUG(3) 在 Combination.xml 中检索为 0 命中，均由模块内联定义：

IMVSMultiImageFusionModu.xml InputImage/ACQUIMAGE => ImageCount:int, InImage0Distribution:float, InImage0Irradiation:float, ... InImage7Irradiation:float (共 17) SaveImage.xml InDebugInfo/DEBUG => InDebugInfoState:int, InDebugInfoSize:int, InDebugInfoAddr:string (共 3)

推断 ACQUIMAGE = 一次采集产出的"多路光分布图 + 照射图"复合端口（8 路 × (Distribution, Irradiation) + 计数）。 ImageAcquisitionModule 的 OutImage/ACQUIMAGE(17) 与 IMVSMultiImageFusionModu 的 InputImage/ACQUIMAGE(17) 字段完全同构， 说明二者是配套的"采集→多光融合"数据链。该推断不排除其它生产者。

1.6 形状声明与端口字段不同步 观察到

UroBox 声称"无旋转矩形"，但对应模块的 InputROI 端口仍然完整提供 roiangle：

IMVSImageMathModu.xml InputROI/ROIBOX => roiwidth:float | roiheight:float | roiangle:float | {ROI CenterPoint}(roicenterx, roicentery) IMVSImageResizeModu.xml InputROI/ROIBOX => roiwidth:float | roiheight:float | roiangle:float | {ROI CenterPoint}(roicenterx, roicentery) IMVSMultiImageFusionModu.xml InputROI/ROIBOX => roiwidth:float | roiheight:float | roiangle:float | {ROI CenterPoint}(roicenterx, roicentery)
不要据此改造我方模型。这只是"UI 允许的形状集合"与"端口字段集合"未同步的原件现象 —— 推断 上层的形状选择器在运行期把 roiangle 置 0 或忽略。 我方不存在这种双份真相：ShapeType 单一决定字段表（RoiFieldSchema），因此不需要引入 UroBox 类型。 若要读取原件已存方案中的 UroBox ROI，按 RotatedRectangle 解析并忽略角即可。

1.7 角度语义：AngleExtend 而非起止角 观察到

来源字段我方 RoiFieldSchema.Annulus
ROIANNULUS（全局与模块内联一致） ...InnerRadius、...OuterRadius、...StartAngle、...AngleExtend Center.X/Y、InnerRadius、OuterRadius、StartAngle、EndAngle

原件是起始角 + 角跨度，我方是起始角 + 终止角。换算：EndAngle = StartAngle + AngleExtend。

未知：AngleExtend 的符号约定（负值是否表示反向扫掠）与单位（度/弧度）在静态文件里没有声明，无 Description/单位注释。 R2 已列为待补证据 G4 的一部分；本批未解除。在拿到实机或反汇编证据前，不得按"负值=反向"或"单位=度"写死换算。

1.8 BlindPolygon 盲区机制 观察到

8 个图像处理模块同时提供 BlindPolygon/ROIPOLYGON 输出端口与 BlindPolygonString:string[] 结果：

项内容
图形输出BlindPolygon/ROIPOLYGON，Combination 级 IsArray="true"，内部 BlindPolygonPointNum:int[] + BlindPolygonPoints(POINT，IsArray="true")
标量输出BlindPolygonString:string[]

与我方的关系：我方目前没有"盲区多边形集合"这一输出概念。若后续要做多工序级联（上游屏蔽区传给下游）， BlindPolygon 可作为参照实现：几何用 RoiShape[]（Polygon 数组），文本用 string[] 冗余一份便于协议下发。 不需要为此新建类型 —— RoiShape[] + string[] 已够。
