# 项目级原厂证据先行规则

生效范围：SunEyeVision_V2 全部工具、共享控件、工作流节点、调试窗口、参数页、结果页和生命周期实现。

## 强制顺序

1. 先收集原厂证据，再讨论实现。证据优先级固定为：
   - 同版本反编译源码、程序集和资源中的直接证据
   - 同版本原厂配置、模板、样式、数据模板和组装清单
   - 同版本原厂运行截图、可重复交互录像或 Agent Desktop 运行记录
2. 为每个变更建立 VM/自研差异表，至少记录入口、控件/模板、数据来源、绑定、组装顺序、交互、执行、关闭和释放。
3. 只有差异表闭合后才能修改代码。测试失败先回到差异表定位属于入口、模板、绑定、组装、执行还是释放，不得按自研现状猜测行为。
4. 原厂动态行为没有证据时标记“运行未确认”，不得用自研等价实现冒充原厂事实。

## 证据状态

- `verified`：有直接原厂证据且当前实现已复现。
- `derived`：由多个直接证据推导，推导链记录在差异表中。
- `inferred`：存在合理推断但缺少直接证据，只能进入验证清单。
- `unconfirmed`：尚无足够证据，禁止作为设计依据。

## 缺陷处理闭环

现象 → 复现记录 → 原厂同场景证据 → VM/自研差异定位 → 最小架构修正 → 自动测试 → 原厂/自研截图或运行记录 → Release 构建 → 复核记录。

若本方出现原厂不存在的缺陷，默认先检查架构对应关系和实现偏差。局部修补只有在差异表明确证明共享架构正确、且缺陷属于局部实现时才允许。

## 合并门禁

- 没有原厂证据或差异表的行为修改不得合并。
- 不得新增第二套参数页、控件、模板或生命周期链来绕过共享架构问题。
- 共享控件和窗口根的改动必须说明所有消费者和原厂对应证据。
- 自动测试只能证明本方实现结果，不能替代原厂证据。
- Release 构建通过和 Agent Desktop 运行验证必须分别记录，不能互相替代。
