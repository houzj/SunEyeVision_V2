# 区域工具契约统一（RoI）与工具设计合理性治理 — 最终优化方案

## 一、改前 → 改后 → 依据（用户视角）

**改前（用户视角）**
- 你在绑定树里看到 Blob/阈值等工具输出的是"区域"类型，但想把它当图形用（比如按"圆/矩形/多边形"过滤、存成全局变量复用）却做不到——因为"区域"本质是算法内部的像素集合（Halcon 区域），既不能序列化、也不能当全局变量，下游也消费不了。
- 数据分析面板和绑定树两边的数字经常对不上（例如 Blob 数量面板显示 12，但绑定树里字段不全）。
- 调阈值时想看"检测区灰度分布"辅助判断，结果要么没有、要么混在结果主字段里很乱。
- 工具参数里"阈值方向"同时有下拉（Binary/BinaryInv）和独立开关（Invert），你选了下拉的 BinaryInv 实际不生效，纯误导。

**改后（用户视角）**
- 所有区域类工具的输出统一是"图形定义（RoI）"——可在绑定树按 `[Type=圆/矩形/多边形]` 过滤、可存全局变量跨节点复用、下游直接消费。算法内部怎么算区域你不用管。
- 数据分析面板和绑定树读**同一份数据**，不再出现两边不一致。
- 调参辅助信息（灰度直方图、耗时）归到独立的"诊断"分组，想看就看、不污染主结果。
- "阈值方向"只有一个清晰开关，结果里如实报区间，不再有死分支和下中点误导。

**依据（业界参考）**
- 视觉软件行业通行做法：**算法区域（iconic，运行时易逝）与用户几何（RoI，可序列化）严格分离**，工作流绑定契约只承载可序列化的几何。VisionMaster 变量模型即如此（项目内部调研结论见 `.codebuddy/research/2026-07-16_node-result-tree-best-practice.md`：当前 `OutputVariable` 契约 + `SdkTypeVocabulary` 固定词汇 + `GetPropertyMap` 声明性映射整体符合 VisionMaster 最佳实践，缺口正是"Region/RoI 语义未分清"）。
- Halcon 自身：`HRegion` 是 iconic 数据，提取几何需显式 `area_center` / `smallest_rectangle2` 等算子——本方案 `RegionToRoi` 就是这一思想的显式桥接。

## 四、问题分析（Phase 0）

### 4.1 需求拆解
- **表面需求**：区域工具输出统一、工具设计合理化。
- **根本问题**：工作流契约混入了"算法内部 iconic 数据（Region）"，导致它既不可序列化、不可全局变量、下游也消费不了；同时工具自身存在冗余/漂移/死分支。
- **问题分类**：架构契约缺陷（Region 越界）+ 设计随意（D1-D8 各项）。

### 4.2 架构分配检查
- 最自然归属层：① 词汇/契约层（`SdkTypeVocabulary`/`GlobalVariableValueConverter`）；② 算法工具输出映射层；③ 工具内部参数/结果设计。
- 已有类似机制：位置修正/检测区域已由 `RegionParameters` 基类提供（只需推广去重）；`GetPropertyMap()` 已是绑定树唯一契约源（只需数据面板向其派生）。
- 不改是否可覆盖：否——Region 越界是契约级错误，必须治本。

### 4.3 方法对比（核心："Region 在工作流里的位置"）

| 维度 | 方案 A（推荐·最终） | 方案 B（双词汇并存） | 方案 C（Region 序列化） |
|------|------|------|------|
| 做法 | Region 完全退出工作流契约，仅 RoI；算法内部 `Region→RoI` 桥接外发 | Region/RoI 双词汇，Region 可下游绑定不可全局变量 | 强行序列化 Region（存掩码/轮廓） |
| 架构一致性 | ✅ 符合行业"iconic/几何分离" | ⚠️ 仍允许错误消费 | ❌ iconic 数据持久化反模式 |
| 复杂度 | 中（4 工具输出改造+桥接工具） | 低（但留后患） | 高（掩码序列化体积/版本） |
| 长期 ROI | 高（契约干净、下游统一） | 低（消费 Region 错误设计延续） | 负（体积爆炸+迁移债） |

> 方案 B 是你已否决的（"本来消费 region 就是错误的设计"）；方案 C 因 iconic 不可序列化被 `GlobalVariableValueConverter` 直接 `throw`，行不通。

## 五、Bug 模式分析（Phase 0.5）

**当前问题**：`Region` 作为工作流契约类型"越界"——既出现在 4 个工具输出、又出现在全局变量创建下拉，但序列化层对它 `throw`。

**真因分类**：**契约漏洞**（词汇表把算法内部类型暴露成可绑定/可创建类型）。

**同类潜伏点**：

**治本点**：删词汇 `Region` 条目 + 工具输出改 RoI 经桥接，而非在转换器里 `throw` 兜底（rule-015：禁止静默/兜底，应前置堵死入口）。

**证据缺失警告**：本次为系统性契约缺陷，非孤例。

## 七、解决方案

### 7.1 方案概述
1. **契约层**：`SdkTypeVocabulary` 删除 `Region` 条目，工作流只认 `RoI`；`GlobalVariableValueConverter` 删 Region 死分支。
2. **桥接层（新增 `RegionConverter`）**：`RegionToRoi`(exact 默认零失真 + fit 显式 opt-in) / `RoiToRegion` / `RegionCircularity`，算法工具在输出映射处把 `IVisionRegion` 转 `RoI` 外发。
3. **工具设计合理性**：对 Blob 等区域工具逐条过 D1-D8 标准（见 7.2）。
4. **试点→推广**：Blob 先打通，再 Threshold/Morphology/ImageThreshold，最后脚本动态工具。

### 7.3 Region ↔ RoI 转换契约（具体，回应你的"失真"质疑）

**为什么默认零失真**：`IVisionRegion.GetContour()`（`HalRegion.cs:53-62`，Halcon `GetRegionContour`，返回外轮廓，图像坐标）直接喂给 `Polygon2d.Vertices`（`Polygon2d.cs:17`）。一个区域在数学上就是其边界，用边界多边形填充即像素级还原——与 RoI→Region（几何栅格化）镜像对称。

**真实失真边界（必须写进 XML 注释）**：
1. **孔洞**：`GetRegionContour` 只返外轮廓，带孔区域（环/带孔 blob）的孔在转 RoI 时丢弃（`Polygon2d` 单环不支持孔）。Blob 流程通常先 `FillUp`，少见但需明示。
2. **亚像素 1px 边界误差**：轮廓为整数像素坐标，重栅格化可能差 ≤1px，对几何用途可忽略（与 RoI→Region 同理）。

**脚本/桥接 API（你确认的三档）**：

```csharp
// 落地位置：src/Plugin.SDK/VisionAdapters/RegionConverter.cs（或 Execution/Helpers）
public static class RegionConverter
{
    // 默认 exact = 精确多边形，零失真（仅丢孔洞）
    public static ShapeParameters RegionToRoi(IVisionRegion region, string fitMode = "exact")
    {
        if (region == null || region.IsEmpty)
            throw new ArgumentException("区域为空，无法转换");   // rule-015 报错优先
        var contour = region.GetContour();                       // 外轮廓点集, 与 RoI 同坐标系
        return fitMode switch
        {
            "exact" => new ShapeParameters { Geometry = new Polygon2d(contour, isClosed: true) },
            "fit-circle" => new ShapeParameters { Geometry = FitCircle(contour) },   // 失真=1-圆度, 显式选
            "fit-rect"   => new ShapeParameters { Geometry = FitRotatedRect(contour) },
            "fit-bbox"   => new ShapeParameters { Geometry = new Rect(region.BoundingBox) },
            _ => throw new NotSupportedException($"不支持的 fitMode: {fitMode}")
        };
    }
    public static IVisionRegion RoiToRegion(ShapeParameters roi) { /* 几何栅格化, 零失真, 你认可的易方向 */ }
    public static double RegionCircularity(IVisionRegion region) { /* 先量圆度, 再决定 fit-circle */ }
}
```

- 脚本运行时 API 暴露 `RegionToRoi` / `RoiToRegion` / `RegionCircularity`（满足"下游脚本转 RoI"诉求，且 `exact` 默认安全）。
- 静态工具输出映射直接调用 `RegionToRoi(region, "exact")`，无需脚本。

## 十二、已知限制（透明，不藏）

1. **孔洞丢失**：`RegionToRoi(exact)` 用 `GetRegionContour`（只返外轮廓），带孔区域（环/带孔 blob）的孔在转 RoI 时丢弃。这是 Region 退出工作流契约后的唯一信息损失点；Blob 流程通常先 `FillUp` 故少见，但需在转换工具 XML 注释明示。
2. **旧 recipe 迁移**：历史方案若绑定了 `Region` 输出，加载时按 rule-008 直接报错提示迁移，不静默兼容。
3. **lossy 拟合失真**：`fit-circle`/`fit-rect`/`fit-bbox` 会产生几何失真，幅度由用户用 `RegionCircularity` 等辅助函数事先判断，转换本身不抛不静默（畸变由用户知情选择）。
